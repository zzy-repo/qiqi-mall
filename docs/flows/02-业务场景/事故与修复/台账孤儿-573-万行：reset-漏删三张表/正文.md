## 台账孤儿（orphan rows）

**事实**　压测脚本 `bench/tools/prepare.sh` 的 reset 语义是「只删自己造的」：按测试会员（`username like 'lg\_%'`）圈出订单，逐级删包裹 → 发货单 → 明细 → 支付流水 → 订单，最后把库存写回 50 万。库里另一类是只追加的证据表：订单状态台账、包裹状态台账、售后台账、库存台账、后台操作审计、支付流水。它们记的是「这件事发生过」，删业务主表时不会跟着消失，删它们只能由删单那段代码自己负责 —— 这次漏掉了三张：`order_status_ledger` / `delivery_status_ledger` / `return_status_ledger`。一天下来订单状态台账 5,717,917 行，其中 5,717,908 行的 `order_id` 已不存在。症状是 `/admin/ledgers` 打开要等 25 秒，而接口、业务功能与监控全部正常。出处：`bench/tools/prepare.sh` 第 237 行的事故注释。

**经过**　每轮压测的审核、发货、取消都写台账，一轮留下 30 万~70 万行（量级，由压测轮次与台账行数对照得出，未逐轮复测）。reset 删 9 张业务表、漏 3 张状态台账，订单行消失而台账留下，孤儿行逐日累积。5,717,908 是差集算法：总数减去属于真实订单的那 9 行，不是另一次抽样；这 9 行也正是「不许清空整表」的直接理由。

**措施**　清理一次性、分批、可中断：条件是「`order_id` 已不存在 且 `created_at` 不早于当天 02:00」，29 批 × 20 万行、116 秒删完；带时间条件是因为 02:00 之前的孤儿属更早的遗留，不在本次范围。reset 修成按订单 id 删（`… where order_id in (select id from lg_o)`），禁止 `TRUNCATE` 全表。reset 跑完必须打出「台账残留(应为 0)=0」这一行。两个坑写进脚本注释：一条语句里三次引用同一临时表 `lg_o` 会报 ERROR 1137，改成三张台账 UNION 只引用一次；执行函数是 `mysql … 2>/dev/null`，stderr 被丢弃，报错不上屏，那条自检曾静默无输出，所以口径定为「自检行缺失 = 失败」。体检与清理分开：`scripts/check-data-integrity.sh` 第 ①⑥ 项只发 SELECT、退出码可当门禁。验证（2026-11-14 18:05）：两个库孤儿均 0 行；`qiqi_mall` 订单台账 2222 行 / 包裹 2067 / 售后 351，不一致 0；`qiqi_mall_test` 为 9 / 0 / 0；清理后页面 0.059 秒打开（当晚会话记录，未复测）；六源行数合计 791 = 76 + 27 + 15 + 640 + 27 + 6（当晚会话快照，页里给命令不给常数）。

**边界**　「孤儿」的定义只看父行在不在，与时间无关，时间条件只用于本次清理范围。台账能按 id 删、不能清空：`qiqi_mall_test` 那 9 行就是种子真单的台账，一旦 TRUNCATE 会被一起切掉，事后无法回答「当时谁把它改成了什么」。三条自检红线：同一张临时表一条语句只引用一次，否则 ERROR 1137；`sql_db` 吞 stderr，报错不会出现在输出里；因此「没输出」必须当失败。体检与清理必须分开，清理前先 dump。数字状态：5,717,917 与 25 秒出自 `prepare.sh:237`；5,717,908 为差集推导；每轮 30 万~70 万为量级；29 批 / 116 秒 / 0.059 秒 / 791 为当晚会话记录，均未复测。
