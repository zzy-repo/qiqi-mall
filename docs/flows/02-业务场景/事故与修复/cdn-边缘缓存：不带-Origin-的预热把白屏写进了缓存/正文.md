## CDN 边缘缓存（edge cache / CORS）

**事实**　后台 admin-web 是 Vite 打包的 SPA：52 个 `.js` 以 `<script type="module" crossorigin>` 加载，90 个 assets 放在私有桶 `qiqi-mall-static`，由 cdn.rose7.cn 回源。两条前提决定了这次事故：桶的 CORS 规则只在请求带 `Origin` 头时才加 `Access-Control-Allow-Origin: *`；CDN 边缘不把 `Origin` 算进缓存键。于是「带不带 Origin」只影响回源响应，不影响命中哪一份缓存 —— 谁先填充，缓存里就存下谁那一份。`assets/*` 的 `Cache-Control` 是 `public, max-age=31536000, immutable`，坏副本挂一年。结果：52 个 `.js` 里 50 个被写成无 ACAO 的副本，`/order-audit`、`/audit-policy`、`/channel` 三页白屏，控制台 21 条错误、`data-testid` 一个不出现；不是接口 500，也不是桶坏。

**经过**　2026-11-14，出处 `scripts/cdn-converge/RUNBOOK.txt` 第九节。`00:26` v1.1.1 首轮发布，90 个 assets（其中 52 个 `.js`）上传到新前缀，上传脚本当时只对 2 个样本做了带 Origin 的 HEAD 预热。`00:26` 之后按验证剧本巡检：裸 curl 查 index 的 3 个资源，再对 90 个 assets 逐个 curl 查 200，全部不带 Origin；这些对象在边缘缓存里还是空的，这一遍请求就是首次填充。`00:35` 回滚后台前端，后端保持新镜像。50/52 这个分布由「只预热 2 个样本」加「50 个坏」倒推，属推断，不是直测。

**措施**　不回滚旧前缀、不刷新 CDN、不改 CDN 配置（本账号默认禁止刷新、预热与配置变更），改用未被缓存过的新前缀 `qiqi-mall-v111` 重发，只新增对象。上传之后带 Origin 全量预热：脚本遍历全部 js/css，逐个 `HEAD -H 'Origin: …'`，预热与自检是同一步。随后做 ACAO 全数校验：汇总行直接给 `js X/Y 有 ACAO`，任何 `.js` 不是 200 或缺 ACAO 就把清单和一行 ★「不要切流量」打到 stderr；没看到 52/52 不许切流量，这条写进运行手册。验证线上 CDN 必须带 `-H 'Origin: https://admin.rose7.cn'`，巡检与监控探针同理；判读口诀是同一 URL 加 `?t=1` 再请求一次，两次 ACAO 不同就是缓存里存了坏副本。位置：`scripts/upload-web-assets.sh` 的自检预热段、RUNBOOK 第九节。修复后新前缀 52/52 都有 ACAO，三页控制台错误 0。

**边界**　缺 ACAO 只在浏览器眼里是错：curl 一样拿到 200 和完整响应体，所以「curl 全绿」推不出「页面能开」。css 同样缺 ACAO 却不白屏 —— 它走 `<link>`，不是 CORS 请求，现场表现因此是「样式还在、脚本全死」。边缘不把 Origin 当缓存键是 CDN 侧行为，不是配置写错，治根要改缓存键，而那属于 CDN 配置变更（默认禁止）。`x-oss-cdn-auth: success` 只说明回源鉴权通过，与 CORS 无关，私有桶回源是另一条红线。52 与 50 是当晚的实测值，assets 数量随每次构建变（本地 dist 现为 90 个 assets / 52 个 js），要用就按当次构建重数；本轮未复测，只给可复跑的只读判据。
