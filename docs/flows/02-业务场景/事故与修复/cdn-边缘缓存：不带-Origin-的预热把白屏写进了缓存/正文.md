**那 50 个 js 不是上传坏的，是"看一眼"看坏的** —— 边缘缓存不把 Origin 算进缓存键，一次不带 Origin 的首个请求就把"没有 `Access-Control-Allow-Origin`"的副本按 immutable 存进了 CDN，有效期一年。52 个 js 里 50 个中招，后台三个页面白屏。

## 场景

后台（admin-web）是 Vite 打包的 SPA，52 个 `.js` 以 `<script type="module" crossorigin>` 加载，90 个 assets 放在私有桶 qiqi-mall-static 里，由 cdn.rose7.cn 回源。发版三步：构建 → 把 assets 传到 OSS 新前缀 → 切 CDN 指向。

两条前提事实决定了这个事故：桶的 CORS 规则会给响应加 `Access-Control-Allow-Origin: *`，但**只在请求带 Origin 头时才加**；而 CDN 边缘**不把 Origin 算进缓存键**。于是"带不带 Origin"只影响回源时的响应，不影响命中哪一份缓存 —— 谁先来填充，缓存里就存下谁那一份。

## 撑不住的时候（事故经过）

时间线（2026-11-14，出处：`scripts/cdn-converge/RUNBOOK.txt` 第九节）：

- **00:26** v1.1.1 首轮发布：90 个 assets（其中 52 个 `.js`）上传到新前缀。上传脚本当时只对 **2 个样本**做了带 Origin 的 HEAD 预热。
- **00:26 之后** 按验证剧本巡检：裸 curl 查了 index 的 3 个资源，又对 90 个 assets **逐个 curl 查 200** —— **全都不带 Origin**。这些对象在边缘缓存里还是空的，这一遍请求就是首次填充。
- **结果**：52 个 `.js` 里 **50 个**被写成无 ACAO 的副本（另外 2 个恰好就是预热过的那两个样本 —— 这是由"只预热 2 个 + 50/52 坏"倒推的，属推断不是直测）。`assets/*` 的 Cache-Control 是 `public, max-age=31536000, immutable`，这份坏副本会挂一年。
- **症状**：`/order-audit`、`/audit-policy`、`/channel` 三页白屏，控制台 21 条错误、`data-testid` 一个都不出现。不是接口 500、不是桶坏 —— 是模块脚本被浏览器按 CORS 拒了。
- **00:35** 当次回滚后台前端（后端保持新镜像）。

一个会把人带偏的细节：css 同样缺 ACAO，但 css 走 `<link>`、不是 CORS 请求，**缺了也不白屏**。所以现场表现是"样式还在、脚本全死"，直觉会先怀疑业务代码。

## 改了什么

① **不回滚旧前缀，也不刷新 CDN**：本账号默认禁止刷新/预热/变更 CDN 配置（需明确批准），所以改用一个**没被缓存过的新前缀 `qiqi-mall-v111`** 重发 —— 只新增对象，一个 CDN 配置都不动。

② **上传后带 Origin 全量预热**：脚本遍历全部 js/css，逐个 `HEAD -H 'Origin: …'`。这一步既是预热（把好副本写进边缘缓存），也是自检（顺手把 ACAO 读回来）。

③ **ACAO 全数校验**：汇总行直接给数字（`js 50/52 有 ACAO` 这种），任何 `.js` 不是 200 或缺 ACAO 就把清单和一行 ★「不要切流量」打到 stderr，并给出判读：`ACAO=<无>` 要么是桶没 CORS 规则，要么是有人用不带 Origin 的请求先填充了缓存。脚本不替人切流量（切换在脚本之外），但**没看到 52/52 就不许切**这条，写进了运行手册。

④ **红线进文档**：验证线上 CDN 资源必须带 `-H 'Origin: https://admin.rose7.cn'`，线上巡检/监控探针同理；排查口诀是"同一 URL 加个 `?t=1` 再请求一次" —— 带参数那次有 ACAO、不带那次没有，就是缓存坏副本，不是桶配置坏了。

代码/文档位置：`scripts/upload-web-assets.sh`（第 335~410 行的自检+预热段，含【CORS 事故】注释与判读提示）、`scripts/cdn-converge/RUNBOOK.txt` 第九节「静态资源 CORS 红线」。

## 凭什么证明好了

这不是一段能"演"的事故（现场是浏览器白屏 + 一份已经挂在 CDN 上的坏副本），证据只能是**命令输出 + 数字**：

- 事故时：52 个 js → **50 个无 ACAO**（会白屏）。
- 修复后：新前缀 + 带 Origin 全量预热 → **52/52 都有 ACAO**，三页控制台错误 **0**。
- 出处：RUNBOOK 第九节的四条事故记录与三条正确做法；上传脚本的自检段（★ 行、`js X/Y 有 ACAO` 汇总行、`ACAO=<无>` 的判读）。

复查命令（只读，不改任何配置）：

```
# 全量自检 + 预热（脚本遍历全部 assets，一律带 Origin）
scripts/upload-web-assets.sh admin-web --verify

# 单条判据：三个字段齐了才算好
curl -sSI -H 'Origin: https://admin.rose7.cn' <CDN 地址>/<前缀>/admin-web/assets/<文件>
#   HTTP=200 + x-oss-cdn-auth= success + Access-Control-Allow-Origin: *  → 好
#   缺ACAO → 会白屏（模块脚本是 CORS 请求）
```

## 附：口径与边界

- **"缺 ACAO"只在浏览器眼里是错**：curl 一样拿到 200 和完整响应体。所以"curl 全绿"不能推"页面能开"，这也是初查方向跑偏的原因。
- **边缘缓存不把 Origin 当缓存键**是 CDN 侧行为，不是配置错误。治根要改缓存键，那是 CDN 配置变更（默认禁止）；本页的做法是"换未缓存前缀 + 全量预热"。
- **`x-oss-cdn-auth: success` 只说明回源鉴权通过**，与 CORS 毫无关系。私有桶回源那是另一条红线（RUNBOOK 第四节），两件事别混。
- **52/52 是当晚的实测值**，assets 数量随每次构建变（本地 dist 现在也是 90 个 assets / 52 个 js），数字要按当次构建重数，别抄；本页没有对 50/52 做过今日复测，只给了可复跑的只读判据。
- **不改桶、不改 CDN、不刷新**：本页所有动作都在"新增对象"这一侧完成，回滚副本（另一个桶）保留未动。
