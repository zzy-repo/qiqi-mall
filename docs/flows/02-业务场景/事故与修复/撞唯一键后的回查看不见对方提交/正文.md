## 撞唯一键后的回查看不见对方提交（REPEATABLE READ snapshot）

**事实**　`payment_record` 上有两个唯一键：`uk_idem`（幂等键，形状 `{orderSn}:PAY` 或 `{orderSn}:REFUND:{returnApplyId}`）与 `uk_channel_trade(channel, trade_no)`（渠道流水号）。写入策略是先试着插，撞键再判断这是不是重放：按幂等键回查命中即「已入账」、静默返回；没命中说明撞的是别的唯一键，抛可读的业务异常让这次业务失败。

**经过**　缺陷在「撞了之后怎么回查」：回查用的是同一事务内的 `count(*) where idem_key = ?`。REPEATABLE READ 下事务的 consistent snapshot 在第一条查询（`pay()` 开头那句 `getById`）就定住了，另一条连接之后提交的同一幂等键那一行，本事务永远看不见 —— 于是数到 0 行，判定「这不是重放」，把 `DuplicateKeyException` 原样抛出。`GlobalExceptionHandler#handleDuplicateKey` 把它映射成 `Result.fail("已存在相同记录，请检查唯一字段")`，调用方看到的是 HTTP 200 加 `code=1`，一次失败，重试多少次都失败，而库里其实只有一行、钱也没记两遍。更坏的旁路是用 `INSERT IGNORE` 或 `ON DUPLICATE KEY UPDATE id = id`：撞 `uk_channel_trade` 时那条流水会被静默丢弃，那是丢钱。原来的 e2e「支付并发冲突」验不到这里 —— 第二笔在到达 `record()` 前就被状态守卫与版本 CAS 拒了，`uk_idem` 一次都没命中，「幂等键兜住重放」一直只是设计意图。

**措施**　两道回查：本事务内的读，看得见自己刚插、还没提交的行（同事务里 `record()` 调两次就是这种）；`REQUIRES_NEW` 新事务的读，换一条连接等于新快照，才看得见别的写入方刚提交的行 —— 缺它就把真重放判成「不是重放」。新事务用 `TransactionTemplate` 显式开，不用 `@Transactional(REQUIRES_NEW)` 注解：`record()` 是同类内部自调用，注解式事务靠代理生效，自调用时静默失效，代码看起来已经修了、行为一点没变。只容忍幂等键，撞 `uk_channel_trade` 包成 `IllegalStateException`、原始异常挂 cause；回查自己出错时把失败挂 `suppressed` 再抛原始异常，两个事实都留在堆栈里。`trade_no` 加随机后缀：原来只精确到毫秒，同毫秒的两笔合法流水会撞键。2026-11-14 18:36 真跑 `PaymentIdemKeyTest` 九条用例：9/9 通过、14.97 秒，其中 ⑥ 真并发 20 轮、每轮恰好 1 行且两个调用都不抛。

**边界**　这是视野问题，不是锁问题：不加 `FOR UPDATE`、不改隔离级别 —— 撞键那次 `INSERT` 已在本事务对唯一索引留了共享锁，同事务再加锁读等于跟自己抢锁，还可能升级成死锁。两道回查的顺序不能反：先本事务（覆盖同事务重放），再新事务（贵一次连接，只在前者没命中时才用）。「只容忍幂等键」是硬边界：这张表另一道唯一键撞了就是「同一笔钱可能记了两遍」的疑似场景，静默吞掉等于丢钱。幂等键必须带 `refId`，不同退货申请是两笔真的退款。变异验证（把新事务回查退回旧行为，用例 ⑤ 应当立刻红）本轮没做 —— 要临时改源码再改回，不碰业务代码。
