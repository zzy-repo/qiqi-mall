**撞了唯一键，不等于"这笔钱已经记过了"** —— 在 REPEATABLE READ 下，事务的快照在第一条查询时就定住了；对方之后提交的那一行，你在**本事务里永远看不见**。于是"重放"被当成"写不进去"，用户看到的是一次失败，而设计承诺的是幂等跳过。

## 场景

`payment_record`（支付流水）有两个唯一键：`uk_idem`（幂等键）与 `uk_channel_trade(channel, trade_no)`（渠道流水号）。幂等键的形状是 `{orderSn}:PAY` 或 `{orderSn}:REFUND:{returnApplyId}` —— 同一笔支付、同一次退款，重建多少次都只该有一行。

`PaymentRecordServiceImpl#record()` 的做法是"先试着写，撞了就判断这是不是重放"：捕获 `DuplicateKeyException` 后按幂等键回查，命中就是重放（已入账）→ 静默返回；没命中就是撞了别的唯一键 → 抛出可读的业务异常，让这次业务失败。

## 撑不住的时候（事故经过）

缺陷就在"撞了之后怎么回查"这一步。

- **时序（可构造，不靠运气）**：`pay()` 这个事务的**第一条** `getById` 就把 consistent snapshot 定住了；此时另一条连接提交了同一幂等键的一行；本事务再调 `record()` → 撞 `uk_idem` → 在**同一个事务里**回查 `count(*) where idem_key=?` → **数到 0**（快照是事务开头那一刻的，看不见对方刚提交的行）→ 于是判定"这不是重放" → 把 `DuplicateKeyException` 原样抛出去。
- **线上形态**：`DuplicateKeyException` 被统一异常处理映射成 `Result.fail("已存在相同记录，请检查唯一字段")` —— 也就是 **HTTP 200 + `code=1`**。用户/调用方看到的是一次"失败"，重试多少次都失败，而库里其实**只有一行**、钱也没记两遍。这类"看起来像脏数据、其实是判重判错"的失败最难归因。
- **更坏的旁路（这也是不能偷懒用"忽略重复"的原因）**：如果无脑用 `ON DUPLICATE KEY UPDATE id = id` 或 `INSERT IGNORE`，撞 `uk_channel_trade` 时那条流水会被**静默丢弃** —— 那不是判重，那是丢钱。

而且原来的 e2e「支付并发冲突」**验不到这里**：第二笔在到达 `record()` 之前就被状态守卫（`status != 0 → code=1`）与版本 CAS（409）拒了，`uk_idem` 一次都没被命中。也就是说"幂等键兜住重放"一直是**设计意图**，不是被验事实。

出处：`qiqi-mall-server/src/main/java/com/qiqi/mall/oms/service/impl/PaymentRecordServiceImpl.java`（类注释"回查必须跨两道视野"一节、`idemKeyAlreadyBooked`、`countCommittedByIdemKey`）；`PaymentIdemKeyTest.java` 类注释（九条用例的分工）。

## 改了什么

① **两道回查，缺一不可**：
- 第一道 **本事务内**的读（`countByIdemKey`）—— 看得见"本事务自己刚插、还没提交"的那一行（同事务里 `record()` 调两次就是这种）；
- 第二道 **`REQUIRES_NEW` 新事务**的读（`countCommittedByIdemKey`）—— 换一条连接 = 新快照，才看得见"别的写入方刚提交"的那一行。缺它就会把真重放判成"不是重放"。

② **新事务用 `TransactionTemplate` 显式开，不用 `@Transactional(REQUIRES_NEW)` 注解**：`record()` 是同类内部调用，注解式事务靠代理生效 —— **自调用时那个注解会静默失效**，代码看起来"已经修了"，行为一点没变。

③ **只容忍幂等键**：撞 `uk_channel_trade` 包成可读的 `IllegalStateException`（原始 `DuplicateKeyException` 挂在 cause 上），宁可这次业务失败，也不静默丢一条流水。

④ **回查自己失败也不许吞原始异常**：DB 抖动导致回查抛错时，把回查失败挂成 `suppressed` 再抛原始异常 —— 两个事实都留在堆栈里（既不能当"已入账"，也不能把"回查失败"伪装成"撞了别的唯一键"）。

⑤ **给 `trade_no` 加随机后缀**：它原来只精确到毫秒，同一毫秒的两笔**合法**流水会撞 `uk_channel_trade`。

⑥ 顺带一条不是修复但是必要的自证：`④` 号用例绕过 service 直接用 JDBC 插一条相同幂等键，断言报文里就是 `uk_idem` —— 证明约束是**库上的事实**，不是"代码里的君子协定"。

## 附：口径与边界

- **这不是"锁的 bug"，是"视野的 bug"**：修法不是加 `FOR UPDATE`、也不是改全局隔离级别 —— 撞键失败的那次 INSERT 已经在本事务里对唯一索引留了共享锁，再在同一事务里加锁读等于跟自己抢锁（还可能升级成死锁）。新事务里的**普通快照读**不加锁、不阻塞，也不需要动全局配置。
- **两道回查的顺序不能反**：先本事务（最便宜、覆盖同事务重放），再新事务（贵一次连接，只在前者没命中时才用）。
- **"只容忍幂等键"是硬边界**：这张表上的另一道唯一键撞了就是"同一笔钱可能记了两遍"的疑似场景，静默吞掉等于丢钱。宁可失败。
- **幂等键必须带 `refId`**：不同退货申请是两笔真的退款，不能因为"同一订单"就吞掉第二笔。
- **复测状态**：九条用例今天真跑过（9/9 全绿、14.97s，含 ⑥ 的 20 轮真并发）；**"变异后退回旧行为立刻红"是当晚会话的判定，本轮没做**（要临时改源码再改回，不碰业务代码）。线上"HTTP 200 + code=1"的形态来自 `GlobalExceptionHandler#handleDuplicateKey`（把 `DuplicateKeyException` 映射成 `Result.fail("已存在相同记录，请检查唯一字段")`）—— 这条可从代码直接读到。
