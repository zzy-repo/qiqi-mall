## 过期的冒烟期望码（stale ASSERT / exit code）

**事实**　`scripts/publish.sh` 的冒烟段是「发布完还活着吗」的最小信号：四个地址各断言一个期望状态码，加网关双实例连打 8 次、商品图 200、登录接口可用；任一项不符即冒烟失败、脚本退出码 2（发布动作其实已经完成）。期望码都是环境变量，默认值写在脚本里：`EXPECT_MALL` / `EXPECT_ADMIN` / `EXPECT_DOCS` / `EXPECT_HEALTH`。

**经过**　`admin.rose7.cn` 早期由 ECS 上的 Caddy 提供、挂着 basic auth，未认证请求返回 401，所以冒烟期望 401。后来 basic auth 撤了、域名落地方式也换了，默认值一直没跟上，还停在 401。于是每次发布实际拿到 200、脚本期望 401，`smoke_one` 返回 1，冒烟失败、退出码 2 —— 而发布本身是成功的。真正的伤害不是「发布坏了」，是人开始无视退出码：每天必红一次的门禁等于没有门禁，等到某天真红，第一反应是「又是那条 401」。

**措施**　`EXPECT_ADMIN` 默认值 401 改成 200，并把判断依据写进注释，不是「改成 200 了」而是「凭什么 200 才算健康」：响应里没有 `WWW-Authenticate`（有它才说明在要求认证）；返回的是 admin 这个单页应用的 `index.html`（今天实测 464 字节，引的是 CDN 上的构建产物）—— 服务器活着、静态入口能取到，就是健康信号。覆盖入口保留：将来重新挂 basic auth，只设 `EXPECT_ADMIN=401`，不用改脚本。结论是改前退出码 2、改后退出码 0，发布本身两次都成功。复核时还校正了原注释里一句不严谨的推断：当时用 `Server: nginx/1.31.8` 反推「不是那台 Caddy」，但响应头里仍有 `via: 1.1 Caddy`，链路上仍有 Caddy、只是不再要求认证 —— 能站住的依据是「无 `WWW-Authenticate`」加 body 大小这一组，不是 `Server` 长什么样。

**边界**　401 与 200 都不是「更安全」或「更健康」，它们只是当时那个落地方式下的实测结果；默认值必须跟着落地方式走，否则它就是一句会过期的谎。不要用「删掉这条冒烟」来治它：发布需要一个与业务无关的最小健康信号，删了等于把门禁换成一封邮件。退出码语义要保住，`publish.sh` 在 CI 里就是靠它拦人，所以「每天红一次」比「没有这条检查」更糟。识别同类漂移的方法是：默认值旁边必须有一句「依据是什么、什么时候测的」，只写结果的注释，下一个人没法判断它是否还成立。同源残余仍在：dry-run 那行文案还写着「→ 200（Caddy basic auth）」（`scripts/publish.sh:1852`），不影响判定，但下一个读脚本的人会先被它误导。改前「退出码 2」、改后「退出码 0」是当次发布的记录，本轮不复测（要复测就得真跑一次发布）；响应侧数字是今天真测的 —— HTTP 200、无 `WWW-Authenticate`、body 464 字节，其中字节数随前端构建变，判读时现场重量。位置：默认值与注释在 `scripts/publish.sh:304`，调用点在 `:1864`。
