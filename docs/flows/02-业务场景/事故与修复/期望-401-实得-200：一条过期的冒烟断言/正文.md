**一条过期的默认值，让每次发布都以退出码 2 结束** —— 而发布本身是成功的。冒烟期望 `admin.rose7.cn` 返回 401（那时它挂在机器上的 Caddy 上、带 basic auth），后来 auth 撤了、默认值没跟上，于是门禁天天红一项。

## 场景

`scripts/publish.sh` 的冒烟段是"发布完还活着吗"的最小信号：四个地址各断言一个期望状态码，加网关双实例连打 8 次、商品图 200、登录接口可用。任一项不符 → 冒烟判失败 → **脚本退出码 2**（发布动作其实已经完成）。

期望码都是环境变量，默认值写在脚本里：`EXPECT_MALL / EXPECT_ADMIN / EXPECT_DOCS / EXPECT_HEALTH`。

## 撑不住的时候（事故经过）

- 早期 `admin.rose7.cn` 由 ECS 上的 Caddy 提供，挂了 **basic auth** ⇒ 未认证请求返回 **401**，所以冒烟期望 401。
- 后来 basic auth 去掉了（域名也换了落地方式），**但默认值一直没跟上**，还停在 401。
- 结果：每次发布冒烟都红一项 —— 实际拿到 **200**，脚本期望 401 ⇒ `smoke_one` 返回 1 ⇒ 冒烟失败 ⇒ **退出码 2**。
- 真正的伤害不是"发布坏了"，而是**人开始无视退出码**：每天都红一次的门禁，等于没有门禁；等到某天真的红了，第一反应是"又是那条 401"。

## 改了什么

① `EXPECT_ADMIN` 默认值 **401 → 200**，并把**判断依据**写进注释（不是"我改成 200 了"，而是"凭什么 200 才算健康"）：

- 响应里**没有** `WWW-Authenticate` 头（有它才说明在要求认证）；
- `Server` 是 **nginx/1.31.8**，不是当年挂着 basic auth 的那台 Caddy —— 落地路径已经变了；
- 返回的是 admin 这个单页应用的 `index.html`（**599B**，引的是 CDN 上的构建产物）⇒ "服务器活着 + 静态入口能取到"就是健康信号。

> 今天复核时发现第三条推断**不严谨**：响应头里还有 `via: 1.1 Caddy` —— 链路上**仍然有** Caddy，只是它不再要求认证（`Server` 报的是它背后那台 nginx）。所以"Server=nginx ⇒ 不是 Caddy"这句站不住；真正能站住的是前两条 + body 599B 这一组（见下）。注释当时写的是"当时实测"的归纳，本页把它校正过来，别让下一个人拿一句错推断去解释 200。

② **保留覆盖入口**：将来重新挂 basic auth，只需 `EXPECT_ADMIN=401`，不用改脚本。

③ 结论写清：改前**退出码 2**、改后**退出码 0**（发布本身两次都成功）。

位置：`scripts/publish.sh:290`（默认值与那段注释）、`:1817`（`smoke_one "admin.rose7.cn" … "$EXPECT_ADMIN"`）。

## 凭什么证明好了

证据是**退出码**这一个数字，加上"依据可被复核"的三条响应特征，不是界面（这件事的现场是 CI 的输出，不是某个页面），所以不录视频。

```
# 改之前：每次发布结尾
════ 冒烟 ════
✗ admin.rose7.cn 期望 401 实得 200
...
退出码 2          # 发布本身是成功的，红的是这条过期断言

# 改之后：
✓ admin.rose7.cn → 200
退出码 0
```

复核依据（只读、任何时候都能重跑）。**今天的实测输出（2026-11-14 18:36）**：

```
$ curl -sSI https://admin.rose7.cn/ | head -14
HTTP/2 200
cache-control: no-cache
content-type: text/html
last-modified: Sat, 14 Nov 2026 03:21:34 GMT
server: nginx/1.31.8
via: 1.1 Caddy
content-length: 599

$ curl -sS https://admin.rose7.cn/ | wc -c
599

$ curl -sSI https://admin.rose7.cn/ | grep -ci "www-authenticate"
0
```

三项都对上了：**200 + 没有 `WWW-Authenticate` + body 599 字节（单页应用的 index.html）** ⇒ "实得 200"不是巧合，也不是哪次配置抖出来的。

**还有一处同源漂移没修（本轮刻意不改脚本逻辑，只记在这里）**：dry-run 那行文案仍写着"→ 200（Caddy basic auth）"（`scripts/publish.sh:1805`）—— 注释跟上了、文案没跟上。它不影响判定，但下一个读脚本的人会先被这句话误导，所以它是这颗雷的**残余**。

## 附：口径与边界

- **401 与 200 都不是"更安全/更健康"**，它们只是"当时那个落地方式下的事实"。默认值必须跟着落地方式走，否则它就变成一句会过期的谎。
- **不要用"删掉这条冒烟"来治它**：发布需要一个和业务无关的最小健康信号（域名活着、静态入口取得到），删了等于把门禁换成一封邮件。
- **退出码的语义要保住**：`smoke` 失败 → 退出码 2，`publish.sh` 在 CI 里就是靠它拦人。所以"每天红一次"比"没有这条检查"更糟 —— 它训练人忽略退出码。
- **同一类漂移的识别方法**：默认值/期望值旁边必须有一句"依据是什么、什么时候测的"。只写结果（`EXPECT_ADMIN=200`）的注释，下一个人没法判断它是否还成立。
- **未复测**：改前"退出码 2"、改后"退出码 0"是当次发布的记录（要复测就得真跑一次发布，本轮不做发布）。但**响应侧的数字是今天真测的**（见上：200 / 无 `WWW-Authenticate` / 599B）；599 会随前端构建变，判读时要现场重量。
- **一条判据被今天的数据校正**：`Server: nginx/1.31.8` 不等于"链路上没有 Caddy" —— 响应头里 `via: 1.1 Caddy` 明写着有。以后写这类注释，别把"某个头长什么样"当成"某台机器不在了"的证据。
