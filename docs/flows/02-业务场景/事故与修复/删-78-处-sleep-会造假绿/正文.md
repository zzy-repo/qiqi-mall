## 删 78 处固定等待（flaky sleep / false green）

**事实**　e2e 里长期有大量固定等待（`waitForTimeout`），它们等的是异步产物：列表刷新后的新行、toast 出现、抽屉里的数据到位。这些等待慢，所以一直有人想删。这一轮真去删了：93 处里删掉 78 处，判定依据只有一句「后面有断言兜着」。

**经过**　判据错在没人证明过「断言断的是上一步动作的异步产物」。等待去掉之后有两种结果，都不是跑红那么简单：假绿 —— 上一步留下的旧数据也满足断言，用例永远绿，被测行为坏了也看不出来；最典型的形状是松断言，`group_concat` 没命中时返回的是字符串 `NULL`，`rows.length` 于是等于 1，「查 0 行」被当成「有 1 行」，这一条在 `后台操作审计.spec.js` 里真撞过。偶发红 —— 断言恰好落在刷新之前那一瞬，于是 flaky，而 flaky 的常规处置是「再跑一次」，门禁被噪声驯化。所以 78 处不是删错了几行，是把一整批用例的判别力换成了「看起来在跑」，全部回滚。

**措施**　重判三类，判据不是「后面有没有断言」，而是「断言的对象是不是异步产物、断言 API 自己会不会轮询」。真静态可删 8 处：断言对象是页面标题、固定文案这类静态事实，且 `toContainText` / `toBeVisible` 自带轮询，删了不新增假绿。需要改造 72 处：断言对象是列表行数、金额、状态、抽屉数据这类异步产物，先把固定等待换成「轮询到条件成立」（`expect.poll`），再谈删。不能动 13 处：删了会改变时序语义，保留并在注释里写清为什么这里必须等。验证方法固化成四步：先 `grep` 被改 helper 的所有调用方（support 的改动波及所有 spec，漏一个只证明了半个入口）；独占一个 shard（`bench-lock.sh` 加 `pgrep -f playwright` 确认没有别的跑批）；同一 shard 上 `--repeat-each=20 --workers=1`（不加 worker，并发本身会制造新的互相干扰）；判据是零失败 —— 任何一次红都算该处不成立，把等待从 git 原值恢复，不许为了让绿去改断言或放宽 timeout。本轮验证 27 条用例 × 3 遍 = 81/81 全绿、0 flaky，在独占 shard 上跑。

**边界**　81/81 是当晚会话的记录，本轮未复测（复测要跑 81 条、几分钟起步，还要独占 shard，命令在 `bench/README.md` 第 10 节，任何人都能重跑出同一口径）。可删的不是等待本身，是「等一个必然已经成立的静态事实」：同一句 `waitForTimeout(1000)` 断在静态标题后面是纯浪费，断在异步列表后面是判别力，长得一样、语义完全不同。A/B/C 的分界是可操作判据而不是主观判断：断言对象是不是异步产物、断言 API 有没有自带轮询、删了之后旧数据会不会也满足。「跑一次绿」不构成证据，竞态窗口是概率性的。回滚不是失败，是判据生效 —— 它把「零风险可删」这个结论当场证伪了。能直接查的现状（2026-11-14 21:32 `grep -rc waitForTimeout e2e/tests`）：`scenarios` 193 处、`support` 129 处 —— 这一轮的目标不是把等待清零，而是不许把等异步产物的等待当成可删。93 / 78 / 8 / 72 / 13 这几个数字来自当晚会话。
