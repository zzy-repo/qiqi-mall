## 种子灌进真库（hard-coded USE）

**事实**　重置测试库的入口是 `scripts/init-test-db.sh`，库名由调用方给（`DB_NAME`）：先 Flyway 建结构（39 表 + 1 视图），再灌 `sql/testdb/02-seed.sql`。种子文件不是手写的，由 `scripts/fetch-seed-data.mjs` 生成，口径是「先关外键检查 → 逐表清空 → 按固定 id 插入」，因此可以反复重跑 —— 这正是危险处：跑错库也照样成功。而 `02-seed.sql` 的第一行写着 `USE qiqi_mall_test;`。

**经过**　2026-11-13 有人复制一份 init 脚本、把 `DB_NAME` 改成 `zz_init_check`；调用方那行 `mysql_exec "$DB_NAME" < "$SEED"` 完全正常，库名也确实传了进去。但文件第一行的 `USE` 在文件内部把目标库改回真库，于是「重置临时库」变成「重灌真库」：29 张业务表被 `TRUNCATE` 重灌，admin 口令被打回种子里的弱口令，而目标库 `zz_init_check` 反而空着。最难查的地方是没有任何一条语句报错，日志全绿，只是成功在了错的库上。同一晚还有一次同源事故：`sql/schema.sql` 与 `sql/testdb/01-schema.sql` 开头都带 `USE <库名>` 加逐表 `DROP TABLE IF EXISTS`，谁 source 一次（哪怕只想看结构）删掉的就是文件里写死那个库的表，`qiqi_mall_test` 因此缺了 3 张 channel 表。

**措施**　把库名从文件里彻底拿掉，7 处文件去掉硬编码 `USE`；生成器源头（`fetch-seed-data.mjs` 拼 SQL 处）写死一条规矩：本文件不许出现 `USE <库名>` / `CREATE DATABASE`，库名必须由调用方给 —— 改产物只能补一次，改生成器才不把雷埋回去。所有调用点改成显式传库。加多库安全验证，改完任何 SQL 或脚本都跑一遍 `grep -nE '^USE |CREATE DATABASE' sql/*.sql sql/testdb/*.sql`，期望 0 命中（2026-11-14 18:55 实测 0 命中 / 6 个在用文件）。重置完的对错不靠人看：脚本在建结构后有一道 fail-closed 断言（业务表 39 张、视图 1 张、V1 迁移记录 1 条、`channel_shop` 3 行，任一项不符退出 1），灌种子前先探一次 admin 口令，拿不到就一步都不动。铁律写进留档目录：含 `USE <库名>` 或建库语句的 SQL 不许被直接 source。

**边界**　「0 命中」只管在用的那 6 个文件：`sql/_rollback/` 下 4 个历史脚本仍各带 2 处 `USE`（`01-schema.sql`、`migrate-ledger-idem-shard.sql`、`migrate-optimistic-lock.sql`、`migrate-sku-bucket.sql`），它们已整体下线、README 明写禁止执行 —— 留档不等于安全，所以铁律写的是「不许直接 source」，不是「这些文件里没有 USE」。29 张是当时的记账，现在生成器的 `TRUNCATE` 列表是 24 张，别拿 29 当核对基准。两次事故同源：都是「文件能自己选库」，所以规矩针对的是文件结构本身，不是某人某次手滑。29 张被清空与 admin 口令打回弱口令来自 README 的当晚记录，本轮没有重演（重演一次就是再出一次事故）。
