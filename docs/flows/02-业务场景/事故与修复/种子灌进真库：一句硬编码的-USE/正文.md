**一句话就把 29 张表清空了**：种子文件的第一行写着 `USE qiqi_mall_test;`。调用方明明把库名传对了，文件自己又把目标库改了 —— 于是"重置临时库"变成了"重灌真库、并把 admin 口令打回种子弱口令"。

## 场景

重置测试库的入口是 `scripts/init-test-db.sh`，库名由调用方给（`DB_NAME=…`）：先用 Flyway 建结构（39 表 + 1 视图），再灌种子 `sql/testdb/02-seed.sql`。种子文件不是手写的，由 `scripts/fetch-seed-data.mjs` 生成（商品数据来自 DummyJSON、图片传到对象存储），它的口径是"先关外键检查 → 逐表清空 → 按固定 id 插入"，所以**它可以反复重跑**——这正是它危险的地方：跑错库也照样"成功"。

## 撑不住的时候（事故经过）

2026-11-13，要重置一个临时库：

- 有人把 init 脚本复制一份，把 `DB_NAME` 改成 `zz_init_check`；调用方那一行代码**完全正常**（`mysql_exec "$DB_NAME" < "$SEED"`）。
- 但 `02-seed.sql` 第一行是 `USE qiqi_mall_test;`。库名在**文件内部**被改写，调用方传的那个库名当场失效。
- 结果：种子灌进了真库 `qiqi_mall_test` —— **29 张业务表被 TRUNCATE 重灌**，admin 口令被打回种子里的弱口令；而目标库 `zz_init_check` 反而空着。
- 这件事最难查的地方：**没有任何一条语句报错**。日志里全是成功，只是"成功在了错的库上"，错误发生在最外层那个 `USE` 词上。

同一晚还有一次同源事故（`sql/_rollback/README.txt` 记的"事故①"）：`sql/schema.sql` 与 `sql/testdb/01-schema.sql` 开头都带 `USE <库名>;` 后面跟逐表 `DROP TABLE IF EXISTS` —— 谁在自己的环境里 source 一次（哪怕只是想看结构），删掉的就是文件里写死那个库的表。当晚 `qiqi_mall_test` 因此缺了 3 张 channel 表。

出处：`sql/_rollback/README.txt`「事故①／事故②」两段原文；`scripts/init-test-db.sh` 灌种子那段的注释；`scripts/fetch-seed-data.mjs` 拼 SQL 处的禁用注释。

## 改了什么

① **把库名从文件里彻底拿掉**：7 处文件去掉硬编码 `USE`（README 记的"7 个文件"，本轮能直接验的是**现在这些文件 0 命中**，见下）。

② **在生成器源头拆雷**：`scripts/fetch-seed-data.mjs` 在拼 SQL 的地方留了一条硬规矩——"本文件里不许出现任何 `USE <库名>;` / `CREATE DATABASE`，库名必须由调用方给"，并写清了两次事故的后果。这条比改产物重要：**改产物只能补一次，改生成器才能不把雷埋回去**。

③ **所有调用点改成显式传库**：`mysql_exec "$DB_NAME" < "$SEED"`，并在注释里写明"文件里不写库名，调用方必须传库名"。

④ **加「多库安全验证」**：README 给了一条自查命令，改完任何 SQL/脚本都跑一遍：

```
grep -nE '^USE |CREATE DATABASE' sql/*.sql sql/testdb/*.sql   # 期望 0 命中
```

⑤ **铁律写进留档目录**：**含 `USE <库名>` 或建库语句的 SQL，不许被直接 source**。库名只能由调用方传 —— "调用方传了库名、但文件里的 `USE` 又把目标库覆盖掉"是最阴的一种：看调用方代码完全正常，事故却出在文件内部。

## 凭什么证明好了

证据是命令输出 + 一次可复跑的自查，不是界面（这条路径根本没有界面），所以不录视频。

**今天的自查（2026-11-14 18:55 实测）**：

```
$ grep -nE '^USE |CREATE DATABASE' sql/*.sql sql/testdb/*.sql | wc -l
0
$ ls sql/*.sql sql/testdb/*.sql | wc -l
6
```

即：这 6 个在用的 SQL 文件里一个 `USE` 都没有。

**调用点也确实改成"显式传库"**（`scripts/init-test-db.sh`）：

```
mysql_exec "$DB_NAME" < "$SEED"
#  库名一律由本脚本显式传给 mysql。02-seed.sql 里不再有任何 USE / 建库语句 ——
#  2026-11-13 有人用改了库名的副本去重置别的库，seed 里写死的 USE 把种子灌进了真库、还 TRUNCATE 了它。
```

**重置完"是不是真的对"也不靠人看**：脚本在建结构后有一道 fail-closed 断言 —— 业务表必须 39 张、视图 1 张、V1 迁移记录 1 条、`channel_shop` 3 行，任一项不符直接退出 1。灌种子前还要先探一次 admin 口令拿不拿得到，拿不到就一步都不动（避免"灌完种子却停在弱口令上"）。

## 附：口径与边界

- **"0 命中"只管在用的那 6 个文件**。`sql/_rollback/` 下 4 个历史脚本里仍带 `USE`（今天实测：`01-schema.sql`、`migrate-ledger-idem-shard.sql`、`migrate-optimistic-lock.sql`、`migrate-sku-bucket.sql` 各带 2 处）。它们已整体下线、README 明写"禁止执行"——**留档不等于安全**，所以铁律写的是"不许直接 source"，而不是"这些文件里没有 USE"。
- **29 张表是当时的记账**；现在生成器的 TRUNCATE 列表数一遍是 **24 张**（`scripts/fetch-seed-data.mjs` 的 `tables` 数组）。库演进后两个数字对不上，本页按 README 的 29 写，但**别拿 29 当核对基准**。
- **两次事故同源**：都是"文件能自己选库"。一次是 schema 文件带 `USE` + 逐表删，一次是种子文件带 `USE`。所以规矩针对的是**文件结构本身**，不是"某人某次手滑"。
- **未复测的部分**：29 张表被清空、admin 口令被打回弱口令，都来自 README 的当晚记录，本轮没有重演（重演一次就是再出一次事故）。
