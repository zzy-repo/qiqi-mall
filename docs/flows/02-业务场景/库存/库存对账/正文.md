## 库存对账（inventory reconcile）

分桶之后一个规格的库存有两个数：`SUM(sku_bucket.stock)` 是权威值，裁决只认它；`sku.stock` 是展示缓存，由回写任务按桶和覆盖。对账把两者摆在一起，`drift = 权威值 − 缓存`，正的是缓存少记、负的是缓存多记；这一对才是应当相等的一对。

第三个数 `SUM(stock_ledger.delta)` 是全生命周期进出和，不参与对平：期初库存不经台账，净额天生差着那一笔，与桶和永不相等。页面把它单独摆一块并写明「不是余额」「不能与上面的权威值相互对平」—— 三个数并排，人一定会去比较。

对账只读：两个端点都是 `GET`，不写桶、不写缓存、不写台账。让缓存回到权威值只有两条正路：走扣减/回补让桶变，或后台重置库存重铺分桶并标脏，再由回写任务刷成桶和。在对账接口里补一句 `update`，偏差「为什么产生、产生了多久」这条线索就没了，且对账不写台账，那次改动事后也无法解释。

偏差 TOP 是派生值：`ABS(桶和 − 缓存) > 阈值`，按绝对值倒序分页，阈值默认 100，传 0 表示任何非零偏差都列出。`ABS()` 在 `WHERE` 上走不了索引，这条查询全表扫，所以只读、按需触发、`size` 上限 50。

另两项同屏给出：桶数与配置值是否一致（不等则 warn，分桶扣减会去找不存在的桶，表现成假性缺货）；`lastRefreshAt` 取 `MAX(sku_bucket.updated_at)`，不是缓存回写时刻。

**效果**　`库存对账.spec.js`：2 条用例、37 处断言，真点界面 + 真读库，跑在分桶模式（`qiqi.stock.bucket-enabled=true`）下；被测规格按桶形态现挑（恰好 8 桶、桶和 ≥ 1000），不写死 id。用例一「只报不改」：把展示缓存写成桶和 + 500 → 连续 3 次调对账接口，偏差恒为 −500、`bucketCount` 恒为 8；页面再点 2 次「对账」数字不动；逐项断言缓存仍是假值、桶和不变、`stock_ledger` 行数与净额不变、页面文本含「不是余额」。偏差 TOP 在阈值 100 下列出这一行（含 `-500`），阈值抬到 600 后消失。用例二「缓存追平」：偏差先在页面看见 → 走真实入口（SKU 编辑 → 重置分桶并标脏）→ 以 300 / 600 / 1200ms 间隔轮询，15 秒内归零 → 页面偏差 0、TOP 行消失、台账一行没多。库上只读快照（2026-11-14 21:26，`qiqi_mall_e2e_a`）：121 个规格、缓存偏差 0 个、恰好 8 桶且桶和 ≥ 1000 的 108 个、阈值 100 的 TOP 0 行。

**边界**　三个数不能互推：`缓存 = 桶和` 应恒成立，`净额 = 桶和` 永不成立，`净额 = 单据数 × 件数` 只在单笔时成立。偏差非零不是异常：回写周期默认 250ms，被扣减的规格必然短暂不一致，「不收敛」才是异常。阈值判定是严格大于（`ABS(...) > threshold`），正好等于阈值的偏差不列出 —— 页面表头提示写的是「≥」，以 SQL 为准。一个桶都没有的规格会以 `drift = −skuStock` 进 TOP，那是桶缺失的信号。规格不存在时接口报错，不给三个数都是 0 的卡片。对账没有写能力：AI 密钥侧只登记只读档 `stock:read`，没有写 scope。数字出处：阈值 100 与 `size` 上限 50 在 `AdminInventoryController`，最近流水 20 条在 `InventoryReconcileService`，250ms 在 `StockCacheRefresher`；21:26 那组是今晚只读查询的真实输出，重跑会变。
