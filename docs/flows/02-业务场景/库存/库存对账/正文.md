**对账页最容易犯的错，是"看见了就顺手修一下"** —— 它把三个数摆在一起，其中只有前两个应当相等；第三个（台账净额）本来就不该对平。而"修"这件事必须由动账路径做，不能由只读的对账接口做，否则证据就变成了结论。

## 场景

分桶之后，库存有了一份权威值（`SUM(sku_bucket.stock)`）和一份展示缓存（`sku.stock`）。页面 `admin-web/src/views/inventory-reconcile/index.vue` 就是给这两者做对账的：

- 上半部分是**单个规格**的对账：输入 `skuId`（或从规格列表里挑）→ 三块卡「权威值 / 展示缓存 / 偏差」，偏差为 0 时绿色、非 0 时红色并说明正负含义；
- 中间单独一块「台账净额」（`SUM(stock_ledger.delta)`），特意用另一种颜色、与上面三块隔开，并写明**它不是余额**；
- 下面是最近 20 条库存流水（时间 / 原因 / 增减 / 落点桶 / 关联单据 / 幂等键）；
- 再往下一张「全库偏差 TOP」表：`|偏差| > 阈值` 的规格按偏差倒序分页，点一行直接跳到该规格的对账卡片。

## 撑不住的时候

这套东西存在的理由只有一个：**分桶之后，"库存"变成两个数了**。桶是裁决依据，`sku.stock` 只是给人看的缓存，由周期任务（默认 250ms）从桶回写。于是"两个数不一致"不是异常，而是常态的一小段 —— 正在被扣减的规格，缓存必然滞后一个周期。

危险就藏在这个常态里，有两条：

- **想顺手修一下**。看到偏差就想在对账接口里补一句 `update`：偏差是"为什么会产生、产生了多久、谁改的"的唯一线索，一修就没了；而且对账不是记账路径，它**不写台账**，所以那次"修正"事后无法解释。这就是页面口径里的红线：**对账只报结论，不写证据**。
- **想拿台账净额去对平**。`SUM(delta)` 是全生命周期进出和，把历史上每一次扣减与回补累加在一起，必然差着"那笔没有被台账覆盖过的初始库存"。真拿它去校验 `SUM(桶)`，结果只有两种：报一堆假错，或者顺手改掉真库存。

还有一条容易误读的：桶数不等于配置值时（比如该规格只有 7 个桶），分桶扣减会去找不存在的桶，**表现成假性缺货**。所以接口把桶数与配置值一起返回，页面在不等时点亮一个提醒。

## 改了什么

① **三个数分区摆放，不让人误读**：偏差卡按 0/非 0 换色并直接写"正的偏差＝缓存少记，负＝缓存多记"；台账净额单独一块、写明"这是全生命周期进出和，不是余额""不能与上面的权威值相互对平"。这不是文案修饰 —— 页面上并排放四个数，人一定会去比较，所以必须把"哪两个该相等"写在它们中间。

② **偏差 TOP 是按需查询的派生值**：`ABS(bucketSum - skuStock) > 阈值`，按绝对值倒序，`threshold` 默认 100（100 件以内的滞后不值得报警），传 0 表示任何非零偏差都列出来（排查"回写是不是在工作"时用它）。这条查询是全表扫（`ABS()` 在 WHERE 上走不了索引），所以它只读、按需触发、单页 50 行封顶。

③ **接口天然只读**：两个端点都是 `GET`，AI 密钥那条链路里也只登记了只读档 `stock:read`，**没有对应的写 scope** —— 不是"我们小心没写"，是"这条路径根本没有写的能力"。

④ **两个容易被误当成"能修"的字段，各自带了说明**：`bucketCount` / `expectedBucketCount`（不等就 warn + 页面提示）、`lastRefreshAt`（取的是 `MAX(sku_bucket.updated_at)`，**不是"缓存回写时刻"** —— 库里没有那一列，页面就这么如实写，不编一个假时间）。

## 凭什么证明好了

**① 能演的：UI 测试（已跑绿）+ 录屏（本轮待补，登记在「待补视频」，不是"无界面"）**

`e2e/tests/scenarios/库存/库存对账.spec.js`，两条用例，全部真点界面 + 真读库：

- **用例 1「只报不改」**：把某个规格的展示缓存直接写成「桶总量 + 500」（模拟一份没追平的缓存）→ 连续调 **3 次**对账接口，三次偏差都是 **−500**；再在页面上点 **2 次**「对账」，数字一动不动；全程断言 `sku.stock` 仍是那份假值、`SUM(桶)` 不变、**库存台账行数不变**（对账没写证据）。顺带断言页面明写了"不是余额"、"不能与上面的权威值相互对平"。
- **用例 2「缓存追平」**：同一个偏差 → 页面先看见它（卡片 −500 + 偏差 TOP 里有这一行，阈值 100）→ 从**真实入口**把该规格库存设回权威值（SKU 编辑 → 重置分桶并标脏）→ 等回写任务把缓存刷成 `SUM(桶)`（`expect.poll` 到库里偏差为 0）→ 回页面刷新：偏差归零、**TOP 里那一行消失**、**台账一行没多**（缓存回写不是动账）。

## 附：口径与边界

- **只有前两个数该相等**：`bucketSum` 与 `skuStock` 应当相等，`drift = 桶 − 缓存`；`ledgerNet = SUM(delta)` 是全生命周期进出和，**永远不参与对平**，也不许拿它去修正任何一边。
- **偏差符号**：正 = 缓存少记，负 = 缓存多记。阈值判定用的是绝对值，且是**严格大于**（`ABS(...) > threshold`）—— 阈值 500 时，正好 500 的偏差**不会**被列出，这一点用例里也钉了（阈值抬到 600 后那一行必须消失）。
- **缓存滞后是正常现象**：回写周期默认 250ms，正在被扣减的规格必然短暂不一致。所以"偏差 ≠ 0"不是报警，**"偏差不收敛"**才是。
- **对账接口没有写能力**：两个端点都是 GET，AI 密钥只有 `stock:read`。想修偏差只有两条正路 —— 走扣减/回补让桶变，或让回写任务把缓存刷成桶之和。
- **造偏差的方式只有一种**：直接写 `sku.stock`（用例里就是这么造的）。后台的"编辑库存"走的是 `resetStock`（重铺分桶 + 标脏），**不会**造出偏差 —— 这也是为什么"造偏差"必须落在测试的造数阶段，而不是指望界面点出来。
- **`lastRefreshAt` 不是缓存回写时间**：它是 `MAX(sku_bucket.updated_at)`（该规格库存桶最近一次变动），因为 `sku` 表没有回写时间列。页面如实标注，不假装有。
- **本页数字出处**：回写周期 250ms、`RECENT_LEDGER_ROWS = 20`、阈值默认 100 / 单页 50 上限，分别来自 `StockCacheRefresher`、`InventoryReconcileService`、`AdminInventoryController` 的常量；"偏差 500 不会被阈值 600 列出"与"台账行数不变"是本次 UI 测试的实测断言。
