## 库存台账（stock_ledger）

动账口子共用一个写入口：下单扣（`ORDER_CREATE`）、审核不通过回补（`AUDIT_REJECT`）、取消包裹回补（`DELIVERY_CANCEL`）、退货审核通过回补（`RETURN_REFUND`）；后台建单同走这一入口、原因码同为 `ORDER_CREATE`。每次变动写一行 `stock_ledger`，带 `delta`（负数扣、正数补）、原因码、关联单据（`ref_type` / `ref_id`，下单为空）、落点桶号 `bucket_no`、幂等键 `idem_key`。

动账之前先声明：调用方用 `StockLedgerContext` 说明这次变动属于哪张订单、什么原因、由哪张单据触发，未声明则 fail-closed 抛异常。写入口按「先记账后动库存」排序，台账写不进去整笔事务不成立，库存一点不动。

去重由 `idem_key = [shard:]orderId:skuId:reason:refId`（`refId` 缺省 0）与唯一索引 `uk_idem` 承担：撞键即视为这件事已经记过，一行不写、库存不动。回补另有一道守恒：同一订单同一规格补到下单量为止，多出的部分跳过，换入口也补不出第二份。

`bucket_no` 记录这批货从哪个桶出去，回补优先回原桶，单笔净额自然归零；台账无桶号（分桶前的历史行）时落最小桶号。该列只用于回补定位，不参与守恒计算，守恒看的是 `delta` 之和。

三个数各自定义，不能互相替代：`SUM(sku_bucket.stock)` 是权威值，裁决只认它；`sku.stock` 是展示缓存，由周期任务按桶和回写；`SUM(stock_ledger.delta)` 是全生命周期进出和，不是余额 —— 期初库存不经台账，净额天生差着那笔期初，它只回答「这单补过货没有、补了多少」。

**效果**　快照 2026-11-14 16:46，e2e 分片库 `qiqi_mall_e2e_a`，五组只读 SQL。全库 127 个 SKU，桶和与展示缓存不一致 0 个。台账 15 行、去重键 15 个，按「订单+规格+原因+单据」分组重复组 0。`ORDER_CREATE` 的扣减量与订单明细逐单逐规格比对 11 对、0 处不符。回补回原桶：订单 37 净额 0、涉及桶数 1、轨迹 `ORDER_CREATE:6 RETURN_REFUND:6`，订单 39 为 2 / 2。最热闹的那个规格 `sku_stock_cache=50 / bucket_sum=50 / ledger_net=-10 / ledger_rows=15` —— 缓存等于桶和，净额为负而账上 15 行。UI 侧 `库存台账与对账.spec.js` 3 条用例、35 处断言：下单只留 1 行 `delta=-2`、`bucket_no` 非空；审核不通过后 2 行、净额回 0，接口重放两次均被状态守卫挡回，行数与净额不变。

**边界**　`bucket_no` 可空只允许出现在分桶前的历史台账上，分桶后的扣减必须记桶号。`idem_key` 可带 `orderId % idem-key-shards` 前缀且可关，断言应匹配语义尾巴而不是整串。台账是证据，`order_id` / `sku_id` 刻意无外键，订单被物理删除后账还在。三组关系不能互推：`缓存 = 桶和` 应恒成立，`净额 = 桶和` 永不成立，`净额 = 单据数 × 件数` 只在单笔时成立。历史记录的「一个规格从 47 变 49」本轮未复测，不作今日数字；上面的 127 / 15 / 11 / 50 / −10 是某次快照，重跑会变，「0 处不符 / 0 重复 / 缓存零偏差」这几条结论不变。
