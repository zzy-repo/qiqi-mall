**同一件货不能被补两次** —— 四个动账口子（下单扣、审核不通过补、取消包裹补、退货通过补）走同一个写入口，先记账再动库存；去重键是「订单:规格:原因:单据」，撞上就当已经记过，一行不写、库存一点不动。

## 场景

库存的变动只有四种原因码：`ORDER_CREATE`（下单扣）、`AUDIT_REJECT`（审核不通过回补）、`DELIVERY_CANCEL`（取消包裹回补）、`RETURN_REFUND`（退货审核通过回补）。四次变动都写 `stock_ledger`，一行一次，带 `delta`（负数扣、正数补）、原因、关联单据（`ref_type` / `ref_id`，下单为空）、落点桶号（`bucket_no`）、幂等键（`idem_key`，有 `uk_idem` 兜底）。

以前这四处是各写各的裸 SQL（`stock = stock + N`），四处叠加起来能把同一件货补两次。后台建单那条路径就真出过：那条路**不扣**库存，但三个回补口子都会补 —— 一个规格从 47 变成 49（历史记录，本轮未复测）。

## 撑不住的时候

**四处各写各的，最大的问题不是算错，是算错了查不出来。**

- 没有账，就说不清「这 8 件到底是补了几次补回来的」。库存虚增不报错、不越界、不触发任何监控，只是数字慢慢变大；发现只能靠盘点，而盘点看见的是结果，看不见是哪一次补重的。
- 换个入口补一次，就没有第二道闸能拦住：`审核不通过` 补过了，`取消包裹` 再走一遍，两边各自都是「按数量加回去」的正确代码，合起来就是一货补两回。
- 更隐蔽的是**补到哪儿去了没人知道**：分桶之后库存是 8 行，回补若随便找一个桶加，账面上「总数对了」，但卖出那一桶永远是 0、退回那一桶越堆越高 —— 单看总数看不出任何异常。

所以这一页要立的规矩不是「加法写对」，而是：**每一次扣补都有账、同一个触发只记一次、而且能查出落点。**

## 改了什么

① **唯一写入口 + 先记账后动库存**：谁要动库存，先用 `StockLedgerContext` 声明这次变动属于哪张订单、什么原因、由哪张单据触发；没声明就 fail-closed 抛异常 —— 不允许出现「改了库存但账上没有」。台账写不进去，建单整笔不成立。

② **去重键 + 唯一键兜底**：`idem_key = [shard:]orderId:skuId:reason:refId`（`refId` 缺省 0，前缀是 `orderId % idem-key-shards`，可关）。撞 `uk_idem` 就当「这件事已经记过」，**一行不写、库存一点不动** —— 不是「再记一行然后对账时发现重复」。

③ **回补再夹一道守恒**：同一订单同一规格，补到下单量为止，多出来的部分直接跳过。所以哪怕换了入口、哪怕幂等键算错，也补不出第二份。

④ **扣减记落点桶，回补优先回原桶**：`bucket_no` 就是「这货从哪个桶出去的」；回补回到那一个桶，单笔净额自然归零。台账没记桶号（分桶前的历史账）才落到最小桶号。

⑤ **三个数各是各的，不能互相替代**（这是最容易看错的地方）：

| 数 | 是什么 | 该不该对平 |
| --- | --- | --- |
| 桶的总和 `SUM(sku_bucket.stock)` | **权威值**，库存事实源，裁决只认它 | 基准 |
| 页面显示的库存 `sku.stock` | **展示缓存**，周期任务（默认 250ms）按桶和回写 | 应当等于权威值，差就是偏差 |
| 台账净额 `SUM(stock_ledger.delta)` | **全生命周期进出和**，从第一笔到现在所有扣与补的累加 | **永远不该对平**，它不是余额 |

净额对不平是数学必然，不是数据脏：初始库存不是台账记进去的（台账只记变动），所以净额天生差着「那笔没被台账覆盖过的期初」。它只回答一件事：**这单到底补过货没有、补了多少**。想拿它去校验库存，结局只有两种 —— 报一堆假错，或者顺手把真库存改掉。三个数怎么读、对账页为什么只读不改，在 `库存/库存对账` 那页；这页讲的是这三个数各自怎么来的。

## 凭什么证明好了

**① 库上的事实（本页下方「📊 实测数字」五组只读 SQL，快照 2026-11-14 16:46，e2e 分片库 `qiqi_mall_e2e_a`）**

先说不会随数据变的那几条，这也是引用这些数字的正确方式 —— 断言恒等式，绝对值只当某次快照的示意：

- **全库 127 个 SKU，桶和 ≠ 缓存的 0 个**（`cache_mismatch=0`）：权威值与展示缓存一处不差；
- **行数 = 去重键数**（15 行 / 15 把键）、**按「订单+规格+原因+单据」分组重复组 0 个**：同一件货没有被记第二次；
- **回补逻辑里出现 `RETURN_REFUND` 的单据，净额 0、涉及桶数 1**（`order 37: ORDER_CREATE:6 RETURN_REFUND:6`）：卖出去的那个桶就是退回的那个桶；
- **`ORDER_CREATE` 的扣减量与订单明细逐单逐规格对得上，待核对 11 对、0 处不符**：扣的就是下单量。

某次快照里那个「最热闹」的规格：`sku_stock_cache=50 / bucket_sum=50 / ledger_net=-10 / ledger_rows=15` —— 缓存与桶和相等（50），而净额是 −10：净扣了 10 件货，但账上有 15 行。**这三个数本来就该是三个不同的数**，这一行就是活证据。

**② 能演的：UI 三条用例 + 录屏（`e2e/tests/scenarios/库存/库存台账与对账.spec.js`，35 条断言）**

- **用例一（下单只留一行）**：后台新增一笔待审核订单（建单即扣库存）→ 库断言这张单**只有 1 行**库存台账、`delta = -2`、原因码 `ORDER_CREATE`、`ref_type/ref_id` 为空、`bucket_no` 非空；幂等键逐字匹配 `…:{orderId}:{skuId}:ORDER_CREATE:0`；台账页按「库存 + 订单 ID」筛选恰好 1 行，且那一行能看出原因码。
- **用例二（回补一行、净额归零、重放不多行）**：审核不通过 → 台账 2 行、原因码序列 `ORDER_CREATE、AUDIT_REJECT`、净额回到 **0**、最大 `delta` 等于下单量、两行都有落点桶；随后**从接口把这条回补重放两次**，两次都被状态守卫挡回（`code=1`），台账仍是 2 行、净额仍是 0、正向回补总量不超过下单量（守恒上限）。
- **用例三（三个数各是各的）**：对账页三块卡片分别等于 `SUM(桶)`、`sku.stock`、两者之差；台账净额单独一块且页面必须写清「不是余额」；流水表列出最近 20 条且能看到落点桶与原因码；偏差阈值设 0 时，这个一致的规格**不出现**在偏差榜上。

## 附：口径与边界

- **`bucket_no` 可空，但它不是「随便填」**：空只允许出现在分桶前的历史台账上；分桶之后的扣减必须记桶号，否则回补只能落到最小桶（用例一专门断言了它非空）。这一列只用于回补定位，**不参与守恒计算** —— 守恒看的是 `delta` 之和。
- **幂等键里带 shard 前缀**：`[shard:]orderId:skuId:reason:refId`，前缀是 `orderId % idem-key-shards`，可以关掉（见 `sql/migrate-ledger-idem-shard.sql`）。键的**语义尾巴**（后四段）是稳定的，断言时应匹配尾巴而不是整串 —— 用例里用的就是 `(^|:)orderId:skuId:reason:0$` 这种宽松前缀匹配。
- **台账是证据，不随订单级联删除**：`stock_ledger.order_id` / `sku_id` 刻意没有外键，订单被物理删掉后账还在（`事故与修复/台账孤儿-573-万行` 讲的就是这类表被 reset 漏删的后果）。
- **别拿这三组关系互推**：`缓存 = 桶和` 是应该成立的恒等式；`净额 = 桶和` 永远不成立；`净额 = 单据数量 × 件数` 只在单笔情况下成立。把不同范围的两个 `SUM` 放在一起比，是最常见的误读。
- **数字的时间戳**：上面的 `127 / 15 / 11 / 50 / −10` 都是 2026-11-14 16:46 那一刻的快照。重跑那批 spec 或换一套库，绝对值会变，**「0 处不符 / 0 重复 / 缓存零偏差」这几条结论不变**。
