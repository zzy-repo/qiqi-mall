## SKU 与规格（SKU / spec）

可售单元是 `sku` 一行，不是 `product`：一个规格组合（如 颜色 × 内存）一行，售价、库存、图片都挂在这行上；商品是多行规格的容器。

规格值结构化存储，落在 `sku_spec(sku_id, attribute_id, value)`，唯一键 `(sku_id, attribute_id)` 约束「一个属性在同一个 SKU 上只能有一个值」。`attribute_id` 外键指向所属商品类型的属性定义，规格名是选出来的，不是自由文本。

规格文本不落库字段：列表上那串「颜色:黑色,内存:256G」由 `SpecTextHelper#buildText` 按 `attribute.name` 现拼。

库存挂在 SKU 上：库存粒度就是可售组合的粒度。`sku.stock` 是规格级一列，分桶表 `sku_bucket.sku_id` 也是规格级，`product` 上没有库存字段。管理端改库存走 `StockStore#resetStock`：分桶模式按新总量重铺全部桶，legacy 直接写 `sku.stock`；只改 `sku.stock` 不改桶会造成界面与实际可扣数量不一致。

编辑是整组替换，不做 patch：`SkuController#update` 先把该 SKU 的 `sku_spec` 全部 `remove`，再 `saveSpecs` 重写。按差异更新会在「删旧行、插新行」之间留下中间态，撞上 `(sku_id, attribute_id)` 唯一键；整组替换没有中间态。同一路径带乐观锁：缺 `sku.version` 返回 400，影响行数 0 返回 409，此时价格、库存、规格值都不落库。

删除先算引用：`CatalogDeleteGuard` 计订单明细数与购物车数，`?dryRun=true` 只预演，返回将被删除的规格（含所属商品、售价、库存）与引用数；有引用即拒，中文原因原样返回。停卖的动作是把整个商品下架，不是删掉这一行。

**效果**　`SKU与规格.spec.js`：4 条用例、32 处断言。新增「颜色 / 内存」两行规格 → 落库价格 1999、库存 100，`specText` 含 `颜色:…` 与 `内存:256G`；改价 1888、库存 66 落库且列表显示 `1888.00`；把 `256G` 改成 `512G` 后 `specText` 含 `内存:512G` 且不含 `256G`，C 端接口与详情页同读到新值。价格或库存清空提交 → 表单项就地报错、弹窗不关、库不落行。被订单引用的规格预演文案含「删除会被拒绝」，确认后返回后端中文原因；无引用规格可删，列表 1 → 0。`sku.pic` 落库为相对路径，弹窗预览、列表缩略图、C 端详情主图三处均实际加载。

**边界**　库存挂在 SKU 上：商品级库存只能由各规格求和得到，没有独立字段可写，改总量也按 SKU 逐个设置，不存在商品级批量扣减。整组替换意味着编辑必须一次提交该 SKU 的全部规格值，两处并发编辑按后写覆盖处理（`version` 冲突则 409），不合并两边差异。「同一商品下规格组合唯一」没有数据库约束：唯一键只到 `(sku_id, attribute_id)`，配出两行相同的「颜色:黑,内存:256G」，库照收，这是已知缺口。规格文本不落快照，属性改名会连带改掉历史订单里的规格展示；被快照的只有 `order_item.product_name` 与 `product_price`。单行库存的并发上限见 `库存/库存分桶`。
