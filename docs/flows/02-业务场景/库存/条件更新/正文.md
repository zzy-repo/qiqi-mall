## 条件更新（conditional update）

扣减的裁决必须落在一条语句里：`UPDATE sku SET stock = stock - ? WHERE id = ? AND stock >= ?`。影响 1 行表示扣到，影响 0 行表示余量不足、一件未扣。

拆成「读余量 → 判断 → 写回」三步会开出一段窗口：两个事务读到同一余量、都判够、都写回，后写覆盖前写，即丢失更新（lost update）。并发越高，落在窗口里的事务越多，超卖随并发放大。

条件写法的原子性由行锁给出：`WHERE` 谓词求值与赋值在同一条语句内完成，第二个事务在第一个提交后才进入，`stock >= ?` 读到的是新值。不需要锁表、不需要 `SELECT ... FOR UPDATE`、也不需要应用层二次校验。

扣不动时抛 `IllegalStateException`，异常穿出 `REQUIRES_NEW` 事务边界，订单、明细、已扣库存一起回滚，不留「库存扣了订单没建」。原因文案随异常回到前端：HTTP 200 + `code=1` 的业务失败，页面停在结算页。

分桶模式下口径不变，条件里的行换成桶：`SkuBucketMapper#deductOne` 的 `AND stock >= #{qty}` 是全部防超卖依据，另有逐桶 `CHECK (stock >= 0)`（机制见 `库存/库存分桶`）。

进入扣减前有两道：幂等键与前置校验。进结算页领一次性令牌，提交时服务端原子消费一次即作废，重复提交返回业务错误；同一 HTTP 请求内的死锁重试不重新消费令牌，重试不会变成第二单。空明细、空收货人、空地址在创建订单前各返回一句中文原因，不产生订单行。

**效果**　`条件更新.spec.js`：1 条用例、36 处断言，两个独立浏览器上下文真并发。库存 2 件、两个会员各买 2 件同一 tick 提交 → 恰一人 `code=0`，另一人 `code=1` 且 `message` 逐字为 `库存不足：<商品名>`，败者无 success 提示、URL 仍停在 `/checkout`；胜者订单 1 笔、明细 1 条 2 件，败者 0 笔 0 明细；`min(sku.stock) >= 0`，分桶镜像下 `SUM(桶)` 精确为 0 且单桶库存无负值。按跑前基线比对，该 SKU 的订单明细只多 1 条、件数只多 2 件。

**边界**　这条语句扣的是 SKU 的总库存池。分仓是拆单时的事：`SplitOrderService#resolveAssignment` 只在 `inventory` 表挑 `stock` 最大的仓作为归属标记，`inventory.stock` 不参与扣减，所以「总池够」不等于「某仓够」。与版本冲突是两件事：这条 UPDATE 不看 `sku.version`，SKU 编辑的乐观锁管的是两个商家并发改价改库存，管不了扣减。断言强度与模式绑定：分桶镜像需显式 `E2E_STOCK_MODE=bucket`，spec 不猜模式。历史观测的「一次多卖十几到二十单」本轮未复测，不作今日实测数字；当前 `SkuMapper` / `SkuBucketMapper` / `LegacyStockStore` 里已无不带条件的先查后写。
