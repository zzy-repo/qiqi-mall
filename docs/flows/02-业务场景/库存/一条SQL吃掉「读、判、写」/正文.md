**判断和减法必须在同一条语句里** —— `UPDATE sku SET stock = stock - ? WHERE id = ? AND stock >= ?`，影响 1 行就是扣到了，影响 0 行就是库存不足。分成「读一次、判一次、写回去」三步，中间那条缝就是超卖发生的地方。

## 场景

同一个规格总库存只有 2 件，两个买家（两个独立会话、两个账号）各要 2 件，几乎同时点「提交订单」。业务上这件事只有一句话：这 2 件货只能卖给一个人。

链路：`portal-web/src/views/checkout/index.vue` → `POST /portal/orders` → 幂等令牌原子消费 → `OrderTransactionalCreator#create`（`REQUIRES_NEW`）→ 逐条明细 `skuService.deductStock(skuId, qty)` 走到 `SkuMapper#deductStock` 那条 UPDATE → 影响 0 行抛 `IllegalStateException("库存不足：" + 商品名)` → `GlobalExceptionHandler` 兜底成 **HTTP 200 + code=1**（业务失败，不是 HTTP 错误）→ 前端显示 `下单失败：` + 后端原话，人停在结算页。

## 撑不住的时候

「先读、再判、再写回」的窗口期，就在「读」和「写回」之间：

```
事务甲：读到 stock = 1 → 判断够 → UPDATE sku SET stock = 0 WHERE id = 1
事务乙：读到 stock = 1（甲还没提交）→ 判断够 → UPDATE sku SET stock = 0 WHERE id = 1
结果：两单都成立，卖了 2 件，库存落到 -1
```

最要命的是**它不报错**：两个人各自都拿到「下单成功」，库存变成负数也没人拦（当时 `stock` 列上没有非负约束），只有事后对账才发现少了一件货。这类窗口在抢购场景下的量级是「一次能多卖出十几到二十单」（历史观测记录，**本轮未复测**；现在这条路径上已经找不到先查后写的代码 —— `SkuMapper` / `SkuBucketMapper` / `LegacyStockStore` 全是单条原子 SQL）。

关键点不是「读错了」，而是**读到的数在写回之前就已经过期**，而代码把它当成了事实。

## 改了什么

① **判断与减法压进同一条 UPDATE**（legacy 路径）：`WHERE id = ? AND stock >= ?`。影响 1 行 = 扣成功；影响 0 行 = 库存不足，一件都没扣。中间没有缝 —— 因为判断和减法是同一个原子语句，由行锁串行。扣不动就抛中文原因，**整笔事务回滚**（订单、明细、已扣库存一起消失），不会出现「库存扣了订单没建」。

② **分桶模式下口径不变，只是「那一行」换成「那个桶」**：`SkuBucketMapper#deductOne` 里的 `AND stock >= #{qty}` 是全部防超卖依据，外加每桶 `CHECK (stock >= 0)`，所以 `SUM(桶) >= 0` 在库层面就写不进去（机制与压测在 `库存/库存分桶`，本页不重复）。

③ **三道前置校验在扣减之前**：明细为空、收货人为空、地址为空各回一句中文（`请选择要结算的商品` / `请填写收货人` / `请填写收货地址`），一个订单都不产生。

④ **幂等令牌**：进结算页先领 `GET /portal/orders/idempotent-token`，提交时带上，服务端 `consume` 一次就作废；第二次提交回 `请勿重复提交订单（或页面已过期），请刷新结算页重试`。**死锁重试不重新消费令牌**（重试在 `OrderCreateService#createWithRetry` 里，同一 HTTP 请求内，最多 3 次，退避 30ms×2^n + 抖动），所以重试不会变成第二单。

`e2e/tests/scenarios/库存/一条SQL吃掉「读、判、写」.spec.js`，1 条用例、36 条断言，两个独立 browser context 真并发：

- 后台把商品 1 的某个 SKU 库存改成 2，并**按数据复核**「恰好 1 个 SKU 是 2」（不假设表格第一行就是目标）；两个会员各自注册、各加 2 件、各自停在结算页，先断言两人页面上的应付金额都是「单价 × 2」；

## 附：口径与边界

- **这里扣的是「总库存」**。分到哪个仓是拆单时的事：`SplitOrderService#resolveAssignment` 只在 `inventory` 表里挑 `stock` 最大的仓当「归属标记」，没配分仓记录的落到默认仓（启用仓里 id 最小的那个）并记 warn。**`inventory.stock` 不参与扣减** —— 所以「总池够」不等于「某个仓够」，那是另一件事，本页不证明。
- **这跟版本冲突不是一回事**：那条 UPDATE 不看 `sku.version`。SKU 编辑用的乐观锁管的是「两个商家同时改价/改库存」，管不了扣库存，两件事别混（见 `并发与竞态/版本冲突/SKU编辑并发`）。
- **断言的强度跟模式绑死**：分桶镜像要显式 `E2E_STOCK_MODE=bucket`，spec 不猜模式 —— 两种模式下断言的对象不同（桶 vs 那一行），混着断言只会两头都不准。
- 「十几到二十单」是历史观测的量级，**未复测**，本文不把它当今天的实测数字用；今天能复现的只有上面那条用例的结果（恰一人成功、库存归零、订单只多一笔）。
