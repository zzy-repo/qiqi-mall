## 库存分桶（bucketed inventory）

单行 `sku.stock` 是热点行：所有扣减在同一行上争用行锁，事务持锁时长即吞吐上限。把该行拆为 8 个桶行 `sku_bucket(sku_id, bucket_no, stock)`，行锁由 1 把变为 8 把。

扣减走条件更新：`UPDATE sku_bucket SET stock = stock - N WHERE sku_id = ? AND bucket_no = ? AND stock >= N`。影响 1 行为成功，0 行为该桶余量不足，换下一个桶。起始桶随机，避免所有事务从同一个桶进入形成新热点；单桶不足时按桶号升序跨桶取货，升序保证加锁顺序一致、不成环；回补回到台账记录的桶号，台账无记录的落最小桶号。

不超卖由三层保证：逐桶 `CHECK (stock >= 0)`、条件更新的影响行数、跨桶取货失败时的回滚。

桶上 `UNIQUE KEY (sku_id, bucket_no)` 约束一个桶只有一行；桶数由 `qiqi.stock.bucket-count` 决定，开关 `qiqi.stock.bucket-enabled`。库存裁决只有一个入口 `StockStore`：legacy 改 `sku` 那一行，bucket 改某一个桶，共用同一套台账；`SkuMapper` 原有的 deduct / restore 已删除。

`sku.stock` 在此模型下降级为展示缓存：扣减与回补都不写它，只标脏，由周期任务按 `SUM(sku_bucket.stock)` 回写。它不参与裁决，读余量走 `StockStore#availableStock`。

**效果**　单行模型 c=8 / c=16 为 298.9 / 300.6 ok/s，并发翻倍而吞吐不变（+0.6%）；分桶后同场景为 337.8 / 363.1 ok/s（+13.0% / +20.8%）。p50 27.8 → 21.5 ms（c=8）、58.8 → 39.5 ms（c=16）。每单行锁等待次数 1.53 → 0.56、1.56 → 1.03；每单等锁时间 30.0 → 4.2 ms、84.3 → 22.3 ms。三臂死锁 0，错误率 0.009%～0.010%，`commits_per_ok` 约 1.9 且三臂一致。`stock_ledger.bucket_no` 23,877 行全部非空、distinct = 8，8 个桶都在用。100% 冷门 SKU 的探针在同一并发档跑到 411.3 ok/s；单行 c=16 档 27 次 `SHOW ENGINE INNODB STATUS` 采样全部命中同一条 `UPDATE sku`。冷启动首轮 242.2 / 257.9 作废，不计入。

**边界**　8 桶覆盖该机型 88.3% 的可达吞吐，即 363.1 / 411.3；8 → 32 桶实测 368.3（+1.0%，在 ±2.8% 噪声内），桶数不是杠杆。收益来自串行点被打散，不是单条 SQL 变快：四档桶数、c=8→c=64，server 容器 ≤72%、MySQL ≤132%（限额 200%），瓶颈在等待。该结论绑定本套配置（4 核机、21 个热点 SKU、2 实例、Tomcat 200 / Hikari 10、已修死锁那版台账），换机器或热点占比下降则增益变小。`sku.stock` 回写周期默认 250ms，是展示延迟而非一致性延迟，对账取 `SUM(桶)`。分桶只解决同一行的并发，下一个限制项是每单约 19 条 SQL 与这台 MySQL（见 `性能与容量/每单19条SQL`、`性能与容量/雪崩点400`）。
