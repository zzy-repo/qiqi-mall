**库存分桶：把一把锁拆成八把** —— 同一个 SKU 的一份库存物理拆成 8 行（`sku_bucket`），下单扣的是「桶」：并发从抢一把行锁，变成抢 8 把互不相干的行锁。

## 场景

爆款上架、大促开始的那一分钟，几百个人同时点同一个规格的「提交订单」。业务上这只是一件事：卖一件少一件。系统要干的是在几十毫秒内回答「还够不够」，然后把数减掉，并且不许把同一件货卖给两个人。

不拆的时候，全仓的库存就是 `sku` 表上那一行 `stock` 字段。所有人在同一毫秒里都想改这一行 —— 数据库只能让他们排队，排多久取决于前一个人持锁多久。

## 撑不住的时候

坏环境是先造出来的：4 核机、同一镜像、死锁已修（台账改 INSERT IGNORE）、连接池保持默认 10、热点 SKU 占八成流量，每档 reset + 预热 60s + 测量 60s。

| 并发 | 吞吐 | 每成功一单等锁 | 每成功一单等锁时间 | 死锁 |
| --- | --- | --- | --- | --- |
| c=8 | 298.9 ok/s | 1.53 次 | 30.0 ms | 0 |
| c=16 | 300.6 ok/s | 1.56 次 | 84.3 ms | 0 |

**并发从 8 翻到 16，吞吐一点没涨**（298.9 → 300.6，+0.6%，噪声内）；等锁时间却翻了 2.8 倍 —— 典型的「排队变长、吞吐不动」。

拐点在哪儿，是量出来的，不是猜的：`SHOW ENGINE INNODB STATUS` 每 2 秒采一次，c16 那一档 **27 次采样全部命中同一句** `UPDATE sku SET stock = stock - 1 WHERE id = 1`，0 次命中台账。再补一个探针：同样机器、同样并发 16，只把流量换成 100% 冷门 SKU，跑到 **411.3 ok/s**（p50 58.8 → 35.5ms）。也就是说「同一行」这一件事就吃掉了 35.7% —— 天花板不在机器上，在一行上。

为什么这个拐点必须处理：它**不报错、不 5xx、不 OOM、监控全绿**。它只是让下单从 20ms 变成 200ms，然后在开抢那一分钟把所有人堵在结算页上。而且加机器、加连接、调 JVM 都不会让它右移一米（见「附」）。

## 改了什么

一句话：把一份库存物化成 8 行，让 8 个事务可以同时改不同的行。

```
sku_bucket(sku_id, bucket_no, stock)   默认 8 桶，CHECK (stock >= 0) 逐桶保证不为负

扣减 ① 快路径（绝大多数走这里）
     随机起点轮询 8 个桶，一次扣减里每个桶号只试一次：
     UPDATE sku_bucket SET stock = stock - N
      WHERE sku_id = ? AND bucket_no = ? AND stock >= N
     影响 1 行 → 扣成功，返回命中的桶号；0 行 → 这个桶不够，换下一个桶
     ② 跨桶拼单（单桶装不下这一单时才走）
     按桶号升序逐桶取货凑够；凑不够就把已拿走的原样补回去 → 库存不足
     升序是为了所有事务同一加锁顺序，不成环
     ③ 回补
     回到台账里记的那个 bucket_no；台账没记桶号（分桶前历史账）落到最小桶号

展示 sku.stock 从「库存本身」降级成缓存：扣减/回补都不写它，只标脏，
     由周期任务按 SUM(桶) 回写（默认 250ms）。它不参与任何裁决。
```

> 本页上图就是这套扣减：随机起点 → 命中桶号 → 单桶装不下时跨桶兜底 → 回补回到台账记的桶 → 逐桶 CHECK 保证合计不为负。

代码位置：`SkuBucketService#deduct` / `#deductAcrossBuckets`、`SkuBucketMapper#deductOne`（那条带 `stock >= N` 的 UPDATE 就是全部防超卖依据）、`BucketRotation#sequence`（随机起点 + 每号恰好一次）、表结构 `sql/migrate-sku-bucket.sql`、开关 `qiqi.stock.bucket-enabled` 与 `bucket-count`。`SkuMapper` 里原来那两条 deduct / restore 已删掉 —— 库存只能有一个裁决处。

## 附：口径与边界

- **8 桶只吃到「无热点上界」的 88.3%**（363.1 / 411.3），不是 100%。桶数 8→32 实测 368.3（+1.0%，在 ±2.8% 噪声内）→ **桶数不是杠杆**，8 是推荐值：更多桶只增加 SUM 回填与桶管理成本。
- 收益来自「串行点被打散」，不是「单条 SQL 变快」。四档桶数、c8→c64，server 容器始终 ≤72%、MySQL ≤132%（限额都是 200%）—— 资源只用三成，瓶颈纯在等待。
- 这是**这套配置**的产物：4 核机 + 21 个热点 SKU + 2 个实例 + Tomcat 200 / Hikari 10 + 已修死锁那版台账。换机器、或热点只占两成流量、或每单 SQL 条数被压下来，增益都会变小 —— 因为那个串行点在变弱。
- `sku.stock` 是缓存：任何「拿它做扣减判断」的写法都是回归；它滞后 ≤250ms，所以对账页必须拿 `SUM(桶)` 当权威。
- 分桶只解决**同一行的并发**。它不解决「每单约 19 条 SQL × 这台 MySQL 约 7.7k QPS」那道闸门 —— 分桶之后下一个天花板正好在那里（见 `性能与容量/每单19条SQL`、`性能与容量/雪崩点400`）。
