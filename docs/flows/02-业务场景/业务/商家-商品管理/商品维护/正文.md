## 商品维护（product CRUD / delete guard）

上下架与删除挤在同一张列表上，门槛却完全不同：下架只改一个字段、随时可逆；删除要过引用守卫，被订单明细引用过的商品永远删不掉，出路是改成下架。订单明细里存着商品 id，商品一删历史订单的明细就指向空 —— 那张单还挂在「已完成」，但说不清买的是什么。

上下架就是 `publishStatus` 一个字段，C 端两道门都看它：列表接口 `eq(publish_status, 1)`，详情接口遇到 `publishStatus != 1` 直接回「商品不存在或已下架」。下架后列表与搜索立刻看不到，直接拿链接开详情也拿不到内容 —— 前端没有缓存兜底这一层；而已有订单不受影响，明细存的是下单时的商品与价格快照。

删除改成预演、确认、执行三段。`DELETE /admin/products/{id}?dryRun=true` 只算不落库，文案自动拼出会连带删掉什么：「将删除商品「X」（id=N），下辖 N 个 SKU 与相册一并删除。当前被 N 条订单明细、N 个购物车引用」，被引用时后半句直接改成「—— 删除会被拒绝，建议改为下架」，于是预演永远 `code=0`、前端只有一条渲染路径，不用为「预演被拒」写第二个分支。真实拦截在后端且分两种情况：有订单明细回「该商品已被 N 条订单明细引用，不能删除（可改为下架）」，只在购物车里回「该商品还在 N 个买家的购物车里，不能删除（可改为下架）」，校验顺序是存在性 → 引用数守卫 → 执行。编辑走乐观锁 fail-closed：缺 `version` → 400「缺少版本号，请刷新页面后重试」，UPDATE 影响 0 行 → 409，且因为整组替换相册排在更新之后，冲突时相册也不会被动；新建即 `version = 0`。相册整组替换，`sort` 为空就按传入顺序补号，库里按 `sort, id` 升序返回 —— 那是展示顺序，主图是单独的 `pic` 字段。

**验证**　`商品维护.spec.js`：3 条用例，真点界面 + 读库。新增与编辑：主图与描述落库对得上，详情接口回 `gallery` 恰好 2 张且 `sort` 升序 `[1,2]`；C 端详情页的名称、描述、主图都能看到，图片按 `naturalWidth > 0` 判定真加载，不是只看 `<img>` 在不在。上下架切换：下架后库里 `publishStatus = 0`，C 端首页商品格里不出现这个商品名，直接开详情拿到「商品不存在或已下架」；再上架回 1，C 端又能取到。删除两条分支：种子商品 1（被演示订单引用）点删除 → 预演文案里就写着「删除会被拒绝」，点确认执行后后端原因留在弹窗里且含「不能删除」「下架」；新建的空商品能删掉、库里查不到。

**边界**　预演与真删是同一套守卫的两个入口：预演先把结论说出来（会删什么、会被拒），真删再拦一次，所以「预演说会被拒」本身就是证据的一部分。购物车引用也算硬拦，但 `CatalogDeleteGuard` 注释里写的是两句不同的话 —— 订单明细引用提示「改成下架」（历史订单必须可追溯），购物车引用哲学上是临时数据（顺手清掉更合理），实现上仍拦以免用户困惑，这是口径与实现的一处有意不一致。相册排序是展示顺序，不是主图顺序；换主图要改的是 `pic`。用例里 `gallery` 的 `[1,2]` 是当次运行造出来的两条，不是全局常量。
