**商品分类是一棵树，但父分类本身也能被商品选中** —— 想给商品挂「数码配件」这种大分类，不必先造一个子分类垫在下面。这一条直接决定了父分类选择器不能做成「只能选叶子」：做成只能选叶子，商家想挂父分类就点不动。

## 场景

后台 `admin-web/src/views/category/index.vue`：一张 `el-table`，`row-key="id"` + `default-expand-all`，用 `setChildren()` 把平铺列表拼成树；子分类缩进挂在父分类下面，铺开显示。行内只有「编辑」「删除」，新建走页头「新增分类」。

演示数据只有两层（父分类 + 子分类），但**层级不封顶**：父分类的下拉里连子分类也在，所以能在已有子分类底下再挂一层，长出第三层、第四层，缩进跟着多一级。

## 规矩落在哪

① **父分类选择器必须是 `check-strictly` 的树选择器**。`el-tree-select` 默认是非严格模式 —— 点父节点会把子节点一起选中，且不把父节点本身当可选项；`check-strictly` 打开后每个节点都是独立可选项，父节点才能被单独选中。这不是样式问题，是「商品能不能挂到父分类上」的开关。

② **「能挂父分类」在接口层是通的，且被钉住了**：商品只存 `category_id`，没有任何「必须是叶子」的校验，所以挂父分类天然合法。用例三造一个父分类、把商品直接挂上去，回读 `categoryId === parentId`。

③ **删除的顺序是「先问，再拦」**：行内点「删除」先弹确认框（「确认删除分类「X」？删除后不可恢复。」），确认后交给 `CatalogDeleteGuard.checkCategory` —— 有子分类或商品就返回「该分类下还有 N 个子分类 / M 个商品，不能删除」，返回 null 才真删。空分类确认后当场从树里消失。

④ **改名就地更新，不动层级**：`PUT` 只改 name（`parentId` 原样带回），走影响行数校验；0 行 → 409「记录已被删除」，不报假成功。

⑤ **必填在弹窗里就地拦**：分类名不填点确定 → 「请输入分类名称」，弹窗不关。

## 凭什么证明好了

`e2e/tests/scenarios/业务/商家-商品管理/商品分类.spec.js`，4 条用例：

- **新增顶级 → 新增子分类 → 改名**：顶级分类落库且 `parentId === 0`；子分类落库且 `parentId === 父分类 id`；子分类行能取到 `el-table__indent` 且 `paddingLeft` 不为 `0px`（这是「缩进真的表达了层级」的可测证据，不是看图说话）；改名后新名字在、旧名字不在。
- **必填校验**：空名点确定 → 「请输入分类名称」可见。
- **父分类可被商品直接使用**：新建父分类 → 在后台商品弹窗里把商品挂到这个父分类 → 库里 `categoryId` 就是那个父分类 id。这是 `check-strictly` 的回归点。
- **删除两条分支**：种子「手机数码」（下有子分类与商品）删不掉、回显「不能删除」且分类仍在；新建的空分类能删掉、刷新后库里也没有。

## 附：口径与边界

- **本页没有「撑不住的时候」这一节，不是漏写**：这一页没有独立的事故或缺陷记录 —— 删除守卫与「商品类型与属性」是同一行 `CatalogDeleteGuard` 的相邻方法，父分类可选是设计口径而不是修过的故障。硬凑一条痛点就是编的，所以它落在上面的「规矩落在哪」。
- **层级不封顶是「能」不是「推荐」**：演示数据两层，系统不限层数。层数一多缩进会把行挤窄 —— 这是树形表格的通用代价，本页不做手动折叠。
- **分类删除没有级联**：有子分类就整条拒掉，不会「删父带子」。要清多层得逐层来。
- **`parentId` 在表单规则里是 required，但默认值就是 0**：所以「不选父分类」= 顶级分类，不是「校验不过」。
- **本页数字出处**：删除文案来自 `CatalogDeleteGuard#checkCategory`；「确认删除…不可恢复」来自 `category/index.vue`；`check-strictly` 与 `default-expand-all` 直接读自模板。子分类个数、层数随演示数据漂移，正文一律写 N / M。
