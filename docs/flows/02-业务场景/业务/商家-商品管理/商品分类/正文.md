## 商品分类（category tree）

后台是一张 `el-table`，`row-key="id"` 加 `default-expand-all`，用 `setChildren()` 把平铺列表拼成树；子分类缩进挂在父分类下面铺开显示。演示数据只有两层，但层级不封顶：父分类的下拉里连子分类也在，所以能在已有子分类底下再挂一层，长出第三层、第四层，缩进跟着多一级。

关键在父分类选择器必须是 `check-strictly` 的树选择器。`el-tree-select` 默认是非严格模式 —— 点父节点会把子节点一起选中，且不把父节点本身当可选项；打开 `check-strictly` 之后每个节点都是独立可选项，父节点才能被单独选中。这不是样式问题，是「商品能不能挂到父分类上」的开关：接口层只存 `category_id`，没有任何「必须是叶子」的校验，所以挂父分类天然合法，能不能点得动才是那个开关。

删除的顺序是先问再拦：行内点「删除」先弹确认框（「确认删除分类「X」？删除后不可恢复。」），确认后交给 `CatalogDeleteGuard.checkCategory` —— 有子分类或商品就返回「该分类下还有 N 个子分类 / M 个商品，不能删除」，返回 null 才真删；空分类确认后当场从树里消失。改名只改 name（`parentId` 原样带回），走影响行数校验，0 行 → 409「记录已被删除」，不报假成功。必填在弹窗里就地拦：分类名不填点确定 → 「请输入分类名称」，弹窗不关。

**验证**　`商品分类.spec.js`：4 条用例，真点界面 + 读库。新增顶级、新增子分类、改名：顶级分类落库且 `parentId === 0`；子分类落库且 `parentId === 父分类 id`；子分类行能取到 `el-table__indent` 且 `paddingLeft` 不为 `0px` —— 这是「缩进真的表达了层级」的可测证据，不是看图说话；改名后新名字在、旧名字不在。必填：空名点确定 → 「请输入分类名称」可见。父分类可被商品直接使用：新建父分类 → 在后台商品弹窗里把商品挂到这个父分类 → 库里 `categoryId` 就是那个父分类 id，这是 `check-strictly` 的回归点。删除两条分支：种子「手机数码」（下有子分类与商品）删不掉、回显「不能删除」且分类仍在；新建的空分类能删掉、刷新后库里也没有。

**边界**　分类删除没有级联：有子分类就整条拒掉，不会「删父带子」，要清多层得逐层来。`parentId` 在表单规则里是 required，但默认值就是 0，所以「不选父分类」等于顶级分类，不是校验不过。层级不封顶是「能」不是「推荐」：演示数据两层、系统不限层数，层数一多缩进会把行挤窄，这是树形表格的通用代价，本页不做手动折叠。本页没有独立的事故或缺陷记录：删除守卫与「商品类型与属性」是同一行 `CatalogDeleteGuard` 的相邻方法，父分类可选是设计口径而不是修过的故障，硬凑一条痛点就是编的。
