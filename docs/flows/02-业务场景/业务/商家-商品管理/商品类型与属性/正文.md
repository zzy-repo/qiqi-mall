## 商品类型与属性（product_type / attribute）

商品类型与属性是同一个聚合的两层：先建类型（手机、食品），再在那个类型下挂属性（颜色、内存、容量）；属性页只认一个 `typeId`，看不见别的类型下的属性。`is_filter` 是买家列表页那排筛选条件的开关 —— 开着才出现，关了不出现，新增和编辑都能改，它不参与规格生成，也不影响价格与库存。

五类删除接口原来都是直接 `removeById`：被引用时数据库抛外键异常，前端只能弹兜底那句「数据处理失败，请稍后重试」。用户在那句话里既不知道删不掉什么，也不知道该先处理哪一样 —— 「类型还被 3 个属性和 8 个商品引用」和「网络抖了一下」长得完全一样。所以现在删之前先把引用数查出来，用中文说清（`CatalogDeleteGuard`）：类型回「该类型下还有 N 个属性 / M 个商品，不能删除（请先迁移或删除它们）」，属性回「该属性已被 N 个 SKU 使用，不能删除」，返回 null 才真删。理由很直接：类型、分类的「子分类、属性、商品」都是硬引用，删了存量商品就成了没归属的孤儿。

属性页把 typeId 钉死在路由里：`/product-type/:typeId/attributes`，进页面就用它查列表，新增时也把它写进请求体；弹窗里「所属类型」是禁用输入框，只显示不能改 —— 属性没有「不属于任何类型」这个状态。属性列表接口 `GET /admin/attributes?typeId=` 的 typeId 是可选参数，不传就返回全表，这不算接口的错（别处查属性值也要用），但页面必须每次都带上它，少带一次就会让「手机的属性页里出现食品的属性」，而串了之后没有任何地方会报错。改不动时明说：`PUT` 走影响行数校验，0 行 = 这行读完就被别人删了 → 409「记录已被删除」，类型与属性都没有 `version` 列，所以这里只认「行没了」这一种信号，不假装有版本锁。

**验证**　`商品类型与属性.spec.js`：4 条用例，真点界面 + 读库。类型新增与改名：新建后按名字回读库确认落库；改名后新名字在、旧名字不在。必填：空名点确定 → 本地提示「请输入类型名称」可见，且弹窗仍然可见（没被连带关掉）。属性聚合于类型：给 A 类型加两个属性（`is_filter` 一个 1 一个 0）→ 库里回读分别是 1 与 0、列表列显示「是」/「否」；改名同时关掉筛选 → 库里变 0；最后打开 B 类型的属性页，断言 A 的属性名字不出现。删除校验四条：种子「手机」类型（有属性也有商品）删不掉并回显「不能删除」；新建的空类型能删掉；被 SKU 规格值用过的属性删不掉；新建的空属性能删掉。

**边界**　「属性只属于当前类型」是靠页面每次带 typeId 撑住的，不是数据库强制：`attribute.type_id` 有值，但列表接口允许不带它，所以这条规则的证据是「B 类型属性页看不到 A 的属性」那条断言，而不是约束本身。被 SKU 用过的属性删不掉是刻意的：规格值是商品骨架的一部分，删了存量 SKU 就丢了那一维。类型改名不影响存量商品，商品只存 `type_id`。删除文案里的条数随演示数据漂移，正文一律写 N 与 M 占位，不写具体数。
