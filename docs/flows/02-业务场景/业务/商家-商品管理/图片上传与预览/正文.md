**上传不是「把文件丢给后端」，是一条链路加三道闸** —— 主图、相册、SKU 图三处走同一个上传组件、同一个接口、同一套限制：**超 5MB 不收、不是图片不收、地址必须是相对路径**。前两道拦的是「坏东西进来」，第三道拦的是「收进来的东西换台机器就找不到」。

## 场景

三处入口，一个实现（`admin-web/src/components/ImageUploader.vue`）：商品弹窗的「主图」、商品弹窗里「添加图片」逐行加的相册、SKU 弹窗里的「SKU 图片」。每处都是「一个地址输入框 + 一个上传按钮 + 下面一张预览」，传成功后地址自动回填进字段，旁边立刻出预览图。

后端是 `POST /admin/upload/image`，与商品提交完全解耦：图先落对象存储，商品保不保存是后面的事。同一个类里还挂着 `POST /admin/upload/image-from-url`，那是给 AI 补商品图用的 —— 模型产不出 5MB 的 base64，也不该把服务器本地路径当上传通道，所以由后端自己按 URL 去拉（SSRF 防护全在 `MinioStorageService#fetchFromUrl`，含「只许 https / 禁内网 / 禁重定向」）。两条入口的落地规则（bucket、`products/年/月` 归档、返回结构）完全一致。

## 撑不住的时候

**早拦比晚拦好。** 一个 8MB 的文件传完再被拒，用户白等半分钟、白占一次带宽，而且他会再试一次 —— 于是再烧一遍。所以类型与大小两道闸在**前端 `beforeUpload` 就先挡一次**，后端再挡一次：前端挡是为了体验（立刻提示、不发起请求），后端挡是因为前端可以绕过（直接打接口、换个客户端）。

**相对路径这道闸没有提示、但更贵。** 上传成功后返回的地址是 `/qiqi-mall/products/2026/11/<uuid>.png` 这种相对路径，写进库、写进 `pic` / `product_gallery.url` / `sku.pic` 的也是它。如果哪一步把对象存储的内网绝对地址落进库，那么换一套环境、换一个域名，整站的商品图会集体 404 —— 而库里那些字段没有任何地方会报错，只有人眼能发现。

## 改了什么

① **前端先挡**：`beforeUpload` 判 `file.type ∈ {image/jpeg, image/png, image/webp}`、`file.size > 5*1024*1024`，任一不满足就 `return false`，提示分别是「仅支持 jpg / png / webp」「图片不能超过 5MB」；`accept` 属性同步写死这三种。

② **后端再挡，且给的是真 HTTP 状态码**（不是一律 200 + code=1）：
- 文件为空 → 400「请选择要上传的图片」
- 超限（`MinioStorageService.MAX_SIZE = 5 * 1024 * 1024`）→ **413**「图片不能超过 5MB」
- 类型不在白名单（`image/jpeg` / `image/png` / `image/webp`）→ **415**「仅支持 jpg / png / webp」
- 未登录 → **401**（接口在 `/admin/**` 下，走 JWT 过滤器）

③ **落地路径固定、且重写文件名**：objectKey 是 `products/<yyyy>/<MM>/<uuid>.<ext>`，写入键再拼上对象前缀；dev/test 的前缀是 `qiqi-mall/`，所以返回与入库的地址是 `/qiqi-mall/products/…` 这种相对路径。历史图也在这个前缀下，老数据不用改。原名可能是中文、可能带路径、可能重名，UUID 才是唯一可信的键。

④ **传完立刻看得见**：返回体是 `{url, objectName}`，前端把 `url` 回填进字段并渲染 72×72 的预览。传错了当场能看出来，不用等保存再回前台翻。预览真不真，看的是图片能不能解码（`naturalWidth > 0`），不是 input 里有没有字符串。

⑤ **相册的排序号决定买家看到的顺序**：每行一个 `sort`，保存时整组按 `sort, id` 升序落库与返回 —— spec 特意把 3 张图的排序改成 3 / 2 / 1，验证顺序来自 `sort` 而不是添加先后。

⑥ **缺图有兜底**：C 端详情页主图取值优先级是「用户点的缩略图 → 当前规格图 → 商品主图」；切规格时还会把缩略图选中态对齐到当前规格图（规格图不在相册里就清空选中）。所以某个规格没配图时会自然落回商品主图，不会白一块。

## 凭什么证明好了

`e2e/tests/scenarios/业务/商家-商品管理/图片上传与预览.spec.js`，4 条用例：

- **主图全链路**：点「上传」→ 系统文件选择框（用 `filechooser` 事件接管，跟真人路径一致）→ 选文件 → 预览图 `naturalWidth > 0` → 表单字段带回的地址匹配 `^/qiqi-mall/` → 保存 → 库里 `pic` 就是那个地址 → 这个地址 `GET` 回来是 200 且 `content-type` 含 `image/` → C 端详情页用的就是它。
- **三道边界一次跑完**：未登录上传 → **401**；非图片（`text/plain`）→ **415** 且 message 含 `jpg`；5.5MB → **真 413** 且 message 含 `5MB`；最后再传一张正常小图 → **200** 且 `data.url` 匹配 `^/qiqi-mall/`（反向确认，避免上面几条因为别的故障「恰好」通过）。
- **相册多图排序**：加 3 张、排序改成 3 / 2 / 1 → 库里 `gallery` 的 `sort` 是 `[1,2,3]`，而 `sort=1` 对应的是**最后添加**那张；C 端相册 `src` 顺序与库里完全一致，且每张都真加载。
- **SKU 图与回退**：后台 SKU 列表缩略图真渲染；C 端切到配了图的规格 → 主图正是那张 SKU 图；切到没配图的规格 → 回退成商品主图。

## 附：口径与边界

- **「超 5MB 能打到后端」是有前提的**：multipart 上限 5MB、nginx 上限 6m，所以 5.5MB 的请求能穿过网关进到 Controller 才拿到 413。再大就会被网关自己挡掉，那时看到的不是这套文案。
- **上传不校验商品是否已保存**：图先落对象存储，商品可能最后没保存（取消弹窗），于是存储里会留下没人引用的对象。现状如此，没有清理任务。
- **没有压缩、没有缩略图、没有格式转换**：传什么存什么，C 端直接用原图。所以 5MB 的图上首页也会是 5MB。
- **SKU 图回退不是「合并」**：只在「这个 SKU 没 `pic`」时用商品主图顶上，不会把 SKU 图和商品主图拼起来；而「用户点了缩略图」能盖过规格图，是相册（SPU 级）该有的优先级，不是回退。
- **本页数字出处**：`5MB` 来自 `MinioStorageService.MAX_SIZE`；白名单三个 content-type 与扩展名映射来自同类的 `ALLOWED`；三种状态码与文案来自 `AdminUploadController#uploadImage`；相对路径前缀来自 `MinioStorageService` 的 objectKeyPrefix 说明（dev 前缀为空、test 为 `qiqi-mall/`）；72×72 预览尺寸读自 `ImageUploader.vue` 的样式；主图优先级链读自 `portal-web/src/views/product/detail.vue` 的 `coverPic`。
