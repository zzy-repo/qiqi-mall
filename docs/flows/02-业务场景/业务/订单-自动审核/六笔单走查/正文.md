## 六笔单走查（six-case walkthrough）

同一套演示策略跑六笔待审核单，每笔都能读出「事实 → 判定 → 结论 → 原因」，判定那一行必须点名是哪条策略、哪条条件、什么实际值。

QT-1001：淘宝、应收 268.00、1 个 SKU 乘 2 件、毛利 62 —— 「淘宝-标准单」三条条件全满足，`AUTO_PASS`，7 推到 8 待发货。
QT-1002：淘宝、应收 268.00、客服备注含「改」—— 「淘宝-标准单」满足，但被全局排除挡下，`MANUAL`，状态仍 7。
QT-1003：抖音、应收 1580.00、8 件、1 个种类 —— 「抖音-标准单」差在应收上限（1580 不小于 500），`NO_MATCH`，状态仍 7。
QT-1004：直营门店、应收 199.00、毛利 −12.00 —— 阻止策略「毛利不为正」命中（第 3 段，先于自动），`BLOCKED`，状态仍 7，同时回填「本会命中直营-小单」。
QT-1005：淘宝、应收 320.00、有待处理退款申请 —— 异常策略「退款申请冻结」命中，第 1 轮 `FROZEN`；处理申请并解冻后第 2 轮 `AUTO_PASS`（淘宝-标准单，7 推到 8）。
QT-1006：淘宝、应收 420.00、6 个种类 6 件 —— 「淘宝-标准单」差在种类数（6 大于 5），`NO_MATCH`；人工审核时才查出缺货，最终落到 4 已关闭。

这六笔暴露一处缝：不命中的单从来不做「会改结论」的库存预检。库存预检只给准过审的单做，不够就降级成 `MANUAL` 并打「库存不足」标；对 `NO_MATCH` 的单，引擎只把缺货写进证据、不改结论 —— 改了会让五类计数对不平，还会给一张连策略都没命中的单打上业务标。QT-1006 就是现场：它因种类数不命中一路留到人工，光看 `sku.stock` 看不出问题，直到审核那步才发现缺货。

还有三条：判定行不能写「系统觉得该人工」，QT-1002 的首句是「「淘宝-标准单」条件满足但被排除」，与「没命中」指向不同处置；「差在哪」只列真不满足的条件，QT-1003 的种类数 1 不大于 5、属于满足，灰字原因里一句都不该出现「商品种类数」；结论变了历史行不改，QT-1005 两轮两行都在、状态台账只有 1 行。

**验证**　两条走查 spec 加三条判定链 spec。走查一用 QT-1005 当样本（唯一三段都非空的单）：第 1 轮冻结写 `AUDIT_FREEZE`、人工解冻写 `AUDIT_UNFREEZE`、第 2 轮过审写台账，三段按时间拼成一条，且第 2 轮决策与 7 到 8 的台账行强对齐（`order_status_seq` 与 `ref_type=AUDIT_RUN`、`ref_id=run_id` 同时成立）；顺带一个边界 —— 纯自动过审的单第三段是空的，因为 run 级审计的 `order_id` 为 NULL。走查二防回归：连点两次执行 → QT-1001 只有 1 条决策、1 行台账、状态只推进一次；改优先级后旧决策的 `policy_version_no` 不变、版本快照条数不变。六笔结局由判定链 spec 逐笔钉住（1001 与 1002 一条、1004 与 1005 一条、1003 与 1006 一条）。

**边界**　重复执行是真 run，`MANUAL` 刻意不做 run 级幂等，第二次的差异本身就是证据；已过审的单不在候选范围，所以不会有第二条决策。改配置不改写历史：上移下移之后历史决策行的 `matched_policy_version_no` 一个字都不变，而换位本身不产生版本快照。这六笔的数值来自 `sql/seed-order-audit-demo.sql`，spec 幂等补齐，金额与件数随种子变。
