**策略页不是一张表单，是"先问哪句话"的编辑器** —— 三条自动 + 两条阻止 + 两条异常 + 一条全局排除，同一张单判出不同结论，靠的就是这个顺序。而顺序里最会骗人的是那个数字：**优先级只在同类型内比较，跨类型固定 阻止 > 异常 > 自动**。

## 场景

运营在后台点「新建策略」「上移一位」的时候，改的其实是判定链的执行顺序。页面 `admin-web/src/views/audit-policy/index.vue`：三类策略各一个页签（标签上带条数），一行上是 优先级 / 名称 / 启用开关 / 版本号 / 条件摘要 / 动作，行尾是 上移 / 下移 / 编辑 / 删除；条件编辑器是"字段 + 操作符 + 值"三联；自动页签下面还有一张「全局排除」卡，它对所有自动策略生效。

两个刻意的设计：字段清单**不在前端写死**，来自后端 FieldRegistry（策略接口的 fields / operators），取不到就顶一条红条、不让配 —— 否则能配出"永远命不中"的条件；操作符按字段值类型过滤（数值才有小于/大于，文本才有含/不含，布尔只有等于/不等于），值控件跟着类型换（数字框 / 下拉 / 文本框），"存在/不存在"这类操作符干脆不要值。

## 撑不住的时候

这一节是这个页面存在的理由：**优先级是个会骗人的数字**。

引擎里写死的只有一处：跨类型的执行顺序是 阻止 → 异常 → 自动，与 priority 数字无关；priority 只在同类型内比较。这条不写到脸上会怎样：运营把「退款申请冻结」的优先级调成 5（比所有阻止策略都小），就会以为它会先赢 —— 实际判定链第 3 段整段跑完才轮到第 4 段，它连判都轮不上。

这件事不靠嘴说，靠矩阵用例（`qiqi-mall-server/src/test/java/com/qiqi/mall/audit/AuditVerdictMatrixTest.java`，每一行钉死 result / 命中策略 / 降级原因 / 是否推进状态 / 本来会命中的那条）：

| 用例 | 现场 | 结论 |
| --- | --- | --- |
| M21 | 阻止-双地址（优先级 20）与 异常-退款申请（优先级 10）同时命中 | 阻止命中 —— **数字更小的那条没有先判**，跨类型只认类型顺序 |
| M15 | 两条自动同时命中（直营-小单 100 / 淘宝-标准单 200） | 取数字小的「直营-小单」 |
| M16 | 同 M15，但「直营-小单」被停用 | 次优的「淘宝-标准单」接上 |
| M17 / M18 | 两条异常 / 两条阻止同时命中 | 同类型内按优先级升序，命中哪条必须一眼看出 |

## 改了什么

① **把作用域写在页面上**：页签下面常驻一行"优先级只在**同类型**策略之间比较；跨类型的判定顺序固定为：阻止 → 异常 → 自动"（`data-testid=policy-priority-scope-note`）。这一行不是装饰，它挡掉的就是上面那个误读。

② **上移/下移只在同类型内换位**：后端 `AuditPolicyService#move` 只找**同 type** 的相邻策略交换 priority（两值相同就把当前这条挪到邻居外侧）；跨类型没有换位入口 —— 一个自动策略的 priority 再小也排不到阻止前面，给它留个"上移过去"的按钮只会教人误解。换位**不产生版本快照**：版本号只在条件改动时 +1，历史决策行记的是"当时按第几版判的"。

改优先级其实有两条路，语义不同：**行内上移/下移**只换位、不动 `version_no`；**弹窗里改数字再保存**走的是"整条策略覆盖"，版本号会 +1（`PUT` 是整体覆盖 + 版本递增）。两条路都能把顺序改掉，但只有第一条不会被当成"条件改了一版"。

③ **条件编辑器只管形状，语义交给后端**：字段 / 操作符 / 值三件套的合法组合由字段注册表的 allowedOps 决定，前端只负责别让人选出"这个字段不允许的操作符"。

④ **全局排除单列一块**：它是 scope=ALL_AUTO、policy_id 为 NULL 的条件集合（"客服备注含改"就是这个），判定时每条自动策略都会并进来。编辑入口在任意一条自动策略的弹窗里，保存语义是**整套替换**（传 null 表示不动、传数组表示全量覆盖），所以它不归属任何一条策略。

## 凭什么证明好了

**① 能演的：UI 测试 + 录屏（本轮录屏待补，已登记「待补视频」，不是"无界面"）**

`e2e/tests/scenarios/业务/订单-自动审核/审核策略与优先级.spec.js`，两条用例，全程真点界面、真读库：

- **用例 1「同级内：换位就换结论」**：库里把 QT-1004 的双地址标记置 1（这个字段后台**没有写入口**，只有平台同步能置，见「附」），两条阻止策略同时命中 → 第 1 轮决策命中「毛利不为正」（优先级 10）；在策略页把「双地址」**上移一位**（库里 priority 实测 10↔20 换位）→ 第 2 轮决策命中「双地址」。页面上的顺序一动，判定结果跟着变。
- **用例 2「跨类型：数字大也先赢」**：在阻止页签里把「毛利不为正」的优先级从 10 改成 **5000**（比三条自动策略的 100/200/300 都大），保存后页面上它排到「双地址」之后；再跑一轮 → 结论仍是**阻止命中**，不是自动过审，且决策里"本来会过审的那条"仍是「直营-小单」。**优先级数字大不妨碍它整段先跑**。

两条用例都在 finally 里把优先级与双地址标记按原值写回（不依赖 UI 是否成功），所以连跑多轮不会污染后面的判定顺序。用例 1 只断"上移前后 `version_no` 不变"（用原值比、不硬编码 1），用例 2 只断"弹窗保存后**快照条数 +1**"（同样只断增量）—— 因为库随时可能被别的用例改过，把 1 写死就是在测别人的残留。

```
  "tests/scenarios/业务/订单-自动审核/审核策略与优先级.spec.js" --no-reset
```

**② 不能演的：矩阵 21 行的引擎级证据**

M21 是这条口径的唯一直接证据：它把"异常那条的数字更小"和"实得阻止命中"放在同一行里，任何把类型顺序改成"全局按 priority 排序"的重构都会当场把它打红。

## 附：口径与边界

- **数字小 ≠ 先判**：跨类型只认类型顺序（阻止 > 异常 > 自动）；priority 只在同类型内比较。M21 钉的就是这一条。
- **停用不是删除**：enabled=false 的策略还在表里，历史决策仍能对上它，判定时跳过（M16）。
- **上移/下移不写版本快照**：版本号语义是"条件改了才有一版"，挪位置不算改条件。
- **双地址标记没有后台写入口**：`order.audit_addr_multi` 全仓只有实体字段与读取，没有任何写入路径 —— 后台只能看判定结果，造这个现场只能靠平台同步或直接写库。用例 1 的造数就落在这条边界上（造完写回 0）。
- **全局排除是"整套替换"**：保存时传 null = 不动，传数组 = 全量覆盖。它不是某条策略的附属条件，所以页面上它只有编辑入口、没有归属关系。
- **弹窗里的优先级输入框是个布局缺陷**：`:span="4"` 的列 + 96px 标签宽度把 `el-input-number` 挤到 39px，内层 `<input>` 实测 **0×22px** —— 鼠标点它的中心只会命中右侧那对加减箭头（实测点一下把 10 点成了 9），`fill()` 则因"元素不可见"必然超时。当前唯一能用的入口是**键盘**：点进「名称」→ Tab 一格落到优先级 → 覆盖输入。用例走的就是这条路（不注入 DOM、不改前端），缺陷本身记在交付说明里，不在这里"绕过并装作没看见"。
- **本页数字出处**：M15/M16/M17/M18/M21 来自 `AuditVerdictMatrixTest.java`；优先级 100/200/300 与 10/20 来自 `sql/seed-order-audit-demo.sql`；"上移一位 = 10↔20 换位"来自 `AuditPolicyService#move` 的实现（并已在用例里回读库验证）；"优先级输入框 39px / 内层 input 0×22px"是本次在 1280×900 视口的实测（浏览器量出来的 boundingBox）。
