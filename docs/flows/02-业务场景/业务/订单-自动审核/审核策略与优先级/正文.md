## 审核策略与优先级（audit policy / priority scope）

策略页不是一张表单，是「先问哪句话」的编辑器：三类策略各一个页签（标签带条数），一行上是优先级、名称、启用开关、版本号、条件摘要、动作，行尾是上移、下移、编辑、删除；条件编辑器是「字段 + 操作符 + 值」三联；自动页签下面还有一张「全局排除」卡，它对所有自动策略生效。运营点「上移一位」时，改的其实是判定链的执行顺序。

顺序里最会骗人的是那个数字：引擎里写死的只有一处 —— 跨类型的执行顺序是阻止 → 异常 → 自动，与 priority 数字无关；priority 只在同类型内比较。所以把「退款申请冻结」的优先级调成 5（比所有阻止策略都小）并不会让它先赢，判定链第 3 段整段跑完才轮到第 4 段。页签下面因此常驻一行说明（`policy-priority-scope-note`）：「优先级只在同类型策略之间比较；跨类型的判定顺序固定为：阻止 → 异常 → 自动」—— 这一行不是装饰，它挡掉的就是上面那个误读。

上移与下移只在同类型内换位：`AuditPolicyService#move` 只找同 type 的相邻策略交换 priority，跨类型没有换位入口 —— 给自动策略留一个「上移过去」的按钮只会教人误解。换位不产生版本快照，版本号只在条件改动时 +1，历史决策行记的是「当时按第几版判的」。改优先级其实有两条路，语义不同：行内上移下移只换位、不动 `version_no`；弹窗里改数字再保存走整条策略覆盖，版本号 +1。两条都能把顺序改掉，但只有第一条不会被当成「条件改了一版」。

条件编辑器只管形状，语义交给后端：字段清单不在前端写死，来自后端 `FieldRegistry`（策略接口的 fields 与 operators），取不到就顶一条红条、不让配 —— 否则能配出「永远命不中」的条件；操作符按字段值类型过滤（数值才有小于与大于，文本才有含与不含，布尔只有等于与不等于），值控件跟着类型换，「存在/不存在」这类操作符干脆不要值。全局排除单列一块：它是 `scope=ALL_AUTO`、`policy_id` 为 `NULL` 的条件集合，判定时每条自动策略都会并进来，所以它不归属任何一条策略，保存语义是整套替换（传 `null` 表示不动、传数组表示全量覆盖）。

**验证**　矩阵用例在服务端（`AuditVerdictMatrixTest`，每一行钉死 result、命中策略、降级原因、是否推进状态、本来会命中的那条）。M21：阻止-双地址（优先级 20）与异常-退款申请（优先级 10）同时命中 → 实得阻止命中，数字更小的那条没有先判，跨类型只认类型顺序。M15：两条自动同时命中（直营-小单 100 与淘宝-标准单 200）→ 取数字小的「直营-小单」。M16：同 M15 但「直营-小单」被停用 → 次优的「淘宝-标准单」接上。M17 与 M18：两条异常、两条阻止同时命中 → 同类型内按优先级升序，命中哪条必须一眼看出。界面侧另有两用例，真点界面、真读库，覆盖页签计数、上移下移只动同类型、弹窗改数字会推版本号。

**边界**　跨类型没有换位入口是设计而不是漏做：自动策略的 priority 再小也排不到阻止前面。两条改优先级的路径语义不同，混着说会得出错误结论 —— 「换了个位」不等于「条件改了一版」。全局排除不归属任何策略，它在自动策略弹窗里编辑、对所有自动策略生效，所以「某条策略被排除」与「全局排除成立」在证据里是两个字段。字段清单只能在运行时从后端取，接口挂了就禁用保存，绝不回落到一份前端写死的清单 —— 那样配出来的条件可能永远命不中。
