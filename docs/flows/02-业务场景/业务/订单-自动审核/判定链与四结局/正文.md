**九步固定，不能插队** —— 一笔待审核订单进来，先过状态和冻结两道闸，再按「阻止 → 异常 → 自动」三段判，最后才看库存。顺序不是风格问题：**每一段跑完之前，后面那段连判都轮不上**。

## 场景

入口在「订单自动审核」队列页的「立即审核一轮」。候选范围只有两种单：`status=7` 待审核，以及已被冻结的单（后者进来只为触发「跳过」这一支）。每单先装配一份上下文：店铺、渠道、应收、样数、毛利、库存可用量。

页面读的是**每单最新一轮**的决策行：徽标（自动过审 / 留人工 / 阻止 / 冻结 / 不命中）+ 原因首句（命中了哪条策略）+ 灰字（具体哪条条件、期望多少、实际多少）+ 第几轮。行里还能点开「差在哪」抽屉，逐条策略、逐条条件给出 satisfied / 未求值。

## 撑不住的时候

**① 顺序一旦能被数字改掉，「阻止」就成了摆设。** 引擎里写死的只有一处：跨类型固定 **阻止 → 异常 → 自动**，与 priority 数字无关；priority **只在同类型内**比较。这条不写清会怎样：运营把「退款申请冻结」的优先级调成 5（比所有阻止策略都小），就会以为它会先赢 —— 实际第 3 段整段跑完才轮到第 4 段，它连判都轮不上。矩阵用例 M21 钉的就是这一条（阻止-双地址优先级 20 与异常-退款申请优先级 10 同时命中 → 实得阻止命中）。

**② 结论必须归因到「第几步、哪条策略、哪条条件、什么实际值」。** 「转人工」三个字如果背后没有这些，运营接过来还得重算一遍 —— 那这套系统只是把活推给了人。

**③ 「未求值」不能混进「不满足」。** AND 链上首个不满足之后的条件，引擎**不再求值**（值照实给出，只是不再决定结论）。页面把它们画成「不满足」，就是在替引擎猜哪些条件比过了。

## 规矩落在哪

**九步判定链（顺序固定）**：

```
[1] 状态闸门   status ≠ 7                         → SKIPPED（不落决策行）
[2] 冻结闸门   有 active 冻结标                    → SKIPPED（不落决策行）
[3] 阻止策略   同类内 priority 升序，命中即停        → BLOCKED（原因带具体数值差）
      [3] 命中后仍继续跑 [5]，只看不执行 → 回填 would_be_auto_policy
           并对 [4] 整段做一次只读求值 → 写进 evidence.other_gates
[4] 异常策略   命中                              → FROZEN（打冻结标 + 写操作审计，状态仍 7）
[5] 自动策略   逐条：5a 条件没全满足 → 记 miss_reason（哪条、期望 vs 实际）
                     5b 排除条件（本策略级 ∪ 全部全局级）成立 → 记 excluded_by
                     5c 无排除 → AUTO_PASS
[6] 全都不中   若曾有策略「条件全满足、只被排除挡掉」→ MANUAL（被排除）
               否则 → NO_MATCH（逐条列出「差在哪」）
[7] 库存预检   只给准过审的单做：桶和 ≥ 需求？不够 → MANUAL + 降级原因 STOCK_SHORT
               （成本价缺失而毛利 ≤ 0 → MANUAL + COST_MISSING）
[8] 执行       只做结论允许的事：过审才改状态（7→8）、冻结才打标
[9] 落库       每单每轮一行决策；过审那笔同时在状态台账记一行，行上带本轮 run 号
```

**五种判定，各落一行决策行**：`AUTO_PASS` / `MANUAL` / `BLOCKED` / `FROZEN` / `NO_MATCH`。第六个枚举 `SKIPPED` **不写决策行** —— 它只累加 run 的 `skipped` 计数。为什么不留行：候选范围故意包含「已冻结」的单，冻结单每跑一轮就多一行「什么都没发生」的 SKIPPED，`round_no` 一直涨、证据表被无意义的行撑大，而「它为什么一直没人审」这件事 `order_audit_tag` 早就答了。

**硬约束（违反就整轮回滚）**：每条决策行恰好落在五类之一，所以 **五类之和 == 本轮决策行数**；而 `total == 五类之和 + skipped`。转人工有三支来路（被排除 / 库存不足 / 成本缺失），它们在 `result` 上**都是 MANUAL**，靠 `downgrade_reason` 区分 —— 给「库存不足」单独立一个枚举值，会让「留人工」的计数分散在两个值上，对外永远数不平。

**跨类型优先级是固定的**：`阻止 > 异常 > 自动`，与数字无关；`priority` 只在同类型内升序（相同再按 id 升序，保证同配置两次跑结果一致）。

**「留人工」和「不命中」不是一回事**：前者是「有策略条件全满足，但被排除挡下」（写 `excluded_by_json`），后者是「一条都没命中」（写 `miss_reason_json`，逐条策略给差值）。三列 JSON 形状一致（策略组 → 条件数组），页面才能用一套渲染。

`e2e/tests/scenarios/业务/订单-自动审核/` 下 3 条判定链 spec，对应 2 段录屏，各自钉一类结局：

- **自动过审与留人工**（QT-1001 / QT-1002，唯一自变量是客服备注）：QT-1001 → `AUTO_PASS`、命中「淘宝-标准单」、**7→8**、台账恰好 1 行且 `reason=AUDIT_AUTO_PASS`、`ref_type=AUDIT_RUN`、幂等键 `{orderId}:1`；QT-1002 → `MANUAL`、`matched_policy_name` 仍是「淘宝-标准单」（本来命中的是它）、**状态仍 7、台账 0 行、无标**。抽屉里：hint 行解释「留人工 = 条件满足但被排除」、恰好 2 条「差在哪」、0 条「未求值」、全局排除单独一块（「排除：客服备注 含 改」），且「去改这条策略」跳的是**第一条真不满足**的策略（带 `focusPolicy` 与 `focusSeq=0`）。
- **阻止与冻结**（QT-1004 / QT-1005）：QT-1004 → `BLOCKED`、命中「毛利不为正」、**状态仍 7、台账 0 行、无标**，`would_be` 回填「直营-小单」并带上策略 id 与条件留痕（应收门槛 300.00、实际 199.00）；QT-1005 第 1 轮 `FROZEN`（打 1 个 `FROZEN%` 标 + 写 `AUDIT_FREEZE` 审计，状态仍 7）→ 处理申请 + 页面解冻（标 `active=0` 但行留着当证据、写 `AUDIT_UNFREEZE`）→ 第 2 轮 `AUTO_PASS`，决策 `round 1→2`，台账只有 1 行 7→8 且 `ref_id` 指向**第 2 轮** run。

## 附：口径与边界

- **页名叫「四结局」指的是运营要分别处置的四类**（自动过审 / 留人工 / 阻止 / 冻结）；技术上还有第五类结论 `NO_MATCH`（一条策略都不命中）和第六个枚举 `SKIPPED`（没参与判定，不落行）。四类 + 不命中 = 五种会落决策行的结论。
- **跨类型只认类型顺序**：`priority` 是**同类型内**的比较键。M21 是这条的唯一直接证据（数字更小的异常策略没有先判）。
- **被拦 / 被冻的单仍会回填 `would_be`**：那是一次「只看不执行」的重跑，命中方式与真过审完全一样，但结果只写进决策行的回填列。`would_be_auto_policy_name` 接口有回显，**前端目前没有渲染它**（`mapQueueRow` 丢掉了这一列），所以「回显」只能在接口与库上证明 —— 这是已登记的前端缺口。
- **NO_MATCH 也查库存，但不改结论**：它把「缺货」写进证据，让下一个人不会在订单页看到 `sku.stock=999` 就点通过。这条**绝不能**复用「库存不足 → 降级 MANUAL」那个分支，否则「不命中」这一类会凭空少一笔，五类计数就对不平。
- **整轮一个事务**：一半单 7→8、另一半没动、run 行还写着 0 —— 这种「批量部分成功」在审核场景里是最糟的形态。要么整轮生效，要么整轮回滚。
- **本页数字出处**：九步顺序与 `[7b]` 的理由来自 `AuditEngine` 类注释；六种枚举与「SKIPPED 不落行」的原因来自 `AuditResult`；计数约束来自 `AuditExecutor` 与 `RunResultDto`；M21 来自 `AuditVerdictMatrixTest`；`AUDIT_AUTO_PASS` / `AUDIT_RUN` / 幂等键 `{orderId}:{status_seq}` 来自 spec 的库断言。
