## 判定链与四结局（audit chain / five verdicts）

九步固定，不能插队。一笔待审核订单进来先过状态与冻结两道校验，再按「阻止 → 异常 → 自动」三段判，最后才看库存 —— 每一段跑完之前，后面那段连判都轮不上。

九步的顺序：状态校验（`status != 7` 直接 `SKIPPED`）、冻结校验（有 active 冻结标也 `SKIPPED`）、阻止策略（同类内 priority 升序，命中即停，原因带数值差）、异常策略（命中即 `FROZEN`，打冻结标并写操作审计）、自动策略（逐条：没全满足记 `miss_reason`，被本策略级或全局排除挡掉记 `excluded_by`，无排除才 `AUTO_PASS`）、全都不中（曾有策略条件全满足却只被排除挡掉 → `MANUAL`，否则 `NO_MATCH`）、库存预检（只给准过审的单做，桶和不够 → `MANUAL` 加 `STOCK_SHORT`）、执行（只做结论允许的事）、落库（每单每轮一行决策，过审那笔同时在状态台账记一行）。

五种判定各落一行决策行：`AUTO_PASS`、`MANUAL`、`BLOCKED`、`FROZEN`、`NO_MATCH`。第六个枚举 `SKIPPED` 不写决策行，只累加 run 的 `skipped` 计数 —— 候选范围故意包含已冻结的单，若每个冻结单每轮都留一行「什么都没发生」，`round_no` 会一直涨、证据表被无意义的行撑大。由此得两条硬约束，违反就整轮回滚：每条决策行恰好落在五类之一，所以五类之和等于本轮决策行数；且 `total` 等于五类之和加 `skipped`。转人工有三支来路（被排除、库存不足、成本缺失），它们在 `result` 上都是 `MANUAL`，靠 `downgrade_reason` 区分 —— 给「库存不足」单独立一个枚举值会让「留人工」的计数分散在两个值上，对外永远数不平。

跨类型优先级固定为「阻止 > 异常 > 自动」，与 priority 数字无关；priority 只在同类型内升序，相同按 id，保证同配置两次跑结果一致。所以把「退款申请冻结」的优先级调成 5 并不会让它先赢 —— 第 3 段跑完才轮到第 4 段。另外，「未求值」不能混进「不满足」：AND 链上首个不满足之后的条件引擎不再求值，值照实给出、只是不再决定结论。

**验证**　`订单-自动审核` 下 3 条判定链 spec，对应 2 段录屏，各自钉一类结局；矩阵用例 M21 钉跨类型顺序：阻止-双地址（priority 20）与异常-退款申请（priority 10）同时命中 → 实得阻止命中，证明数字改不动段落顺序。计数自洽由机制单测钉住（`fiveVerdictBucketsAddUpAndStockShortIsManualDowngrade`）：五类计数之和与决策行数相等，且库存不足是降级为人工而不是「过审后失败」。决策行每单每轮一行、唯一键 `(order_id, round_no)`、`result` 是六值枚举、行上照抄本轮结束时的 `order_status_seq`。

**边界**　「留人工」与「不命中」不是一回事：前者是「有策略条件全满足但被排除挡下」（`excluded_by_json`），后者是「一条都没命中」（`miss_reason_json`，逐条给差值）；三列 JSON 形状一致，页面才能用一套渲染。`SKIPPED` 不写行的直接后果是「某轮跳过了几张单」只能从 run 的计数看，别去决策表里数。库存预检只对准过审的单做，所以「没库存」不会出现在阻止与异常两段的结论里。
