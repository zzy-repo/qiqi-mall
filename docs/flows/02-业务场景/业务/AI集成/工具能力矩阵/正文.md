**这一页不列清单，是划边界** —— 哪些事敢交给 AI 做，答案由三个问题决定：**会不会改数据**、**改之前能不能让人看清**、**会不会改变「谁能用 AI」**。三档的颜色不是形容词，是一条条能指到接口和 scope 的判据。

## 场景

读者是准备发一把 AI 密钥的人。他打开「令牌管理」页勾权限域的那一刻，实际在决定的是这张表的哪几行对 AI 开放。所以这一页的正确读法是：**先看档位，再看这一档要过哪道闸，最后看它落在哪个权限域上。**

三档的分界：

- **绿 · 只读**：AI 自己就能调，只看不改、不落库。
- **黄 · 写**：必须先预演（只算不落库，把「将要发生什么」讲清）、人在界面上点头、再过一道闸门才执行。
- **红 · 红线**：根本不给 AI，只能人工。

## 能力矩阵与权限域

**绿档（只读）** —— 订单查询、发货单查询、商品与规格查询、分类/类型/属性查询、库存可用量与数据概览、七类台账、审核轨迹与队列、渠道店铺与同步日志。对应 `*:read` 系列 scope。

**黄档（写）** —— 能改的是这七类：

| 能改什么 | 走哪个域 | 闸门深浅 |
| --- | --- | --- |
| 商品与规格的修改（含价格、库存） | `catalog:write` | 有版本号 |
| 商品 / 分类 / 类型 / 属性 / SKU 的增删、图片上传 | `catalog:write` | 无版本号（按影响行数 + 引用守卫） |
| 订单审核（通过 / 不通过）、订单发货、删单 | `order:write` | 有版本号 |
| 发货单：改仓改量、拆分、合并、删除 | `order:write` | 有版本号 |
| 发货单：下发仓库、取消 | `order:write` | **无**版本号（看状态 + 影响行数） |
| 退货审核、代客登记退货申请 | `order:write` | 无版本号（申请行「待处理」写进 WHERE） |
| 仓库、订单设置、退货原因字典 | `config:write` | 无版本号 |
| 会员资料、地址、购物车 | `member:write` | 资料有版本号；地址与购物车没有 |

**闸门只有两种深浅，判据是「这份数据本身有没有版本号」**：

- **有版本号的写**（商品、SKU、会员资料、订单、发货单的改仓改量/拆分/合并/删除）：你确认之后数据又被别人改过 → **直接拒（409）**，一个字段都不写。
- **没有版本号的写**（下发、取消、退货审核、退货原因、仓库、订单设置、会员地址、购物车、分类/类型/属性）：先看**状态对不对**，再拿「到底改到了几行」复核 —— **改到 0 行就说明这条记录已被别人删掉或改过**，同样拒（409）。

**红档（两条红线，任何状态下都成立）** —— `GET /admin/api-keys` 与 `/admin/admins` 对任何 API Key 一律 403。理由不是「敏感」，是**闭环**：能建管理员就等于能给自己发任何权限；能改自己的密钥就等于没有授权体系。配套的实现细节：这两条红线在**密钥有效性判定之前**就拦，所以拿一把**已经删掉**的 key 去读，拿到的仍是 403 而不是 401。

**权限域到底有几个 —— 13 个可授予 + 5 个不可授予，页面上的目录由后端接口现算**：`AiApiKeyService.ALL_SCOPES` 里是 **13 个**（上表 9 个 + `ledger:read` / `stock:read` / `audit:read` / `channel:read`），「令牌管理」页把它们**全部**渲染成勾选框（9 个只读一档 + 4 个可写一档）；另有 5 个刻意不授予的写 scope（`ledger:write` / `stock:write` / `audit:write` / `channel:write` / `payment:write`）渲染成**置灰、勾不上**，并在页面上写明为什么。所以「给 AI 只读台账 / 库存 / 审核 / 渠道」现在是页面上点两下的事，不必再走接口写库。

**这份目录不是前端抄的一份，是运行时读后端**：页面加载时调 `GET /admin/api-keys/scopes`（`ApiKeyAdminController#scopes`），该接口直接读 `ALL_SCOPES` 与 `ApiKeyAuthFilter.unGrantableWriteScopes()`，自身不存任何 scope 清单 —— 后端加一个 scope，页面当天就多一个勾选框，没有第二处需要同步。接口拉不到时页面**直接报错并禁用保存**，绝不回落到一份前端写死的清单：2026-11-13 给 MCP 补那四个只读域时，正是「前端抄了一本、后端加了值、抄本走散」导致页面上勾不到，整整一天只能由接口直接写入。

**另有一批 scope 刻意不存在**：`audit:write` / `stock:write` / `ledger:write` / `channel:write` / `payment:write` 都不在 `ALL_SCOPES` 里（这 5 个在页面上都按「不可授予」置灰展示，勾不上）。原因写在代码注释里 —— 过滤器只能按路径前缀匹配，而 `/admin/order-audit/**` 下同时有读和写，若整段登记成 `audit:read`，一把只读 key 发 POST 也会通过，那就等于「AI 能触发审核、能解冻订单」。让那个写 scope 根本不存在，比让过滤器按方法区分更省事，也更难被改坏。

## 凭什么证明好了

这一页是**数据类页面**：它本身没有专属界面，也没有录屏，验收方式是**逐行对得上代码与实测响应码**，不借邻居场景的视频。构建清单把它登记为「无界面场景」，视频不适用。

能对上的是这些（每条都能自己重跑一遍）：

- **权限域数量与红线**：`AiApiKeyService.ALL_SCOPES` 的 13 项、`ApiKeyAuthFilter` 的路径前缀 → scope 映射表、以及 `/admin/api-keys` 与 `/admin/admins` 的 403 分支（含「红线先于密钥有效性」这一句）。
- **红线 403 的实测**：`业务/AI集成/令牌管理.spec.js` 第 ⑧ 步用一把**仍然有效**的密钥去读 `/admin/api-keys` 与 `/admin/admins`，断言都是 403 且 message 分别含「禁止访问」与「管理员账号」；第 ⑦ 步把 key 删掉后再读一次，仍是 403 —— 这条实测把「红线在 key 校验之前」这个实现细节钉住了。
- **黄档「有版本号 / 无版本号」两种闸门的实测**：`带版本号的写` 的 409 由「发货单调整」和「审核策略与优先级」两条 spec 直接打出来（真 HTTP 409 + 「数据已被他人修改」）；`无版本号的写` 的 409 由 `DeliveryEditService` / `ReturnApplyController` 的影响行数闸门给出。
- **文档本身的量级**：`mcp-server/README.md` 的工具清单按域列出每个工具是读还是写、要不要 `version`、支不支持 `dryRun` —— 这张矩阵就是从那份清单 + 过滤器规则反推的，不是凭印象画的。

本轮只写文档，**没有重跑任何 spec，也没有重跑 mcp-server 套件**；上面的响应码与文案以 spec 与源码为准。

## 附：口径与边界

- **本页没有「撑不住的时候」这一节**：它是数据类页 —— 内容的形态是「档位 + 判据 + 域」，不是「遇到过什么坑、怎么改的」。硬套痛点叙事会把它写成故事，反而丢掉可核对的判据。
- **「黄档」不等于「AI 能随便写」**：三道加工（预演 → 人点头 → 闸门）缺一不可，而且这三道里有两道是后端强制的（业务守卫 + 版本号/影响行数），只有「人点头」靠 AI 客户端的自觉（`instructions` 里写着「先预演并把后果念给用户、拿到明确同意再执行」）。**这是一个诚实的软边界**：后端拦得住重复与冲突，拦不住「AI 没问人就调了」。
- **红线的判据是路径，不是语义**：新增一条 `/admin/xxx` 下的接口而忘了在 `ApiKeyAuthFilter` 里登记规则，它的默认行为才是关键 —— 这一点见该类的 `Rule` 表与默认分支，改动时容易漏。
- **本页数字出处**：13 个可授予 scope 与 5 个不可授予的写 scope 都来自 `GET /admin/api-keys/scopes`（`ApiKeyAdminController#scopes`：可授予部分原样取 `AiApiKeyService.ALL_SCOPES`，不可授予部分原样取 `ApiKeyAuthFilter.unGrantableWriteScopes()`，接口自身不存目录）；页面上的分组、项数与中文标签也由这次响应驱动（标签按「域-动作」拼，前端没有 scope 清单，见 `admin-web/src/views/api-key/scopeCatalog.js`）；403 文案两条来自 `ApiKeyAuthFilter`。
