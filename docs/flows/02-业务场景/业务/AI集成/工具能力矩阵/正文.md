## 工具能力矩阵（tool tiers / scopes）

这一页不列清单，是划边界。哪些事敢交给 AI 做，答案由三个问题决定：会不会改数据、改之前能不能让人看清、会不会改变「谁能用 AI」。三档由此分出来：绿档只读，AI 自己就能调、不落库；黄档写，必须先预演（只算不落库）、人在界面上点头、再过一道校验才执行；红档根本不给，只能人工。

校验只有两种深浅，判据是「这份数据本身有没有版本号」，不是「这操作危不危险」。有版本号的写（商品、SKU、会员资料、订单、发货单的改仓改量/拆分/合并/删除）：人确认之后数据又被别人改过，直接 409、一个字段都不写。没有版本号的写（下发、取消、退货审核、退货原因、仓库、订单设置、会员地址与购物车、分类/类型/属性）：先看状态对不对，再拿「到底改到了几行」复核 —— 改到 0 行说明这条记录已被别人删掉或改过，同样 409。

红线只有两条，任何状态下都成立：`GET /admin/api-keys` 与 `/admin/admins` 对任何 API Key 一律 403。理由不是「敏感」，是闭环 —— 能建管理员就等于能给自己发任何权限，能改自己的密钥就等于没有授权体系。配套的细节是这两条判在密钥有效性之前，所以拿一把已经删掉的 key 去读，拿到的是 403 而不是 401。

权限域的账目是 13 个可授予（9 个只读加 4 个可写）加 5 个刻意不授予的写 scope（`ledger:write` / `stock:write` / `audit:write` / `channel:write` / `payment:write`），页面把那 5 个渲染成置灰、勾不上，并写明为什么。这份目录不是前端抄的一份，是运行时读后端：页面加载时调 `GET /admin/api-keys/scopes`，该接口直接读 `ALL_SCOPES` 与 `ApiKeyAuthFilter.unGrantableWriteScopes()`，自身不存任何清单 —— 后端加一个 scope，页面当天就多一个勾选框；接口拉不到时页面直接报错并禁用保存，绝不回落到前端写死的清单。

**验证**　这一页的形态是判据页，不是操作页，证据分三层。其一，页面上的 scope 目录来自 `GET /admin/api-keys/scopes` 这一个接口，`ApiKeyAdminController#scopes` 只读 `ALL_SCOPES` 与不可授予集合，没有第二处需要同步的清单 —— 2026-11-13 给 MCP 补四个只读域时就吃过这个亏：前端抄了一本、后端加了值、抄本走散，页面上勾不到，整整一天只能由接口直接写入。其二，`scripts/mcp-coverage.mjs` 维护「工具 → scope → 路径」的账目，与 `ApiKeyAuthFilter` 的前缀规则互为印证，改一处而不改另一处会被这个脚本点出来。其三，两条红线的可执行证据在令牌管理那条用例里：删掉的 key 去读密钥管理拿到的是 403 而不是 401，说明红线判在密钥有效性之前。

**边界**　一个 scope 覆盖的是一组能力而不是一个动作：`order:write` 同时管审核、发货、删单、退货审核与代客登记退货申请，所以「给他订单写权限」等于给了一整组。校验深浅由数据有没有 `version` 决定，不由主观判断，想给某类写操作加锁就得先给那份数据加版本列。红线只针对 API Key：管理员用页面 JWT 照常能管密钥与管理员，别把 403 读成「功能被关掉了」。不可授予的 5 个写 scope 是有意留白，不是待补，页面置灰就是它的最终形态。
