**三句话：只读随便问、写之前先预演、写完必回读** —— 用户说人话（「把待审核的订单列出来」），AI 挑工具，走 MCP 打到中台。整条链按「会不会改数据」分三档，而每一档的松紧不一样。

## 场景

MCP 服务是 stdio 的最小闭环（`mcp-server/`），把后台「订单审核 + 拆单」暴露成一组工具，给任意 MCP 客户端调。**后端一行没改** —— 它就是个纯粹的 REST 客户端，认证用 API Key。

```
① list_pending_orders()      列出待审核订单（只读）
② preview_split(orderId)     拆单方案（dry-run 不落库）→ { willDo, plan }
③ execute_audit_pass(orderId) 订单 7→8 并真的生成发货单（写）
④ list_deliveries(orderId)   回读，确认包裹数与方案一致
```

## 撑不住的时候

**AI 直接落库的风险不是「它会不会算错」，是「人没看见就生效了」。** 一次审核通过会 7→8 并生成发货单，紧接着仓库就拣货；预演这一步存在的意义是把「将拆成 2 个包裹、一个从深圳仓发、一个从杭州仓发」先摆到人眼前。少这一步，AI 的每一次判断都是静默生效的。

第二个风险是**并发**：AI 预演时看到的是一张待审核单，人在这期间点了「审核通过」，AI 再执行就该被拒 —— 否则同一张单会被审两次、生成两批包裹。

## 规矩落在哪

① **第一档 · 只读**：`list_orders` / `list_pending_orders` / `get_order_detail` / `list_deliveries` / `count_deliveries` / `preview_split` 等，随便查、不落库。`preview_split` 走的是 `POST /admin/orders/{id}/split-preview`（等价 `?dryRun=true`），返回 `{willDo, plan}`，**预演本身不写任何数据**。

② **第二档 · 写要先预演**：`execute_audit_pass` 的入参只有一个 `{orderId}` —— 没有确认码、没有票据。它的安全边界不靠「AI 手里握着什么」，靠两件后端事实：**业务状态守卫**（只有 `status=7` 能审核，重复执行会被拒「只有待审核订单可以审核通过」）+ **版本号乐观锁**（预演只回答「会做什么」，写操作靠 `version` fail-closed：缺 → 400，被抢改 → 409）。

③ **第三档 · 写完回读**：`list_deliveries(orderId)` 把落地结果读回来，和预演里的方案对齐（包裹数、各从哪个仓发）。「AI 说做完了」不算证据，回读出来的包裹才算。

④ **权限同源**：AI 走后台**同一套接口、同一把锁**。过滤器 `ApiKeyAuthFilter` 按「路径前缀 → scope」判权，`ALL_SCOPES` 里没有的写 scope（`audit:write` / `stock:write` / `ledger:write` / `channel:write`）**任何 key 都拿不到**，所以那类写操作对 API Key 天然 fail-closed，人工 JWT 完全不受影响。人能做的它才能做，人不能做的它也做不了。

⑤ **写开关是环境变量**：`MCP_ENABLE_WRITE=1` 才注册写工具，否则只有只读那批。启动日志会打 `write=on|off`。

⑥ **AI 和人在同一把锁下**：AI 会撞到的 409，人也会撞到；这不是给 AI 开的后门，是同一个接口的同一套并发控制。

## 凭什么证明好了

**这一页目前没有 UI 级用例、也没有录屏** —— 构建清单里它登记在「待补视频」，原因是 MCP 的可视入口是 Inspector（`scripts/start-inspector.sh`），属「能演未演」，不是「无界面」。

现在的证据是 `mcp-server/test/` 的套件，其中闭环那条（`loop.mjs`）用 SDK client **通过 stdio 真启动** `src/index.mjs`，逐条断言 11 步；数据自给自足（自己造一笔待审核订单，跑完自己删），不依赖 reset 库。它钉的是这几件事：预演返回 `willDo` + 方案、执行成功后包裹数增加、**重复执行被业务守卫拦**、回读与方案一致。并发的 `version` 那一套单独在 `test/optimistic-lock.mjs` 里验。

构建清单里给这个套件登记的量级是「195 条断言（两轮全绿）」—— **本轮只写文档，没有重跑这个套件**，把它当量级看，别当成本轮实测。

## 附：口径与边界

- **没有「一次性确认码」这一层**：早期版本有 `confirmCode` / `expiresInSec`，现在整套删了。并发保护的责任边界改成了「后端业务守卫 + 热表 version 乐观锁」。所以现在能证明的是「重复执行会被拒」，不是「AI 手里必须握着一张票」。
- **`execute_audit_pass` 与 `audit_reject_order` / `ship_order` / `delete_order` 的差别**：后三个支持 `?dryRun=true`，前者的预演是另一个工具（`preview_split`）。所以「先预演」在两处的实现方式不同，别混着说。
- **`create_order` 的总额由后端重算**（明细单价 × 数量），传进去的金额不算数；新建 `version=0`。
- **`update_order` 改不了状态**：`status` 被后端强制忽略，状态只能走审核 / 发货接口。
- **`delete_order` 不可恢复**，会级联删明细 / 发货单 / 物流 —— 与后台删单走同一套守卫。
- **本页数字出处**：三档与工具清单来自 `mcp-server/README.md` 与 `src/index.mjs` 的 instructions；`preview_split` 返回结构、`execute_audit_pass` 入参、重复执行的拒因来自 `README.md` 的闭环段与 `loop.mjs` 文件头；`ALL_SCOPES` 与「不可授予的写 scope」来自 `AiApiKeyService` 与 `ApiKeyAuthFilter`；「195 条断言」来自构建清单里这条场景的登记文案（本轮未复跑）。
