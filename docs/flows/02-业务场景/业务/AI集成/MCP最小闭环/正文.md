## MCP 最小闭环（stdio MCP / audit pass）

三句话：只读随便问、写之前先预演、写完必回读。MCP 服务是 stdio 的最小闭环（`mcp-server/`），把后台「订单审核 + 拆单」暴露成一组工具，给任意 MCP 客户端调；后端一行没改，它就是个纯 REST 客户端，认证用 API Key。四步是这个形状：`list_pending_orders` 列待审核订单（只读）→ `preview_split` 拿方案（dry-run，回 `{willDo, plan}`）→ `execute_audit_pass` 把订单 7 推到 8 并真的生成发货单 → `list_deliveries` 回读、确认包裹数与方案一致。

整条链按「会不会改数据」分三档，松紧不同。只读那批随便查、不落库，`preview_split` 走 `POST /admin/orders/{id}/split-preview`（等价 `?dryRun=true`）写要先预演：`execute_audit_pass` 的入参只有一个 `{orderId}`，没有确认码、没有票据，它的安全边界不靠「AI 手里握着什么」，靠两件后端事实 —— 业务状态守卫（只有 `status=7` 能审，重复执行被拒「只有待审核订单可以审核通过」）加版本号乐观锁（预演只回答「会做什么」，写操作靠 `version` fail-closed：缺 → 400，被抢改 → 409）。写完回读：`list_deliveries` 把落地结果读回来与方案对齐 —— AI 说做完了不算证据，回读出来的包裹才算。

权限同源：AI 走的是后台同一套接口、同一把锁。`ApiKeyAuthFilter` 按「路径前缀 → scope」判权，`ALL_SCOPES` 里没有的写 scope（`audit:write` / `stock:write` / `ledger:write` / `channel:write`）任何 key 都拿不到，那类写操作对 API Key 天然 fail-closed。写工具也是开关：`MCP_ENABLE_WRITE=1` 才注册，否则只有只读那批，启动日志打 `write=on|off`。

**验证**　这一页目前没有 UI 级用例与录屏：构建清单登记在「待补视频」，可视入口是 Inspector（`scripts/start-inspector.sh`），属「能演未演」而不是「无界面」。现有证据是 `mcp-server/test/` 的套件：闭环那条 `loop.mjs` 用 SDK client 通过 stdio 真启动 `src/index.mjs`，逐条断言 11 步，数据自给自足（自己造一笔待审核订单、跑完自己删），不依赖 reset 库；它钉的是预演返回 `willDo` 与方案、执行成功后包裹数增加、重复执行被业务守卫拦住、回读结果与方案一致。并发的 `version` 那一套单独在 `test/optimistic-lock.mjs` 里验。构建清单给这套件登记的量级是「195 条断言、两轮全绿」，本轮没重跑，当量级看。

**边界**　没有「一次性确认码」这一层：早期版本有 `confirmCode` 与 `expiresInSec`，现在整套删了，并发保护的责任边界改成「后端业务守卫 + 热表 version 乐观锁」，所以能证明的是「重复执行会被拒」，不是「AI 手里必须握着一张票」。`execute_audit_pass` 与 `audit_reject_order` / `ship_order` / `delete_order` 的预演方式不同：后三个支持 `?dryRun=true`，前者的预演是另一个工具 `preview_split`，别混着说。
