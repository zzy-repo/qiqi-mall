## 令牌管理（API key lifecycle）

明文只发一次，权限按最小给，停和删立刻生效。新建令牌时那句「请立即复制保存」不是客气话：关掉弹窗之后，页面和接口里就只剩一个前缀，复制不到就只能重建一条。

创建要填名称、勾权限、设有效期：权限按域分读与写（订单、商品、会员、配置各有，概览只有读），有效期二选一是「永不过期」或精确到分秒，快捷 7 天按钮把值填成 `yyyy-MM-dd HH:mm:ss`。提交后返回明文，形如 `ak_` 加 64 位十六进制、共 67 字符，弹窗里可复制；关闭后弹窗 `destroy-on-close`，明文节点从 DOM 里消失。库里存的是哈希，接口从不回读明文，列表只给前缀 —— 前缀等于后端返回的 `keyPrefix`，长度远短于明文，也确实就是明文的前几位。权限落库是数组，改权限是整组覆盖，后端复核。

停用即失效、启用即恢复：行内开关改 `status 1↔0`，禁用后同一把 key 下一次调用立刻 401「API Key 无效或已过期」。删除不可恢复：确认框点名这把令牌，删完同一把 key 立即 401，列表里也搜不到。每次有效调用写回 `lastUsedAt`（同一 key 60 秒内只写一次，避免每次调用都写库），页面上那一列从「从未使用」变成时间。

两条硬性禁止约束：`/admin/api-keys` 与 `/admin/admins` 对任何 API Key 一律 403，而且判在密钥有效性之前 —— 一把已经删掉的 key 去读密钥管理，拿到的仍是 403 而不是 401。理由不是「敏感操作要小心」：一条能管理密钥的 key 等于能给自己勾上任何权限，一条能管管理员的 key 等于能凭空造一个管理员，这是授权体系的自毁开关，所以直接不给。

**验证**　`令牌管理.spec.js`：1 条用例把密钥从生到死走完，每一步都真点页面、真拿这把 key 去调接口（`X-Api-Key`，不带任何 JWT）。建令牌（勾「订单-读」与「商品-读」，故意不勾「商品-写」，设 7 天）→ 明文匹配 `^ak_[0-9a-f]{64}$`，复制到剪贴板的内容就是它 → 关闭后页面任何可见文本里都没有明文、明文节点 `count = 0`、列表只显示前缀且前缀等于服务端 `keyPrefix`。用这把 key 调 `GET /admin/orders` → 200，`lastUsedAt` 从此非空，刷新页面后那列不再是「从未使用」。同一把 key 去 `POST /admin/products`（商品-写没勾）→ 403 且 message 含 `catalog:write`。在页面上补勾「商品-写」→ 同一个请求 200 并真建出商品，随后用商品列表的行内删除加高危确认弹窗把它删掉还原。接着把停用、启用、删除与两条硬性禁止约束走完：禁用后同一把 key 返回 401，重新启用恢复 200，删除后立即 401，而删掉的 key 去读密钥管理仍是 403 而不是 401。

**边界**　明文只出现一次是设计而不是疏忽：库里存哈希、接口从不回读明文，换来「库被拖走也拿不到可用的钥匙」，代价是「人没复制就等于没拿到」，第一次用的人容易以为关掉弹窗还能再看见。有效期到点自动失效，不需要人工操作。`lastUsedAt` 同一把 key 60 秒内只写一次，所以那一列是近似时间，不是逐次精确。两条硬性禁止约束只针对 API Key：管理员用页面 JWT 照常能管密钥与管理员，别把 403 理解成「这个功能被关了」。
