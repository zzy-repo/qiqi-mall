**三个平台走同一条路，差异只活在适配器里** —— 淘宝「果小铺」、抖音「果小铺严选」各是一套模拟平台，报文与错误码自己一套；自营商城「上海直营」真调开放接口、也老实走一遍网络。从「统一模型」往下，三家共用一条主干。

## 场景

入口是后台「渠道」页（`admin-web/src/views/channel/index.vue`）：三张店铺卡（每张一个「立即拉单」）、一张同步日志表（可按结果筛「成功 / 失败」）。

拉到单之后的流程完全复用已有的东西：平台订单 → 统一模型 → 落成**待审核订单（status=7）** → 交给已有的审核模块 → 过审拆单 → 逐包裹下发、出库 → 「回传发货」把运单号写回平台。全程一次外呼一行同步日志。

## 撑不住的时候

**① 平台会重推。** 拉单接口按水位线取单，网络抖一下、mock 重推同一批，是很平常的事。如果每拉一次就建一次单，同一笔生意会在库里变成两笔 —— 之后库存扣两次、发两次货。所以**闸门必须在建单之前**。

**② 回传是不可撤回的外呼。** 运单号写回平台之后，平台侧就开始给买家发短信了。这个动作失败要能重试，但**重试不能重复回传** —— 否则平台侧收到两条发货，买家收到两条通知。

**③ 三个平台的差异如果是散在业务代码里的，加第四个平台就得改主干。** 这条不是理论：淘宝和抖音的适配器是**同一份代码换路径段**，在注册表里注册成两个。

## 规矩落在哪

① **适配器 SPI**：平台差异只允许活在适配器里（拼地址、解报文、译错误码、超时与非成功响应一律判失败）。业务层只认统一模型（平台单号 / 收件人 / 明细 / 金额）。再加平台 = 再写一个适配器，**主干一行不改**。

② **幂等闸门在建单之前**：一道「平台单号映射」校验 —— 这个店铺 + 这个平台单号来过没有？来过就是重复：记一行「跳过 · 重复」，**不建单、不动库存、也不当错误**（这是正常业务，不是失败）。唯一键在库上兜底（`uk_map`）。

③ **一张单一个事务**：先查闸门，再对商品编码 —— **任一明细对不上，整单放弃**，不留半张单。

④ **落单即待审核**：新单直接 `status=7`，交棒审核模块。渠道不自己造一套审核逻辑。

⑤ **三表各管一件事**：店铺（`channel_shop`，带拉单水位）、映射（`channel_order_map`，幂等闸门）、同步日志（`channel_sync_log`，一次外呼一行、只追加）。

⑥ **回传只挑已出库的包裹**：取消的不算；一次外呼一行日志，带动作 / 结果 / 失败原因 / 第几次尝试。

⑦ **失败要记账、重试要另起一行**：第一次外呼 503 → 一行 `FAIL`（`attempt=1`，原因里带 503）；重试成功 → 另一行 `OK`（`attempt=2`）。所以「失败过、后来成功了」在日志里是**两行**，不是被覆盖成一行。

## 凭什么证明好了

`e2e/tests/scenarios/业务/渠道-多平台接入/接入主链路.spec.js`，一条用例 5 个阶段，**断言以直查库为主**（`channel_order_map` / `order` / `channel_sync_log` 是唯一事实来源），UI 只用在外呼结果真的被页面显示出来这件事上：

- **① 起 mock → 三家拉单**：三家各点一次「立即拉单」→ 商城新建 1 笔、淘宝 2 笔、抖音 1 笔（服务端回报的 `created`）；库里映射正好 4 行、4 笔映射对应的订单**全是 `status=7`**；平台分布 1/2/1；`order.channel` 记下 `DOUYIN/MALL/TAOBAO`；渠道单统一挂「平台买家」账号；4 笔共 5 条明细（淘宝第二单 2 条）；每家一条 `PULL/OK` 汇总行。
- **② 再点一次（mock 重推同一批）→ 订单数不变**：三家 `created` 都是 0，映射行数与待审核订单数都不变，且 **`PULL` + `SKIP` + `reason=IDEMPOTENT` 至少 3 行**、`FAIL` 为 0 行。这是幂等闸门的直接证据。
- **③ 审核通过 → 拆单 → 下发 → 拣货 → 出库 → 回传发货**：审核后订单 8 待发货、生成 1 个待下发包裹、出库后 `status=3` 且写运单号；「回传发货」接口 `ok=1`、用的是**平台单号**；**mock 平台侧真的收到 1 条发货**（`shippedCount=1`，不信我们自己的日志）；我们这边留一行 `SHIP_PUSH/OK`（`attempt=1`，`ref_type=DELIVERY`）。
- **④ 注入 503 → 回传 → 两行日志**：`attempt=1 FAIL`（原因带 503）+ `attempt=2 OK`，**恰好 2 行**；平台侧最终只收到 1 条（第一次 503 没落库）。
- **⑤ 日志页看得见**：按结果筛「失败」→ 那一行可见，失败原因列显示的是 **503 这类具体原因，不是「失败」两个字**；筛「成功」→ `attempt=2` 那行「重试次数」显示 **1**（口径是 `attempt - 1`）。

三个刻意的测试手法值得记下来（别照抄成坏习惯）：mock 服务用**精确 PID**（`spawn` + `SIGTERM`）起停、绝不宽匹配 pkill；`MOCK_RUN_ID` 每轮唯一，所以平台单号每轮都是新的一批；商城那笔单来自**真实买家下单支付**，证明开放接口读的是真订单。另外，拉单前要把 MALL 店铺水位钉到「那笔单支付前 1 秒」—— 否则库里的历史已付款单会被一起拉进来，「商城 1 笔」就成了运气的产物而不是结论。

## 附：口径与边界

- **不做策略、不做库存同步、不做退款同步、不做对账**：这一条链只到「回传发货」为止。别把它当成完整的多平台中台。
- **平台单号映射是幂等的唯一依据**：同一店铺同一个平台单号只能建一次单。所以「同一笔生意在两个平台各下一单」不会被合并 —— 那是两笔。
- **失败重试的次数是有限口径**：「重试次数 = attempt - 1」是页面口径；日志表里每次外呼各占一行，不去重、不合并。
- **mock 平台不是真平台**：`mock-platform/server.mjs` 是零依赖单文件、独立端口（示例用 19090），不进 compose。它的错误码与字段名是照着两个平台仿的，但**报文的真实性只到这一层**。
- **同步日志只追加**：不更新、不删除。所以「这条回传最后成没成」要看同一 `ref_id` 下的全部行，不能只看最后一行。
- **本页数字出处**：阶段划分与四个断言口径来自 spec 的文件头；三张表名与 `uk_map`、`PULL` / `SHIP_PUSH` / `SKIP` / `FAIL` / `IDEMPOTENT` / `attempt` 等取值来自 spec 的 SQL 与断言；「同一份代码换路径段注册成两个」来自 mmd 的适配器层说明；1/2/1 与 5 条明细是那一轮造数的结果，随 mock 批次变化，不是全局常量。
