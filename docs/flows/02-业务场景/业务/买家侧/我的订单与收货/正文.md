**买家只看自己的单，看到的每个状态都得是真的** —— 列表按会员隔离，别人的订单号在这一页根本不存在；确认收货是不可逆终态，所以点它要先问一句，服务端还要再守一次。

## 场景

「我的订单」（`portal-web/src/views/order/index.vue`）一行给的信息不多但都要有用：订单号、金额、状态、售后标记，行尾按状态长不同的按钮 —— 待付款有「模拟支付」、已发货有「确认收货」、已付款或已发货才有「申请退货」、任何状态都能点「包裹」。

状态文本是前端一张十项映射表（`statusText`）：待付款 / 已付款 / 已发货 / 已完成 / 已关闭 / 退款中 / 已退款 / 待审核 / 待发货 / 部分发货。其中「部分发货」不是谁写进去的，是包裹聚合推出来的。

三个弹层：详情（订单号、收货信息、商品明细）、包裹抽屉（每个包裹的发货单号、仓库、运单号、状态）、退货表单（在 `售后退货` 那页讲）。

## 撑不住的时候

**确认收货这件事，原来是「只写父单、不碰子单」。** 于是真实存在过这样的组合：父单说「已完成」，而它下面还有一个包裹在运输中。更糟的是它会**来回跳**：之后任何一次 WMS 回传按子单重新聚合，又把订单从已完成写回已发货 —— 一个被标成「不可逆终态」的状态，实际上可逆。

这类分叉的麻烦在于每一天都自洽：
- 买家看订单是「已完成」，所以不能点确认收货了（入口没了）；
- 商家看包裹还是「已出库」，所以还会去催物流；
- 两边都拿着「事实」，但这两个事实互相矛盾，而且没有任何一处报错。

根因是**父单被当成了事实源**。订单状态本来应该是子单的函数（几个包裹、各自到哪一步），一旦允许某处直接硬写父单，就出现了两个写者争同一个字段。

## 规矩落在哪

① **列表隔离靠 `member_id`**：列表接口按当前登录会员过滤，别人的订单号在你的列表里压根不出现 —— 不是前端藏起来，是查询条件里就没有那一条路。

② **详情是快照**：收货人、电话、地址、商品名、单价都是下单那一刻写进 `order` / `order_item` 的字符串与数值。商品后来改名改价，历史订单不跟着变。

③ **确认收货两道守卫**：前端只有 `status === 2` 才渲染按钮，且点了先弹一句「确认已收到货？确认后订单完成，不可撤销。」（点取消**一个请求都不发**、状态不变、入口还在）；服务端 `confirm` 再守一次：不是本人 → `订单不存在`，状态不是 2 → `只有已发货订单可以确认收货`。

④ **先推子单，再让聚合算父单**：`signRemainingDeliveries` 把该订单所有未取消、未签收的包裹推到「已签收」（与 WMS 回传同一条落库路径 + 补运单），再由 `recomputeOrderStatus` 由子单推导父单 → 已完成。唯一例外是**直发单**（订单下没有任何未取消包裹，单仓直发时直接从 1 置到 2），那里父单只能由这一步推进，是唯一写者。

## 凭什么证明好了

`e2e/tests/scenarios/业务/买家侧/我的订单与收货.spec.js`，3 条用例、20 条断言：

- **列表 + 详情 + 包裹**：订单推进到「已发货」后，列表显示「已发货」；详情弹窗里有订单号、收货人、1 条明细；包裹抽屉里**恰好 1 个包裹**、带运单号（正则 `SF` + 至少 6 位数字）、状态「已出库」。
- **确认收货**：点按钮先出确认框且文案含「确认后订单完成，不可撤销」→ 点「确定」→ 列表就地变「已完成」、**确认收货入口消失**；随后从接口**重放一次**确认 → 被服务端拒绝（`code != 0`），订单仍停在已完成 3。
- **越权**：A 账号下单后，B 账号登录 → B 的订单列表接口返回 0 条，页面上也不含 A 的订单号。

## 附：口径与边界

- **「已发货」不等于「所有包裹都出库」**：一单拆多仓就是多个包裹，订单状态是聚合结果 —— 所以「部分发货」确实会出现，买家看到它不该被当成异常。
- **确认收货的「0 行 = 409」**：聚合写父单那一步若影响 0 行，说明期间有别人改过（最常见是并发的另一次确认收货，或 WMS 恰好回传），整笔回滚并回 409，前端提示刷新。真并发的完整对照在 `并发与竞态/状态竞态/确认收货并发`。
- **包裹与运单是两张表**：`delivery_order`（发货单：仓库、状态）+ `delivery_logistics`（运单：`delivery_id`、运单号）。所以「一个包裹一个运单号」是列结构决定的，不是凑出来的。
- **本页不证明退款**：退款后的状态（退款中 / 已退款）由售后流程推进，见 `业务/买家侧/售后退货`。
