## 收货地址（member_address / default_status）

地址簿的不变量只有一条：一个账号里 `default_status = 1` 的行**至多一条**。设默认不是给这一条打勾就完了 —— 结算页默认选中那条地址，两条都标默认，结算页就不知道该用哪个。这条一致性由接口一起守，不靠前端克制。

设默认 = 先清别人、再写自己：`addAddress` 与 `updateAddress` 见到 `defaultStatus=1` 就先 `clearOtherDefault(memberId, 自己)`，把其余地址的默认标记清零。两个接口都带 `@Transactional`，编辑那条尤其不能省：`clearOtherDefault` 已经执行，若后面的 `updateById` 失败却静默返回成功，账号就落到「一条默认都没有」的状态，所以那一步写成 `requireAffected(rows, 记录已被删除)`，影响 0 行就 409、整笔回滚。

删掉默认地址时，剩下里按 `id` 升序取第一条补位（`orderByAsc(id).last("limit 1")`），全删光不报错、只是列表空。反过来不成立：新增时不勾「默认」，这个账号就没有默认地址（`default_status` 全 0 是允许的正常状态），所以逻辑只能假设「至多一条」，不能假设「必有且仅有一条」。六项必填由前端就地拦，少一项就报错、弹窗不关、数据不落库。长度是真截断而不是假装截断：收件人 `maxlength="50"`、电话 20、省市区各 50、详细地址 200，与 `member_address` 的列宽一一对应，输 80 个字进收件人框，框里只剩 50 个字，库里存的也是 50 个字。

**验证**　`收货地址.spec.js`：5 条用例、34 处断言，真点界面 + 读库。全流程：新增两条都不勾默认 → 列表不标默认、库里 `defaultStatus=1` 的行数为 0；编辑改写收件人与详细地址 → 旧收件人不再出现在收件人列（逐格比对）；设为默认 → 该行标「默认」、排到列表第一位、库里记为 1；删除另一条 → 服务端只剩 1 条。必填：六项全不填 → 就地报错、不提交。超长文本：输入 80 个字的收件人与 300 个字的详细地址 → 输入框里长度分别是 50 与 200，落库读回来同样 50 与 200（只测输入框不够，前端能截、库能存才算）。默认唯一：A 设默认后 B 设默认 → 库里 `defaultStatus=1` 有且只有 1 条且是 B；再把 A 改回默认 → 编辑路径同样取消 B。删除补位：三条地址、把中间那条设为默认 → 删掉它 → 剩下 id 最小的自动成为默认、仍然只有 1 条；再全删 → 列表 0 行、服务端为空、不报错。

**边界**　没有条数上限，页面上没有「最多 20 条」这类限制（现状未做）。补位那一步刻意不检查影响行数：`updateById(oldest)` 若 0 行，说明这条「最早地址」恰在此刻被同账号另一端点删了，此时也没有别的行可提升，而且地址不是账务数据，保持原样即可。地址是快照不是引用：订单存的是 `receiver_name` / `receiver_phone` / `receiver_address` 三个字符串，改地址簿不会改动任何历史订单 —— 这也是删地址可以很轻的前提。`default_status` 没有唯一约束，库里是普通 `tinyint`，唯一性靠接口里那两行 `clearOtherDefault` 守，绕开接口直接写库能造出两条默认，守门位置在接口层，不伪装成表级约束。「一条默认都没有」不是缺陷，要防的是两条都标默认。
