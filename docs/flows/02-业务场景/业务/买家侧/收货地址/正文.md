**默认地址最多一条，设新的必须取消旧的** —— 增删改查本身不难，难的是这条不变量：一个账号里 `default_status=1` 的行最多只有一条；把某条设成默认，原来那条必须同时失效，否则结算页不知道该选哪个。

## 场景

买家中心 →「收货地址」（`portal-web/src/views/address/index.vue`）：列表按「默认在前、同状态按 id 升序」排，行尾是编辑 / 设默认 / 删除，表单弹窗六项：收件人、电话、省、市、区、详细地址。

「设默认」不是给这一条打勾就完了 —— 结算页会默认选中那条地址，所以**两条都标默认，等于结算页不知道该用哪个**。这条一致性由 `PortalMemberController` 的三个接口一起守，不是靠前端克制。

## 规矩落在哪

① **设默认 = 先清别人，再写自己**：`addAddress` / `updateAddress` 见到 `defaultStatus=1` 就先 `clearOtherDefault(memberId, 自己)`，把该会员其余地址的默认标记清零。两个接口都带 `@Transactional` —— 编辑那条尤其不能省：`clearOtherDefault` 已经执行了，如果后面的 `updateById` 失败却静默返回成功，账号就会落到「一条默认都没有」的状态。所以那一步写成 `OptimisticLockGuard.requireAffected(rows, 记录已被删除)`：0 行就 409 整笔回滚。

② **删掉默认地址 → 剩下最早的那条自动补位**：`deleteAddress` 先看被删的是不是默认；是默认就从剩下的里按 `id` 升序取第一条（`orderByAsc(id).last("limit 1")`）提升为默认。全删光不报错，只是列表空。

③ **反过来不成立：有地址不一定有默认**。新增时不勾「默认」，这个账号就没有默认地址（库里 `default_status` 全 0）—— 这是允许存在的正常状态，所以任何逻辑都不能假设「必有且仅有一条默认」，只能假设「至多一条」。

④ **六项必填，前端就地拦**：少一项就报 `el-form-item__error`，弹窗不关、数据不落库。

⑤ **长度是真截断，不是假装截断**：收件人 `maxlength="50"`、电话 20、省市区各 50、详细地址 200 —— 与 `member_address` 的列宽一一对应（`name varchar(50)` / `phone varchar(20)` / `detail varchar(200)`）。输 80 个字进收件人框，框里只剩 50 个字，**库里存的也是 50 个字**。

## 凭什么证明好了

`e2e/tests/scenarios/业务/买家侧/收货地址.spec.js`，5 条用例、34 条断言：

- **全流程**：新增两条（都不勾默认 → 断言列表**不标**默认、库里 `defaultStatus=1` 的行数为 **0**）→ 编辑改写收件人与详细地址（旧收件人不得再出现在收件人列，逐格比对）→ 设为默认（该行标「默认」、**排到列表第一位**、库里记为 1）→ 删除另一条（被删的不再出现、没删的还在、服务端只剩 1 条）。
- **必填**：六项全不填 → 就地报错、不提交。
- **超长文本**：输入 80 个字的收件人 / 300 个字的详细地址 → 输入框里长度分别是 **50 / 200**，落库读回来同样是 50 / 200（只测输入框长度是不够的，前端能截、库能存才是真的）。
- **默认唯一**：A 设默认 → B 设默认时 A 的默认被取消（库里有且只有 1 条 `defaultStatus=1`，且是 B）；再把 A 改回默认 → 编辑路径同样取消 B 的默认。
- **删除补位**：三条地址、把中间那条设为默认 → 删掉它 → 剩下 id 最小的那条自动成为默认、仍然只有 1 条默认；再全删 → 列表 0 行、服务端为空、**不报错**。

## 附：口径与边界

- **没有条数上限**：地址簿想存多少存多少，页面上没有「最多 20 条」这类限制（现状，未做）。
- **补位那一步刻意不检查影响行数**：`updateById(oldest)` 若 0 行，说明这条「最早地址」恰在此刻被同账号另一端点删了 —— 此时也没有别的行可提升，且地址不是账务数据（下单时收货地址已经快照进订单），保持原样即可。
- **地址是快照，不是引用**：订单存的是 `receiver_name` / `receiver_phone` / `receiver_address` 三个字符串，所以改地址簿不会改动任何历史订单 —— 这也是「删地址可以很轻」的前提。
- **`default_status` 没有唯一约束**：库里是普通 `tinyint`，唯一性靠接口里那两行 `clearOtherDefault` 守。绕开接口直接写库能造出两条默认 —— 这是已知的守门位置（接口层），不伪装成表级约束。
- **「一条默认都没有」不是 bug**：地址簿非空但没有默认是允许的（见规矩 ③）。真正要防的是**两条都标默认**。
