## 结算下单与支付（checkout / idempotent token）

结算页三个坑形状不同、后果同一种 —— 都会让账和货对不上：连点两下变成两张单；库存不足时留下「半张单」；已支付的单还长着支付入口。三条里没有一条会报错，它们都表现为「系统一切正常，只是数不对」。

防重复靠一次性令牌：进页面先 `GET /portal/orders/idempotent-token` 领 `tokenId`，提交时随请求带上，领不到就留空、那一单提交时被后端直接拒（不存在「没有令牌照样放行」的分支）；`consume(token)` 消费一次即作废，第二次回 `请勿重复提交订单（或页面已过期），请刷新结算页重试`。关键细节是死锁重试不再消费令牌 —— 重试发生在 `OrderCreateService#createWithRetry` 的同一 HTTP 请求内（最多 3 次、退避 30ms×2ⁿ 加抖动），所以锁冲突重试不会变成第二单。

校验分两层：缺收货人或地址时前端提示 `请填写收货人和收货地址`、停在结算页、不发请求；后端 `create` 里三句中文各管一件事（`请选择要结算的商品` / `请填写收货人` / `请填写收货地址`），一个订单都不产生。扣减与建单在同一个事务里：`OrderTransactionalCreator#create` 是 `REQUIRES_NEW`，任一步失败整笔回滚，订单、明细、已扣库存、台账一起消失，所以不会出现「库存扣了订单没建」或「订单建了库存没扣」。支付也有两道守卫：状态必须是 0 待付款，再用 `order.version` 做条件更新，影响 0 行说明期间被改过 → 409 整笔回滚且流水不落库；流水自身带幂等键 `{orderSn}:PAY`，重放撞键静默跳过。金额以明细为准：页面上的合计是给眼睛看的，落库的 `total_amount` 由后端按「明细单价 × 件数」算出，请求体里传的金额不算数。

**验证**　`结算下单与支付.spec.js`：4 条用例、21 处断言。正常链：结算清单 1 行、合计含单价两位小数 → 提交后跳 `/orders` 且列表显示「待审核」；直查库只产生 1 笔订单、`status=7`、收货人等于填的、`totalAmount` 等于单价、`paymentTime` 已落、库存 2 秒内少 1（分桶模式下这是缓存回写，用轮询等收敛而不是硬断言同步）。必填：什么都不填就提交 → 警告 `请填写收货人和收货地址`、URL 仍在 `/checkout`、订单 0 笔；只填收货人不填地址同样被拦住。库存不足：把库存压到 1、车里放 2 件 → 提交失败、停在结算页、订单 0 笔、库存仍是 1（不是扣了一半）。支付守卫：状态 7 的订单行上没有「模拟支付」按钮，接口确认状态是 7。

**边界**　支付是模拟的：`payType` 固定 1，没有渠道回调、没有对账文件、没有退款到渠道，退款只在售后台账里记一笔，别把这段当成接支付网关的实现。清购物车在事务之外：下单成功后由 portal 侧按明细逐条删（`fromCart=true` 时），刻意放在 oms 事务外 —— 购物车是意图清单，允许与订单有轻微不一致，以此解除 oms 到 member 的模块依赖。「连点两次」在 UI 用例里点不出来，人手工点不出真并发，所以防重复的证据是「令牌一次性 + 第二次提交被拒」这条机制断言，真并发用例在 `并发与竞态/重复提交与幂等` 那两页，本页不假装演过双击。
