**结算这一步，校验要拦住、扣减要原子、重复要认得出来** —— 三件事少一件就会产生「钱和货对不上」的账：没校验就建出一张没地址的单，没原子就超卖，认不出重复就一次点击生成两单。

## 场景

买家在购物车点「去结算」→ `portal-web/src/views/checkout/index.vue`：左边是清单（来自购物车条目），右边是应付金额（单价 × 数量），下面填收货人 / 电话 / 地址 → 点「提交订单」。

进页面第一件事是领令牌：`GET /portal/orders/idempotent-token` 拿 `tokenId` 存起来，提交时随请求带上；领不到就留空字符串，那一单提交时会被后端直接拒掉（不存在「没有令牌照样放行」的分支）。

提交成功后 `router.replace({ path: '/orders', query: { pay: 订单id } })`：跳转本身带上了「该付哪一单」。订单页 `onMounted` 里 `load()` 完再检查这个参数，找到那张 `status === 0` 的订单就自动发起一次模拟支付，`0 待付款 → 7 待审核`，然后等商家审。没有这个参数、或那一单已经不是待付款，都不会自动付。

## 撑不住的时候

结算页的三个坑，形状不一样但后果同一种：都会让「账」和「货」对不上。

**① 连点两下 = 两张单。** 网络卡的时候人会点第二次，这不是操作失误，是正常人的反应。没有一次性凭证的话，第二次请求就是一笔真订单，然后这笔「根本没想要的单」还会去扣一次库存、写一条支付流水。

**② 库存不足时「半张单」留下来。** 如果扣库存和写订单不是一个事务，会出现最难看的一种：库存扣了、订单没建（货少了但没人知道卖给了谁），或者订单建了、库存没扣（卖了但库存没动，下一次还能再卖一遍）。

**③ 已支付的单还长着支付入口。** 待审核的订单如果还能点「模拟支付」，同一笔钱会被记两次 —— 而支付流水是按订单号作对账键的，重复的那条要么被唯一键吃掉、要么让对账出现一笔解释不清的钱。

三条里没有一条会报错，它们都表现为「系统一切正常，只是数不对」。

## 改了什么

① **前端先拦一层，后端再拦一层**：缺收货人或地址 → 前端提示 `请填写收货人和收货地址`、停在结算页、不发请求；后端 `create` 里三句中文各管一件事（`请选择要结算的商品` / `请填写收货人` / `请填写收货地址`），一个订单都不产生。

② **幂等令牌原子消费**：`idempotentTokenStore.consume(token)` 消费一次即作废，第二次回 `请勿重复提交订单（或页面已过期），请刷新结算页重试`。关键细节：**死锁重试不再消费令牌** —— 重试发生在 `OrderCreateService#createWithRetry` 的同一 HTTP 请求内（最多 3 次、退避 30ms×2^n + 抖动），所以「锁冲突重试」不会变成第二单。

③ **扣减与建单在同一个事务里**：`OrderTransactionalCreator#create` 是 `REQUIRES_NEW`，任一步失败整笔回滚 —— 订单、明细、已扣库存、台账一起消失。库存判断与减法压在同一条 SQL（机制见 `库存/一条SQL吃掉「读、判、写」`，本页不重复）。

④ **支付两道闸**：先看状态必须是 `0 待付款`（否则 `当前订单状态不可支付`），再用 `order.version` 做条件更新；0 行 = 期间被改过 → 409 整笔回滚，**支付流水也不会落库**。流水本身带幂等键 `{orderSn}:PAY`，重放撞 `uk_idem` 静默跳过。

⑤ **入口跟着状态走**：「模拟支付」按 `status === 0` 渲染，待审核的订单上根本没有这个按钮。

## 凭什么证明好了

`e2e/tests/scenarios/业务/买家侧/结算下单与支付.spec.js`，4 条用例、21 条断言：

- **正常链**：结算清单 1 行、合计含 `单价` 两位小数 → 提交后跳 `/orders` 且列表显示「待审核」；库断言只产生 1 笔订单、状态 7、收货人等于填的、`totalAmount` 等于单价、`paymentTime` 已落、库存 2 秒内少 1（分桶模式下是缓存回写，所以用轮询等收敛而不是硬断言同步）。
- **必填**：什么都不填就提交 → 警告 `请填写收货人和收货地址`、URL 仍在 `/checkout`、**订单 0 笔**；只填收货人不填地址 → 同样拦住。
- **库存不足**：把库存压到 1、车里放 2 件 → 提交失败、停在结算页、**订单 0 笔**、**库存仍是 1**（不是「扣了一半」）。
- **支付守卫**：已支付（状态 7）的订单行上**没有**「模拟支付」按钮，且接口确认状态是 7。

## 附：口径与边界

- **支付是模拟的**：`payType` 固定 1，没有渠道回调、没有对账文件、没有退款到渠道 —— 退款只在售后台账里记一笔。别把这段当成接支付网关的实现。
- **金额以明细为准**：页面上的合计是给眼睛看的，落库的 `total_amount` 由后端按「明细单价 × 件数」算（`OrderTransactionalCreator` 里一次算出再 INSERT），请求体里传的金额不算数。
- **清购物车在事务之外**：下单成功后由 portal 侧按明细逐条删（`fromCart=true` 时），刻意放在 oms 事务外 —— 购物车是意图清单，允许与订单有轻微不一致，以此解除 oms → member 的模块依赖。
- **「连点两次」在 UI 用例里点不出来**（人手工点不出真并发），所以防重复的证据是「令牌一次性 + 第二次提交被拒」这条机制断言，以及 `并发与竞态/重复提交与幂等` 那两页的真并发用例；本页不假装演过双击。
