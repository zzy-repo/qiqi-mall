## 仓库管理（warehouse / split default）

仓库是拆单的地基：名字随便叫、状态随时停，但被发货单用过的那个仓必须留着。拆单按 `warehouse_id` 分配、不认名字，所以「深圳仓」能建出两个 —— `warehouse` 表没有唯一索引，新增也不查重；重名不会让货发错仓，只会让人在列表里点错行。默认仓是启用状态里 id 最小的那个（不是名字排序、也不是最近改过的），拆单兜底就用它，所以把 id 最小的启用仓停掉，兜底落点就换到下一个。

删除被引用的仓，原来只会抛外键异常、被兜底成「数据处理失败，请稍后重试」—— 那句话把三种完全不同的处境说成同一件事：网络抖了、后端崩了、还是这个仓被历史发货单钉住了。现在 `DataIntegrityViolationException` 被单独翻译成「数据被其它记录引用，无法删除（请先处理关联的物流、退货、明细等记录）」，语义没变（仍然拒删），变的是说清为什么；真要停用一个仓，改成停用就行。

每次增删改都写一条后台操作审计（`WAREHOUSE_CREATE` / `WAREHOUSE_UPDATE` / `WAREHOUSE_DELETE`），与改动同一事务：审计写不进去，仓也建不出来 —— 仓库是拆单归属与库存的落点，增删改必须留证，而且仓被删之后，它的名字只在那条审计里还读得到。编辑走影响行数校验，0 行 → 409「记录已被删除」：仓库是发货单与库存的归属依据，静默改失败会让人以为这个仓还能用。名称必填在前端拦，空着点确定 →「请输入仓库名称」，弹窗不关、列表不变、不落库；新增默认启用（`status` 为 null 时按 1）。删除不校验存在性：`removeById` 天生幂等，删一个不存在的 id 也返回成功，所以「删除成功」的提示不代表那一行刚才真的在。

**验证**　`仓库管理.spec.js`：1 条用例、7 步，不只走 happy path。进页面能看到种子仓（深圳仓、杭州仓，拆单链路依赖它们，算一次前置体检）；新增一个启用的仓 → 提示成功、列表多一行、状态「启用」；同名仓库也允许创建（现状如实断言，不是「应该被拦」），建一个停用的、状态显示「停用」；改名并停用 → 那一行立即变样；清空名称点确定 →「请输入仓库名称」、弹窗不关、取消后行数不变；删掉自己新建的那两个 →「删除成功」、列表里不再有；最后一步先用一笔真实订单把某个仓用起来（新增订单 → 审核通过，生成发货单落在该仓），再回仓库管理删它 → 提示「数据被其它记录引用，无法删除」，仓仍在列表、刷新后行数也不变。最后这一步为什么先造订单：守卫依赖「这个仓确实被发货单引用」，而哪个仓被引用取决于演示数据，不自己造一笔，这条断言在任何库上都可能「恰好」通过，那不是证据。

**边界**　这一页没有「查询引用数」的预演：仓库删除不像订单、商品那样有 `?dryRun=true`，也不报被几张发货单引用，拦住它的是数据库外键而不是业务判断，想知道具体是哪些单得自己按 `warehouse_id` 查 `delivery_order`。同名不是脏数据，是当前口径，清理重名只能人工判断，系统不代为合并。「数据被其它记录引用，无法删除」是收口后的文案，看到旧的「数据处理失败」说明跑的是旧镜像。停用会改变默认仓，这一点在改状态前要想清楚，因为它影响「规格没有分仓记录」时货从哪个仓发。
