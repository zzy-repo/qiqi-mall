**仓库是拆单的地基：名字随便叫、状态随时停，但被发货单用过的那个仓必须留着** —— 拆单只认仓库编号不认名字，所以同名仓库能建出两个；而历史发货单要记着这批货从哪个仓发的，所以那个仓删不掉。

## 场景

后台 `admin-web/src/views/warehouse/index.vue`：列表只有 名称 / 启用状态 / 操作。新增和编辑都只填仓库名称 + 选启用或停用，没有别的字段。

演示数据里有两个仓：深圳仓（id=1）与杭州仓（id=2）。拆单演示之所以能拆成两个包裹，靠的就是「不同规格的分仓库存在这两个仓里」这件事 —— 这一页是拆单的上游字典。默认仓是**启用状态里 id 最小的那个**（不是名字排序，也不是最近改过的），拆单兜底就用它。

## 撑不住的时候

**① 原来删不掉的时候只有一句兜底话。** 删一个被发货单用过的仓，后端抛外键异常，被兜底翻译成「数据处理失败，请稍后重试」。这句话把三种完全不同的处境说成同一件事：网络抖了、后端崩了、还是这个仓被历史发货单钉住了。用户没法判断该重试还是该改配置，只能来问「为什么点删除没反应」。

**② 名称没有唯一校验，这是现状不是笔误。** `warehouse` 表没有唯一索引，新增也不查重，所以「深圳仓」能建出两个。系统不挡的理由是：拆单按 `warehouse_id` 分配，重名不会让货发错仓 —— 只会让人在列表里点错行。这一点必须说清，否则下次见到两个同名仓会以为是脏数据。

## 改了什么

① **外键拦截有了具体文案**：删除被引用的仓库时，`DataIntegrityViolationException` 被单独翻译成「数据被其它记录引用，无法删除（请先处理关联的物流、退货、明细等记录）」，不再落到「数据处理失败」。语义没变（仍然拒删），变的是「说清为什么」。真要停用一个仓，改成停用就行。

② **每次增删改都写一条后台操作审计**（`WAREHOUSE_CREATE` / `WAREHOUSE_UPDATE` / `WAREHOUSE_DELETE`），与改动**同一事务**：审计写不进去，仓也建不出来。理由写在代码里 —— 仓库是拆单归属与库存的落点，增删改必须留证；而且仓被删之后，它的名字只在那条审计里还读得到。

③ **编辑走影响行数校验**，0 行 → 409「记录已被删除」。必须拦：仓库是发货单与库存的归属依据，静默改失败会让人以为「这个仓还能用」。

④ **名称必填在前端拦**：空着点确定 → 「请输入仓库名称」，弹窗不关、列表不变、不落库。

⑤ **新增默认启用**（`status` 为 null 时按 1）。

## 凭什么证明好了

`e2e/tests/scenarios/业务/商家-基础配置/仓库管理.spec.js`，一条用例 7 步，把这一页能做的事全走一遍，不只 happy path：

① 进页面能看到种子仓（深圳仓、杭州仓）—— 拆单链路依赖它们，所以这条也算前置体检。
② 新增一个启用的仓 → 提示成功、列表多一行、状态「启用」。
③ **同名仓库也允许创建**（现状如实断言，不是「应该被拦」），建一个停用的，状态显示「停用」。
④ 改名 + 停用 → 列表这一行立即变样。
⑤ 清空名称点确定 → 「请输入仓库名称」、弹窗不关、取消后行数不变。
⑥ 删掉自己新建的那两个 → 「删除成功」、列表里不再有。
⑦ **先用一笔真实订单把某个仓用起来**（新增订单 → 审核通过，生成发货单落在该仓），再回仓库管理删它 → 断言提示「数据被其它记录引用，无法删除」；仓仍在列表；刷新页面后行数也不变、仓仍在。

第 ⑦ 步为什么要先造订单：这条守卫依赖「这个仓确实被发货单引用」，而哪个仓被引用取决于演示数据。不自己造一笔，这条断言在任何库上都可能「恰好」通过 —— 那不是证据。

## 附：口径与边界

- **这一页没有「查询引用数」的预演**：仓库删除不像订单/商品那样有 `?dryRun=true` 预演，也不报「被几张发货单引用」。拦住它的是数据库外键，不是业务判断 —— 想知道具体是哪些单，得自己按 `warehouse_id` 查 `delivery_order`。
- **「数据被其它记录引用，无法删除」是收口后的文案**：早先是兜底那句「数据处理失败，请稍后重试」。如果看到旧文案，说明跑的是旧镜像 —— 这也解释了为什么口语稿里还留着旧说法。
- **同名不是脏数据，是当前口径**：没有唯一索引、没有查重。清理重名只能人工判断，系统不会替你合并。
- **删除不校验存在性**：`removeById` 天生幂等，删一个不存在的 id 也返回成功。所以「删除成功」的提示不代表那一行刚才真的在。
- **停用会改变默认仓**：默认仓取「启用的」里 id 最小的，所以把 id 最小的启用仓停掉，兜底落点就换到下一个 —— 这会影响「规格没有分仓记录」时货从哪个仓发。改状态前先想清楚这一点。
- **本页数字出处**：`WAREHOUSE_CREATE/UPDATE/DELETE` 三个原因码与审计时机来自 `WarehouseController`；外键文案来自 `GlobalExceptionHandler#handleDataIntegrityViolation`；409 文案来自 `OptimisticLockGuard.MSG_RECORD_DELETED`；默认仓规则来自 `SplitOrderService#defaultWarehouseId`（`status=1` + `ORDER BY id LIMIT 1`）；仓库 id 与名字来自 `sql/data.sql` 的种子（某次快照）。
