## 退货原因字典（return_reason）

这张字典是给买家申请退货时选原因用的：商家在这一页加一条，买家那边的下拉立刻能选到；删一条，下拉里也就不再出现。必填在前端拦 —— 空名点确定 →「请输入退货原因」，弹窗不关、不落库。

重名只在前端拦一次（`ElMessage.warning('已存在同名退货原因，请换一个名称')`），服务端不查重也不查空：`ReturnReasonController.create` 直接 `save`。换个入口写进去两条同名的，系统会收 —— 这是现状而不是「应该」，所以「字典里不可能有重名」这句话不能对外承诺。它也不会造成业务事故：原因只是个名字，不参与任何计算。

被申请引用过的那条不许删：`CatalogDeleteGuard.checkReturnReason` 回「该原因已被 N 条退货申请使用，不能删除」，而这个 N 是实时查出来的 —— 把那条申请删掉之后，这条原因立刻就能删。拦的是当前引用数，不是历史痕迹。改名不回写历史：申请单里同时存 `reason_id` 和提交那一刻的原因名称，所以字典改名之后已提交的申请仍显示旧名字，这不是缺陷而是快照语义 —— 编号用于统计、名称用于展示。删除先过确认框（「确认删除退货原因「X」？已被退货申请使用的原因无法删除。」），确认后才去问后端。

**验证**　`退货原因字典.spec.js`：2 条用例、两组。字典维护页六步：菜单里有「退货原因」入口 → 种子原因（质量问题等）在列表里 → 新增一条 → 改名后旧名字消失 → 清空名称点确定 → 提示「请输入退货原因」、弹窗不关、取消后行数不变 → 新增一个已存在的名字 → 出 `warning` 且含「已存在同名退货原因」、弹窗不关、行数不变，同时直接问接口确认字典里只有一条同名（证明服务端确实没有第二道查重）→ 删除自建的那条 → 接口里也没有、种子原因一条不少。消费链路五步：管理端新增一条原因 → 买家下单并推到已发货 → 买家在申请退货的下拉里能看到这条新原因 → 提交后申请单记下的是原因名称（快照）加原因编号 → 管理端「退货申请」页的原因列显示字典里的名称 → 回字典页删这条被引用的原因 → 报错匹配「已被 N 条退货申请使用，不能删除」且该项仍在 → 最后删掉自己造的那条申请，引用解除后同一条原因立刻删成功（`code === 0`），证明拦截是按实时引用数算的。

**边界**　重名只在页面拦、服务端不拦，这是本页唯一一处「前端比后端严」的地方。名称与编号分工清楚：`reason_id` 用于统计，名称快照用于展示。删掉一条「待处理」退货申请不只是字典操作 —— 它会把订单从 5 退款中交回包裹聚合，所以消费链路那条用例的清理顺序必须是先删申请、再删原因，反过来会先撞引用守卫。种子原因不允许被清掉：用例断言「种子原因一条都不能少」，自建的三个名字是 spec 独占的，上轮异常退出留下的同名行会先被自动清理掉。种子原因的数量随 `sql/data.sql` 变化（某次快照为 4 条），所以用例断的是「≥ 4」而不是「等于 4」。
