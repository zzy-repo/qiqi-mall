**退货原因是一张字典，但历史申请存的是「提交那一刻的名字」** —— 所以字典能改名、能删空项，被申请引用过的那条永不许删：删了以后历史申请的原因就说不清了。

## 场景

后台 `admin-web/src/views/return-reason/index.vue`：列表 编号 / 原因名称 / 操作，页头一行提示「退货原因用于买家申请退货时选择；已被退货申请使用的原因不能删除」。

买家侧「申请退货」弹窗里的原因下拉，就是这个字典现读出来的 —— 商家在这一页加一条，买家那边立刻能选到；删一条，下拉里也就不再出现。

## 规矩落在哪

① **必填在前端拦**：空名点确定 → 「请输入退货原因」，弹窗不关、不落库。

② **重名在前端拦一次**：`ElMessage.warning('已存在同名退货原因，请换一个名称')`，不写库、列表不变。**但服务端不查重**：`ReturnReasonController.create` 直接 `save`，既不查重也不查空。换个入口写进去两条同名的，系统会收 —— 这是现状，不是「应该」，所以要说清。

③ **被申请引用过的不许删**：`CatalogDeleteGuard.checkReturnReason` → 「该原因已被 N 条退货申请使用，不能删除」。这里的 N 是**实时查出来**的，所以「把那条申请删掉之后，这条原因立刻就能删」—— 拦截跟的是当前引用数，不是历史痕迹。

④ **改名不回写历史**：申请单里同时存 `reason_id` 和提交那一刻的原因名称，所以字典改名之后，已提交的申请仍然显示旧名字。这不是 bug，是快照语义 —— 那张申请当时选的就是那个名字。

⑤ **删除先过确认框**：「确认删除退货原因「X」？已被退货申请使用的原因无法删除。」确认后才去问后端。

## 凭什么证明好了

`e2e/tests/scenarios/业务/商家-基础配置/退货原因字典.spec.js`，分两组、共 2 条用例。

**字典维护页（6 步）**：菜单里有「退货原因」入口 → 种子原因（质量问题等）在列表里 → 新增一条 → 改名（旧名字消失）→ 清空名称点确定 → 提示「请输入退货原因」、弹窗不关、取消后行数不变 → 新增一个已存在的名字 → 出 `warning` 且含「已存在同名退货原因」、弹窗不关、行数不变，同时**直接问接口确认字典里只有一条同名**（证明服务端确实没有第二道查重）→ 删除自建的那条 → 消失、接口里也没有了、种子原因一条不少。

**消费链路（5 步）**：管理端新增一条原因 → 买家下单并推到已发货 → 买家在申请退货的下拉里**能看到这条新原因** → 提交后申请单记下的是原因名称（快照）+ 原因编号 → 管理端「退货申请」页的原因列显示字典里的名称 → 回字典页删这条被引用的原因 → 报错匹配「已被 N 条退货申请使用，不能删除」且该项仍在 → 最后删掉自己造的那条申请，**引用解除后同一条原因立刻删成功**（`code === 0`），证明拦截是按实时引用数算的。

## 附：口径与边界

- **重名只在页面拦、服务端不拦**：这是本页唯一一处「前端比后端严」的地方。它不会造成业务事故（原因是个名字，不参与计算），但意味着「字典里不可能有重名」这句话不能对外承诺。
- **名称快照 vs 编号**：申请单存 `reason_id` 也存名称。前者用于统计，后者用于展示 —— 所以改名不改历史，删项才被拦。
- **删掉一条「待处理」退货申请不只是字典操作**：它会把订单从 5 退款中交回包裹聚合（见退货处理页），所以消费链路那条用例的清理是「删申请 → 再删原因」，顺序不能反。
- **种子原因不允许被清掉**：用例断言「种子原因一条都不能少」，自建的三个名字是 spec 独占的（上轮异常退出留下的同名行会先被自我修复清掉）。
- **本页数字出处**：删除守卫文案来自 `CatalogDeleteGuard#checkReturnReason`；前端提示两条来自 `return-reason/index.vue`；「服务端不查重不查空」读自 `ReturnReasonController#create` 的实现；「名称快照」来自 `PortalReturnController#apply`。种子原因的数量随 `sql/data.sql`（某次快照为 4 条）变化，所以用例断的是「≥ 4」而不是「等于 4」。
