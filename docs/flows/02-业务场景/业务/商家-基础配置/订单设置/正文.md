## 订单设置（order setting / global row）

这一页只有两个数字：发货后 N 天自动确认收货（`autoConfirmDays`）与下单后 N 分钟未付款自动关闭订单（`autoCloseMinutes`），加一个「保存」。它是全局配置而不是策略列表：`PUT /admin/order-setting` 是纯 upsert，有那一行就改它、没有就插一条，永远不出现第二条 —— 「保存」的语义是「把全系统的规则改成这个」，不是「新增一条规则」，把它当列表理解就会以为多保存几次能多出几条来。

服务端零校验：`update` 不校验范围、不校验空，连影响行数都刻意不查（0 行只可能是那一行刚好被并发删掉，下次 GET 或 PUT 会自动插回；报 409 反而会让「改个自动收货天数」变成随机失败）。所以下限、取整、必填这三项全部只由表单组件当场拦住：`el-input-number` 带 `min=1`、`precision=0`，填 0 或负数失焦后变成 1，而且不弹提示、不报错 —— 它不把输入当错误，只是不允许低于下限；3.7 会被收成 4，所以「半天」这种需求在这一页表达不出来；字母进不去，`type=number` 直接吞掉非数字字符、框变空，然后失焦时按必填抱怨。

闭环还没接上：全仓的定时任务只有两个 —— 库存展示缓存回写（`StockCacheRefresher`）与审核策略的调度（`AuditScheduleJob`），没有任何任务读这两个数字去关单或确认收货。所以这一页是「配置生效在存储与回显层面」，不是「到期就会自动处理」。

**验证**　`订单设置.spec.js`：1 条用例、9 步，把两个数字框的边界全走一遍。页面回显的两个值恰好等于只读接口读到的值、都不小于 1，两句说明文案在页面上；改成 15 / 45 保存 → 提示成功 → 刷新页面仍是 15 / 45 → 接口复核也是 15 / 45 且 `id === 1`，证明是覆盖同一行；填 0、填 −5 → 输入框里都变成 1，且没有任何校验错误提示；填 3.7 → 变 4；输入字母 → 框为空，失焦后提示「请输入自动收货天数」；空着点保存 → 仍是必填提示，再查接口后端还是 15 / 45，证明这一步真的没提交；恢复基线值并保存 → 页面与后端都回到基线；分钟框同样受下限约束（0 → 1），不只测天数那一半。用例在 `beforeEach` 记下基线、`afterEach` 无论成败都恢复 —— 全局单行配置，谁都不该被它改脏。

**边界**　换个入口把负数或空值写进去，后端照收：这一页的合法性完全由表单组件撑住，不是库级约束。两个数字目前只被存下和回显，别对外说过期会自动关单或自动确认收货。它是覆盖语义，任何人保存都影响所有人，没有按店铺、按仓库的差异化。页面没有前端缓存兜底，值的来源只有那一条记录，所以「保存成功但显示没变」只可能是刷新前读了旧响应。
