**后台建单不是"买家下单的另一个按钮"，是另一条路** —— 买家侧是"购物车 → 结算 → 支付 → 建单"，明细来自购物车、金额来自明细；后台是客服替买家建单，**不走支付、不走购物车，金额只认明细**。所以它必须允许明细为空、总额为 0（单先落下来，货后面再补），也必须在"什么状态能建""钱和库存怎么算"上比买家侧更硬。

## 场景

入口是管理端建单接口（`POST /admin/orders`，请求体 `{order, items}`）。典型用法是客服代客下单：买家电话里报地址，客服先把这单建在系统里，明细与金额后面再补 —— 这就是"空明细路径"存在的业务理由。

同一条路径上还有四个必须收敛的点，因为它们都能造出**真实流程产不出的组合**：

- 初始状态只允许 0 待付款 / 1 已付款 / 7 待审核 —— 其余（8 待发货、3 已完成、6 已退款…）各自都需要前置事实（包裹、退款流水、审核不通过）；
- `split_status` 强制 0（建单这一刻一张包裹都没有）；
- 0 / 7 两个状态清掉支付痕迹（`payment_time = null`、`pay_type = 0`）；
- 明细为空 → 总额 0；有明细 → 总额 = 单价 × 件数（**请求体里传的金额一律不算数**）。

## 撑不住的时候

两个层次的坑，都是"能落库、但落进去就再也解释不清"：

**① 组合层面的脏数据**：请求体的 `status`、`split_status`、`total_amount` 原来原样落库，于是能建出"8 待发货却零包裹""已拆单却零包裹""待付款却有支付时间""总金额 999、0 条明细"。这些组合一旦进库，之后所有按状态聚合的报表、所有对账口径都要为它开例外 —— 而它们永远不会被业务流程产出，所以永远不会有第二次。

**② 库存净增（真出过）**：后台建单原来**不扣库存**，但"审核不通过""取消包裹""退货退款"三个入口都会按明细**回补**。这单一旦走到其中任何一个，库存就净增一次 —— 实测把一个规格从 47 补到 49。这是"只减不扣"的单向缺口，比前一类更贵：它直接改了账实。

## 改了什么

① **建单即扣库存 + 记一行 `ORDER_CREATE` 台账**，与买家下单**同一套**口径（`StockLedgerContext` 声明归属 → 记账后动库存）。扣不动就抛中文原因 → 整笔事务回滚（订单、明细、已扣库存、台账一起没了），不会出现"库存扣了订单没建"或"订单建了库存没扣"。明细为空时不扣、也不记账（没有明细就没有库存变动，后续回补同样为空）。

② **状态白名单 fail-closed**：只放行 0/1/7，其余给中文原因拒单 —— 不是"传什么落什么"。

③ **`split_status` 强制 0**、**0/7 清支付痕迹**：把"任何真实流程都产不出的组合"从入口堵掉。

④ **金额以明细为准**：有明细就按 `单价 × 件数` 重算并覆盖请求体；没有明细就归零。数量顺手规整成 ≥1 的确定值（后面扣库存和写明细必须用同一个数，不能一边当 1、一边落 null）。

⑤ **存在性校验的顺序**：先会员（否则撞外键只会回一句"数据处理失败"）、再规格（否则"规格 999999 不存在"会被说成"库存不足只剩 0 件"，排查方向全错）。

## 凭什么证明好了

**① 能演的：UI 测试（已跑绿）+ 录屏（本轮待补，登记在「待补视频」）**

`e2e/tests/scenarios/业务/商家-履约/后台建单.spec.js`，两条用例（40 条断言），**一半走界面、一半走接口** —— 原因见「附」：空明细在建单表单里**点不出来**，所以界面负责证"这条表单路被拦住"，接口负责证"接口允许空明细但金额必须归零"。

- **用例 1「空明细建单」**：界面上只填会员与收货人、不加明细 → 点「确定」被前端拦下（提示"请至少填写一条完整的订单明细"）、弹窗不关、**库里订单总数不变**；再走接口建一张空明细单（请求体里故意塞 `totalAmount: 999`）→ 库里 **总额 0**、状态 **7 待审核**、`split_status` 0、支付时间为 NULL、`pay_type` 0、**明细 0 行**、**库存台账 0 行**、出生台账恰好 1 行；最后回到订单列表搜这张单：状态「待审核」、金额 **¥0.00**。顺带一条反证：传 `status: 8` 必须被拒且不落库。
- **用例 2「总额以明细为准」**：请求体写 `totalAmount: 999`、明细 1 条 × 2 件 → 库里总额 = **单价 × 2**（本次实测 3999.98），既不是 999 也不是明细价本身；同时桶总量**减 2**、`stock_ledger` **恰好 1 行**且原因码是 `ORDER_CREATE`；界面列表上的金额与库里一致。
- 两条用例都在 finally 里删掉自己造的订单（明细 / 台账 / 订单本体），并把用例 2 扣掉的库存按桶补回，所以连跑多轮不污染库。

## 附：口径与边界

- **空明细这条路径只能从接口进**：后台建单表单在提交前就拦了空明细（`if (!isEdit && (!form.items.length || …)) ElMessage.warning('请至少填写一条完整的订单明细…')`），后端注释也明写"这条路径只对直连 API 存在"（MCP 的 `create_order` 还有 zod 要求 items 非空）。所以本页的 UI 测试**不假装**"界面上能建空单" —— 那条断言只会变成假绿。
- **「再加明细 → 总额重算」在现有代码里没有入口**：`PUT /admin/orders/{id}` 收的是订单实体（没有 items 字段），而且 `body.setStatus(null)`（状态也不许从这里改）；后台编辑弹窗同样不渲染明细表、提交不带明细。所以用例改成**同一口径的对照组**：请求体塞 999、明细分文给出 → 库里必须是 `单价 × 2`。这比"再加明细"更直接地证明了"金额只认明细"。
- **初始状态白名单只放行 0/1/7**：1 已付款不是"流程产不出"（退货被拒且无包裹时订单会落回 1，发货的 1→2 直发通道正是为它保留的）。
- **建单扣库存与"审核不通过回补"必须成对**：只补不扣就是库存净增（47→49 那次）。所以这条路径的库存动作不是"顺手加的"，是补上原来缺的那一半。
- **未复测**：47→49 是历史实测记录（要复测得把扣库存这段临时去掉，本轮不碰业务代码）；"空明细 → 库存台账 0 行 / 出生台账 1 行"是本次 UI 测试的库断言。
