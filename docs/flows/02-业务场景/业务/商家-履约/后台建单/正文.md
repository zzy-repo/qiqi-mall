## 后台建单（admin order create）

后台建单不是「买家下单的另一个按钮」，是另一条路：买家侧是购物车 → 结算 → 支付 → 建单，明细来自购物车、金额来自明细；`POST /admin/orders` 是客服替买家建单，不走支付、不走购物车，金额只认明细。所以它必须允许明细为空、总额 0 —— 买家电话里报个地址，单先落下来，货后面再补。

四个必须收敛的点，因为它们都能造出真实流程产不出的组合：初始状态只允许 0 待付款、1 已付款、7 待审核（8 待发货、3 已完成、6 已退款各自都需要前置事实）；`split_status` 强制 0（建单这一刻一张包裹都没有）；0 与 7 两个状态清掉支付痕迹（`payment_time = null`、`pay_type = 0`）；金额以明细为准 —— 有明细就按「单价 × 件数」重算并覆盖请求体，没有明细就归零，数量顺手规整成不小于 1 的确定值（扣库存与写明细必须用同一个数，不能一边当 1、一边落 `null`）。

建单即扣库存并记一行 `ORDER_CREATE` 台账，与买家下单同一套口径：先 `StockLedgerContext` 声明归属，记账后动库存；扣不动就抛中文原因、整笔事务回滚（订单、明细、已扣库存、台账一起没了），不会出现「库存扣了订单没建」或反过来。明细为空时不扣也不记账 —— 没有明细就没有库存变动，后续回补同样为空。这一条是补上的缺口：原来后台建单不扣库存，而「审核不通过」「取消包裹」「退货退款」三个入口都会按明细回补，这单一旦走到其中任一，库存就净增一次，上轮实测把一个规格从 47 补到 49。存在性校验的顺序也有讲究：先查会员（否则撞外键只会回一句「数据处理失败」），再查规格（否则「规格 999999 不存在」会被说成「库存不足只剩 0 件」，排查方向全错）。

**验证**　`后台建单.spec.js`：2 条用例、40 处断言。用例一「空明细建单」：界面只填会员与收货人、不加明细 → 点「确定」被前端拦下（提示「请至少填写一条完整的订单明细」）、弹窗不关、库里订单总数不变；再走接口建一张空明细单，请求体里故意塞 `totalAmount: 999` → 库里总额 0、状态 7 待审核、`split_status` 0、支付时间 `NULL`、`pay_type` 0、明细 0 行、库存台账 0 行、出生台账恰好 1 行；回订单列表搜这张单，状态「待审核」、金额 ¥0.00。顺带一条反证：传 `status: 8` 必须被拒且不落库。用例二「总额以明细为准」：请求体写 `totalAmount: 999`、明细 1 条 × 2 件 → 库里总额等于「单价 × 2」（本次实测 3999.98），既不是 999 也不是明细单价本身；同时桶总量减 2、`stock_ledger` 恰好 1 行且原因码是 `ORDER_CREATE`；界面列表金额与库里一致。两条用例都在 finally 里删掉自己造的订单（明细、台账、订单本体），并把用例二扣掉的库存按桶补回。

**边界**　一半走界面、一半走接口不是捷径：空明细在建单表单里点不出来，所以界面负责证「这条表单路被拦住」，接口负责证「接口允许空明细但金额必须归零」，两件事各归各位。明细为空的单没有库存变动，后续回补自然也为空，所以「空单」不会在别处变成一笔库存账。初始状态白名单只有 0、1、7，「已拆单却零包裹」「待付款却有支付时间」这类组合从入口就堵掉了，不必等报表发现异常。`status` 与 `split_status` 都是原样落库的字段，改口径要动这里，不要指望业务侧兜。
