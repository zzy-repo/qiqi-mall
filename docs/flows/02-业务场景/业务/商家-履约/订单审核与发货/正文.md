## 订单审核与发货（audit pass / delivery aggregate）

审核不是一个勾，是一次分岔：通过就自动拆出待下发包裹、订单变待发货；不通过就关单、把下单时扣掉的库存补回去，而且一张发货单都不生成 —— 不让仓库白拣一趟。

只有待审核能审：`audit-pass` 与 `audit-reject` 都先查 `status != 7`，分别回「只有待审核订单可以审核通过 / 审核不通过」；预演也先过同一道守卫，不许预演说「能通过」而后真做被拒。审核与发货都不再动库存 —— 库存只在下单那一刻扣一次：通过只做状态 7 → 8 加拆单；不通过走 `restoreStock` 并记台账（`REASON_AUDIT_REJECT`），归属声明加幂等键保证「同一订单同一规格只补一次」。这条幂等不是多余的：回补入口有三个（审核不通过、取消包裹、退货退款），裸写 `stock = stock + N` 叠加起来就会给同一件货补第二次。

状态不是谁手动改的，是跟着包裹聚合出来的：一张包裹出库 → 9 部分发货，全部出库 → 2 已发货，全部签收 → 3 已完成，审核通过只是给了它一个起点 8 待发货。状态写入 fail-closed：`auditPass` 改状态走「同一条 `UPDATE` 里带 `status_seq` 自增与 `version` 自增」，影响 0 行说明读到 7 之后、写回之前被别人改过 → 409、整个事务回滚，绝不往下走拆单 —— 否则会留下「订单还是待审核、发货单却已生成」，这种组合只能人工对账。`/{id}/ship` 是给直发单留的旁路，接受 8 待发货与 1 已付款，但有未出库包裹时拒绝：「该订单还有包裹未出库，不能标记为已发货；请先在履约页下发并等待仓库回传出库」。新发货单是 `status=0 待下发` 加 `source=0 自动拆单`，人工改过的才变成 `source=1 人工调整`。

**验证**　`订单审核与发货.spec.js`：2 条用例。用例一（8 步）：下单后列表是「待审核」；审核通过后变「待发货」，库里恰好 1 个发货单、`status=0`、`source=0`；下发后该行变「已下发」；回传「拣货」→「已拣货」、回传「出库」→「已出库」并生出匹配 `SF\d{6,}` 的运单号；全部出库后订单 `status=2`、列表显示「已发货」；签收后 `status=3`。最后一步是这条用例的重点：审核、下发、出库、签收跑完，SKU 展示库存恰好等于「下单前 − 1」，不是 −2 也不是 −3。用例二（4 步）：审核不通过 → 订单变「已关闭」（`status=4`）、发货单 0 张、库存恰好回到下单前的值。

**边界**　库存断言必须轮询、不能读一次就断：分桶模式下 `sku.stock` 只是展示缓存，由后台任务按 `SUM(桶)` 每 250ms 回写，所以用例用 `expect.poll` 等它收敛 —— 但断言口径没放宽，仍然要求恰好等于目标值，不是 ≥ 或 ≈。用例用买家真实下单做基线，是因为要证的正是「订单侧只扣一次」这条链，源头必须是下单入口；后台建单是另一条入口。WMS 是模拟的：抽屉里那个「模拟 WMS 回传」按钮不是真仓库系统，它按真实回传的同一套事件写状态与运单。状态中文名按这套枚举读：0 待付款、1 已付款、2 已发货、3 已完成、4 已关闭、5 退款中、6 已退款、7 待审核、8 待发货、9 部分发货；多仓拆单时「部分发货」确实会出现。
