## 发货单调整（delivery draft / requirePending）

下发前后是两个不同的东西。待下发时包裹是草稿：换仓、改件数、拆分、合并、删除随便改；一点「下发」，编辑 / 拆分 / 合并 / 删除四个入口当场消失，只剩「模拟 WMS 回传」—— 货已经在仓库手上了，再改就是账实不符。

唯一的门槛写成一句文案：`DeliveryEditService#requirePending` 回「只有待下发包裹可以{编辑|拆分|合并|删除}（当前状态 N，已下发的只能取消）」。四个动作共用这一个守卫，而且预演也跑它（`?dryRun=true` 先过守卫再返回文案），所以不会出现「预演说能改、真点却被拒」。任何人工改动都把 `source` 置 1（自动拆出来是 0，人碰过是 1），并重算订单的 `split_status`，事后看列表就知道这个包裹还是不是原始方案。

三条与数量有关的规矩：件数上限是订单原件数，`assertQuantityNotExceeded` 把该订单所有未取消包裹的明细按 `orderItemId` 加总，超过订单明细的 `product_quantity` 就拒 —— 加件数不能凭空多出没买过的货；拆分出的数量不能超过该明细现有数量（「拆出数量 X 超过该明细现有数量 Y」），原包裹被全拆走时自动删掉，不留零明细的空壳；删除等于并到别处 —— 包裹里还有明细时必须指定并入哪个包裹（「该包裹还有 N 条明细，删除前请指定并入的目标包裹 targetId（等同于合并到别处）」），只有空包裹才能直接删，不让货凭空消失。合并只能与同一订单下另一个待下发包裹合并。改得动的前提是没人同时改：`delivery_order` 带 `@Version`，`markManual` 走条件更新，0 行 → 409、整笔回滚、明细改动一并撤销。

**验证**　`发货单调整.spec.js`：4 条用例。主链路九步：造一笔待审核单（同商品两个 SKU）→ 审核通过拆出 2 个待下发包裹、默认「自动拆单」→ 编辑改到新仓，行上出现「人工调整」→ 改量 2 → 1 再改回 2，库里数量与 `source=1` 跟着变 → 拆分出第 3 个包裹（也是人工调整）→ 把新包并回同仓，包裹数回到 2、被并的包裹号消失 → 删除一个还有明细的包裹，强制选并入目标后才成功、只剩 1 个 → 下发后逐个断言「编辑 / 拆分 / 合并 / 删除 / 取消」五个入口 `count = 0`，只剩回传入口可见。编辑弹窗预演失败：并发方把包裹下发后点确定 → 业务码 1、message 是服务端原话「只有待下发包裹可以编辑（当前状态 1，已下发的只能取消）」，表单仍可见、原因在表单内的错误条里、刚填的数量与仓都没被重置、确认弹窗自己收起。合并弹窗预演失败：同上，只是已选的目标包裹不被清空。并发 409 到刷新：页面拿旧 `version` 提交 → 真 HTTP 409 → 冲突弹窗（不是一闪而过的 toast）→ 点刷新 → 表单用最新一行重开、数量是并发方改后的值 → 再保存时提交的 `version` 是最新的、成功、`version` 再 +1。

**边界**　「已下发的只能取消」这句提示与入口现状有出入：按第 ⑨ 步的断言，已下发后编辑、拆分、合并、删除与取消五个入口的 `count` 全是 0，只剩回传入口 —— 文案是旧口径，入口已经先收掉了，这里如实记着，不写成「文案与实现一致」。预演不带 `version`、执行才带，所以「预演通过、执行撞 409」是正常路径而不是缺陷。并发下发在页面上没有入口（弹窗盖着，下发按钮点不到），spec 用另一个客户端触发并发，那是模拟另一个操作员，不是用接口推业务状态的捷径。空包裹可以直接删，没有明细就不需要指定并入目标，因为没有货会丢。
