## 退货处理（return audit / stock restore）

审核通过要做三件事，而且必须一起做：申请转「已通过」、订单转「已退款」并记一条退款流水（金额等于实付）、把这单买过的库存补回去。第三件最容易漏 —— 钱退了、货也回来了，库存不补账面就凭空少一件。

通过前先校验订单当前必须是 5 退款中，不是就回「只有「退款中」的订单可以审核通过为「已退款」：该订单当前是「X」，请先由买家提交退货申请把订单置为退款中(5)后再审核」。白名单只有 5，没有别的入口会把订单写成 6 —— 否则已关闭的单照样被写成已退款，钱没退、货没回、单子却显示退款完成。拒绝交给包裹聚合：`recomputeOrderStatusAfterReturnReject`（全出库回 2、部分回 9、全签收回 3、全未出库回 8），只有直发单才回 1。

三件事同一事务，带两道影响行数校验：申请行 `SET status = ?, status_seq + 1 WHERE id = ? AND status = <读到的状态>`（「待处理」写在 `WHERE` 里，不是只做一次 Java `if`），订单行带 `@Version`；任一影响 0 行 → 409 整笔回滚，不允许「申请已通过、订单没退款」，也不允许「各退一次款、各补一次库存」。回补必须记台账：先声明归属（`REASON_RETURN_REFUND` 加 `refType` / `refId` 指到这张申请）再走 `restoreStock`，重放时幂等键命中即跳过，不同入口补同一件货由数量守恒夹紧。退款流水带幂等键 `{orderSn}:REFUND:{申请id}` 并记 `origin_flow_id` 指向原支付流水 —— 谁批的、因为哪张申请、退的哪一笔钱都在库里；演示环境的流水号带 `MOCKREF` 前缀。审计只记状态与结论，不塞审核意见：`admin_audit_log.reason` 是 32 宽的原因码，意见留在 `return_apply.description` 与 `return_status_ledger.reason_detail`，塞进去会 1406 超长。

**验证**　`退货处理.spec.js`：4 条用例。通过：申请「已通过」、订单 `status=6`；退款流水恰好 1 条、金额等于实付、`tradeNo` 匹配 `^MOCKREF`、支付流水仍是那 1 条；库存等于 `stockBefore + 1`；买家售后列「退款成功」。拒绝：填理由 → 申请「已拒绝」、理由落到说明列；订单由包裹聚合推导回 2（不是常量 1），并断言「不能是 1」「不能停在 5」；退款流水 0 条、库存不变；买家售后列「退货被拒绝」。守卫：已通过的申请仍有「审核」入口（前端对任何状态都渲染），再点一次在预演阶段被拦，toast「该申请已处理，不能重复审核」，表单停在原地、原因写回表单内错误条、刚选的「拒绝」不被重置，申请状态、订单状态、退款流水条数都不变。边界用例：拒绝时把说明清空也能提交成功，库里存成空串，买家原说明被覆盖。

**边界**　拒绝后的订单状态不是常量，断言用 `aggregateOrderStatusOf(未取消包裹)`，与买家侧售后退货 spec 共用同一份实现。spec 显式防退化：先断言「出库后应留下未取消的包裹」，否则用例会退化成直发单路径，那是另一种口径。「详细说明」不是必填而是当前实现的事实：前端只校验订单、申请人、原因，后端只判 `null`，传空串会通过并覆盖买家原说明。删掉一条「待处理」申请会把订单从 5 交回包裹聚合，三个条件同时成立才回退：原状态待处理、订单当前是 5、删完不再有别的待处理申请；不硬写固定状态，否则订单会卡在 5 而没有写者能带出来。
