**通过要做三件事，而且必须一起做** —— 申请转「已通过」、订单转「已退款」并记一条退款流水（金额等于实付）、把这单买过的库存补回去。第三件最容易漏：钱退了、货也回来了，库存不补账面就凭空少一件。

## 场景

商家侧「退货申请」页（`admin-web/src/views/return-apply/index.vue`）：列表能看到 订单号 / 申请人 / 原因 / 说明 / 状态，行内「审核」。点开弹窗选「通过」或「拒绝」，说明可以改。

这条链的起点在买家侧：订单得走到「已发货」才有申请入口 → 买家提交申请 → 订单转 **5 退款中** → 商家才在这个页面看到它。审核结果回传给买家，售后列显示「退款成功」或「退货被拒绝」。

## 撑不住的时候

**① 库存回补原来是裸的 `stock = stock + N`。** 没有台账、没有幂等键。而回补入口有三个（审核不通过、取消包裹、退货退款），叠在一起就是给同一件货补第二次、第三次 —— 补了没人拦，账面净增。

**② 审核通过原来无条件写「已退款」。** 一张已经「4 已关闭」的订单照样会被写成 6 已退款：钱没退、货没回、单子却显示退款完成。这是最难查的那类错账 —— 状态看着是对的。

**③ 拒绝原来无条件硬写「已付款」。** 订单的包裹可能已经出库甚至签收，硬写就造出「已付款却挂着已签收包裹」的分叉，之后任何一次包裹回传按子单重新聚合又会把它改回 2/9 —— 一条真实的状态倒退序列。

## 改了什么

① **通过前先校验订单当前必须是 5 退款中**：不是就回「只有「退款中」的订单可以审核通过为「已退款」：该订单当前是「X」，请先由买家提交退货申请把订单置为退款中(5)后再审核」。白名单只有 5 —— 代码里没有别的入口会把订单写成 6。

② **拒绝交给包裹聚合**：有在途包裹就调 `recomputeOrderStatusAfterReturnReject`（都出库 → 2，部分出库 → 9，都签收 → 3，一张都没出库 → 8）；只有**一张包裹都没有的直发单**才回 1 已付款。

③ **三件事同一个事务，两道影响行数闸门**：申请行 `SET status=?, status_seq+1 WHERE id=? AND status=<读到的状态>`（「待处理」这条守卫写在 WHERE 里，不是只做一次 Java if）；订单行带 `@Version`。任一 0 行 → 409 **整笔回滚**。绝不允许出现「申请已通过、订单没退款」，也不允许「各退一次款、各补一次库存」。

④ **回补必须记台账**：归属声明（`REASON_RETURN_REFUND` + `refType/refId` 指到这张退货申请）后走 `restoreStock`，同一张申请被重放时幂等键命中即跳过；不同入口补同一件货则由数量守恒夹紧。

⑤ **退款流水带幂等键** `{orderSn}:REFUND:{申请id}`，并记 `origin_flow_id` = 原支付流水 —— 「谁批的、因为哪张申请、退的是哪一笔钱」三件事都在库里。演示环境的退款流水号带 `MOCKREF` 前缀。

⑥ **审计只记状态与结论，不塞审核意见**：`admin_audit_log.reason` 是 VARCHAR(32) 的原因码，审核意见是自由文本（留在 `return_apply.description` 与 `return_status_ledger.reason_detail`）—— 塞进去会 1406 数据超长，把整笔审核回滚。

## 凭什么证明好了

`e2e/tests/scenarios/业务/商家-履约/退货处理.spec.js`，4 条用例、4 段录屏：

- **通过**：申请显示「已通过」，订单 `status=6`；退款流水**恰好 1 条**、金额等于订单实付、`tradeNo` 匹配 `^MOCKREF`、支付流水仍是那 1 条没被复制；库存 `stockBefore + 1`；买家售后列「退款成功」、买家与后台订单状态都是「已退款」。
- **拒绝**：填拒绝理由 → 申请「已拒绝」、理由落到说明列；订单由包裹聚合推导回 2 已发货（**不是常量 1**），并额外断言「不能是 1」「不能停在 5」；退款流水 0 条、库存不变；买家售后列「退货被拒绝」。
- **守卫**：已通过的申请仍有「审核」入口（前端对任何状态都渲染，没有状态守卫），再点一次 → 在**预演阶段**就被服务端拦下，toast「该申请已处理，不能重复审核」，表单停在原地、原因写回表单内的错误条、刚选的「拒绝」不被重置；申请状态、订单状态、退款流水条数都不变。
- **边界**：拒绝时把说明清空也能提交成功，库里说明存成空串 —— **买家原说明被覆盖**。

## 附：口径与边界

- **拒绝后的订单状态不是常量**：断言用的是 `aggregateOrderStatusOf(未取消包裹)`，与买家侧售后退货 spec 共用同一份实现，不在这里另写一套。
- **spec 显式防退化**：先断言「前置步骤出库后应留下未取消的包裹」，否则这条用例会悄悄退化成直发单路径，而直发单路径回到 1 是另一种口径 —— 那样就测错了对象。
- **「详细说明」不是必填，是当前实现的事实**：前端只校验订单 / 申请人 / 原因，后端只判 `null`。所以传空串会通过，并且把买家原说明覆盖成空。这不是「应该」，所以放在这里说清，而不是写成一条设计。
- **删掉一条「待处理」申请会把订单从 5 退款中交回包裹聚合**：三个条件同时成立才回退（原状态是待处理、订单当前是 5、删完不再有别的待处理申请），且不硬写某个固定状态 —— 否则订单会卡在 5，而没有任何写者能把它带出来。
- **本页数字出处**：所有守卫与文案来自 `ReturnApplyController#update`；`5 → 6` 的唯一进入条件与「只有退款中可审核通过」的判断在同一方法里；`MOCKREF` 前缀与幂等键来自 `PaymentRecordService`；状态中文名来自该控制器的 `statusText`。用例里的「+1 件」「恰好 1 条退款流水」是那一轮实测的数量。
