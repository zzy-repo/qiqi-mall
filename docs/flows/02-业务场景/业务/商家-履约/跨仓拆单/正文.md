## 跨仓拆单（split plan / warehouse inventory）

拆不拆不是后台挑的，是货在哪儿决定的：商品分散在两个仓就拆两个包裹，每个只装本仓能发的货；都在同一个仓就一个包裹、不拆。`SplitOrderService` 按 `inventory` 的分仓库存把订单明细归到仓库，产出 `[{warehouseId, warehouseName, items}]`；预演调 `preview()` 只算不落库，真做才 `split()` 建发货单 —— 同一份 planner，所以预演说的和真做的不会不一致。

方案渲染在统一确认框的 details 区（没有独立的「查看拆单方案」按钮了），写着「将拆成 N 个包裹、每个从哪个仓发、几条明细」。点「取消」只关前端弹窗、一个请求都不发；预演走 `POST /{id}/split-preview` 或 `?dryRun=true`，两者都在 `status != 7` 处先拒。兜底有话说：某个规格没有分仓库存记录时按默认仓处理，预演文案里明写「该规格未配置分仓库存，已按默认仓「X」处理」，不能让商家审完才发现货是从哪个仓发的；一个启用的仓都没有时直接抛「没有启用的仓库（warehouse.status=1），无法确定默认发货仓」，不会悄悄归到某个停用仓上。同仓不拆，但走的是完全同一条路 —— 只出 1 个包裹，不为「没意义的情况」写第二套逻辑，所以单仓单也能完整演一遍。列表上那一列标「N 个包裹」，点它直接打开订单抽屉看包裹表：包裹是订单状态下钻的第一层。

**验证**　`跨仓拆单.spec.js`：2 条用例。用例一（跨仓，5 步）：买家下单两个不同 SKU（分别落在两个仓）→ 点「审核通过」读 details 区的方案 → 恰好 2 个包裹且两个仓名不同 → 此刻查库，发货单数必须还是 0、订单仍是「待审核」（证明预演没落库）→ 再点同一个按钮确认执行 → 订单变「待发货」，库里 2 个发货单、`warehouseId` 两个不同、都是 `status=0`、`source=0`、每个都有明细 → 列表显示「2 个包裹」、抽屉里正好 2 行、默认都是「自动拆单」。用例二（单仓，4 步）：同一个 SKU 下单 → 预演就是 1 个包裹 → 确认后只生成 1 个发货单、`source=0` → 标签「1 个包裹」。

**边界**　预演的「取消」不发请求是前端行为，弹窗只关、不进任何接口 —— 这一点让「预演是 dry-run」在界面上就能被证明：断的是库，不是按钮文案。拆单读的是分仓库存 `inventory`，不是 `sku.stock` 总量，总量只用于展示。默认仓兜底取「第一个启用的仓」。拆单发生在审核通过的事务里，状态 7 → 8 与建发货单同生共死，所以不会出现「订单还是待审核、发货单却已经生成」。仓库 id 与名字来自 `sql/data.sql` 的种子快照（深圳仓 1、杭州仓 2），用例里「2 个包裹 / 2 个仓」是那次造数的结果，随商品的分仓库存配置变化，不是全局常量。
