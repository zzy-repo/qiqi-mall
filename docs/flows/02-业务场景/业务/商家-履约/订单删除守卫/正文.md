**删单不是点一下就没了，是先查三件事** —— 有物流记录、有退货申请、包裹已出库，任何一条成立就拒删，并告诉你怎么走：先去作废物流、先完成签收，或者干脆把订单关掉。这三样是货和钱的凭据，跟着订单一起删掉，账就对不上了。

## 场景

订单列表行内「删除」。点下去先走统一高危弹窗的**预演**（`DELETE /admin/orders/{id}?dryRun=true`）：弹窗里写清「将删除订单 X（id=N）」，确认后才真删。被守卫拦下时，预演阶段就失败、弹窗自己收起 —— 你根本没机会点「确认执行」。

## 撑不住的时候

拒删的价值不在那一句提示，在**被引用的数据一条都没少**。运单号是「货在哪儿」的唯一凭据，退货申请是退款与对账的证据，已出库的包裹意味着货真的离开了仓库。这些被删单顺手带走，事后对不上账，而且补不回来 —— 页面刷新一下就看不出差别了，所以这件事只能靠库上的事实证明，不能靠界面。

另一个更贵的缺口：**清理支付流水原来只留一条应用日志**。`log.warn` 会轮转、会随容器消失、台账页查不到，所以「这单删之前收过几次钱、每次多少钱」在库里没有凭证。现在清理时会先写一条 `PAYMENT_PURGE` 台账行，再删流水。

## 改了什么

① **三道守卫**（`OrderPurgeService#blockReason`，预演与真删共用同一份）：
- 有物流记录 → 「该订单 SN（id=N）有 K 条物流记录（运单号 X、Y），无法删除；可在履约页先作废物流，或改为关闭订单。」
- 有退货申请 → 同句式 + 「；退货申请是退款与对账的证据，不能随订单一并删除，请改为关闭订单。」
- 包裹已出库（未取消且 `status >= 3`）→ 同句式 + 「；请先完成签收或改为关闭订单。」
- 三条**同时成立时一次说清全部代价**（「有 A和 B和 C」），不让你修一条再被拒一次。
- 只成立「已出库」这一条时走专属文案：「该订单有 N 个包裹已出库（货已离开仓库），不能删除；请先完成签收或改为关闭订单〔订单 SN，id=N〕」—— 这一格最容易被误判成「能删」。

② **预演 = 真删，是两道不是一道**：`purge()` 内部还会再调一次 `blockReason` 做 fail-closed。所以「预演说不能删，真删一定不能删」不是约定，是实现。

③ **删的顺序**：先按库存台账净额回补库存（净额是负数才补，已经补过的按守恒夹紧，一件都不多补）并清台账，再按依赖逐层显式删 —— 物流 → 退货申请 → 发货单明细 → 发货单 → 订单明细 → 支付流水 → 订单。每一层都核对「应删 N 行、实删 N 行」，对不上就抛。

④ **支付流水：先记账，再动手**。清理时先在 `admin_audit_log` 写一条 `PAYMENT_PURGE` 台账行（含订单号 / 条数 / 金额合计 / 每条的流水号+类型+金额，逐条快照在 `before_json` 里），再 DELETE，两者同一事务：审计写失败 → 整笔回滚、流水一行不动；DELETE 影响行数不符 → 审计也一起回滚。所以「有这条台账行」恰好等价于「这次清理真的提交了」，不会留下「审计说删了 3 条、流水其实还在」的假凭证。

⑤ **删单这一笔在台账里恰好两行**：`ORDER_DELETE` + `PAYMENT_PURGE`。

## 凭什么证明好了

`e2e/tests/scenarios/业务/商家-履约/订单删除守卫.spec.js`，4 条用例：

- **用例一（对照）干净订单可以删干净**：后台建一笔待审核单 → 先确认前提事实（发货单 0 / 物流 0 / 退货 0 / 已出库 0 / 明细 1 / 台账净额 = −2）→ 预演「将删除订单」→ 确认执行 → toast「订单已删除」→ 列表里这行消失 → 库里订单 0 行、明细 0、库存台账 0、发货单 0、物流 0、支付流水 0 → 库存按台账净额 **+2** 回补。
- **用例二 有物流记录**：下发 → 出库回传后库里有 1 条物流记录（运单号 `SF…`）、包裹已出库 → 点删除**在预演阶段就被拒**，预演请求本身 HTTP 200、业务码 1，toast 是「预演失败：」+ 后端原话，且**逐字等于** `blockReason` 拼出的那句 → 订单 1 行、物流 1 行、运单号一字未变、包裹还在、抽屉里仍显示「已出库」 → 再预演一次逐字相同 → **不带 dryRun 真删一次也逐字相同被拒**，数据一条没少。

- **用例四 已出库但物流缺行**：用专属文案、**不含「物流记录」**，订单与包裹都还在，包裹状态仍是已出库。

## 附：口径与边界

- **「预演与真删同口径」的唯一直接证据是不带 dryRun 再发一次**：这一步在 UI 上没有入口（前端预演失败就停了），只能从接口触发。所以它验的正是后端 `purge()` 内部那道 fail-closed 守卫。
- **用例四为什么要直接改库**：真实链路里「出库回传」必然同时写运单（`DeliveryFlowService` 出库事件里 `saveLogisticsIfAbsent`），所以「已出库却没有物流行」只会由**历史数据缺行**造成 —— 而那正是这条守卫最容易被误判的一格。spec 只推进自己造的那一行，finally 里连订单一起清掉。
- **清理不裸写库存**：spec 的 finally 只做一件事 —— 断掉守卫依据（删物流行 / 删退货申请 / 把包裹状态回落到未出库），然后把删除交给**真实接口**，让 `purge()` 自己回补库存、清台账。自己实现一遍就是两份口径，早晚对不上，而且裸 SQL 删订单会把「扣了库存却没补」的窟窿留在库里。
- **`PAYMENT_PURGE` 的幂等不靠业务键**：审计的幂等键由 `request_id` 派生，绝不由 `order_sn` 派生；「重复删单不多写」靠业务前置条件 —— 流水数为 0 时一行不写，第二次删同一张单在「订单不存在」处就返回，连 `purge` 都进不去。
- **本页数字出处**：三条守卫文案与判据来自 `OrderPurgeService#blockReason`；删除分层顺序来自 `purge()` 的步骤编号；`PAYMENT_PURGE` 的先记账后删除与两行台账（`ORDER_DELETE` + `PAYMENT_PURGE`）来自 `purgePaymentRecords` 与它的集成测试注释；「−2 / +2」是那一轮造单 2 件的实测数，不是全局常量。
