## 订单删除守卫（order purge guard）

删单先查三件事（`OrderPurgeService#blockReason`）：有物流记录、有退货申请、包裹已出库（未取消且 `status >= 3`）。任一成立就拒，并说明怎么走：先作废物流、先完成签收，或者把订单关掉。运单号是「货在哪儿」的唯一凭据，退货申请是退款与对账的证据，已出库的包裹意味着货真离开了仓库；这些被顺手带走，事后对不上账，而刷新一下看不出差别，只能靠库上的事实证明。

三条同时成立时一次说清全部代价（「有 A 和 B 和 C」），不让人修一条被拒两次；只成立「已出库」这一条时走专属文案：「该订单有 N 个包裹已出库（货已离开仓库），不能删除；请先完成签收或改为关闭订单」。预演与真删是两道不是一道：`purge()` 内部还会再调一次 `blockReason` 做 fail-closed，「预演说不能删、真删一定不能删」是实现而不是约定。

真删的顺序：先按库存台账净额回补（净额为负才补，已补过的按守恒夹紧，一件不多补）并清台账，再按依赖逐层显式删 —— 物流 → 退货申请 → 发货单明细 → 发货单 → 订单明细 → 支付流水 → 订单，每层核对「应删 N 行、实删 N 行」，对不上就抛。支付流水先记账再动手：先在 `admin_audit_log` 写一条 `PAYMENT_PURGE`（订单号、条数、金额合计，逐条快照在 `before_json`），再 `DELETE`，两者同一事务：审计写失败整笔回滚、流水一行不动，`DELETE` 行数不符则审计一起回滚。所以「有这条台账行」等价于「这次清理真提交了」。删单这一笔在台账里恰好两行：`ORDER_DELETE` 加 `PAYMENT_PURGE`。

**验证**　`订单删除守卫.spec.js`：4 条用例。用例一（对照）：后台建一笔待审核单 → 确认前提事实（发货单、物流、退货、已出库都 0，明细 1，台账净额 −2）→ 预演「将删除订单」→ 确认执行 → toast「订单已删除」、列表行消失 → 库里订单、明细、库存台账、发货单、物流、支付流水全 0 → 库存按净额 +2 回补。用例二（有物流）：下发并出库回传后 1 条物流记录、包裹已出库 → 删除在预演阶段被拒：预演请求 HTTP 200 加业务码 1，toast 是「预演失败：」加后端原话且逐字等于 `blockReason` → 订单 1 行、物流 1 行、运单号一字未变、抽屉仍显示「已出库」→ 再预演一次逐字相同 → 不带 dryRun 真删一次也逐字相同被拒。用例三（有退货申请）：同样被拒，申请仍在且仍「待处理」，抽屉里那块不是空状态。用例四（已出库但物流缺行）：走专属文案、不含「物流记录」，订单与包裹都在。

**边界**　「预演与真删同口径」的唯一直接证据是不带 dryRun 再发一次：UI 上没有这个入口（预演失败就停了），只能从接口触发，验的正是 `purge()` 内部那道 fail-closed。用例四为什么要直接改库：真实链路里出库回传必然同时写运单，「已出库却没有物流行」只会由历史数据缺行造成 —— 那正是最容易被误判的一格。清理不裸写库存：用例的 finally 只断掉守卫依据（删物流行、删退货申请、把包裹状态回落到未出库），删除交给真实接口，让 `purge()` 自己回补库存、清台账；自己实现一遍就是两份口径，裸 SQL 删订单还会留下「扣了库存却没补」的窟窿。`PAYMENT_PURGE` 的幂等不靠业务键：审计幂等键由 `request_id` 派生、绝不由 `order_sn` 派生，「重复删单不多写」靠业务前置条件 —— 流水为 0 时一行不写，第二次删同一张单在「订单不存在」处就返回。`−2` 与 `+2` 是那一轮造单 2 件的实测数。
