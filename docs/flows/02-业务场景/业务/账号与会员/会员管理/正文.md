## 会员管理（member / admin side）

后台能建会员，但建出来的号登不进商城：新增弹窗里没有密码字段，`member.password` 落库是空串，登录遇到空密码直接判「用户名或密码错误」。真正能登录的账号只有 C 端注册这一条路。这一页的价值不在「管账号」，在查得清：列表行内四个入口 —— 收货地址、购物车、编辑、删除（危险色排在最后），两个子页是独立路由，只看得到这一个会员的数据，买家反馈地址填错了，点进地址子页直接改，不用问订单号。

删除先弹全站统一的高危确认框（与另外 13 个高危操作同一套），框里写明「地址与购物车一并删除、不可恢复」。拦截不是业务守卫算出来的，是外键：`MemberController.delete` 就一句 `removeById`，没有「数一下这人名下有多少订单」的逻辑，真正拦住它的是 `order.member_id` 与 `return_apply.member_id` 两个普通外键（NO ACTION），异常被统一翻成「数据被其它记录引用，无法删除（请先处理关联的物流、退货、明细等记录）」—— 这句是通用提示，不会写明是几笔订单还是几条退货。而「地址与购物车一并删掉」是真的：这两张表的 `member_id` 都是 `ON DELETE CASCADE`，空账号删掉时子表跟着没。

其余规矩：登录名唯一（`uk_member_username`），重名后端拒、页面红 toast「已存在相同记录」、弹窗不关；必填前端拦（「请输入登录名」）；改昵称不影响登录，登录认的是 `username`；禁用只回「用户名或密码错误」，不提示「账号已被禁用」，代价是本人也不知道是停用还是密码错；密码只写不读，接口从不返回 `password` 字段、库里存 `BCrypt`；超长就地截断（登录名与昵称 50、手机号 20），不报错也不拦保存；编辑必须带 `version`，缺 → 400、被别人改过 → 409，`status` 也是并发敏感字段 —— 禁用被覆盖等于有人被错误放行。

**验证**　`会员管理.spec.js`：4 条用例。列表与地址子页：C 端注册的会员在后台列表可见且默认「启用」；地址子页标题带登录名、行数与该会员地址数一致；另一个没建过地址的会员子页显示「暂无数据」，看不到别人的地址；聚合详情接口里这个会员 `addresses` 有 1 条、`carts` 为 0。购物车子页同理，只看得到自己的购物车。新增到删除一整条：新增弹窗**没有**密码字段（断言 `false`）；重名 toast「已存在相同记录」且行数不变；空登录名提示「请输入登录名」；编辑后昵称列逐格比对只剩新昵称；超长截断到 50 与 20 且服务端也一致；禁用后 `status=0`；删完列表行数回到新增前、接口也查不到。账号可用性五步：C 端注册 → 后台可见并可改昵称 → C 端用原密码仍能登录且看到改后的昵称 → 后台禁用后登录被拒、停在 `/login` → 恢复启用后又能登录。

**边界**　后台建的号登不进商城是现状而不是缺陷：没有密码字段、落库空串，要能登录只有 C 端注册这一条路。删除的拦截来自外键，不是业务判断，所以提示是通用的，也不会报出具体引用数。超长截断是静默的：不报错、不拦保存，只把内容缩到列宽。编辑带版本号的必要性在 `status` 上最明显 —— 两个人同时改，一个禁用一个启用，若允许无版本更新，被覆盖的那次就成了一次静默放行。
