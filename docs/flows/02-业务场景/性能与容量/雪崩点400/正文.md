## 雪崩点（saturation point / open-loop load）

量法决定结论：开环定速阶梯，延迟起点取计划到达时刻而不是发出时刻，否则慢响应会被「少发请求」掩盖（coordinated omission）。判据事前写定：p99 相对上一档翻倍、绝对值超过 200ms、且下一档不回落；错误率 >1%；GC 占比 >20%。

越过阈值之后，到达率继续上升而吞吐钉住，在途请求数按 Little 定律（L = λW）随延迟上升，排队时间线性恶化，再往上开始丢弃请求 —— 生成器调度落后超过 3s 的请求被标 saturated 丢弃，属供不上货。

定位不靠猜：内存、CPU、MySQL、连接池四个直觉逐个打掉。卡在哪用栈说话：`SIGQUIT`（`kill -3`）让 JVM 把 dump 打到容器 stdout，镜像是 JRE、没有 `jcmd` / `jstack`。连接池只改一个环境变量（`HIKARI_POOL` → `SPRING_DATASOURCE_HIKARI_MAXIMUM_POOL_SIZE`），生效证据是数连接：pool=10 时每实例 10 条、pool=30 时 30 条；加连接不改变下游速度，只把更多请求放进同一个队列。

**效果**　口径：开环定速阶梯 50→500 rps、每档 75s、预热 60s、独占窗口、同一镜像同一配置，报 ok/s。350 档 349.9 / p50 66.9ms / p99 322.6ms / 丢弃 0；400 档 399.9 / 1697.2 / 4477.1 / 0；450 档 404.6 / 4937.1 / 7084.4 / 3292；500 档 410.7 / 5255.0 / 7751.1 / 6796；错误率 0.01%~0.03%。p99 由 322.6 跳到 4477.1ms（×13.9）且不回落，p50 由 67ms 跳到 1697ms，整条分布一起塌；450 / 500 两档 λ 仍涨 11%~12.5%，ok/s 只涨 1.2%~1.5%，吞吐钉在 405~415。证伪数据：堆 86MB / 上限 11.5GB、GC 1.2%、0 次 Full GC、`memory.events` 三项全 0；容器 0.72 核、客户端 17%~22%；`Threads_running` 10~14、无死锁、行锁等待约 180/s；池 10 / 15 / 20 不可区分、30 低 3%~5%（450 档 400.4 / 398.1 / 404.7 / 390.5；四个池子拐区起点都是 400）。450 档 SIGQUIT：真跑 SQL 的线程 9~10 → 24~28，等连接 190/202 → 117~166；SQL/s 在所有配置与饱和档钉在 7,300~7,830（每单约 19 条）。复现性：400 档 p99 三轮 4477 / 3130（×11.1）/ 3960ms，300 / 350 / 400 三档 ok/s 差 ≤0.01%。

**边界**　400 是这套配置的产物：4 核共享机、2 实例、Tomcat 200、Hikari 10、每单约 19 条 SQL、热点 SKU 占八成；换机器、换池子、换语句条数则变。线程栈只证明 190/202 个线程在排队等连接，不证明连接数是唯一限制项 —— 池子调大无收益正好说明它只是症状；只交排除法与「下一步动每单语句条数」的方向。判据①在低基线上会误报：150 档 p99 27.8 → 62.5ms（×2.25）会被判成雪崩，但绝对量健康、下一档没恶化。档内状态会累积（400 档时 order 表 20 万行），要把 350→400 定位到 ±25 rps 需每档独立 reset 并各自预热。容器没有内存上限，memcg 的 max / high 不可能触发，那一列只能证明「没 OOM」，「不是内存」靠的是 86MB 对 11.5GB 的量级差。`-Xlog:gc*` 有 <0.1%/事件开销，绝对延迟含此开销。
