**雪崩点：400 rps 之后，再加多少请求都不变成吞吐** —— 这台机器有一个可复现的到达率阈值：越过它，延迟非线性恶化、吞吐钉死。这一页交付的是**排除法**（四个直觉依次证伪），不是「真因就是某一项」。

## 场景

要做扩容决策、或者要回答「这套系统能扛多少」的人。这不是线上事故复盘，是容量账：没有这个数字，扩容只能凭感觉，SLA 只能靠祈祷。

难点在于它**没有报错**。没有 5xx、没有超时、没有限流、错误率 0.02% —— 监控大盘一片绿，只是用户开始觉得「卡」。所以「雪崩」在这套系统里的表现形式是**延迟塌陷**，不是错误率飙升。

## 撑不住的时候

口径：开环定速阶梯 50→500 rps，每档 75s、预热 60s，独占窗口，延迟起点 = **计划到达时刻**（不是发出时刻，理由见「附」）；同一镜像、同一配置；TPS 一律报 ok/s。

| 目标 λ | ok/s | p50 | p99 | 丢弃 | 错% |
| --- | --- | --- | --- | --- | --- |
| 350 | 349.9 | 66.9 ms | 322.6 ms | 0 | 0.03 |
| **400** | **399.9** | **1697.2 ms** | **4477.1 ms** | **0** | 0.02 |
| 450 | 404.6 | 4937.1 ms | 7084.4 ms | **3292** | 0.02 |
| 500 | 410.7 | 5255.0 ms | 7751.1 ms | **6796** | 0.01 |

拐点在 350→400 之间，判据是**事前写定**的（① p99 相对上一档翻倍 ② 错误率 >1% ③ GC 占比 >20%）：p99 322.6 → 4477.1ms（×13.9）且之后不回落；**p50 也从 67ms 跳到 1697ms** —— 不是「少数慢请求」，是整条分布一起塌，典型的排队饱和。

再往上就露底了：450/500 档 λ 还在涨 11%~12.5%，ok/s 只涨 1.2%~1.5%，吞吐钉在 **405~415**，同时开始丢请求（3292 / 6796，生成器调度落后 >3s 的请求被标 saturated 丢弃 —— 是**供不上货**，不是服务器拒绝）。这就是「雪崩点之后，再加多少请求都不变成吞吐」。

## 改了什么

这一页没有改业务代码 —— 它改的是**怎么量**，并顺手把一个直觉证伪掉、把下一个动作指出来。

**① 量法（机制部分，这张图就是它）**

> 本页上图就是这套推法：阶梯 → 拐点 → 饱和 → 四个直觉依次证伪 → 用线程栈说清「卡在哪」，最后一条红线是「别把症状写成真因」。

```
· 开环定速：延迟起点 = 计划到达时刻，不是发出时刻 —— 否则慢响应会被「少发请求」掩盖
· 判据事前写定（p99 翻倍 / 错误率 >1% / GC >20%），不许事后挑一个能命中的
· 没有把握时不要猜原因，用排除法：内存 → CPU → MySQL → 连接池，四个直觉逐个拿数据打掉
· 卡在哪要用栈说话：SIGQUIT（kill -3）让 JVM 自己把 thread dump 打到容器 stdout，
  镜像里是 JRE（没有 jcmd/jstack），这是**唯一不改代码**的取栈办法
```

**② 被证伪的四个直觉（每个都有具体数字）**

| 直觉 | 数据 | 结论 |
| --- | --- | --- |
| 内存不够 | after-GC 堆 86MB / 上限 11.5GB；GC 占比 1.2%；**0 次 Full GC**；`memory.events` 的 oom_kill / max / high 全 0 | 否 |
| CPU 不够 | 容器只用了 **0.72 核**（4 核机），客户端 17~22% | 否 |
| MySQL 被打爆 | 同时段 `Threads_running` 10~14、无死锁、行锁等待约 180/s | 否 |
| 连接池太小 | 见下一节：10 / 15 / 20 不可区分，30 反而更差 | 否 |

**③ 连接池 10→30 没用（只改这一个变量，不重建镜像）**

`HIKARI_POOL=30` 走环境变量 → `SPRING_DATASOURCE_HIKARI_MAXIMUM_POOL_SIZE`；生效的硬证据是数连接（`information_schema.processlist`：pool=10 时每实例 10 条，pool=30 时 30 条）。

| λ | pool10 | pool15 | pool20 | pool30 |
| --- | --- | --- | --- | --- |
| 400 | 399.9 | 399.9 | 399.9 | 393.8 |
| 420 | 403.6 | 407.7 | 406.1 | 392.9 |
| 450 | 400.4 | 398.1 | 404.7 | 390.5 |
| 拐区起点 | 400 | 400 | 400 | 400 |

池子**确实松开了**（450 档 SIGQUIT：真跑 SQL 的线程 9~10 → 24~28，等连接的线程 190/202 → 117~166），**但拐区起点和饱和点在四个池子上完全一样，没有任何右移**；30 反而低 3~5%。同时 `SQL/s` 在每一个配置、每一个饱和档上都被钉在 **7,300~7,830**（每单约 19 条 SQL）。

结论不是「连接池是真因」，而是：**加连接 = 把更多人放进下游队伍，不会让下游变快**。要动的是「每单多少条 SQL」，不是池子大小 —— 那是下一张页（`性能与容量/每单19条SQL`）。

## 附：口径与边界

- **「400」是这套配置的产物**：4 核共享机 + 2 个实例 + Tomcat max-threads 200 + Hikari 10 + 每单约 19 条 SQL + 热点 SKU 占八成。换机器、换池子、换每单 SQL 条数，这个数字就变。它不是一个可以抄到别处的常数。
- **不要把它写成「真因就是连接池」**。线程栈只证明「190/202 个线程在排队等连接」，不证明「连接数是唯一闸门」；而这套配置下把池子调大毫无收益，正好反向说明它只是**症状**。页面只交付排除法：内存 / CPU / MySQL / 连接池 四个直觉依次证伪，以及「下一步该动每单语句条数」这个方向。
- **判据①在低基线上必然误报**：150 档 p99 27.8→62.5ms（×2.25）就被机械扫描判成「雪崩」，但绝对量健康、下一档没继续恶化 —— 所以最终判据改成「×2 且 p99>200ms 且下一档不回落」。
- **档内状态会累积**：第 k 档面对前 k−1 档留下的数据（400 档时 order 表 20 万行），所以要把 350→400 精确定位到 ±25 rps，得每档独立 reset + 各自预热；本页只给到「350→400 之间」。
- **容器没有内存上限**：memcg 的 max/high 事件物理上不可能触发，所以那一列只能证明「没 OOM」，不能证明「没内存压力」——「不是内存」这个判断建立在堆 89MB vs 11.5GB 的量级差上。
- `-Xlog:gc*` 有 <0.1%/事件的观测开销，本页的绝对延迟**含这点开销**。
