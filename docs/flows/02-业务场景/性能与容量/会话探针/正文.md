**会话探针：一行参数 +10.5%** —— JDBC 连接参数 `useLocalSessionState=true` 让驱动不再每条 DML 之前问一句 `SELECT @@SESSION.transaction_read_only`：探针从 5.80 条/单掉到 0，每单语句数 18.20~18.91 → 12.22~12.70，天花板 447.6 → 494.4 ok/s（+10.5%，峰值 501.4）。**但预测的 627 没到（实测 494，低 21%）—— 这一页最值钱的就是这一节。**

## 场景

要把数据库吞吐再往上抬一档、又不想改业务代码的人。上一页（`每单19条SQL`）把画像摊开后，最刺眼的一行是：**一单 20 条语句里，7.04 条是驱动自己在问服务器「我这个会话现在是只读吗」**。它一条都不占业务语义，却吃掉 1/3 的语句预算。

于是一个很自然的想法：让驱动相信自己的本地视图，别每条语句都问一遍。Connector/J 恰好有一个开关做这件事。

## 撑不住的时候

坏环境照旧造出来（4 核共享机、Tomcat 200 / Hikari 10、热点 SKU 0.8、每档 75s + 预热 90s@378）。A 臂（`useLocalSessionState=false`，默认值）的阶梯：

| λ | A ok/s | 每单语句数 |
| ---: | ---: | ---: |
| 480 | 434.0 | 18.79 |
| 520 | 431.6 | 18.36 |
| 560 | 445.2 | 18.58 |
| 600 | **447.6** | 18.76 |

拐点在 450~480 之间：420/450 两档都还能压满目标，480 档就掉到 434（掉 3.7%），之后一路贴着 431~447 平掉。**而每单 18.8 条语句里，5.80 条是探针**（300 rps 档实测，占全部语句 33.4%；A 臂 driver 类合计 8.69 条/单）。

为什么必须处理：这不是「慢一点」，是**每单固定多付 33% 的往返**。而且它完全不在业务代码里 —— 代码一行不用改，改的是一个连接参数。

## 改了什么

一句话：同一个 jar、同一个 JDBC URL，末尾只多 11 个字符 `&useLocalSessionState=true`。

```bash
# 两臂只差这一个参数（URL 通过 SPRING_DATASOURCE_URL 注入，注入路径完全一致）
bench/tools/jdbc-url.sh apply false /tmp/loadgen/jar/b/app.jar   # A 臂
bench/tools/jdbc-url.sh apply true  /tmp/loadgen/jar/b/app.jar   # B 臂
bench/tools/jdbc-url.sh off                                     # 还原发行态
```

原理：`bench/jdbc-url.override.yml` 只做透传（Spring Boot 宽松绑定，优先级高于 yml）。**不重建镜像、不改代码、不改连接池** —— 两臂除那一个参数外完全同构。

驱动从此相信自己的本地视图（`autocommit` / 事务隔离级别 / `read-only`），不再每条语句问服务器一次。省的是「问」这一下，`SET autocommit = ?` 那 2 条**没变**（这个参数只省「问服务器」，不省「设自己」）—— 这正好是「参数真的按理解生效了」的一条旁证。

> 本页上图就是这条链：想省的是探针 → 只改一个参数 → 语句级证据 → 预测 vs 实测 → **预测失败** → 为什么会失败。

## 凭什么证明好了

性能类：**不录视频**，交付语句级证据 + 曲线 + 复现命令。

**① 生效的硬证据：不看吞吐，看语句**

| 300 rps 档 | A（false） | B（true） |
| --- | ---: | ---: |
| 每单语句数 | 17.38 | **11.43** |
| `SELECT @@SESSION.transaction_read_only` | **5.80 条/单**（33.4%） | **0**（该 DIGEST 整条消失） |
| `SET autocommit = ?` | 1.93 | 1.90（没变） |
| driver 类合计 | 8.69 | 2.85 |

**② 阶梯对照（3 轮取中位）**

| λ | A | B | Δ | B 每单语句数 | B 探针/单 |
| ---: | ---: | ---: | ---: | ---: | ---: |
| 480 | 434.0 | **479.9** | **+10.6%** | 12.49 | 0.00 |
| 520 | 431.6 | **501.4** | **+16.2%** | 12.25 | 0.00 |
| 560 | 445.2 | 484.6 | +8.9% | 12.33 | 0.00 |
| 600 | 447.6 | 494.4 | +10.5% | 12.47 | 0.00 |

**③ 预测失败（这一节是本页最值钱的诚实）**

```
开跑前写定：ok/s = QPS_cap ÷ 每单语句数 = 8,215 ÷ 11.43 = 719
（任务书口径 8,215 ÷ 13.1 = 627，两个都算误差）
实测天花板：494.4        → 对 627 低 21%，对 719 低 31%
```

为什么失败：`ok/s × 语句/单` 这个「语句预算」**不是外部常量** —— A 臂 7,922~8,398，B 臂掉到 5,216~6,165（−27%），而语句数掉了 33%。它几乎是同一条方程的另一种写法：

```
吞吐 = 20 条数据库连接 ÷ 每单事务墙钟时长 T
⇒ ok/s × 语句/单 = 20/T × 语句/单        （T 基本不变 ⇒ 「常量」必然跟着语句数变）
```

实测把这个方程钉住（600 档）：每单语句时间 22.1~25.2ms → 20.7~21.3ms，派生 T **44.7~47.5ms → 40.5ms**；ok/s 447.6 → 494.4（+10.5%，与 T 下降 10~15% 同量级）。⇒ **真正的收益是「每单事务变短」，探针本身只值约 2%**；所谓 +10.5% 里大部分是事务墙钟缩短带来的并发周转。

**④ 安全前提（决定这个参数能不能开）**

| 模式 | 命中 | 结论 |
| --- | --- | --- |
| `SET autocommit` / `SET SESSION` / `SET TRANSACTION` / `SET @@` / `SET GLOBAL` | 代码 **0** | 无绕过驱动改状态 |
| `setTransactionIsolation(` / `setReadOnly(` / `@Transactional(isolation` | **0**（37 处 `@Transactional` 只有 `rollbackFor` 35 / `REQUIRES_NEW` 2） | 无隔离级别假设 |
| `connection-init-sql` / `sessionVariables` / `SET NAMES` / `SET time_zone` | **0** | 池不在借出/归还时执行 SET |
| `getConnection(` / `DataSource` / `JdbcTemplate` 注入（`src/main`） | **0**（3 处在 test） | 不存在绕过 Spring 事务的原生 JDBC |
| `setAutoCommit(` | 3，全在 `src/test` | 安全：走驱动自己的 API |

已做成**持续门禁**：`scripts/check-jdbc-session-safety.sh`（5 类检查，A SET 系列 / B 隔离级别与只读 / C 连接初始化 SQL / D 原生连接 / E 正向断言 yml 里真的有这个参数）。

**⑤ 数据正确性（不能只看 TPS）**：31,496 单审计全绿 —— 订单↔明细↔出生台账一一对应、`total_amount` = Σ明细（0 例外）、每单 1 条 `ORDER_CREATE` 且 `Σdelta = −Σqty`、**桶守恒精确相等**（10,468,504 + 31,496 = 10,500,000）、缓存偏差 0、重复键 0、负库存桶 0；库存不足下单一行不留；重复支付被幂等拒绝。外加 `mvn -B clean test` → 246 tests 全绿。

## 附：口径与边界

- **别拿 627（或 719）做容量规划**。预测失败本身就是证据：`ok/s × 语句/单` 从 7.9k~8.4k 掉到 5.2k~6.2k，它随语句数一起变。能用的口径是「每单事务墙钟 T」和「20 条连接」这两个。
- **这条收益里有 2% 是探针，其余是事务变短**：把「省了 33% 语句」直接乘以吞吐会高估。真实可迁移的结论只有一句：**每单事务墙钟每降 10%，吞吐约涨 10%**（在连接池仍是 20 条、且这 20 条能一直忙的前提下）。
- **它有安全前提，且前提会腐烂**：一旦有人写了 `SET SESSION` / `SET autocommit` / `setReadOnly(` / 给 Hikari 配 `connection-init-sql` / 在前面放连接多路复用代理（ProxySQL multiplexing、MySQL Router 连接复用），驱动的本地视图就不可信，**出问题的形态不是崩，是静默做错账**。所以做成 `scripts/check-jdbc-session-safety.sh` 门禁，不是一次性检查。
- **参数必须写进 yml，别用环境变量**：环境变量会覆盖 yml，「某台机器上有人另设了一个 URL」就能悄悄把它关掉（或反过来在没验证过的服务上打开）。本仓库没有 `application-prod.yml`（容器栈跑 test profile），所以落在 `application-{dev,test}.yml`；将来新增 prod profile 必须同步加，门禁会拦。
- **两臂画像几乎重合**：MySQL 1.26~1.45 核、`nr_throttled=0`、行锁 213/s 平均等 25ms、fsync 900~960/s、SIGQUIT 191/202 与 187/202 停在 `HikariPool.getConnection`（真跑 SQL 的 8~9 个）—— 所以这是「事务变短」，不是「DB 变强」。
