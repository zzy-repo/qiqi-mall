## 会话探针（useLocalSessionState）

驱动默认在每条 DML 之前向服务器确认会话状态：`SELECT @@SESSION.transaction_read_only`。`useLocalSessionState=true` 让驱动以本地会话状态视图（`autocommit`、隔离级别、`read-only`）为准，不再逐条询问。省的是「问」：`SET autocommit = ?` 不变，因为该参数只省「问服务器」，不省「设自己」。

两臂同一个 jar、同一个 JDBC URL，URL 末尾只多 `&useLocalSessionState=true`，经 `SPRING_DATASOURCE_URL` 注入：不重建镜像、不改代码、不改连接池。

参数只在驱动本地视图可信时成立：应用不绕过驱动改会话状态 —— 没有 `SET autocommit` / `SET SESSION` / `SET TRANSACTION`，没有 `setTransactionIsolation(` / `setReadOnly(`，Hikari 未配 `connection-init-sql`，`src/main` 无原生 JDBC。这几条做成门禁 `scripts/check-jdbc-session-safety.sh`（五类检查）。

**效果**　环境：4 核共享机、Tomcat 200、热点 SKU 占八成、每档 75s 加预热 90s@378、每臂 3 轮取中位。语句级证据（300 rps 档）：探针 5.80 条/单（占语句 33.4%）→ 0，该 DIGEST 消失；每单 17.38 → 11.43；driver 类 8.69 → 2.85；`SET autocommit` 1.93 → 1.90（没变）。阶梯（A = `false`，B = `true`）：480 档 434.0 → 479.9（+10.6%）、520 档 431.6 → 501.4（+16.2%）、560 档 445.2 → 484.6（+8.9%）、600 档 447.6 → 494.4（+10.5%），B 臂每单语句数 12.25~12.49、探针 0。预测 8,215 ÷ 11.43 = 719（任务书口径 8,215 ÷ 13.1 = 627，两个都算误差），实测天花板 494.4，比 627 低 21%、比 719 低 31%。语句预算不是外部常量：A 臂 7,922~8,398，B 臂掉到 5,216~6,165（−27%），而语句数只掉 33%。每单事务墙钟 44.7~47.5ms → 40.5ms，每单语句时间 22.1~25.2ms → 20.7~21.3ms。数据侧 31,496 单审计全绿：桶守恒 10,468,504 + 31,496 = 10,500,000、缓存偏差 0、重复键 0、负库存桶 0；`mvn test` 246 全绿。

**边界**　别拿 627 或 719 做容量规划：`ok/s × 语句/单` 随语句数一起变，能用的口径是每单事务墙钟 T 与连接数（`吞吐 = 20 条连接 ÷ T`）。收益里约 2% 来自探针，其余来自事务变短；可迁移的结论只有「每单事务墙钟每降 10%，吞吐约涨 10%」，拿 33% 语句去乘吞吐会高估。前提会腐烂：一旦有人写 `SET SESSION` / `setReadOnly(` / 配 `connection-init-sql` / 在前面放多路复用代理，本地视图就不可信，出问题的形态是静默做错账而不是崩溃。参数写在 yml 里不要用环境变量，否则某台机器另设的 URL 能悄悄关掉它；本仓库没有 `application-prod.yml`，新增 profile 必须同步加。画像几乎重合：MySQL 1.26~1.45 核、`nr_throttled=0`、行锁 213/s 平均等 25ms、fsync 900~960/s。
