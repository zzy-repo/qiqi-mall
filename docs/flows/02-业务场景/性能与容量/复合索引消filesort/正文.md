## 复合索引消 filesort（composite index）

「我的订单」这条路有两笔账：分页解决返回量，索引解决排序量。接口改成 `Page` 之后返回量收住了（`size` 限 1~50），但只有 `idx_member(member_id)` 时排序量一点没收：`ORDER BY payment_time DESC` 走 filesort，为了拿 10 行进结果，先把该会员全部订单读出来整批排序再切前 10 行。读放大等于「该会员订单总数 ÷ 每页条数」，线性、无上限，`LIMIT` 帮不上忙，也不报错、不超时 —— 只是每翻一页都在替整个历史买单。

修法是让索引列序变成这条查询要的顺序：先等值、后排序，加 `KEY idx_member_time (member_id, payment_time)`。二级索引本身按 `(member_id, payment_time)` 有序，`member_id = 1` 这一段内部天然有序，反向扫 10 条就是结果，不需要排序。排序键跟着对齐成 `.orderByDesc(payment_time).orderByDesc(id)`，`id` 只做同秒兜底。`payment_time` 为 NULL 的未支付单排在倒序最后（MySQL 的 NULL 升序最小、倒序最大）。

**效果**　克隆库 `qiqi_idxclone`，`order` 表 200,000 行全部归同一会员（其余条件与线上同构），本机 `EXPLAIN ANALYZE` 真跑。无 `idx_member_time`：`key=idx_member`、`Extra: Using filesort`、实际读取 200,000 行、387 ms；有它：`key=idx_member_time`、`Backward index scan`（无 filesort）、读取 10 行、0.095 ～ 0.099 ms。现库 `qiqi_mall_test` 上同一条查询同形状：`type=ref`、`rows=6`、`Backward index scan`。最左前缀三反例：不带 `member_id` 的 `WHERE payment_time >= … ORDER BY payment_time DESC` → `type=ALL`、`key=NULL`、`Using filesort`；`member_id=1 AND payment_time >= …` → `type=range`、`Backward index scan`，范围也有序、照样免排序；`ORDER BY created_at DESC` → `key=idx_member`、`Using filesort`，索引盖住了过滤、盖不住排序。

**边界**　最左前缀是硬约束：这条索引只对「先给 `member_id` 的等值过滤 + 按 `payment_time` 排序」有用，只按 `payment_time` 筛用不上，那种查询要另建 `(payment_time)` 或 `(status, payment_time)`。排序键必须与索引列序一致，换成 `created_at`、`total_amount` 或表达式排序立刻退回 `Using filesort`。它只省排序、不省返回量：`SELECT *` 仍要回表 10 次；一页要 500 行或按非索引列过滤时 filesort 会换形式回来，杠杆是覆盖索引或改写查询。387 ms 属于「200k 行全归一个会员」的极端口径：真实库订单分散在几万个会员上，绝对耗时会小，但读放大仍与该会员单数成正比、与 `LIMIT` 无关。`payment_time IS NULL` 排在最后是 MySQL 的排序规则，不是缺陷。分页那半边的接口耗时不在本页承诺内（原始记录没留档）。
