**复合索引 (member_id, payment_time)：把 filesort 消掉** —— 「我的订单」列表从返回全量数组改成 `Page` 之后，返回量收住了，但**排序量没收住**：只有 `idx_member(member_id)` 时，每取 10 条都要先把该会员的 20 万行捞出来按 `payment_time` 排一遍。加一条复合索引 `(member_id, payment_time)`、把排序键对齐成 `payment_time DESC`，同一条查询从 **387ms 掉到 0.099ms**，`EXPLAIN` 里的 `Using filesort` 变成 `Backward index scan`。

## 场景

买家点「我的订单」的那一刻。老客的历史订单是**单调增长**的，所以这条路径的代价不取决于他今天买了什么，取决于他这些年一共买了多少 —— 一个越用越慢、且不会报错的路径。

这也是「分页已经做过了」之后仍然要看的第二个问题：分页解决的是**返回量**，索引解决的是**排序量**，两件事。

## 撑不住的时候

两段，先给机制、再给坏环境。

**一节 · 分页先把返回量收住（这是机制改动，不是性能数字）**

```
原来：GET /portal/orders 返回全量数组，前端一次渲染
      会员订单一多，响应体跟着线性涨
改后：Page + 主键倒序：size 限 1~50，返回 { records, total, current, size, pages }
```

这一节只交代结构变化。**接口耗时的原始记录仓库里没有，本页不做数字承诺**（当时的量级是 30~170ms 一档，属于「当时实测、v1 之后未复测」，不拿它当证据）。

**二节 · 分页收住了返回量，没收住排序量**

坏环境是现造的：克隆库、**200,000 单全归同一个会员**（其余条件与线上同构），先在只有 `idx_member(member_id)` 的状态下跑：

```
EXPLAIN SELECT * FROM `order` WHERE member_id=1 ORDER BY payment_time DESC, id DESC LIMIT 0,10;
→ type=ref  key=idx_member  rows=99,120(估算)  Extra: Using filesort

EXPLAIN ANALYZE 同一条：
→ Limit: 10 row(s)  (actual time=387..387 rows=10 loops=1)
    -> Sort: `order`.payment_time DESC, `order`.id DESC, limit input to 10 row(s) per chunk  (actual time=387..387 rows=10)
        -> Index lookup on order using idx_member (member_id=1)  (actual time=0.088..338 rows=200000 loops=1)
```

也就是：为了拿 10 行，先把 **200,000 行**读出来，再整批排序、切前 10 行。

拐点在哪：**读放大 = 该会员订单总数 ÷ 每页条数**。会员订单一千行时要读一千行，十万行时要读十万行 —— 它是线性的、没有上限的，而且 `LIMIT` 一点忙都帮不上。为什么必须处理：它不会报错、不会超时（387ms 还在超时线以内），只是每翻一页都在替整个历史买单。

## 改了什么

一句话：让索引的**列序**变成这条查询要的顺序 —— 先等值、后排序。

```sql
KEY idx_member_time (member_id, payment_time)     -- 列序就是「先等值过滤、后排序」
```

```java
// list() 的排序键从「只按 id」改成「按 payment_time，id 只做同秒兜底」
.orderByDesc(Order::getPaymentTime)
.orderByDesc(Order::getId)
```

为什么这一条能免排序：InnoDB 的二级索引本身按 `(member_id, payment_time)` 有序，`member_id = 1` 这一段内部就**天然有序** —— 反向扫一遍，前 10 条就是查询要的那 10 条，不需要任何排序。`payment_time` 为 NULL 的未支付订单会排在最后（MySQL 的 NULL 在升序里最小、倒序里最大），语义上仍是「按时间近似序」。

> 本页上图就是这条链：分页收住返回量 → 200k 实测暴露 filesort → 加复合索引并对齐排序键 → EXPLAIN/EXPLAIN ANALYZE 前后对照 → 最左前缀的三种反例。

## 凭什么证明好了

数据类：**图 + EXPLAIN + 数字**，不录视频。所有 EXPLAIN 都在本机现造的 200,000 行克隆库上真跑（`EXPLAIN ANALYZE` 会实际执行查询，不是估算）。

**① 同一条查询、同一个库，只差一条索引**

| | 无 `idx_member_time` | 有 `idx_member_time` |
| --- | --- | --- |
| `key` | `idx_member` | **`idx_member_time`** |
| `Extra` | **`Using filesort`** | **`Backward index scan`**（无 filesort） |
| 实际读取行数 | **200,000** | **10** |
| `EXPLAIN ANALYZE` 真跑 | **387 ms** | **0.095 ~ 0.099 ms** |

```
带索引：
-> Limit: 10 row(s)  (actual time=0.0952..0.0993 rows=10 loops=1)
    -> Index lookup on order using idx_member_time (member_id=1) (reverse)  (actual time=0.0945..0.0981 rows=10 loops=1)
```

**② 现库（`qiqi_mall_test`）上同一条查询也是这个形状**（小表也走同一条路，只是行数少）：

```
type=ref  key=idx_member_time  rows=6  Extra: Backward index scan
```

**③ 最左前缀：这条索引帮谁、不帮谁**（三个反例，都在同一个 200k 库上跑）

| 查询 | type / key | Extra | 结论 |
| --- | --- | --- | --- |
| `WHERE payment_time >= '2024-06-01' ORDER BY payment_time DESC`（不带 member_id） | `ALL` / `NULL` | `Using where; Using filesort` | **用不上**：第一列没给，第二列也就不存在 |
| `WHERE member_id=1 AND payment_time >= '2024-06-01' ORDER BY payment_time DESC` | `range` / `idx_member_time` | `Using index condition; Backward index scan` | **照样免排序**：范围也是有序的 |
| `WHERE member_id=1 ORDER BY created_at DESC` | `ref` / `idx_member` | `Using filesort` | 索引盖住了过滤，盖不住排序 |

复现（克隆库 + 200k 行 + 前后对照，全程只读真库、只在克隆库上 DROP）：

```bash
mysql -e "DROP DATABASE IF EXISTS qiqi_idxclone; CREATE DATABASE qiqi_idxclone DEFAULT CHARSET utf8mb4;"
mysqldump --no-data qiqi_mall_test member 'order' | mysql qiqi_idxclone
mysql -e "INSERT INTO member SELECT * FROM qiqi_mall_test.member;" qiqi_idxclone
mysql qiqi_idxclone -e "SET SESSION cte_max_recursion_depth=300000;
INSERT INTO \`order\` (order_sn, member_id, total_amount, status, pay_type, payment_time, created_at,
                       receiver_name, receiver_phone, receiver_address)
WITH RECURSIVE seq AS (SELECT 1 AS n UNION ALL SELECT n+1 FROM seq WHERE n < 200000)
SELECT CONCAT('IDXCLONE', LPAD(n,8,'0')), 1, 99.00, 1, 1,
       DATE_ADD('2024-01-01 00:00:00', INTERVAL n MINUTE), DATE_ADD('2024-01-01 00:00:00', INTERVAL n MINUTE),
       '压测买家','13800000000','浙江省杭州市西湖区某路1号' FROM seq;
ANALYZE TABLE \`order\`;"

# 有索引（现状）
mysql qiqi_idxclone -e "EXPLAIN ANALYZE SELECT * FROM \`order\` WHERE member_id=1 ORDER BY payment_time DESC, id DESC LIMIT 0,10;"
# 拿掉索引（只在克隆库上）
mysql qiqi_idxclone -e "ALTER TABLE \`order\` DROP INDEX idx_member_time; ANALYZE TABLE \`order\`;"
mysql qiqi_idxclone -e "EXPLAIN ANALYZE SELECT * FROM \`order\` WHERE member_id=1 ORDER BY payment_time DESC, id DESC LIMIT 0,10;"
```

## 附：口径与边界

- **最左前缀是硬约束，别照抄成「给 payment_time 加索引」**：`(member_id, payment_time)` 只对「**先给 member_id** 的等值过滤 + 按 payment_time 排序」有用。只按 `payment_time` 筛（例如后台报表按时间段拉全站订单）**用不上这条索引**，那种查询要另建 `(payment_time)` 或 `(status, payment_time)`。
- **排序键必须和索引列序一致**：`ORDER BY payment_time DESC` 才免排序；换成 `created_at`、`total_amount`、或加上 `CASE WHEN` 之类的表达式排序，立刻退回 `Using filesort`（上表第三行就是实证）。
- **它只省「排序」，不省「返回量」**：`SELECT *` 仍然要回表 10 次（200k 库上实测 0.099ms，已经够快）；但如果将来一页要 500 行，或者要按非索引列过滤，`filesort` 会换一种形式回来 —— 那时的杠杆是覆盖索引或改写查询，不是加索引列。
- **`387ms` 这个数字属于「200k 行全部归一个会员」的极端口径**：真实库里订单分散在几万个会员上，单个会员几千行是常态，filesort 的绝对耗时会更小（但读放大那条性质不变：它仍然与「这个会员有多少单」成正比，与 `LIMIT` 无关）。
- **`payment_time IS NULL` 的未支付订单排在倒序的最后**，这是 MySQL 的 NULL 排序规则，不是 bug；列表页语义上按「支付时间近似序」展示，需要「下单时间序」时得另加索引列，别改这一条。
- **分页那半边的接口耗时不在本页承诺之内**：原始记录没有留档，所以只写结构与机制（`Page` + `size` 限 1~50 + 主键倒序），不写「快了百分之多少」。要那个数只能重新测一次。
