## 每单 19 条 SQL（per-order statement count）

一单的语句数由三部分构成：业务语句、driver 自己发的语句、`COMMIT`。driver 在每条 DML 之前发一条 `SELECT @@SESSION.transaction_read_only` 探针，另发 `SET autocommit = ?`，每个事务以 `COMMIT` 结束。所以删掉一条业务 DML 能省两条往返 —— DML 一条，附带的探针一条。

合并的是建单：原先是先插一条 `total_amount=0` 的订单、扣完库存再 `UPDATE order` 回填总额；改后把读（SKU、商品、价格）前置，总额算完之后一次 INSERT 写对。等价性逐条对齐：落库终态逐列相同，失败语义相同（整笔 `REQUIRES_NEW` 回滚），同一事务内的一致性读相同；代价是原 `UPDATE` 后那句 `requireAffected(MSG_RECORD_DELETED)` 一并消失，它在本事务内不可达，但确实少了一条防御性检查。

判读依据一条不变式：`ok/s ≈ 语句率上限 ÷ 每单语句数`；预测在压测前写定，再用五列控制变量（SQL/s、MySQL 核数、行锁、fsync、GC）确认没有别的变量跟着变。

**效果**　环境：4 核共享机、2 个实例、Tomcat 200 / Hikari 10、热点 SKU 占八成、每档 75s 加预热 90s@350、每臂 3 轮取中位、噪声带 ±2.8%。A 臂 420 档画像（30,199 单）：合计 20.10 条/单，其中探针 7.04、`SET autocommit` 2.01、`COMMIT` 1.00（4.11ms/次）、`INSERT order` 1.00、`UPDATE sku_bucket` 1.00（16.84ms/次，占语句时间 63.8%），其余 8.05。每单语句数 20.62 → 18.77（−9.0%）。450 档吞吐 398.4 → 441.0 ok/s（+10.7%），420 档 400.5 → 419.9（+4.8%）；拐区起点 400 → 450 rps，饱和点 420 rps（弹性 0.06）→ 450 以上（弹性 0.71）。预测 8,215 ÷ 18.77 = 437.5，实测 441.0，偏差 +0.8%；反向 8,215 ÷ 20.62 = 398.4 与实测吻合。五列几乎重合：SQL/s 7,703~7,767 → 7,575~7,716（−0.4%）、MySQL 1.43 → 1.42 核、行锁 190.3 → 193.5/s、fsync 900/855 → 914/868、GC 0.8% → 0.9%。裸机 `SELECT 1` 闭环保压 21,832 / 22,026 与 21,419 / 21,694（差 ≤2%）。`mvn -B clean test` 246 tests 全绿。

**边界**　「19 条」不是常数：它是这套代码、这组驱动参数、这个版本的画像；`useLocalSessionState` 一开，探针那 7 条消失，每单掉到 12 条（见 `性能与容量/会话探针`），加一条 DML 或换批处理策略也会变，要用就当场取 DIGEST。8,215 语句/s 是这台 4 核机的整机预算，不是 MySQL 的算力上限：MySQL 只用 1.42 核（36%）、`nr_throttled=0`，业务饱和时还能额外跑 9k~14k 条 `SELECT 1`/s，而整机已 4.00/4 吃满、`cpu.pressure some` 91%，所以被证伪的是「限制项 = MySQL 算力打满」。合并只吃了 9% 的条数，剩下最大两块是探针 7 条与 `COMMIT`（4.11ms/次，占语句时间 16%）。380 / 400 两档的 r1/r2 是冷 JVM 假崩（`SQL/s < 7500` 判冷启动），只有热机轮可比。
