**每单 19 条 SQL：只合并一处，450 档 +10.7%** —— 下单这件事一单要跟数据库说 20 来句话，其中一半不是业务 SQL；只把「建单」那一处两条 DML 合成一条，每单语句数 20.62 → 18.77，450 档吞吐 398.4 → 441.0 ok/s（+10.7%），而 SQL/s、MySQL 核数、行锁、fsync、GC 五列几乎一点没动 —— 所以涨的那 10.7% 只可能来自语句条数。

## 场景

做容量规划或排查「为什么压到 400 就上不去」的人。压测已经告诉我们：加连接没用、热点行锁也不是唯一闸门，那接下来最该问的是**一单到底要跟数据库打多少次招呼**，以及其中有多少是白打的。

这个问题的价值在于它是**可数的**：不是「感觉慢」，是一单 20 条还是 12 条，DIGEST 画像能精确数出来。

## 撑不住的时候

先把环境造出来：4 核共享机、2 个实例、Tomcat 200 / Hikari 10、热点 SKU 占八成、每档 75s + 预热 90s@350。A 臂（改前）的饱和档：420 档只有 **400.5 ok/s**，450 档 **398.4**，p50 已经 4.6 秒。

不看吞吐，先看语句画像（420 档，30,199 单）：

| # | 语句（DIGEST 归一化） | 条/单 | 占语句时间 |
| --- | --- | ---: | ---: |
| 1 | `SELECT @@SESSION.transaction_read_only`（驱动探针，每条 DML 前一条） | **7.04** | 0.14ms/次 |
| 2 | `SET autocommit = ?` | 2.01 | 0.12ms/次 |
| 3 | `COMMIT` | 1.00 | **4.11ms/次** |
| 4 | `INSERT INTO order` | 1.00 | 0.52ms |
| 5 | `UPDATE sku_bucket SET stock=stock-?` | 1.00 | **16.84ms** → 一档累计 510s，占全部语句时间 **63.8%** |
| — | 其余业务语句（明细、两张台账、三次 SELECT…） | 8.05 | 0.3~0.6ms |
| | **合计** | **20.10** | |

拐点在哪：**时间**上 63.8% 花在 `UPDATE sku_bucket` 等锁（这和「库存分桶」那页是同一件事），但**条数**上有一半是 driver 自己发的往返。也就是说「一单 19 条」里有 10 条根本不是业务写的 —— 这决定了「合并一处」到底能省几条：**少 1 条 DML，连带少 1 条探针，实际省 2 条**。

为什么必须处理：这台机的语句预算是固定的（见「附」），每少一条语句就少占一份预算，吞吐按条数倒数上升。这不是「优化一下」，而是**在那道闸门之前唯一还握在手里的一根杠杆**。

## 改了什么

一句话：建单不再「先插一条 `total_amount=0`、扣完库存再 `UPDATE order` 回填总额」，改成把读（SKU / 商品 / 价格）前置、总额算好之后**一条 INSERT 写对**。

```java
// 改前：两条 DML
order.setTotalAmount(BigDecimal.ZERO);
orderService.save(order);              // INSERT order(total=0)
for (ItemInput in : inputs) { ...deductStock...; total = total.add(...); }
orderItemService.saveBatch(items);
order.setTotalAmount(total);
orderService.updateById(order);        // ← 这条消失

// 改后：一条 DML（读前置 → 总额算完 → 一次 INSERT → 再扣库存/写明细）
for (ItemInput in : inputs) { sku = getById; product = getById; total = total.add(...); }
order.setTotalAmount(total);
orderService.save(order);              // INSERT order(total=正确值)
...deductStock / build items / saveBatch...
```

等价性写在类注释里、逐条对齐：落库终态逐列相同；失败语义相同（整笔 `REQUIRES_NEW` 回滚）；读的快照相同（同一事务内的一致性读）；明细为空时抛异常的位置前移，但提交状态同样为空。

**代价如实记**：那条 `updateById` 后面的 `requireAffected(MSG_RECORD_DELETED)` 一起消失了 —— 它在本事务里不可达（同事务内没有 DELETE order，未提交的 INSERT 对其他事务不可见），但确实少了一条防御性检查。

> 本页上图就是这条链：先把「19 条」拆开 → 只合并一处 → 先写预测再对撞 → 用五列控制变量把「涨的 10.7%」钉在语句条数上。

## 凭什么证明好了

性能类：**不录视频**，交付曲线数字 + 一条复现命令。

**① 先写预测，再去压测对撞**（预测在跑之前写定，不是事后凑）

```
不变式：ok/s ≈ 语句率上限 ÷ 每单语句数
预测：ok/s_B = 8,215 ÷ 18.77 = 437.5
实测：441.0                        → 偏差 +0.8%
反向：ok/s_A = 8,215 ÷ 20.62 = 398.4，实测 398.4（完全吻合）
```

**② 阶梯对照**（每臂 3 轮取中位，噪声带 ±2.8%）

| λ | A 改前 | B 改后 | Δ |
| ---: | ---: | ---: | ---: |
| 420 | 400.5 | 419.9 | +4.8% |
| 450 | **398.4** | **441.0** | **+10.7%** |
| 拐区起点 | 400 rps（p50 319→2337ms） | **450 rps**（p50 60→241→649→3570ms） | 右移 50 |
| 饱和点 | 420 rps（弹性 0.06） | **> 450 rps**（弹性 0.71，还在涨） | — |

**③ 五列控制变量：除了语句条数，其它几乎重合**

| 指标（450 档） | A 改前 | B 改后 |
| --- | ---: | ---: |
| 每单语句数 | 20.62 | **18.77（−9.0%）** |
| SQL/s | 7,703~7,767 | 7,575~7,716（−0.4%） |

## 附：口径与边界

- **「19 条」不是常数，别照抄**：它是「这套代码 + 这个驱动参数 + 这个版本的画像」。`useLocalSessionState` 一开，探针那 7 条就没了，每单直接掉到 12 条（见 `性能与容量/会话探针`）；加一条 DML、换 MySQL 版本、换 ORM 批处理策略都会让它变。要用就当场量一次 DIGEST。
- **`8,215 语句/s` 是这台 4 核机的整机预算**，不是 MySQL 的算力上限：MySQL 只用了 1.42 核（4 核的 36%）、`cpu.max=max`、`nr_throttled=0`，业务饱和时还能额外跑 9k~14k 条 `SELECT 1`/s；而整机已经 4.00/4 吃满、`cpu.pressure some` 91%。换机器、换核数、把平台其它容器挪走，这个预算都会变。
- **结论只说「关系成立、机制被改写一半」**：`ok/s ≈ 语句率 ÷ 每单条数` 这个关系成立（预测 437.5 vs 实测 441.0）；但「闸门 = MySQL 算力打满」被证伪；更接近的解释是「整机 CPU 预算 ÷ 每条语句的固定成本」。
- **合并只吃了 9% 的条数**：20.62 → 18.77。剩下那 12 条里最大的一块是探针（7 条），第二块是 `COMMIT`（4.11ms/次，占语句时间 16%，是提交落盘的钱，与条数无关）。
- 这条改动删掉了一条防御性检查（`requireAffected`），接受它的前提是「同一事务内不可能 DELETE 这张订单」—— 如果将来有人在这个事务里加了 DELETE，这条守卫要补回来。
