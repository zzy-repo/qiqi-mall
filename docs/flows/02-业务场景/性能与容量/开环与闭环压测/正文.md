**闭环会把上限测低：开环定速与 coordinated omission** —— 用固定并发（闭环）压出来的「390.4 rps 上限」是**配置出来的天花板**，不是机器的；换成开环定速、把延迟起点定成**计划到达时刻**，同一套系统同一目标负载报 **474.6 rps**（+21.6%）。差的那 21.6% 不是优化出来的，是原来的量法把最坏的样本删掉了。

## 场景

要给系统定容量、要写 SLA、要对「能扛多少」给一个数的人。这个数一旦测低，后果很具体：按虚低的上限去扩容，白花钱；按虚低的上限去限流，白丢单。

而且它有一个特别隐蔽的性质 —— **两种量法都不会报错**，都会给你一条平滑的曲线，只是其中一条把峰值剪掉了。

## 撑不住的时候

先把两种量法摆在一起（同一台机、同一个独占窗口、相邻测量，旧法与新法必须相邻，否则比的是机器漂移）。

**旧法（闭环，固定并发 VU，每档独立一场）**

| 并发 | 吞吐 | p50 | p99 |
| ---: | ---: | ---: | ---: |
| c8 | 350.0 | 20.6ms | 53.1ms |
| c16 | 367.7 | 38.6ms | 114.0ms |
| c32 | 387.9 | 72.1ms | 244.3ms |
| c64 | **390.4** | 128.2ms | 735.6ms |

看到 390 就上不去了，很自然会得出「这台机的上限是 390」。**这个是错的**。

**新法（开环阶梯，一个进程跑完、一次 reset、一次预热）**

| 目标 λ | 实测 ok/s | 达成 | p50 | p99 | 丢弃 |
| ---: | ---: | ---: | ---: | ---: | ---: |
| 388 | 387.9 | 100% | 40.7ms | 462.7ms | 0 |
| **530** | **474.6** | **89.6%** | 4861ms | 6914ms | **2,486（标 saturated）** |

闭环连「530 rps 这个负载」都表达不出来 —— 64 个槽位，每个槽位「发一个 → 等回来 → 再发一个」，系统一慢，槽位就自动少发。**于是闭环测出来的是「客户端供不上」，不是系统上限。**

拐点在哪：把延迟起点从「发出时刻」改成「计划到达时刻」。同一个 388 rps 负载，两法的 p99：

```
15.8 → 20.9ms (+32.6%)    18.1 → 46.5ms (+157.4%)   24.9 → 166.6ms (+570.0%)
53.1 → 524.3ms (+887.9%)  114.0 → 174.8ms (+53.3%)  244.3 → 462.7ms (+89.4%)
```

7 档里 6 档 p99 更高。**吞吐几乎一样（差 ≤0.6%），长尾差了 1.3~9.9 倍** —— 这不是机器变了，是口径把排队时间算进去了。

为什么必须处理：错的不只是一个 p99，是**「上限」这个结论的符号**。同一台机器，一种量法说 390，另一种说 474.6。

## 改了什么

一句话：把「发多快」从**客户端的命运**里拿出来，改成**时间表的输入**；把延迟的起点定成**它本来该出发的那一刻**。

```
旧法（闭环）：固定 N 个槽位，每个槽位 发一个 → 等回来 → 再发一个
   ⇒ 系统慢 → 槽位少发 → 到达率跟着系统一起掉 ⇒ 测出的是「客户端能供多少」

新法（开环）：时间表说 530 就按 530 发，慢不慢都照发（落后太多的请求丢弃并标 saturated=1）
   ⇒ 系统慢 → 请求堆在队列里 → 延迟如实涨上去 ⇒ 测出的才是「系统能吃多少」
   延迟起点 = 计划到达时刻（不是发出时刻）
```

最后那条是整页的核心：**如果起点取「发出时刻」**，一个在队列里排了 3 秒才发出的请求，那 3 秒会被算到别人头上，它自己的延迟看起来只有 20ms —— 越慢 → 发得越少 → 样本里快请求占比越高 → 报出来的 p99 越好看。这就是 **coordinated omission**：不是撒谎，是口径把最坏的样本删掉了。

> 本页上图就是这套对照：左边是「怎么测错」，右边是「怎么测对」，最后一格是 coordinated omission 的机制。

## 凭什么证明好了

性能类：**不录视频**，交付两臂对照数字 + 复现命令。

**① 上限的差**：`474.6 ÷ 390.4 = +21.6%` —— 机器的真实容量至少比闭环报的高 21.6%。

**② 长尾的差**：同负载 p99 在 7 档里 6 档更高，+33%~+888%（明细见上）。c64 那档出现例外（735.6 → 462.7，−37.1%）**不是计时起点错**，而是操作点不同：c64 的 64 个槽位本身就在排队（L=64、W≈164ms），新法 388 rps 档的 inflight 只有 26 —— 「吞吐相同但并发不同」不是同一操作点，所以拿它当反例不成立。

**③ 自校验（Little 定律）**：`L = ok/s × W`，L 取该档 inflight 的**精确时间加权积分**（`gen.mjs` 每次 inflight 变化就按墙上秒记账，不是采样近似）。6 档最大偏差 **0.6%**，全部 ≤10%。

**④ 顺带的收益：同样的结论，一半的时间**。整段（reset + 预热 + 测量 + 清理 + 聚合）875s → 391s（2.24×）；压测段 996s → 381s（2.30×）。省下来的全是重复的固定开销，不是靠少测 —— 同负载 TPS 两法差 ≤0.6%，证明测的是同一件事。

复现（旧法与**必须相邻**，否则比的是机器漂移）：


## 附：口径与边界

- **闭环测出来的是「客户端供不上」，不是系统上限** —— 这句话就是本页的全部。任何用固定 VU 数压出来的「上限」，先问一句：是系统到顶了，还是槽位到顶了？
- **延迟起点必须是计划到达时刻**。用「发出时刻」做起点，等于把排队时间从统计里删掉；负载越重，删得越多。这一条对开环/闭环都成立，只是闭环更容易掩盖它（因为闭环本来就少发）。
- **`474.6` 也不是「机器的绝对上限」**：它是「530 目标下达成了 89.6%、丢弃 2,486 条」的那一档。要继续往上推，得继续加档、继续看丢弃率与 p99 的拐点 —— 而且换机器、换热点分布都会变。
- **两法必须在同一个独占窗口内相邻测量**：`run-all.sh` 的顺序（旧法 7 档 → 新法阶梯）是刻意排的，中间没有别的负载；否则比的是机器漂移，不是方法。
- **c64 那个「p99 反而更低」的例外不要当反例**：闭环 c64 本身已经排队（L=64、W≈164ms），与新法 388 rps 档（inflight 26）不是同一操作点。要判断口径问题，只能比「同一操作点」的档。
- 这套口径的适用范围是**本仓库这套压测工具**（`bench/bench.sh` / `gen.mjs` / `run-all.sh`）；换成别的压测器时，最少要确认两件事：是否开环定速、延迟起点取的是哪一个时刻。
