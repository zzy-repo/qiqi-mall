## 开环与闭环压测（open-loop / coordinated omission）

两种量法都不会报错，都会给出一条平滑曲线，区别是其中一条把峰值剪掉了。闭环是固定 N 个槽位、每个槽位「发一个 → 等回来 → 再发一个」：系统一慢，槽位就自动少发，到达率跟着系统一起掉，测出来的是「客户端能供多少」。开环是时间表说 530 就按 530 发，慢不慢都照发，落后太多的请求丢弃并标 `saturated`：系统慢则请求堆在队列里、延迟如实涨上去，测出来的才是「系统能吃多少」。

延迟起点是这套口径的核心：必须取计划到达时刻，不是发出时刻。一个在队列里排了三秒才发出的请求，若从「发出时刻」起算，那三秒会被算到别人头上，它自己看着只有 20ms —— 越慢发得越少、样本里快请求占比越高、报出来的 p99 越好看。这就是 coordinated omission：不是撒谎，是口径把最坏的样本删掉了，负载越重删得越多。

两法必须在同一台机、同一个独占窗口内相邻测量（旧法各档 → 新法阶梯，中间不插别的负载），否则比的是机器漂移而不是方法。自校验用 Little 定律 `L = ok/s × W`，`L` 取该档 inflight 的精确时间加权积分（每次 inflight 变化就按墙上秒记账，不是采样近似）。

**效果**　同一台机、同一独占窗口、相邻测量；旧法为闭环固定并发、每档独立一场，新法为开环阶梯、一个进程跑完、一次 reset 一次预热。闭环四档 c8 / c16 / c32 / c64 的吞吐是 350.0 / 367.7 / 387.9 / 390.4 ok/s，p99 53.1 / 114.0 / 244.3 / 735.6 ms —— 390 看上去就是天花板。开环阶梯：目标 388 达成 387.9 ok/s（100%）、p99 462.7 ms、丢弃 0；目标 530 达成 474.6 ok/s（89.6%）、p50 4861 ms、p99 6914 ms、丢弃 2,486 条（标 `saturated`）。上限差 `474.6 ÷ 390.4 = +21.6%`。同一 388 rps 负载下的 p99 在 7 档里 6 档更高（+33% ～ +888%），而吞吐差 ≤0.6% —— 变的是口径，把排队时间算进去了。Little 定律 6 档最大偏差 0.6%，全部 ≤10%。整段耗时（reset + 预热 + 测量 + 清理 + 聚合）875s → 391s（2.24×），压测段 996s → 381s（2.30×），省下来的是重复的固定开销而不是少测。

**边界**　`474.6` 不是机器的绝对上限，它是「530 目标下达成了 89.6%、丢弃 2,486 条」的那一档；要继续往上推得继续加档、继续看丢弃率与 p99 的拐点，换机器或换热点分布都会变。c64 那档 p99 反而更低（735.6 → 462.7，−37.1%）不能当反例：闭环 c64 的 64 个槽位本身已经在排队（`L=64`、`W≈164ms`），而新法 388 rps 档的 inflight 只有 26，两者不是同一操作点 —— 判断口径问题只能比同一操作点。闭环测出来的是「客户端供不上」，任何用固定并发数压出来的「上限」都要先问一句：是系统到顶还是槽位到顶。延迟起点这一条对两种量法都成立，闭环只是更容易掩盖它。这套口径绑定本仓库这套压测工具（`bench/bench.sh` / `gen.mjs` / `run-all.sh`）；换成别的压测器至少要确认两件事：是否开环定速、延迟起点取的是哪一个时刻。数字出处：`bench/results/2026-11-13-closed-vs-open/`（`report.txt` / `compare.txt` / `persecond.csv`），本轮未复测。
