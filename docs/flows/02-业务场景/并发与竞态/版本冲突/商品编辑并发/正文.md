**商品编辑并发：两个运营同时改同一件商品，后提交的那次必须当场被拒** —— 甲先存，版本号 0 → 1；乙手里还是 0，后端回**真 HTTP 409** +「数据已被他人修改（可能其他人在编辑），请刷新后重试」，乙那次**一个字段都没写进去**（库里仍是甲的名字、版本号仍是 1）。乙点「刷新」重填成甲的值、再改一次才能写进去（版本号 1 → 2）。底线是：**后提交的人不会被静默覆盖，冲突当场暴露，谁都不白改。**

## 场景

一件商品的名字、描述、分类、上下架状态，经常是两个人同时在改：运营改文案、类目运营调分类、老板临时让下架。他们各自打开编辑弹窗、各自看到一份数据，**谁也不知道对方也在改**。

这页就是那条最常见的路：管理后台商品编辑（`admin-web/src/views/product/index.vue` + `PUT /admin/products/{id}`）。它要回答的问题只有一个：**两个人同时点保存时，会发生什么**。

## 撑不住的时候

不加任何约束时，坏环境是这样的（这就是 last-write-wins）：

- **两个人各自打开弹窗，都拿到同一份数据**，甲改名字、乙改描述，看起来毫不冲突；
- 乙后保存，请求里带的是**整份表单**。数据库按 `WHERE id = ?` 覆盖 —— 甲改的名字被乙那份"基于旧数据"的表单悄悄改回去；
- 甲那边收到「保存成功」，乙那边也收到「保存成功」。**两个人都以为自己改了，其中一个白干，而且没有任何人收到提示**。

这条路径的可怕之处不是"丢一次修改"，而是**它不留任何痕迹**：接口 `code=0`、页面绿字、库里有值 —— 一周后没人能解释"为什么这件商品的描述变回去了"。

所以需要的是一条**能当场说出口的拒绝**：让后到的那次拿到一个明确的失败、一个可执行的下一步（刷新重来），而不是让它悄悄赢。

## 改了什么

① **每条可编辑记录带 `version`，写入只认没变过的版本**。请求必须带 version（缺了 `code=400`「缺少版本号，请刷新页面后重试」，**绝不退化成无版本 UPDATE** —— 那等于什么都没做，而且外人看不出来）。落库那句是 `UPDATE ... WHERE id = ? AND version = ?`，**影响行数 0 行 = 冲突**。

② **0 行必须变成"真 409"，不能是 `200 + body.code`**。`OptimisticLockGuard` 的注释把这条踩坑写死了：写成 `Result.fail(...)` 时 Spring 会包成 **HTTP 200**，于是 curl 脚本、监控、网关日志、第三方全都会把这次冲突记成成功。所以统一走**抛异常**（`LockException` → `GlobalExceptionHandler` 映射成真 400/409），body 里同时带 `code=409`。

③ **两种"0 行"要分开说清楚**：有 version 列的表 → 「数据已被他人修改（可能其他人在编辑），请刷新后重试」；**没有 version 列**的表（字典、子表等）→ 「记录已被删除，请刷新后重试」/「发货明细已被删除，请刷新后重试」。原因不同，但都 fail-closed：继续按成功返回就是假成功。

④ **前端给的是可执行的下一步，不是一句红字**：`ConflictDialog` 弹窗（`conflict-message` + `conflict-hint`）—— 主文案说明被别人改过，提示明写「你刚才填写的内容没有被保存。点「刷新」拉取最新数据后，请重新修改一次。」，旁边就是「刷新」按钮。点它去重拉最新数据、把表单重填成最新内容（`conflict-hint` 随之变成「已重新拉取最新数据，表单已是最新内容，请确认后重新保存。」）。

⑤ **刷新是"重做"而不是"重试"**：拿旧 version 反复点保存，永远还是 409 —— 后端不会覆盖被抢改的数据。这一点在 UI 文案、`OptimisticLockGuard` 注释、MCP 工具描述里写的是同一句话。

## 凭什么证明好了

**① 能演的：一条用例，两个独立 browser context**（`e2e/tests/scenarios/并发与竞态/版本冲突/商品编辑并发.spec.js`）

| 步骤 | 断言 |
| --- | --- |
| ① 建一件一次性商品 | 新建即 `version=0`；两个会话各自打开的弹窗里名字都是原始值（**两边都是同一份 V**） |
| ② 甲保存 | HTTP **200** + `code=0`；库里名字变成甲的值；`version` 由 **0 → 1**；甲的弹窗收起 |
| ③ 乙保存（手里还是 0） | HTTP **409**（不是 200 + body 里说失败）+ `body.code=409` + `message` 一字不差是那句后端原文 |
| ③b 库里没被覆盖 | 名字仍是甲的值、`version` 仍是 **1** —— 乙这次**一个字段都没写进去** |
| ③c 界面给下一步 | 冲突弹窗可见、`conflict-message` / `conflict-hint` 都在、**「刷新」按钮必须存在** |
| ④ 乙刷新后重来 | 表单被重填成**甲的值**；再改再存 → HTTP 200；库里变成乙的值、`version` **1 → 2** |

证据落盘：这次 409 的**状态码 + 完整响应体**（含 `sentVersion: 0`、`sentName`）写进 `e2e/report/shots/6-商品编辑并发冲突-乙409响应.json`。用例自给自足（自己建、自己删），同一份库连跑两轮不留残留。

```bash

  scripts/e2e-run.sh "tests/scenarios/并发与竞态/版本冲突/商品编辑并发.spec.js" --no-reset
```

## 附：口径与边界

- **409 是这套系统里唯一"非 0/1"的业务 code**（沿用 HTTP 语义），前端据此弹「刷新」对话框。看到 `200 + code=1` 的，那是**业务守卫**（状态不对），不是版本冲突 —— 两者别混。
- **`version` 缺了是 400，不是 409**：缺版本号说明调用方（老前端 / 脚本 / MCP）根本没带锁，属于调用错误；409 才是"带对了但过期了"。
- **刷新之后必须"重新确认"，不是"自动重放"**：重填成最新值再把改动叠上去，人得再看一眼（可能别人的改动和你的改动语义冲突，比如一个改了分类、一个改了类型）。`conflict-hint` 的第二句就是在要求这一步。
- **它只管"同一行被两个人改"**：跨行/跨表的一致性（改了 SKU 价格但商品主表没动）不在这里兜，那要靠业务事务，不是乐观锁。
- **本页不给新数字**：所有数字（`version` 0→1→2、HTTP 200/409、`code=0/400/409`）都来自用例断言与 `OptimisticLockGuard` 的常量原文。这一批没有「实测数字」块，证据形态是"两个会话 + 真 409 响应落盘"。
