## 商品编辑并发（optimistic lock / product.version）

商品编辑弹窗拿到的是整份表单。两个人同时打开、各自改一个字段，后保存的那份按 `WHERE id = ?` 整行覆盖，先保存的改动被静默改回去，而两边都收到「保存成功」—— 这就是 last-write-wins，不留痕：`code=0`、页面绿字、库里有值，一周后没人能解释某个字段为什么变回去了。

拒绝的依据是落库那句的影响行数，不是读到了什么。每条可编辑记录带 `version`，请求必须带（缺了返回 `code=400`，绝不退化成无版本 UPDATE —— 那等于什么都没做，外人还看不出来），落库是 `UPDATE ... WHERE id = ? AND version = ?`：影响 1 行是赢，影响 0 行是手里那份已经过期。

0 行必须变成真 HTTP 409，不能是 `200 + body.code`。写成 `Result.fail(...)` 时 Spring 会包成 HTTP 200，curl 脚本、监控、网关日志、第三方都会把这次冲突记成成功；所以统一抛 `LockException`、由异常处理映射成真 409，body 里同时带 `code=409`。两种「0 行」要分开说：有 `version` 列的表是「数据已被他人修改（可能其他人在编辑），请刷新后重试」，没有 `version` 列的表（字典、子表）是「记录已被删除，请刷新后重试」—— 都 fail-closed，按成功返回就是假成功。

前端给的是可执行的下一步：`ConflictDialog`（`conflict-message` + `conflict-hint`）说明被别人改过、这次填写的内容没有被保存，旁边就是「刷新」按钮；点它重拉最新数据并重填表单，提示随之变成「表单已是最新内容，请确认后重新保存」。刷新是重做不是重试 —— 拿旧 version 反复点保存，永远还是 409。

**验证**　`商品编辑并发.spec.js`：1 条用例、39 处断言，两个独立 browser context 真并发，自建一次性商品。断言要点：两个会话弹窗里是同一份原始值；甲保存 HTTP 200 + `code=0`、库里名字变甲的值、`version` 0 → 1、弹窗收起；乙保存（手里还是 0）拿到 HTTP 409 而不是 200 + body 里说失败、`body.code=409`、`message` 逐字等于后端原文；库里名字仍是甲的、`version` 仍是 1，乙一个字段都没写进去；冲突弹窗可见，`conflict-message` 与 `conflict-hint` 都在且「刷新」按钮存在；点刷新后表单重填成甲的值，再改再存 HTTP 200、`version` 1 → 2。这次 409 的状态码与完整响应体（含 `sentVersion: 0`）落盘到 `e2e/report/shots/6-商品编辑并发冲突-乙409响应.json`。

**边界**　409 是这套系统里唯一非 0/1 的业务 code（沿用 HTTP 语义）；`200 + code=1` 是业务守卫（状态不对），不是版本冲突。缺 `version` 是 400 而不是 409：说明调用方根本没带锁，属于调用错误。刷新之后必须重新确认，不是自动重放 —— 别人的改动可能与这次的改动语义冲突。它只管同一行被两个人改，跨行跨表一致性靠业务事务。没演到的路径：缺 version 的 400 只有后端断言，没有 UI 路径；「记录已被删除」那类文案没有 UI 用例；三会话并发未测。数字出处：`version` 0→1→2、HTTP 200/409、`code=0/400/409` 全部来自这条用例的断言与 `OptimisticLockGuard` 的常量原文。
