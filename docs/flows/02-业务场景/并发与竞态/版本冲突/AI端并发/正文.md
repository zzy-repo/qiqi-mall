## AI 端并发（MCP write tools / version passthrough）

MCP 服务能改真数据：`update_product` 改商品名、描述、分类、上下架，`update_sku_stock` 改 SKU 价格与库存。要回答的问题只有一个：AI 会不会绕过人在 UI 上会撞的那把锁。绕过的话它就是一条能静默覆盖别人改动的旁路，且不知道自己在覆盖谁；撞上同一把锁，它只是「另一个客户端」—— 谁先写谁算数，后到的被拒。

锁在数据层：`UPDATE ... WHERE id = ? AND version = ?` 影响 0 行即过期，后端统一映射成 409。浏览器、curl、MCP、另一个 AI 走同一句 SQL，所以 AI 这一侧不需要新机制，只需要把锁值可靠地传进传出。

四件事必须做对。读工具必须吐 `version`，那是写工具唯一合法的输入，不能因为「详情不需要」就过滤掉。写工具的 `version` 在 zod 层必填 —— 一旦可选模型就一定漏（它只有上下文，没有「上次读到什么」这种状态）。409 必须原样透给模型并显式带 `[409]`，文案写明「手上的 version 已过期，请重新调用 `get_product_detail` 拿最新 version，把最新数据和要改的内容一起念给用户确认后再重试；旧 version 重试不会成功」；只说「失败了」，模型会重试，而这类 409 重试无用。写成功后回读一次把新 version 交给模型，否则上下文里留着旧锁，下次改同一对象必然 409。

另外两条边界。分类 / 商品类型 / 属性这三张字典表没有 `version` 列，写工具也就没有 version 参数，并发兜底靠另一种 409 ——「记录已被删除」（改一条刚被别人删掉的记录，影响 0 行），语义是「读到的那条已经没了」，与「被别人改过」不是一回事。写权限也是开关：`write=0` 启动时两个写工具不出现，只读工具齐全。

**验证**　`mcp-server/test/optimistic-lock.mjs`：stdio 真启动 `src/index.mjs`，连真库与真后端，12 处 `assert`：只读工具返回里含 `version`（商品与每个 SKU）；带正确 version 修改成功、回读 version +1 并直连库确认；带旧 version 被拒，错误文本同时含「数据已被他人修改」与 `[409]`，库里名字仍是上一轮的值；不带 version 被 zod 层拒绝、DB version 前后不变（请求没到后端）；并发场景 —— MCP 先读到 V，再由「另一个人」用裸 HTTP 改同一商品（`code=0`），MCP 拿 V 提交被 409，重读 V+1 后提交成功；`update_sku_stock` 同口径三种情形；`write=0` 启动后两个写工具消失、只读工具齐全。数据自给自足：只改动态探测到的一个商品和它的第一个 SKU，每个用例都重读最新 version 再改，不硬编码 version、不 reset 库，能连跑两轮。

**边界**　AI 没有特权是设计：给它放宽就得在后端开一条旁路，那等于把静默覆盖重新引进来。安全边界不靠提示词 —— 工具描述里的「请重新读取、不要重试」只是引导，真正拦住的是后端那句 SQL。`409` 是「重新读」不是「重试」，旧 version 重试一万次还是 409；任何「自动重试 + 自动换 version」的实现都在做未确认的覆盖。没演到的路径：并发那一格只有「裸 HTTP 抢先写一次」这种形态，两个 MCP 进程同抢一个对象没测；MCP 侧没有 UI 冲突弹窗，「人机混合并发」的体验本页没有承诺；字典三表「记录已被删除」有机制没有用例。数字出处：全部来自这份机制测试的断言与错误文本原文。
