**AI 端并发：AI 和人站在同一个闸门前，谁先写谁算数** —— AI 读完一件商品拿到 `version`，这中间有人在后台改了同一件商品（版本往后推一格），AI 拿着旧版本提交改名 → 后端 **409**，且错误文本**原样透给模型**并显式带 `[409]`；工具描述和错误文案都把下一步写成"**重新读，不是重试**"。AI 重读拿到新版本再提交，这次才写得进去。**锁加在数据层，不在 AI 那侧** —— 它的安全边界不靠提示词，靠后端那把锁。

## 场景

AI 助手（通过 MCP 服务）现在能改真数据：`update_product` 改商品名/描述/分类/上下架，`update_sku_stock` 改 SKU 价格与库存。这就带来一个必须回答的问题：**AI 会不会绕过人在 UI 上会撞的那把锁？**

- 如果它绕过去了，AI 就是一条"能静默覆盖别人改动"的旁路 —— 而且是最危险的那种：它不知道自己在覆盖谁，操作人也没看到任何冲突提示。
- 如果它撞上了同一把锁，那 AI 就只是"另一个客户端"，人和 AI 的并发行为完全一致：**谁先写谁算数，后到的被当场拒绝**。

这一页讲的正是后者，以及为了让后者成立，MCP 那一层必须做什么。

## 撑不住的时候

坏环境有四种形态，每一种都不是"崩了"，而是**看起来很顺**：

- **读接口不吐 version**。模型手上没有锁值，只能凭记忆猜一个数字提交 —— 于是"改成功"和"改了个寂寞"取决于运气。所以读工具（`list_products` / `get_product_detail` / `list_skus`）必须把 `version` 一起吐出来，那是写工具**唯一合法的输入**。
- **写工具不强制带 version**。一旦 `version` 是可选参数，模型就一定会漏（它没有"上次读到什么"这种状态概念，只有上下文）。所以 `version` 在 **zod 层就是必填** —— 缺了连后端都调不到，报的是参数校验错误而不是业务错误。
- **409 被包装成一句"失败了"**。模型看到"失败了"的默认策略是**重试**；而乐观锁的 409 是**重试无用**的（后端 fail-closed，一个字段都不会覆盖）。于是模型会拿旧 version 反复重试，每次都失败，最后向操作人汇报"系统不稳定"。
- **成功之后不回读新版本**。后端写成功只回 `{code:0, data:null}`，**不回新 version**。如果工具层不回读，模型上下文里留着的还是旧 version，下一次改同一个对象必然 409 —— 而且它不知道为什么。

## 改了什么

① **读工具吐 `version`**：商品本体与它下面每个 SKU 都带。这是写工具的输入来源，不许在详情/列表里把它过滤掉。

② **写工具强制 `version`（zod 必填）**，描述里写清"必须来自最近一次读取（`list_products` / `get_product_detail` / `list_skus` 返回的 version）；不要凭记忆猜"。缺了 → MCP 层就拒（请求根本到不了后端，DB version 不变）。

③ **409 原样透给模型，并显式带 `[409]`**（`failWrite`）。文本是四段：

```
❌ 商品修改失败：[409] 数据已被他人修改（可能其他人在编辑），请刷新后重试
对象：productId=… 目标名称=「…」
原因：你手上的 version=… 已经过期，说明期间有人改过这条数据（你读完它之后又被写了一次）。
下一步：请重新调用 get_product_detail 拿最新 version，把最新数据和这次要改的内容一起念给用户确认后再重试。
        不要重复使用旧 version —— 后端不会覆盖被抢改的数据，旧 version 重试多少次都还是这个 409。
```

`400`（缺版本）走另一段文案：说明后端 fail-closed、绝不静默降级成后写覆盖，下一步是"先用只读工具拿 version"。

④ **成功后回读一次，把新 version 交给模型**：工具层在写成功后调一次只读工具拿 `newVersion`，并在响应里写「下次再改这个商品请用 `version=<新值>`（旧 version 会被后端 409 拒掉）」—— 这样模型下一轮不会拿着一把已经作废的锁去撞墙。

⑤ **没有 version 列的表不许凭空造 version**：分类 / 商品类型 / 属性这三张字典表**没有** `version` 列，所以它们的写工具**没有** version 参数（用户定的口径：没有 version 列就不造）。并发兜底靠另一种 409 ——「记录已被删除」：改一条刚被别人删掉的记录 → `UPDATE` 影响 0 行 → 409，而不是静默返回成功。

⑥ **写权限本身也是一道闸**：`write=0` 启动时两个写工具直接不出现（`update_product` / `update_sku_stock`），只读工具齐全 —— AI 能做什么由**部署时的工具集**决定，不是由提示词决定。

## 凭什么证明好了

**① 可复跑的机制测试：`mcp-server/test/optimistic-lock.mjs`**（stdio 真启动 `src/index.mjs` + 真库 + 真后端，`node test/optimistic-lock.mjs`）

| 断言 | 内容 |
| --- | --- |
| ① | `search_products` / `get_product_detail` 返回里**含 `version`**（商品 + 每个 SKU） |
| ② | `update_product` 带正确 version → 成功，**回读 version +1，并直连库双确认**（回读的值是真的） |
| ③ | 带**旧** version → 被拒，错误文本同时含「数据已被他人修改」与 `[409]`，且**库里名字仍是上一轮的值**（没被改） |
| ④ | **不带** version → zod 层拒绝，且 DB version 前后不变（证明请求没到后端） |
| ⑤ | **并发场景（核心）**：MCP 读到 V → 另一个人用裸 HTTP 改同一商品（`code=0`）→ MCP 拿 V 提交 → **409** → 重读 V+1 → 提交成功 |
| ⑥ | `update_sku_stock` 同口径（正确 / 旧 / 缺 version 三种） |
| ⑦ | `write=0` 启动 → 两个写工具消失、只读工具齐全 |

第 ⑤ 条是本页的题眼：它不是"我们相信 AI 会撞锁"，而是**让一个"别人"真的先把数据改掉**，再看 AI 那一次提交会不会被拒 —— 撞的确实是同一把锁。

```bash
# 前置：后端 18080 可达 + export MALL_API_KEY=$(cat /tmp/test-env-ai-key.txt)
cd mcp-server && node test/optimistic-lock.mjs
```

数据自给自足：只改一个动态探测到的商品（和它的第一个 SKU），结束后尽量恢复原值；每个用例都**重读最新 version 再改**，不硬编码 version、不 reset 库、不删行，所以能连跑两轮。

## 附：口径与边界

- **AI 没有特权，这是设计而不是巧合**：锁在数据层（`UPDATE ... WHERE id=? AND version=?`），任何客户端 —— 浏览器、curl 脚本、MCP、另一个 AI —— 走的是同一句 SQL。想给 AI 放宽，就得在后端开一条旁路，那等于把"静默覆盖"重新引进来。
- **安全边界不靠提示词**：工具描述里那些"请重新读取、不要重试"只是**引导**，真正拦住的是后端的 409；反过来，如果没有后端这把锁，光靠提示词约束一个模型是不可能的。
- **`409` 是"重新读"，不是"重试"**：旧 version 重试一万次还是 409。任何"自动重试 + 自动换 version"的实现都在做**未经用户确认的覆盖**，这正是要禁止的动作。
- **没有 version 列的表不造 version**：字典三表用「记录已被删除」的 409 兜底，语义是"你读到的那条已经没了"，和"被别人改过"不是一回事。
- **本页不给新数字**：没有吞吐/耗时类数字可给，证据形态是**机制测试的断言清单**（8 条）+ 错误文本原文。这一批没有「实测数字」块。
