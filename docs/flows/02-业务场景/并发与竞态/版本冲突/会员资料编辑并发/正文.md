## 会员资料编辑并发（optimistic lock / member.version）

锁和商品页是同一把（`member.version`），失败之后人该怎么做却完全不同：会员编辑弹窗**没有**冲突弹窗，也没有「刷新」按钮。两个客服同时改同一个会员的昵称时，甲保存成功、乙拿到 409，乙能做的只有关弹窗、重拉列表、重开这个会员，再改一次。

拒绝的依据仍是落库那句的影响行数：缺 `version` → `code=400`；落库 `UPDATE ... WHERE id = ? AND version = ?`；影响 0 行 → 真 HTTP 409（`OptimisticLockGuard.requireAffected`）。会员页的失败提示照抄后端原话，不另编文案：`ElMessage.error('保存失败：' + e.message)`，于是红字就是「保存失败：数据已被他人修改（可能其他人在编辑），请刷新后重试」—— 提示语自带下一步，这是没有冲突弹窗时的兜底设计。失败时弹窗必须保持打开、表单不清空：如果 409 之后弹窗自己收起，客服刚填的内容和正在处理的上下文一起消失，「刷新后重试」就变成「从头再填一遍」。

会员页的「刷新」是三个真实动作：取消或关闭弹窗 → 重新拉一次会员列表（昵称列已显示甲的值）→ 重开这个会员的弹窗（表单回填甲的值）。用例就是这么走的，没有走「内部偷偷重放」的捷径 —— 那等于把别人刚改的内容在用户不知情时覆盖掉，正是版本号要禁止的动作。弹窗只暴露真实字段：登录名 / 昵称 / 手机号 / 状态，没有密码项（`member.password` 在库里可以是空串，登录走另一套流程），出现一个改不了的密码框只会让客服以为自己在改密码。

**验证**　`会员资料编辑并发.spec.js`：1 条用例、38 处断言，两个独立 browser context 真并发，两个 context 各有自己的令牌（用例比对了 `storageState`），不是同一浏览器两个标签页共享登录态造出来的假并发。断言要点：自建会员 `version=0`；两边弹窗里是同一个旧昵称；甲保存 HTTP 200 + `code=0`、库里昵称变甲的值、`version` 0 → 1、弹窗收起；乙保存（手里还是 0）→ HTTP 409 + `body.code=409` + `message` 等于后端原文，页面红字是 `保存失败：` + 原话，**没有任何成功提示**（`success` toast 计数为 0），**弹窗仍开着**；库里昵称仍是甲的、`version` 仍是 1；乙关弹窗、重拉列表、重开 → 列表昵称列与弹窗回填都是甲的值；再改一次保存 → HTTP 200、`version` 1 → 2。

**边界**　锁相同、交互不同：商品与 SKU 页有 `ConflictDialog` 与「刷新」按钮，会员页没有 —— 这不是漏做，是两个页面的既有形态，所以「409 之后怎么继续」必须按页面分开写，不能把商品页的交互当通用答案。缺 `version` 是 400（调用错误，刷新也救不了，得改调用方），过期才是 409（并发冲突），两者在页面上都表现为红字但含义不同。没演到的路径：缺 version 的 400 没有 UI 路径、只有后端断言；会员禁用/启用的并发没做用例（本页只演改昵称）；三个会话同时写未测；「列表里别人刚改的行要不要自动刷新」这类交互本页没有承诺。数字出处：`version` 0→1→2、HTTP 200/409、`code` 0/400/409 全部来自这条用例的断言与 `OptimisticLockGuard` 常量。
