**会员资料编辑并发：同一把锁，但页面没有"冲突弹窗"可点** —— 两个客服同时改一个会员的昵称。甲保存成功（`version` 0 → 1）；乙手里还是 0，保存 → **真 HTTP 409**，页面显示的是 `保存失败：` + 后端原话（会员页没有冲突弹窗），库里昵称仍是甲的值、版本号仍是 1；乙要**自己**关弹窗 → 刷新列表 → 重开这个会员 → 表单回填成甲的值 → 再改一次才写得进去（`version` 1 → 2）。

## 场景

会员资料是客服每天都在动的东西：改昵称、改手机号、禁用/启用。两个客服同时打开同一个会员的编辑弹窗非常容易发生 —— 一个人在处理工单，另一个人在核对资料。

入口：后台会员管理（`admin-web/src/views/member/index.vue`，`PUT /admin/members/{id}`）。这页跟 `商品编辑并发` 是**同一个母题、不同的页面事实**：锁是同一把（`member.version`），但**失败之后人该怎么做**完全不一样，而这正是最容易写歪的地方。

## 撑不住的时候

- **晚到的那次不许静默覆盖**。没有 version 时，两次保存都成功：甲把昵称改成「小七」，乙把昵称改成「阿九」，最后库里是乙的，甲那份改动无声消失，而甲看到的是「保存成功」。客服照着"改成功了"的回复去回工单，客户那边看到的却是另一个名字。
- **页面没有"刷新"按钮可点，人就会拿旧表单硬试**。这是本页最具体的坏环境：会员弹窗**没有** `ConflictDialog`，409 之后只有一条红字提示。如果文案只说"失败了"，客服的直觉动作是**再点一次保存** —— 拿的还是旧 `version`，于是**永远还是 409**，反复几次之后他会认为"系统坏了"。所以文案本身必须带下一步（原话里就有"请刷新后重试"），而且刷新这件事在 UI 上要能真的做到：关弹窗 → 重新拉列表 → 重开。
- **失败时弹窗不能自动关掉**。如果 409 之后弹窗自己收起，客服刚填的内容和他正在处理的上下文一起消失，"刷新后重试"就变成了"从头再填一遍"。

## 改了什么

① **`member.version` 乐观锁**，同一套守卫：缺 version → `code=400`；落库 `WHERE id = ? AND version = ?`；**影响行数 0 → 真 409**（`OptimisticLockGuard.requireAffected`）。

② **失败提示照抄后端原话，不另编文案**：会员页走 `ElMessage.error('保存失败：' + e.message)`，于是红字就是「保存失败：数据已被他人修改（可能其他人在编辑），请刷新后重试」。**提示语里自带下一步**，这是会员页没有冲突弹窗时的兜底设计。

③ **失败时弹窗保持打开**（表单不清空、不自动收起），让人还能看清自己填了什么、也能取消重来。

④ **"刷新"在会员页是三个真实动作**：取消/关闭弹窗 → 重新拉一次会员列表（列表里昵称列已显示甲的值）→ 重开这个会员的编辑弹窗（表单回填甲的值）。用例就是这么走的，**没有**走"内部偷偷重放"的捷径。

⑤ **弹窗只暴露真实字段**：登录名 / 昵称 / 手机号 / 状态，**没有密码项**（`member.password` 在库里可以为空字符串，登录走的是另一套流程）。弹窗里出现一个改不了的密码框，只会让客服以为自己在改密码。

## 凭什么证明好了

**① 能演的：一条用例，两个独立 browser context**（`e2e/tests/scenarios/并发与竞态/版本冲突/会员资料编辑并发.spec.js`）

| 步骤 | 断言 |
| --- | --- |
| ① 自建一个会员 | 新建即 `version=0`；库里昵称 = 新建时填的 |
| ② 两会话各开编辑弹窗 | 两边输入框里都是**同一个**旧昵称（同一份 V=0） |
| ③ 甲改昵称保存 | HTTP **200** + `code=0`；库里昵称变成甲的值；`version` **0 → 1**；弹窗收起 |
| ④ 乙保存（手里还是 0） | HTTP **409** + `body.code=409` + `message` 等于后端那句原文；页面红字 = `保存失败：` + 原话；**没有任何成功提示**（`success` toast 计数为 0）；**弹窗仍开着** |
| ④b 没被覆盖 | 库里昵称仍是甲的值、`version` 仍是 **1** |
| ⑤ 乙按提示刷新（关弹窗 → 重拉列表 → 重开） | 列表昵称列已显示**甲的值**；重开的弹窗回填的是**甲的值** |
| ⑥ 乙再改一次保存 | HTTP 200；库里变成乙的值、`version` **1 → 2** |

隔离性也是断言的一部分：两个 context 各有自己的令牌（用例里比对了 `storageState`），不是"同一个浏览器两个标签页共享登录态"造出来的假并发。

```bash
E2E_FRONT_MODE=dev E2E_SHARDS=1 E2E_SHARD_FROM=1 \
  scripts/e2e-run.sh "tests/scenarios/并发与竞态/版本冲突/会员资料编辑并发.spec.js" --no-reset
```

## 附：口径与边界

- **锁相同，交互不同**：商品/SKU 页有冲突弹窗（`ConflictDialog` + 「刷新」按钮），会员页没有 —— 这不是漏做，而是两个页面的既有形态。所以"409 之后怎么继续"必须按页面分开写，别把商品页的交互当成通用答案。
- **`409` 与 `400` 的区别照旧**：缺 version 是 400（调用错误），过期是 409（并发冲突）。两者在页面上都表现为红字，但含义与处置不同 —— 400 是"你没带锁"，刷新也救不了，得改调用方。
- **"刷新"必须真的重读，不许内部重放**：如果前端拿到 409 之后偷偷把 version 换成最新的再提交一次，看上去"自动修好了"，实际是把别人刚改的内容**在用户不知情的情况下**覆盖掉 —— 那正是版本号想禁止的事。
- **本页不给新数字**：`version` 0→1→2、HTTP 200/409、`code` 0/400/409 全部来自用例断言与 `OptimisticLockGuard` 常量；本批没有「实测数字」块。
