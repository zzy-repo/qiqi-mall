## SKU 编辑并发（optimistic lock / sku.version）

商品编辑走 `product.version`，SKU 编辑走 `sku.version` —— 两张表、两条链路、两把锁。只在一个对象上验证过乐观锁，证明不了另一个对象也挡得住；而 SKU 恰恰是价格与库存同在一行、最容易被并发改坏的地方（运营改价、仓管调库存、活动临时调价同时在跑）。

拒绝的依据同样是落库那句的影响行数。请求必须带 `version`（缺 → `code=400`），落库 `UPDATE ... WHERE id = ? AND version = ?`，影响 0 行 → `LockException` → 真 HTTP 409 + body `code=409`。判据不能用「`updateById` 没抛异常」：它返回的是 int，不看它就没有任何信号，0 行也会被当成功返回。

两个 SKU 特有的点。一是价格与库存是同一行的两列：乙那份基于旧数据的表单里 `stock` 也是旧值，若整行覆盖，后提交会顺手把库存改回旧值 —— 这就是「改价带走库存」的成因。所以只提交真的改了的字段（价格 + version），库存一动不动，这条不变量在用例里单独钉住。二是刷新回调按对象分开写：商品弹窗刷新后重拉商品、重填并关弹窗；SKU 弹窗刷新后重拉 `GET /admin/skus/{id}` 重填、弹窗不关（人还在原地继续改）。两条链路各写各的回调，不共用一份「看起来差不多」的代码；冲突弹窗仍是同一个 `ConflictDialog`，保证两个页面的文案不漂移。

**验证**　`SKU编辑并发.spec.js`：1 条用例、40 处断言，两个独立 browser context，自建一次性商品与 SKU。断言要点：初始 `price=1200`、`version=0`，两个会话弹窗里都是 1200；甲改 1999 → HTTP 200 + `code=0`、库里 1999、`version` 0 → 1、弹窗收起；乙改 888（手里还是 0）→ HTTP 409 + `body.code=409` + 那句中文原文，冲突弹窗可见、「刷新」按钮文案就是「刷新」；被拒那次不推进版本号，库里仍是 1999、`version` 仍是 1；乙点刷新后冲突弹窗收起、SKU 编辑弹窗仍然开着、价格输入框被重填成 1999；再改 888 保存 → HTTP 200、库里 888、`version` 1 → 2；全程 `stock` 恒为 30。

**边界**　两把锁互不影响：改商品名不会让 SKU 编辑的 version 过期，反之亦然 —— 所以「商品页面能挡住」推不出「SKU 页面也能挡住」。`stock` 是展示缓存，由桶和周期回写，扣减与回补都不写它，所以这里「库存不动」指的是这次改价没有写 `sku.stock`，不是库存永远不变。刷新不等于重试：拿旧 version 再点一次保存永远是 409。`code=1` 是业务守卫、`code=409` 才是版本冲突，页面上走的是不同组件。没演到的路径：缺 version 的 400 只有后端断言，没有 UI 路径；同一次请求里既改价又改库存的路径没有用例（本页只演「只改价」）；三个会话并发也没测。数字出处：1200 / 1999 / 888 / 30 与 `version` 0 → 1 → 2 全部来自这条用例的常量与断言。
