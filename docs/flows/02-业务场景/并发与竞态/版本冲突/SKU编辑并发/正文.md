**SKU 编辑并发：撞的是另一张表、另一把锁** —— 两个管理员同时打开同一个 SKU 的弹窗，甲改价 1200 → 1999 保存成功（`sku.version` 0 → 1）；乙手里还是 0，改 888 提交 → **真 HTTP 409**，库里价格仍是 **1999**、版本号仍是 **1**；乙点「刷新」（SKU 弹窗**不关**，直接重拉 `GET /admin/skus/{id}` 重填）→ 表单变 1999 → 再改成 888 提交成功（版本号 1 → 2）。全程 `stock` 一直是 **30** —— **改价不许带走库存**。

## 场景

商品编辑走的是 `product.version`，SKU 编辑走的是 **`sku.version`** —— 两张表、两条链路、两把锁。为什么值得单独一页：只在一个对象上验证"乐观锁能用"，证明不了别的对象也挡得住；而 SKU 恰恰是**价格与库存都在这张表上**、最容易被并发改坏的地方（运营改价、仓管调库存、活动临时调价）。

入口：商品维护 → 某商品的 SKU 列表 → 行内「编辑」（`admin-web/src/views/product/skus.vue`，行锚点 `sku-row-<skuId>`），保存走 `PUT /admin/skus/{id}`（`SkuController#update`）。

## 撑不住的时候

- **两个窗口拿到同一份数据，各自改价**。甲、乙打开弹窗时看到的都是 1200、手里都是 `version=0`。没有版本号时，两次保存都成功，**后到的把先到的盖掉**：甲把价改成 1999、乙把价改成 888，最后库里是 888，甲那份改动连痕迹都不剩，而且甲收到的是「保存成功」。
- **价格与库存是同一行的两列，一起被覆盖**。这是 SKU 特有的风险：乙那份"基于旧数据"的表单里，`stock` 也是他打开时的旧值。如果保存时整行覆盖，乙的后提交会**顺手把库存改回旧值** —— 库存明明被下单扣过，却因为一次改价被推回去。这就是"改价带走库存"那个 bug 的成因。
- **影响行数是唯一能分辨"赢"与"输"的东西**。接口如果只看 `updateById` 没抛异常就当成功，那么 0 行的 UPDATE 也会被当成成功返回（MyBatis-Plus 的 `updateById` 返回 int，不看它就没有任何信号）。所以判据必须是**落库那一句的影响行数**：0 行 = 你手里那份已经过期。

## 改了什么

① **`sku.version` 乐观锁**：请求必须带 version（缺 → `code=400`），落库 `UPDATE ... WHERE id = ? AND version = ?`，**影响行数 0 → 真 409**（`OptimisticLockGuard.requireAffected` → `LockException` → 真 HTTP 409 + body `code=409`）。

② **刷新回调按对象分开实现**：商品弹窗刷新后是重拉商品、重填表单**并关弹窗**；SKU 弹窗刷新后是**重新拉 `GET /admin/skus/{id}` 重填表单、弹窗不关**（人就在原地继续改）。两条链路各写各的回调，不共用一份"看起来差不多"的代码。

③ **只提交"真的改了的字段"，尤其不碰库存**：弹窗里改的是价格，保存就只带价格（+ version）。所以乙被拒时库存一动不动；乙刷新后重来也只改价。这条约束是**用例单独钉住的不变量**（`final.stock === STOCK_0`），不是"相信它不会动"。

④ **冲突弹窗与商品页共用同一个组件**（`ConflictDialog`：主文案 + "你刚才填写的内容没有被保存"的提示 + 「刷新」按钮），保证两个页面上的处理体验一致、文案不漂移。

## 附：口径与边界

- **两把锁是分开的**：`product.version` 与 `sku.version` 互不影响。改商品名不会让 SKU 编辑的 version 过期，反之亦然 —— 所以"商品页面能挡住"不能推出"SKU 页面也能挡住"。
- **`stock` 是展示缓存**：`sku.stock` 由 `SUM(sku_bucket.stock)` 周期回写，扣减/回补不写它、也不拿它裁决（见 `库存对账` 那一页）。所以这里"库存不动"指的是**这次改价没有写 `sku.stock`**，不是说库存永远不变 —— 下单、回补都会让它在别的路径上变。
- **刷新 ≠ 重试**：拿旧 version 再点一次保存，永远还是 409。必须先拿新 version（刷新），再重新提交。这条在 UI 提示、后端异常文案、MCP 工具描述里是同一句。
- **409 与"状态守卫"不是一回事**：`code=1` 是业务守卫（状态不对，例如"只有待下发包裹可以编辑"），`code=409` 才是版本冲突。两者在页面上走的是不同组件（一个 toast / 表单内错误、一个是冲突弹窗），别互相顶替。
- **本页不给新数字**：1200 / 1999 / 888 / 30 与 `version` 0→1→2 都来自这条用例的常量与断言；本批没有「实测数字」块，证据形态是"两个会话 + 真 409 落盘 + 库存不变量"。
