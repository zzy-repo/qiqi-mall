**发货单与仓库回传：商家在弹窗里犹豫，仓库已经把包裹发出去了** —— 商家的改仓提交必须被拒，而且**改仓一个字段都没写进去**：库里仓库仍是原仓、包裹仍是已出库(3)、来源仍是自动拆单(0)。挡它的是两道不同的闸：**预演阶段的状态守卫**先拦（HTTP 200 + `code=1`），执行阶段才轮到**版本号**（`code=409`）。本页这一撞停在第一道，因为包裹已经被回传出库了。

## 场景

包裹在「待下发」阶段是**可以人工干预**的：改发货仓、改数量、拆分、合并、删除。这些动作的价值就在这个窗口里 —— 仓库还没接单，还来得及改。

而窗口的另一侧是活的：仓库随时可能把这个包裹下发、拣货、出库，并回传事件。**改单的人看不到仓库也在动同一个包裹**，他眼前只有一个开着没提交的弹窗。所以这一页要证的不是"界面能拦住"，而是：**两个会话各自动作之后，库里的数据只按先到的那一次算，晚到的那次一个字段都不落。**

## 撑不住的时候

坏环境长这样：商家在改仓弹窗里选好了另一个仓，停住不提交；这期间仓库把包裹下发、还回传了「已出库」，包裹状态从 0 → 1 → 3，版本号一路往后走两格。商家这时点「确定」。

不许发生的事有两条，都很具体：

- **后到的整段覆盖**。如果提交只按 `WHERE id = ?` 落库，商家那份"基于待下发"的表单会连同仓库的两步回传一起被冲掉：包裹被拽回一个已经不存在的状态，仓库那边"已出库"的事实被抹平，而**没有任何提示**。这就是 last-write-wins，看不出错，但账已经错了。
- **靠状态守卫单打独斗不够**。状态守卫看的是"是不是还是待下发"。可是还有一种撞法：状态**没变**（还是待下发），但另一个人刚改过数量/仓库 —— 守卫照样放行，于是两笔修改里后到的那笔把先到的那笔盖掉。这种情况只有版本号接得住。

所以两道闸各管一件事，顺序也有讲究：`DeliveryController` 的执行路径是 **① 参数/存在性 → ② version（缺 → 400，冲突 → 409）→ ③ 业务守卫（待下发）** —— **version 排在业务守卫前面**，因为"数据被别人改过"和"状态不对"是两件事，混在一起会让调用方（和看日志的人）查错方向。

## 改了什么

① **两段式接口：先预演，再执行**。7 个写操作统一契约：`?dryRun=true` 只算不落库、返回 `{ willDo: "中文描述" }`；同一地址不带 `dryRun` 才是执行。预演方法（`DeliveryEditService#previewXxx`）与执行路径**共用同一套守卫** `requirePending` —— 所以"这个包裹已经不能改了"在预演阶段就说得出口，不用等真正提交。

② **守卫的原文是给现场人看的**：`只有待下发包裹可以编辑（当前状态 3，已下发的只能取消）` —— 带上**当前状态码**，因为读的人下一步要判断"是等签收、还是取消重发"。

③ **执行路径的版本号**：待下发阶段的四个干预动作都收 `version`（`PUT` / `split` / `merge` 走 body，`DELETE` 走 **query 的 `?version=`** —— DELETE 带 body 过代理/CDN 不可靠）。缺版本号一律 `code=400`「缺少版本号，请刷新页面后重试」，**绝不静默降级成无版本 UPDATE**。版本冲突抛 `code=409` +「数据已被他人修改（可能其他人在编辑），请刷新后重试」。

④ **状态流转类接口（dispatch / cancel / wms-callback）不收 version**：它们由「状态守卫 + 影响行数检查」兜住，而且调用方（WMS、运维）手上根本没有前端页面上的 version。这是有意的分流，不是漏做。

⑤ **前端的失败要留在原地**：预演失败的原因写进表单里的 `delivery-form-preview-error`（不是一闪而过的 toast），**表单不收、刚选的仓不回退**；确认弹窗收起。人看得见"为什么不让改"以及"我填的东西还在"。

## 凭什么证明好了

**① 能演的：一条用例，两个独立 browser context**（`e2e/tests/scenarios/并发与竞态/双向竞态/发货单与仓库回传.spec.js`）

构造方式（这才是"并发"，不是点两次按钮）：

- **甲（商家）**：订单详情抽屉 → 该包裹「编辑」弹窗 → 选好另一个仓，**停住不提交**（手里是待下发那一帧的版本号）；
- **乙（仓库/另一位操作员）**：另起 context，同一个包裹「下发」→「模拟 WMS 回传：出库」→ 包裹变已出库(3)；
- **甲再提交** → 预演阶段被拒。

断言要点（全部按实际返回写，不假装是 409）：

| 断言 | 值的来源 |
| --- | --- |
| 预演请求被拒 | `PUT /admin/deliveries/{id}?dryRun=true` → **HTTP 200 + `code=1`**，`message` = `只有待下发包裹可以编辑（当前状态 3，已下发的只能取消）` |
| 拒绝原因可读、表单不丢 | `delivery-form-preview-error` 的文本 = `预演失败：` + 上面那句；编辑弹窗仍可见；刚选的仓仍在 `delivery-form-warehouse` 里 |
| **改仓没生效** | 库里 `warehouseId` / `warehouseName` 仍是原仓；`status=3`；`source=0`（自动拆单，不是人工调整） |
| 不多不少 | 订单下包裹数仍是 **1** |
| 证据落盘 | 请求体、响应体、截图都写进 `e2e/report/shots/`（不是只留一句"通过了"） |

为什么这次不是 409：`409` 是**执行阶段**版本号对不上时抛的；本次包裹已经出库，预演阶段的状态守卫**先一步**拦下，所以拿到的是 `200 + code=1`。把这条写成 409 就是假验收 —— 那等于在考一条这次没走到的路。

```bash
E2E_FRONT_MODE=dev E2E_SHARDS=1 E2E_SHARD_FROM=1 \
  scripts/e2e-run.sh "tests/scenarios/并发与竞态/双向竞态/发货单与仓库回传.spec.js" --no-reset
```

## 附：口径与边界

- **"改仓没生效"的判据是四个字段一起看**：`warehouseId`、`warehouseName`、`status`、`source`。只看"提示弹出来了"不算证明 —— 提示弹了、数据也改了，才是最坏的那种。
- **预演与执行是两套校验时机**：预演不需要 version（不落库就没有冲突），但**跑同一套业务守卫**；执行阶段才按 `version → 业务守卫` 的顺序查。所以"预演通过"绝不等于"执行一定成功"，中间还隔着别人可能插进来改数据。
- **`409` 只属于"状态没变但数据被改过"**：例如两位操作员同时改同一个待下发包裹的仓库，谁都没动状态。这条本次没被演到（本次是先被状态守卫拦下），别把本页当成 409 的证据。
- **状态流转不收 version 是设计**：dispatch / cancel / wms-callback 的判据是"状态 + 影响行数"，因为它们的调用方拿不到 version。想给它们硬塞版本号，只会让 WMS 回传整批 400。
- **本页不给新数字**：数字全部来自用例断言（状态 0/1/3、`code=1`、包裹数 1、`source=0`）与 `DeliveryController` / `DeliveryEditService` 的守卫原文；这一批没有「实测数字」块，因为证据形态是"两个会话 + 数据落盘"。
