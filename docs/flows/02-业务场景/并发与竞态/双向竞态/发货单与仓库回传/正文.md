## 发货单与仓库回传（preview-then-commit / delivery version）

包裹在待下发阶段可以人工干预：改发货仓、改数量、拆分、合并、删除。窗口的另一侧是活的：仓库随时可能下发、拣货、出库并回传事件，而改单的人看不到仓库也在动同一个包裹。要证的是两个会话各自动作之后，库里只按先到的那次算，晚到的那次一个字段都不落。

接口两段式：7 个写操作统一 `?dryRun=true` 只算不落库、返回 `{ willDo }`，同地址不带 `dryRun` 才执行；预演与执行路径共用同一套守卫 `requirePending`，所以「这个包裹已经不能改了」在预演阶段就说得出口。守卫原文带当前状态码：`只有待下发包裹可以编辑（当前状态 3，已下发的只能取消）`。

执行路径的顺序是 参数与存在性 → version → 业务守卫，version 排在业务守卫前面：缺版本号返回 `code=400`「缺少版本号，请刷新页面后重试」，版本对不上抛 `code=409`「数据已被他人修改（可能其他人在编辑），请刷新后重试」。「数据被别人改过」和「状态不对」是两件事，顺序混了会让调用方查错方向。四个干预动作都收 version（`PUT` / `split` / `merge` 走 body，`DELETE` 走 query 的 `?version=`：DELETE 带 body 过代理与 CDN 不可靠）。状态流转类接口（dispatch / cancel / wms-callback）刻意不收 version：调用方拿不到前端页面上的 version，判据是「状态守卫 + 影响行数」。前端把失败留在原地：原因写进表单里的 `delivery-form-preview-error`，表单不收起、刚选的仓不回退。

**验证**　`发货单与仓库回传.spec.js`：1 条用例、31 处断言，两个独立 context。构造方式：甲打开该包裹的编辑弹窗、选好另一个仓、停住不提交（手里是待下发那一帧的版本号）；乙另起 context 对同一个包裹「下发」再「模拟 WMS 回传：出库」，包裹变已出库(3)；甲再提交，预演阶段被拒。断言要点：`PUT /admin/deliveries/{id}?dryRun=true` 返回 HTTP 200 + `code=1`，`message` 逐字等于那句守卫原文；`delivery-form-preview-error` 是 `预演失败：` + 同一句，编辑弹窗仍可见，刚选的仓仍在 `delivery-form-warehouse` 里；库里 `warehouseId` / `warehouseName` 仍是原仓、`status=3`、`source=0`（自动拆单，不是人工调整）；订单下包裹数仍是 1；请求体、响应体与截图落盘 `e2e/report/shots/`。

**边界**　「改仓没生效」的判据是四个字段一起看：提示弹了、数据也改了才是最坏的那种。预演不需要 version（不落库就没有冲突）但跑同一套业务守卫，「预演通过」不等于「执行一定成功」，中间还隔着别人改数据。`409` 只属于「状态没变但数据被改过」，例如两人同时改同一个待下发包裹的仓库 —— 这条本次没演到，别把本页当 409 的证据。状态流转不收 version 是分流不是漏做，硬塞只会让 WMS 回传整批 400。没演到的路径：`DELETE ?version=` 与 `split` / `merge` 的并发、以及预演后别人改了数据再执行（真 409 那条）都没有用例。数字出处：状态 0/1/3、`code=1`、包裹数 1、`source=0` 与守卫原文，来自用例断言与 `DeliveryController` 常量。
