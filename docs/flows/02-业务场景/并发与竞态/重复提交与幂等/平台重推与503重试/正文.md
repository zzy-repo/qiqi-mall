## 平台重推与 503 重试（channel sync idempotency）

外部世界会抽风：平台把同一批单又推一遍（水位重叠、平台重推、手动再拉），外呼回传时对方回 503 或超时。要能回答两个问题：这批单会不会变成两批，这次失败会不会既没送到、也查不出发生过。

重复拉单的拒法在映射表上：`uk_map(shop_id, platform_sn)` 是幂等键，拉单先查，命中抛 `DuplicateOrderException`，调用方记一行 `SKIP / IDEMPOTENT` —— 不建单、不动库存、也不当错误；整轮最后落一行店铺级汇总。每张单再套 `REQUIRES_NEW` 独立事务：SKU 编码匹配不到就整单失败、记一行 `FAIL / SKU_NOT_MATCHED`、不建半张单，同批其他单照常进待审核 —— 整批一个事务会把「跳过该单」变成「跳过整批」。

回传失败只重试一次、两次各留一行：`MAX_ATTEMPTS = 2`，第 1 次失败落 `FAIL`（`attempt=1`，原因等于平台原话），立刻重试一次，成功再落 `OK`（`attempt=2`）。第几次尝试写在行上，重试过几次由数据自己说明；两次都失败就把错误交回后台，绝不假成功。幂等键落在唯一索引上而不是代码自觉：`idem_key` 是生成列，只在 `action='SHIP_PUSH'` 时等于 `{shopId}:SHIP_PUSH:{refId}:{attempt}`，其余 `NULL`；写入用 `INSERT ... ON DUPLICATE KEY UPDATE id=id`，影响 0 行即这次尝试已记过账，按 `SKIP` 处理，不报错、不覆盖第一行。所以人工再点一次回传是零新增：`attempt` 又从 1 开始，必然撞上第一次那条。

**验证**　`平台重推与503重试.spec.js`：1 条用例、40 处断言，全部直查库与直查 mock、不看 toast；mock 自起在 19090（后端 `channel.mock.base-url` 默认值）。断言要点：淘宝与抖音各拉一次 → 3 笔待审核 + 3 行映射；同一批再推一次 → 每单一行 `SKIP / IDEMPOTENT`、订单数一个不多、该轮只落一行成功汇总；注入 503 后回传 → 该包裹在同步日志里正好 2 行、`attempt=1` 那行 `FAIL` 且原因带 `503`、`attempt=2` 那行 `OK`；抖音侧 `shippedCount = 1`（503 那次没被受理），且记的成功行数等于平台受理次数；再点一次回传 → 库里零新增、老两行全列快照逐字相同（全列都比）、接口 `code=0`、`skipped=1`、`ok=0`、平台侧仍 1 次。两处手法：老行不改用全列快照比对（只比行数会放过改字段改时间）；平台侧计数与自己的成功行数交叉验证（只查自己的库证明不了没重复发出去）。

**边界**　跳过不是错误但必须留痕：`SKIP / IDEMPOTENT` 与 `FAIL` 分开 —— 把跳过当失败会让每次重推都告警，不记录又证明不了这批单收到过两次。只重试一次：长时间重试得由后台或人工再点，在请求里死等会把一次失败放大成雪崩。`uk_sync_idem` 只闸回传单据行：拉单汇总行与 `SKIP` 明细行的 `idem_key` 是 `NULL`、不参与约束，拉单幂等由 `uk_map` 负责。没演到的路径：`TIMEOUT` 那一档归仓库侧台账，不在本页；多批并发拉单、跨店铺撞同一个 `platform_sn` 没测；「重试第二次也失败」只有代码口径（本次两次都成功）。数字出处：3 笔与 3 行、2 行、`attempt` 1 与 2、`shippedCount=1` 全部来自这条用例的断言。
