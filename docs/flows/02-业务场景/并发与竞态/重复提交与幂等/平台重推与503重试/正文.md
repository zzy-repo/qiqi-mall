**平台重推与 503 重试：重复进来的单不会变成第二张，外呼失败也不会变成糊涂账** —— 同一批单被平台再推一遍：每单落一行 `SKIP / IDEMPOTENT`、**订单表零新增**、只多一行成功汇总（新建 0 / 跳过 N / 失败 0）。回传遇到 503：先记一行 `FAIL`（第 1 次尝试，原因里带 503）→ 立刻重试一次 → 再记一行 `OK`（第 2 次尝试），**同一个包裹两行、老那一行一个字段都不改**；平台侧只受理 1 次，与我们记的成功行数一致。再点一次回传 = 幂等命中：**库里零新增**、老两行逐字不变、接口回报 `skipped=1 / ok=0`。

## 场景

这一页讲的是"外部世界会抽风"的那一半。两个现场，每天都会遇到：

- **平台把同一批单又推一遍**。水位重叠、平台重推、运维手动再拉一次，都是正常现象，不是故障。
- **外呼失败了**。回传发货时平台回 503、超时、返回一句看不懂的错。

运维要能回答的两个问题：**这批单会不会变成两批？这次失败会不会既没送到、也查不出发生过？** 这页就是这两个问题的答案。

## 撑不住的时候

- **重复拉单 = 重复建单**。没有幂等闸门时，同一张平台单被拉两次就是两张内部订单：两份库存被扣、两次发货、两笔售后。而重复在平台侧是**常态**（不是异常）。
- **失败没有留痕**。外呼失败只在应用日志里留一行、或者干脆不记 —— 三小时后平台说"你们没回传"，我们既证明不了发过，也证明不了发了两次。日志会轮转，容器一重建就没了。
- **重试把失败的那行"改"成成功**。如果实现是"重试成功之后回头更新那一条记录"，那么历史上"第一次失败了"这个事实被抹掉 —— 事后看数据只能看到一次成功，看不出"平台抽风过一次"。**只追加**的表不允许这种修法。
- **一次失败拖垮整批**。如果整批 4 张单共用一个事务，一张单的编码对不上就全部回滚 —— "跳过该单"变成了"跳过整批"。
- **假成功**。两次尝试都失败却返回 `code=0`，运维以为回传成功、平台那边其实什么都没收到 —— 这是最坏的一种，因为它把问题推到了几小时后。

## 改了什么

**① 重复拉单：闸门在映射表上，命中就记"跳过"**

`channel_order_map` 的 `uk_map(shop_id, platform_sn)` 是幂等闸门：拉单时**先查**，命中就抛 `DuplicateOrderException`，调用方记一行 `SKIP / IDEMPOTENT`（**不建单、不动库存、不当错误**）。整轮拉单最后落一行店铺级汇总，写出"新建 x / 跳过 y / 失败 z"。

**② 一张单一个独立事务，失败不拖累同批**

`ChannelOrderImporter` 每张单 `REQUIRES_NEW`：SKU 编码匹配不到 → 整单失败、记一行 `FAIL / SKU_NOT_MATCHED`（缺哪个编码写进原因）、**不建半张单**；同批其他单照常进待审核。整批一个事务的话，"跳过该单"就变成了"跳过整批"。

**③ 回传失败：只重试一次，两次各留一行，老行不改**

`ChannelSyncService` 的回传路径 `MAX_ATTEMPTS = 2`：第 1 次失败 → 落一行 `FAIL`（`attempt=1`，原因 = 平台原话）；立刻重试一次 → 成功就再落一行 `OK`（`attempt=2`）。**第几次尝试写在行上**，重试过几次由数据自己说明，不另立统计列。两次都失败 → 把错误交回后台（`finalResult=FAIL`），**绝不假成功**。

**④ 幂等闸在唯一索引上（`uk_sync_idem`），不是代码自觉**

`channel_sync_log.idem_key` 是生成列：`action='SHIP_PUSH'` 时才等于 `{shopId}:SHIP_PUSH:{refId}:{attempt}`，否则 `NULL`（拉单汇总行、SKIP 明细行都不参与唯一约束）。写入用 `INSERT ... ON DUPLICATE KEY UPDATE id=id`：**影响 0 行 = 这次尝试已记过账 = 当 `SKIP` 处理**，不报错、不覆盖第一行。

所以"人工再点一次回传"的正确表现是**零新增**（不是"追加一行 SKIP"）：`attempt` 又从 1 开始，必然撞上第一次那条 `attempt=1` 的行，闸门直接空转。

## 凭什么证明好了

**① 能演的：一条用例，四条硬断言（全部直查库 + 直查 mock，不看 toast）**

`e2e/tests/scenarios/并发与竞态/重复提交与幂等/平台重推与503重试.spec.js`（自起 mock 在 **19090** —— 后端 `channel.mock.base-url` 的默认值就是它，换端口后端根本不理）

| 断言 | 内容 |
| --- | --- |
| ① 拉单基线 | 淘宝/抖音各拉一次 → **3 笔待审核 + 3 行映射**（订单集合基线） |
| ② 重推不建单 | 同一批再推一次 → 每单一行 `SKIP / IDEMPOTENT`；**订单数一个不多**；该轮只落一行成功汇总 |
| ③ 503 留痕 | 注入 503 后回传：该包裹在同步日志里**正好 2 行**；`attempt=1` 那行 `FAIL` 且原因里带 `503`；`attempt=2` 那行 `OK` |
| ④ 平台侧只受理一次 | 抖音侧 `shippedCount = 1`（503 那次没被受理）；且**我们记的成功行数 == 平台受理次数** |
| ⑤ 幂等命中 | 再点一次回传：库里**零新增**；老两行**全列快照逐字相同**（id / attempt / result / reason / 耗时 / 报文 / 时间戳全比）；接口 `code=0`、`skipped=1`、`ok=0`；平台侧仍是 1 次、同一平台单号只 1 条受理记录 |

两条手法值得单独说：**"老行不改"用全列快照前后比对**（只比行数的话，改字段、改时间这类污染会全被放过）；**平台侧计数与我们的成功行数交叉验证**（只查自己的库，证明不了"没有重复发出去"）。

```bash
E2E_FRONT_MODE=dev E2E_SHARDS=1 E2E_SHARD_FROM=1 \
  scripts/e2e-run.sh "tests/scenarios/并发与竞态/重复提交与幂等/平台重推与503重试.spec.js" --no-reset
```

## 附：口径与边界

- **"跳过"不是错误，但必须留痕**：`SKIP / IDEMPOTENT` 是一行正常记录（橙色那一档），和 `FAIL` 分开。把跳过当失败处理，会让"平台重推"每次都触发告警；不记录它，又没法证明"这批单我们确实收到过两次"。
- **只重试一次，不做无限重试**：`MAX_ATTEMPTS = 2`。真要长时间重试，得由后台/人工再点，而不是在请求里死等 —— 那样只会把一次失败放大成一次雪崩。
- **`uk_sync_idem` 只闸回传单据行**：拉单汇总行与 `SKIP` 明细行的 `idem_key` 是 `NULL`（MySQL 唯一索引允许多个 `NULL`），完全不参与约束；拉单的幂等由 `channel_order_map.uk_map` 负责。两处防重别混成一处（详见 `与内部系统的边界` 那一页）。
- **两次都失败就把错误交回后台**：接口返回失败、原因写清平台回了什么，绝不 `code=0`。
- **本页不给新数字**：3 笔/3 行、2 行、`attempt=1/2`、`shippedCount=1` 都来自这条用例的断言；本批没有「实测数字」块。`19090` 是后端配置里的默认 mock 端口，不是本页造的数。
