## 支付并发冲突（payment idempotency）

一张待付款订单被付两次，只能成功一笔、只留一条流水。买家开两个页面、都看到「待付款」、都点得动模拟支付，这是最容易发生的重复提交；而支付这一侧的错误最贵：多记一条流水就是「这张单收了两笔钱」，少记一条是「钱收了没记录」。

拒的依据分三道，各管一种重复，谁也替代不了谁。状态守卫管「顺序再来一次」：`status != 0` → HTTP 200 + `code=1`「当前订单状态不可支付」。版本号管「两边同时读、同时写」：状态写入走 `UPDATE ... WHERE id = ? AND version = ?`，影响 0 行 → 真 HTTP 409「订单状态已变化，请刷新后重试」，整笔回滚、连刚写进去的流水一起撤。幂等键 `uk_idem` 管「同一次支付被提交多遍」（网络重试、用户连点、前端重放）：一张订单只准一条支付流水，撞键静默跳过。把三者当成「随便一条就行」，一定会在某一种时序下漏过去。

支付成功的目标状态是待审核(7)，不是「已付款」：`0 → 1 → 7` 在同一笔里合成一步（自动进审核），所以断言写 `status=7` 才是这套口径，写 1 会红。状态与流水在同一个事务里，409 抛出去之后库里既没有状态推进、也没有流水。

**验证**　`支付并发冲突.spec.js`：2 条用例、46 处断言，造数时掐掉下单后前端那一次自动支付，让订单真实停在待付款。用例一（顺序）：甲 HTTP 200 + `code=0`、提示「支付成功（模拟）」、订单 `status=7`、落支付时间、流水 1 条；乙 HTTP 200 + `code=1` + `当前订单状态不可支付`、页面 `支付失败：` + 这句原话、成功提示计数 0、按钮仍可点、订单 `status` 仍 7、流水仍 1 条；刷新后两页都没有支付入口。用例二（两页真并发）：恰一笔成功（`winners=1`、`losers=1`），不是「至少有一笔成功」；败者文案必须是后端原话之一，且 409 配真 HTTP 409 + `body.code=409`、守卫配 200 + `code=1`；败者页面原文照显、无成功提示；直查库订单仍 `status=7`、按 `order_sn` 数 `payment_record` 只有 1 条；刷新后两页都是待审核、支付入口消失。

**边界**　`code=1` 与 `409` 不能合并：前者是业务状态不对（刷新也没用），后者是并发冲突（刷新才是正确动作），用例对两者的 HTTP 状态码与 `code` 做了配对断言。「只留一条流水」是数出来的，不是看页面显示几行。回滚必须连流水一起撤，这是「整笔」的另一半含义。没演到的路径：用例二里败者到底命中守卫还是版本号取决于时序，所以按实际命中的那道分开断，不预设 409；第三道幂等键触发的是「同一次支付被提交多遍」，UI 上造不出来 —— 它的证据在 `支付流水` 那页的用例（连续重放两次均 `DUPLICATE`、库里仍 1 行）与 `PaymentIdemKeyTest` 的九条真库用例。数字出处：`status` 0/7、流水 1 条、HTTP 200/409、`code` 0/1/409 与两句文案，全部来自用例断言与 `PortalOrderController` / `OptimisticLockGuard` 源码。
