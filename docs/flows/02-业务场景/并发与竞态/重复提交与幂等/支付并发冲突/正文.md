**支付并发冲突：一张待付款订单被付两次，只能成功一笔、只留一条流水** —— 买家开两个页面、都看到「待付款」、都点得动模拟支付。三道闸依次收口：**状态守卫**（`200 + code=1`「当前订单状态不可支付」）→ **版本号**（`409`「订单状态已变化，请刷新后重试」，整笔回滚、连刚写的流水一起撤）→ **幂等键**（`uk_idem` 上一张订单只准一条支付流水，重放静默跳过）。结果：订单停在**待审核(7)**、`payment_record` 按订单号数出来**只有 1 条**、失败那页原样显示 `支付失败：` + 服务端原话、刷新后两边支付入口都消失。

## 场景

模拟支付是买家侧最容易被点两次的动作：手机点一下、电脑上那个标签页还开着；或者点完没反应又点一次。而支付这一侧的错误**是最贵的**：多记一条流水就意味着对账时"这张单收了两笔钱"，少记一条则是"钱收了没记录"。

入口：买家端「我的订单」行内「模拟支付」（`portal-web/src/views/order/index.vue`，`POST /portal/orders/{id}/pay`，`PortalOrderController#pay`）。

## 撑不住的时候

- **两道闸都不够，必须三道**。这不是"多写一层保险"，而是三种**不同的**重复：
  1. **顺序再来一次**（甲付完、乙才点）→ 状态已不是待付款 → 靠**状态守卫**；
  2. **两边同时读、同时写**（都读到 `status=0`、都判可付）→ 守卫全部放行 → 只能靠**影响行数**：`UPDATE ... WHERE id=? AND version=?` 后到那笔**影响 0 行** → 409；
  3. **同一次支付被提交两遍**（网络重试、用户连点、前端重放）→ 状态可能还没变、版本可能刚好一样 → 靠**幂等键** `uk_idem` 挡住第二条流水。
- **0 行却返回成功**。这是最坏的一档：买家看到"支付成功"，实际状态没动、流水没落（或者反过来）。所以 `pay()` 里落库那一句的影响行数是**唯一判据**，0 行必须抛 409 并把整笔事务回滚 —— 流水也不能留。
- **流水和状态不在一个事务里**。分开写就会出现"状态没推进、流水记了一条"或"状态推进了、流水没记" —— 前者对账多一笔钱，后者钱收了没记录。所以 `pay()` 是 `@Transactional`，且状态与流水在**同一条路径**里。
- **失败页假成功或静默**。被拒那页如果显示"成功"或什么都不显示，买家会重复点、或以为付了两次而投诉。

## 改了什么

① **状态守卫**（第一句）：`if (order.getStatus() != 0) return Result.fail("当前订单状态不可支付")` → **HTTP 200 + `code=1`**，买家视角的明确原话。

② **版本号 + 影响行数**：状态推进统一走 `OrderStatusService#change`（`payType` / `paymentTime` 与 `status` 在**同一条** UPDATE 里 —— 拆成两条会多涨一次 version，买家的乐观锁语义就变了），随后 `OptimisticLockGuard.requireAffected(rows, MSG_ORDER_STATE_CHANGED)`：**0 行 → 真 409** +「订单状态已变化，请刷新后重试」，事务回滚，**刚写的支付流水一起撤掉**。

③ **幂等键兜第三层**：支付流水带 `{orderSn}:PAY` 幂等键（`payment_record.uk_idem`）。同一次支付被提交两遍 → 撞唯一键 → 静默跳过，不会记第二条。注意这里"跳过"的理由是**钱已经记过了**，不是"失败"（两道闸的语义分开，见 `支付流水` 那一页）。

④ **失败文案照抄服务端**：页面 `ElMessage.error('支付失败：' + e.message)` —— 于是红字就是 `支付失败：当前订单状态不可支付` 或 `支付失败：订单状态已变化，请刷新后重试`，**不出现任何成功提示**，按钮也不会卡住（失败后仍可点，避免用户以为页面死了）。

⑤ **刷新后入口消失**：订单进了待审核(7) 就没有支付入口（`v-if` 判状态），两页刷新后都看不到按钮 —— 这比"按钮还在但点了报错"更诚实。

## 凭什么证明好了

**① 能演的：两条用例，覆盖两条真实可达的拒绝路径**

`e2e/tests/scenarios/并发与竞态/重复提交与幂等/支付并发冲突.spec.js`（造数时**掐掉**下单后前端那一次自动支付，让订单真实停在待付款）

| 用例 | 断言 |
| --- | --- |
| ① 甲付完乙再付（顺序） | 甲：HTTP 200 + `code=0`、提示「支付成功（模拟）」、订单 `status=7`、落支付时间、流水 **1 条**；乙：HTTP **200** + `code=1` + `当前订单状态不可支付`、页面 `支付失败：` + 这句原话、**成功提示计数 0**、按钮仍可点、订单 `status` 仍 **7**、流水仍 **1 条**；刷新后两页都没支付入口 |
| ② 两页真并发点支付 | **恰一笔成功**（`winners=1`、`losers=1`）；败者文案必须是后端原话之一，且 **409 配真 HTTP 409 + `body.code=409`**、守卫配 **200 + `code=1`**；败者页面原文照显、无成功提示；库里订单 `status=7`、`payment_record` **只有 1 条**；刷新后都是待审核、支付入口消失 |

关键点：**两条路径都不放松**。写成"只要不是 `code=0` 就算失败"会漏掉最坏的那种结果（两笔都成功），所以用例钉的是 `winners === 1` —— **恰好一笔**，而不是"至少有一笔成功"。


## 附：口径与边界

- **三道闸各管一种重复，缺一条就有一种漏过去**：守卫管"顺序重来"、版本号管"同时读同时写"、幂等键管"同一次支付被提交多遍"。把三者当成"随便一条就行"，一定会在某一种时序下漏。
- **`code=1` 与 `409` 不能合并**：前者是业务状态不对（不用刷新，刷新也没用），后者是并发冲突（刷新是正确动作）。用例对两者的 HTTP 状态码与 `code` 都做了配对断言。
- **"只留一条流水"是数出来的**：按 `order_sn` 直查 `payment_record`，不是看页面上显示几行。
- **支付成功的目标状态是待审核(7)**，不是"已付款"：`0 → 1 → 7` 在同一笔里合成一步（自动进审核）。所以断言写成 `status=7` 才是这套口径；写 `1` 会红。
- **回滚必须连流水一起撤**：状态与流水在同一个事务里，409 抛出去之后库里既没有状态推进、也没有流水 —— 这是"整笔"的另一半含义。
- **本页不给新数字**：`status` 0/7、`payment_record` 1 条、HTTP 200/409、`code` 0/1/409 与两句文案全部来自用例断言与 `PortalOrderController` / `OptimisticLockGuard` 源码；本批没有「实测数字」块。
