## 订单审核并发（state guard vs split transaction）

审核通过不是「改个状态」：它一次做三件事 —— 推进状态、按拆单方案生成发货单、往状态台账写一行。两个人同时审核同一笔单，最坏结果不是状态被改两次，而是仓库收到两组发货指令、同一批货发两遍，后续拣货、回传、签收全按两组走，等发现时已经出库。

拒的依据也分两道。第一道是业务状态守卫，`auditPass` 第一句就是 `status != 7` → `Result.fail("只有待审核订单可以审核通过")`，返回 HTTP 200 + `code=1` + 中文原因，不是 409 —— 「这单不是待审核」是业务状态不对，不是数据被别人改过。第二道是状态写入的影响行数：`UPDATE ... WHERE id = ? AND version = ?`（连带 `status_seq` 自增）影响 0 行即 409、整笔回滚，`split()` 根本不会被执行 —— 没有这一道就会出现「订单停在待审核、发货单却已生成」这种只能人工对账的半截状态。

预演与执行共用同一套守卫：`?dryRun=true` 与 `split-preview` 都只算不落库，且第一句守卫完全相同，所以「两个人都能打开弹窗、都看到待审核→待发货」是可以被证明的事实，不是猜测。拆单与状态在同一个事务里，`change(...)` 成功后才有 `split(id)`，任一步失败整笔回滚。前端把原因留在原地：执行失败时确认弹窗不自动关闭，原因写进 `danger-confirm-error`，人还看得清自己选了什么。

**验证**　`订单审核并发.spec.js`：1 条用例、36 处断言，两个独立 browser context。断言要点：两人各自打开审核弹窗时，甲的预演 `willDo` 含「待审核→待发货」，乙的预演**同样** HTTP 200 + `code=0` + 待审核→待发货 —— 这一条证明两人确实是在「订单还是待审核」这一帧点进来的；甲确认执行 → HTTP 200 + `code=0`、弹窗收起、提示「审核通过，已生成发货单」、订单 `status=8`、`version = version0 + 2`（状态写入与拆单标记各一次）、发货单 1 组且状态待下发(0)、件数 1；乙确认执行 → HTTP 200 + `body.code=1`、`message` 一字不差是「只有待审核订单可以审核通过」、`danger-confirm-error` 显示这句原文、弹窗不关；乙被拒之后订单仍 `status=8`、`version` 与甲审核刚结束时完全一致（乙那次没有第二个 update）、发货单仍只有 1 组且单号仍是甲那一个。

**边界**　本页的失败是 `code=1`，不是 409，用例也**不断言 409** —— 把 409 写死就是假验收，因为那条窄窗口（读到 7 之后、写回之前被别人抢先）概率极低。守卫挡的是「重复点」，影响行数挡的是「同时点」：真实世界两种都会发生，本用例走的是第一种主路径，第二种只存在于代码里，这条边界要如实说。`version` 一次推进 2 是正常的，断言「版本号只 +1」在本页是错的。发货单是「一组」不是「一张」：拆单可能按仓拆成多个包裹，`split()` 一次生成的是这笔订单的全部发货单，本用例恰好 1 张，口径不能写死成 1 张。没演到的路径：真并发下守卫与版本号同时命中的组合没演；三个运营同时点、审核撞上取消订单也没测。数字出处：`status` 7/8、`version0 + 2`、发货单 1 组、HTTP 200 与守卫原文，全部来自用例断言与 `OrderController` 源码。
