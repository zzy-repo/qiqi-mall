**订单审核并发：两人同时点「确认通过」，账只能记一遍** —— 甲乙各自打开同一笔待审核订单的审核弹窗、各自预演一遍，都看到「待审核 → 待发货」，谁也不知道对方也开着。甲点确认：订单 **7 → 8**、版本号推进 **2**（状态与拆单标记各写一次）、生成 **1 组**发货单。乙再点：**HTTP 200 + `code=1`** +「只有待审核订单可以审核通过」，原因留在弹窗里、**弹窗不关**。不变量是：**订单只推进一次、发货单只有一组、乙必须看到明确失败。**

## 场景

审核通过不是"改个状态"那么简单：它一次性做三件事 —— 推进状态、生成拆单方案对应的发货单、把这一笔写进状态台账。所以两个人同时审核同一笔单，最坏的结果不是"状态被改两次"，而是**仓库收到两组发货指令、同一批货发两遍**。

这页就是后台「订单列表 → 审核通过」那条路（`POST /admin/orders/{id}/audit-pass`，`OrderController#auditPass`）。它也是整个并发板块里**唯一一条主路径被业务守卫（而不是 409）拦下**的用例 —— 这个区别值得单独讲清楚。

## 撑不住的时候

- **两个人的"通过"都生效**。没有守卫时，两次 `audit-pass` 都会成功：订单被推进两次，`split()` 被调两次，于是**两组发货单**、仓库收两次通知、同一批货发两遍。后续的拣货、回传、签收全都按两组走，等到发现时已经出库了。
- **读到旧状态之后才写**。守卫（`status != 7 → 拒`）是"读一次、判一次"，它挡得住"已经审过了再点一次"，挡不住"两个请求都读到 7、都判通过、然后各自往写"。这一段空档必须由 **影响行数**兜：状态写入是 `UPDATE ... WHERE id=? AND version=?`（`OrderStatusService#change` 里连带 `status_seq` 自增），**0 行 = 读到之后别人已经改过** → 抛 409 让整笔回滚。绝不往下走 `split()` —— 否则会出现"订单停在待审核、发货单却已生成"这种只能人工对账的半截状态。
- **失败提示一闪而过**。审核是走「确认弹窗」的高危动作，如果被拒之后弹窗自动关掉、只留一条 toast，人会以为"点成功了"。原因必须留在弹窗里（`danger-confirm-error`）。

## 改了什么

① **第一道：业务状态守卫**（`OrderController#auditPass` 第一句）：

```java
if (order.getStatus() == null || order.getStatus() != 7)
    return Result.fail("只有待审核订单可以审核通过");
```

返回的是 **HTTP 200 + `code=1` + 中文原因**，不是 409 —— 因为"这单不是待审核"是**业务状态不对**，不是"数据被别人改过"。

② **第二道：状态写入的影响行数**（`OrderStatusService#change` → `OptimisticLockGuard.requireAffected(rows)`）：`0 行 → 409`（真 HTTP 409），整笔事务回滚，`split()` 根本不会被执行。这一道只在"读到 `status=7` 之后、写回之前"那个极窄窗口才用得上 —— 所以本页的用例**不断言 409**，写死成 409 就是假验收。

③ **预演与执行共用同一套守卫**：`?dryRun=true` 与 `POST /admin/orders/{id}/split-preview` 都只算不落库，且第一句守卫完全相同。所以"两个人都能打开弹窗、都看到待审核→待发货"这件事是**可证明的**（用例抓的是两次预演的真实响应），而不是"我们猜他们同时点进来了"。

④ **拆单与状态在同一个事务里**：`change(...)` 成功之后才 `split(id)`；任一步失败整笔回滚。所以"订单推进了、发货单没生成"或反过来的组合不会留在库里。

⑤ **前端把原因留在原地**：执行失败时确认弹窗**不自动关闭**，原因写在 `danger-confirm-error` 里；人还能看清自己选了什么、也能取消。

## 凭什么证明好了

**① 能演的：一条用例，两个独立 browser context**（`e2e/tests/scenarios/并发与竞态/状态竞态/订单审核并发.spec.js`）

| 阶段 | 断言 |
| --- | --- |
| 两人各自打开审核弹窗 | 甲的预演 `willDo` 含「待审核→待发货」；**乙的预演同样 HTTP 200 + `code=0` + 待审核→待发货**（证明两人确实是在"订单还是待审核"这一帧点进来的） |
| 甲确认执行 | HTTP 200 + `code=0`；弹窗收起；提示「审核通过，已生成发货单」；订单 **status=8**；`version = version0 + 2`（状态写入 + 拆单标记各一次）；**发货单 1 组**、状态待下发(0)、件数 1 |
| 乙确认执行 | HTTP **200** + `body.code=1` + `message` 一字不差是「只有待审核订单可以审核通过」；`danger-confirm-error` 显示这句原文；**弹窗不关**、确认按钮此刻仍可点 |
| 乙被拒之后 | 订单仍 **status=8**；`version` **与甲审核刚结束时完全一致**（乙那次没有第二个 update）；**发货单仍只有 1 组**、单号仍是甲那一个 |

这里每个数字都咬住了同一个论点：**账只记一遍**。如果只有"提示对不对"的断言，两组发货单这种灾难是看不出来的。

## 附：口径与边界

- **本页的失败是 `code=1`，不是 409**。业务守卫（"这单不是待审核"）与并发冲突（"版本对不上"）是两件事：前者用 `code=1` 说清业务原因，后者用 409 让人刷新。把两者混成一种，用户就不知道该刷新还是该换个单子。
- **`version` 一次推进 2 是正常的**：审核通过要写两次（状态 + 拆单标记），两次都在同一个事务里。所以"版本号只 +1"这种断言在本页是错的。
- **守卫挡的是"重复点"，影响行数挡的是"同时点"**。真实世界两种都会发生：运营手滑点两次（守卫命中）、两个人同时点（守卫都放行，靠 0 行接住后到的那笔）。本用例走的是第一种主路径，第二种只存在于代码里 —— 这一条边界要如实说。
- **发货单是"一组"不是"一张"**：拆单可能按仓拆成多个包裹，`split()` 一次生成的是这一笔订单的**全部**发货单。所以断言的是"组数 1"，不是"张数 1"（本用例恰好 1 张，但口径不能写死成 1 张）。
- **本页不给新数字**：`status` 7/8、`version0 + 2`、发货单 1 组、HTTP 200/409 与那句守卫原文，全部来自用例断言与 `OrderController` 源码。本批没有「实测数字」块。
