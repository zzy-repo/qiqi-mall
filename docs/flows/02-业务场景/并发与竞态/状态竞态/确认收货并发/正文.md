## 确认收货并发（state guard + version CAS）

「确认收货」推进的是状态机：已发货(2) → 已完成(3)，这一步之后连带签收、结算、售后窗口开始计时。两次请求都读到 `status=2`、都判「可以确认」，状态字段最后可能还写着已完成 —— 看起来没坏，但连带动作做了两遍：包裹签收两轮、状态台账多一条流转、下游结算按两次触发。

拒的依据分两道，各管一个窗口。状态守卫在前：`status != 2` 直接返回 HTTP 200 + `code=1`「只有已发货订单可以确认收货」，挡的是「甲已经确认完、乙才点」。版本号在后：状态写入走 `UPDATE ... WHERE id = ? AND version = ?`（同一条语句里 `status_seq` 与 `version` 一起自增），影响 0 行 → 真 HTTP 409 + 买家视角文案「订单状态已变化，请刷新后重试」，挡的是「两边都读到旧状态、同时写」。买家文案单独一句，不复用后台那句「数据已被他人修改…」—— 买家不懂版本，看到那句会以为账号被盗。

子单是事实源，父单是推导值。`confirm` 不硬写 `order.status=3`：有在途包裹时顺序是先把该订单所有未取消未签收的包裹推到「已签收」，再由子单重新聚合父单状态到 3，整笔一个事务，任一步失败全部回滚，不留「包裹已签收、订单没完成」。唯一例外是没有在途包裹的直发路径（单仓直发或包裹全被取消），此时没有子单事实可依，父单由买家这一步推进，这一笔是唯一写者，仍带版本号与 0 行检查。页面不假成功：失败显示「确认收货失败：」+ 服务端原话，不出现任何成功提示；刷新后按钮消失（`status !== 2` 就没有入口）。

**验证**　`确认收货并发.spec.js`：1 条用例、33 处断言，同一会员两个独立 context。造数全走真实 UI（注册 → 加购 → 结算下单并自动模拟支付 → 审核通过 → 下发 → WMS 出库），让订单停在已发货(2)，然后两页抢。断言要点：`winners.length === 1` 且 `losers.length === 1`（不许两笔都成功）；胜者 HTTP 200、`status=3`、提示「已确认收货，订单完成」、列表行显示已完成；败者文案必须是后端原话之一，按实际命中的校验分开断：409 必须配真 HTTP 409 + `body.code=409`，守卫必须配 200 + `code=1`，不放松成「不是 0 就行」；败者页面出现「确认收货失败：」+ 该页真实响应的 message、成功提示计数为 0；直查库 `status = 3`、版本号只推进一次；刷新后两页都是已完成、`orders-row-confirm` 入口两边都不存在。

**边界**　两条失败路径的码不同：`code=1` 是业务原因（状态不对），`409` 是并发冲突（让他刷新），用户看到的东西也不一样。父单状态是聚合推导的，「确认收货后订单一定等于 3」只在所有包裹都被推到已签收时成立；有包裹被取消或回传晚到，聚合按当时事实算。由此还有一条真实风险：老实现只写父单、不碰子单，会出现「父单已完成 + 另一包裹仍在运输」，晚到的回传按子单重新聚合会把已完成写回已发货 —— 这正是必须先写子单事实再聚合的理由。没演到的路径：本用例不保证撞进 409 那条极窄窗口，实际多为守卫先拦（`code=1`），409 只有代码口径保证；三标签页同时点、以及「确认收货撞上取消订单」的组合都没测。数字出处：`status` 2/3、HTTP 200/409、`code` 0/1/409 与两句文案来自用例断言与 `OptimisticLockGuard` / `PortalOrderController` 源码。
