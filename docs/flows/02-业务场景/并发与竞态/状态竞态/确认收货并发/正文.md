**确认收货并发：同一笔已发货订单点两下，只能成功一次** —— 买家开两个标签页，两边都看得见「确认收货」，几乎同时点下去：**恰好一胜一败**。胜者把订单推到**已完成(3)**，败者看到的是它自己那一次的真实拒绝（`只有已发货订单可以确认收货`，或者真并发下的 **409「订单状态已变化，请刷新后重试」**），页面上是 `确认收货失败：` + 原话，**绝不假成功**。两页刷新后都是已完成，**确认收货入口两边都消失**。

## 场景

「确认收货」是买家侧最小、最典型的并发动作：一个买家、一笔单、两个标签页（或手机+电脑），两边都停在同一个按钮上。它没有金额、没有库存，看起来"点两次也就是多点一次"，但它推进的是**状态机**：已发货(2) → 已完成(3)，而这一步之后会连带签收、结算、售后窗口开始计时。

入口：买家端「我的订单」列表行内按钮（`portal-web/src/views/order/index.vue`，按钮 `v-if="row.status === 2"`），接口 `POST /portal/orders/{id}/confirm`（`PortalOrderController#confirm`）。

## 撑不住的时候

- **只看"是不是已发货"就改状态，两下都会成功**。两次请求都读到 `status=2`，都判"可以确认"，于是订单被推进两次 —— 状态字段最后可能还是"已完成"（看起来没坏），但**连带动作做了两遍**：包裹被签收两轮、状态台账多出一条不该存在的流转、下游结算按两次触发。**表面上没有报错，账已经多记了一笔。**
- **两边看到同一份旧状态**。这是同一件事的另一面：标签页二是十分钟前打开的，它手里的 `status=2` 早就过期了。没有版本号，它的写入会把中间发生的事（比如另一个入口已经确认过、或仓库刚回传签收把状态推到了 3）**覆盖回 2**，然后立刻再改成 3 —— 状态机的历史被抹平。
- **影响行数为 0 却返回成功**。这是最隐蔽的形态：`UPDATE ... WHERE id=? AND version=?` 影响 0 行（因为它读到之后被别人改过），接口却返回 `code=0`。用户看到「已确认收货」，实际什么都没发生；或者反过来，实际发生了但他看到失败。判据必须是**落库那一句的影响行数**。
- **失败页静默无反应**。如果被拒的那页什么都不显示，买家的结论是"没点上"，于是**再点一次** —— 而这次他手里的状态更旧。

## 改了什么

① **两道闸，各自负责不同的窗口**：

- **状态守卫**（先）：`if (order.getStatus() != 2) return Result.fail("只有已发货订单可以确认收货")` → **HTTP 200 + `code=1`**。它挡住"顺序再来一次"（甲已经确认完，乙才点）。
- **版本号**（后）：状态写入走 `OrderStatusService#change`，`UPDATE ... WHERE id=? AND version=?`（同一条 UPDATE 里 `status_seq` 与 `version` 一起自增）；**0 行 → 409** + 买家视角文案「订单状态已变化，请刷新后重试」。它挡住"两边都读到旧状态、同时写"。

② **买家视角的文案单独一句**：`OptimisticLockGuard.MSG_ORDER_STATE_CHANGED`。为什么不复用后台那句「数据已被他人修改（可能其他人在编辑）」—— 买家不懂"版本"，看到那句会以为账号被盗。买家只需要知道：**这张单的状态和我看到的已经不一样了**。

③ **子单是事实源，父单是推导值**：`confirm` 不是"硬写 `order.status=3`"。有在途包裹时，顺序是 **① 把该订单所有未取消未签收的包裹推到「已签收」（`signRemainingDeliveries`）→ ② 由子单重新聚合父单状态（`recomputeOrderStatus` → 3 已完成）**。整笔一个事务：任一步失败全部回滚，不会留下"包裹已签收、订单没完成"。

④ **直发路径是唯一的例外**：订单下没有任何未取消包裹时（单仓直发，或包裹都被取消），没有子单事实可依，父单只能由买家这一步推进 —— 此时这一笔写入是**唯一写者**，仍然带版本号与 0 行检查。

⑤ **页面不假成功**：成功 `已确认收货，订单完成`；失败 `确认收货失败：` + `e.message`（原样显示服务端那句话），且**不出现任何成功提示**；刷新后按钮消失（`status !== 2` 就没有入口）。

## 凭什么证明好了

**① 能演的：一条用例，同一会员两个独立 context**（`e2e/tests/scenarios/并发与竞态/状态竞态/确认收货并发.spec.js`）

造数全走真实 UI：注册 → 加购 → 结算下单（自动模拟支付）→ 管理员审核通过 → 下发 → WMS 出库，让订单真实停在**已发货(2)**，然后两页抢。

| 断言 | 内容 |
| --- | --- |
| 恰一胜一败 | `winners.length === 1`、`losers.length === 1`（**不许两笔都成功**） |
| 胜者 | HTTP 200；响应里订单 `status=3`；页面提示「已确认收货，订单完成」；列表行状态显示已完成 |
| 败者 | 文案必须是后端原话之一；**409 必须配真 HTTP 409 + `body.code=409`**，守卫必须配 **200 + `code=1`** —— 两条路径都不放松成"只要不是 0 就行" |
| 败者界面 | 出现 `确认收货失败：` + 该页真实响应的 message；**成功提示计数为 0**（不许假成功） |
| 库里的事实 | `order.status = 3`（用例直查库，不只看接口返回）；版本号只被推进一次 |
| 刷新后 | 两页都是「已完成」，`orders-row-confirm` 入口**两边都不存在** |

## 附：口径与边界

- **并发要求不是"别报错"，而是"只成功一次 + 失败那次被明确告知"**。两笔都成功是最坏结果；一笔成功一笔静默失败是第二坏（用户会再点）。
- **两条失败路径的码不同，不要合并**：`code=1`（状态守卫，业务原因）vs `409`（版本冲突，让他刷新）。用户看到的东西也不该一样。
- **父单状态不是"硬写"的**：有在途包裹时它由子单聚合推导。所以"确认收货后订单一定等于 3"只在**所有包裹都被推到已签收**时成立 —— 若某个包裹被取消、某个回传晚到，聚合结果要按当时事实算。
- **状态回退是真实存在的风险**：老实现只写父单、不碰子单，于是会出现"父单已完成 + 另一个包裹还在运输中"，之后一次晚到的 WMS 回传按子单重新聚合，会把已完成为**写回已发货**。这就是为什么必须先写子单事实再聚合。
- **本页不给新数字**：`status` 2/3、HTTP 200/409、`code` 0/1/409 与两句文案都来自用例断言与 `OptimisticLockGuard` / `PortalOrderController` 源码；本批没有「实测数字」块。
