**退货审核并发：这套并发里最贵的一条 —— 重复通过就是退两次钱、补两次库存** —— 两个客服同时审同一笔待审核退货申请。甲通过：申请转**已通过(1)**、订单转**已退款(6)**、记 **1 条**退款流水（金额 = 订单实付）、库存回补 **1 件**。乙点通过：在**预演阶段**就被拦下（HTTP 200 + `code=1` +「该申请已处理，不能重复审核」），表单停在原地、刚选的「通过」不被重置。最终：**退款流水 1 条、库存只补 1 次、申请只处理一次、订单只退一次。**

## 场景

退货审核是唯一一条**同时动钱和动货**的审核：通过 = 记一条退款流水 + 回补库存 + 订单转已退款。所以它的并发不是"状态显示对不对"的问题，而是**真金白银的重复**。

入口：后台「退货申请」列表 → 行内审核（`PUT /admin/return-applies/{id}`，`ReturnApplyController#update`，支持 `?dryRun=true` 预演）。

为什么它跟前面几页不一样：`return_apply` 表**没有 `version` 列**。所以这里不靠乐观锁版本号，靠的是**把守卫写进 UPDATE 的条件里**，再看影响行数。

## 撑不住的时候

- **两个"通过"都生效 = 退两次钱、补两次库存**。两位客服各自读到"待处理"，各自判"可以审"，于是各自走完整套动作：两条退款流水（同一张申请退两次）、库存回补两次（凭空多出货）、订单被推两次。这类错误**不会自己暴露** —— 页面上两边都显示"审核完成"，只有对账时才会看到钱多了。
- **只有 Java 里那句 `if (status != 0) 拒绝`，挡不住同时点**。两个请求都在 `status=0` 时读进来，两个 `if` 都通过 —— 状态守卫在这种时序下完全失效。**读-判-写不是原子的**。
- **影响行数 0 行被当成成功**。这是最隐蔽的一档：`UPDATE ... WHERE id=? AND status=0` 第二个请求影响 0 行，如果代码不检查这个 0，就会继续往下记流水、补库存 —— 于是"申请只被审一次，但钱和货各走了两次"。
- **失败时表单被重置**。乙在弹窗里选好了"通过"、填好了意见，被拒之后如果表单收起或重置，他既不知道自己错在哪，也得从头再选一遍 —— 而这次他手上的数据更旧。

## 改了什么

① **把守卫写成 UPDATE 的条件**（这是本页的核心手法）：

```sql
UPDATE return_apply
   SET status = ?, status_seq = status_seq + 1
 WHERE id = ? AND status = <读到的那个状态>
```

这就是"读-改-写"的原子版：两个管理员同时审时，InnoDB 用行锁把两次 UPDATE 排成先后，后一个的 `WHERE status=0` 不再命中 → **影响 0 行** → `OptimisticLockGuard.requireAffected(...)` → 409，整笔回滚（不会记流水、不会补库存）。这段 SQL 现在收敛在 `ReturnStatusService#change` 里，入口那句话依旧是"带状态条件更新"，不是"先 if 一下再 update"。

② **预演与执行共用同一套守卫**：`?dryRun=true` 时也会跑 `if (exist.getStatus() != 0) → Result.fail("该申请已处理，不能重复审核")`。顺序上**守卫在 dryRun 分支之前**，所以预演绝不会说"将通过"而后真做被拒。

③ **0 行还有第二种原因**：这条申请被并发删了。往一条不存在的申请上记账同样不行，一样 fail-closed。

④ **审核意见不塞进审计的原因列**：`admin_audit_log.reason` 是 `VARCHAR(32)` 的原因码，审核意见是自由文本（`return_apply.description` 是 `VARCHAR(500)`）。塞进去会 1406 数据超长，**把整笔审核回滚**（实测踩过）。所以意见的原文留在 `return_apply.description` 与 `return_status_ledger.reason_detail`（按列宽裁）。

⑤ **前端把原因留在原地**：预演失败 → 表单**不收起**（`return-apply-form-preview-error` 显示服务端原话）、刚选的「通过」仍是选中状态，同时一条 `预演失败：…` 的提示。人能在原地改主意（比如改成"拒绝"或直接取消）。

## 凭什么证明好了

**① 能演的：一条用例，两个独立 browser context**（`e2e/tests/scenarios/并发与竞态/状态竞态/退货审核并发.spec.js`）

造数全走真实 UI：买家注册 → 加购 → 支付 → 管理员审核通过 → 下发 → WMS 出库 → 买家申请退货，申请停在**待处理**，然后两个客服会话抢。

| 断言 | 内容 |
| --- | --- |
| 两人同帧 | 甲、乙打开时申请状态都是「待处理」 |
| 甲通过 | 确认弹窗里执行成功；申请「已通过」；订单 **已退款(6)**；退款流水**恰好 1 条**、金额 = 订单实付、流水号 `MOCKREF…`；库存 = `stockBefore + 1` |
| 乙通过 | 结果是 **preview-failed**（预演阶段就被拦，没进入确认执行）；预演请求 HTTP **200** + `code=1` +「该申请已处理，不能重复审核」；表单内显示这句原文、**表单停在原地**、刚选的「通过」仍是勾选态 |
| 钱与货的不变量 | 退款流水 `type=2` **1 条**；支付流水 `type=1` 仍是原来那一条（没被复制）；库存仍是 `stockBefore + 1`（**只补一次**） |

## 附：口径与边界

- **这张表没有 `version` 列，所以"版本冲突"这套词在这里不适用**：本页的 409 来自**影响行数 0**，不是版本号对不上。文案也照 409 那套（"数据已被他人修改…请刷新后重试"），但机制是"带状态条件更新的影响行数"。
- **主路径是 `code=1`，不是 409**：因为预演阶段的状态守卫先一步拦下（读完申请就发现已经是"已通过"）。真 409 只在"两次 UPDATE 撞在同一毫秒"的窗口出现 —— 所以用例**不断言 409**，把它写成 409 就是假验收。
- **`0 行即失败` 让这套写法天生幂等**：重复点几次都不会多记一笔账，因为每次都要重新命中 `WHERE status=0`。
- **库存回补必须和状态迁移同事务**：分开写就会出现"申请已通过、库存没补"或"库存补了两次、申请还是待处理"。这套实现的顺序是状态写入成功（影响 1 行）之后才继续，任何一个 0 行都整笔回滚。
- **审核意见的落点**：`return_apply.description`（原文，≤500）与 `return_status_ledger.reason_detail`（裁到 255）。**不进** `admin_audit_log.reason`（那是 32 宽的原因码列）。
- **本页不给新数字**：`status` 0/1/6、退款流水 1 条、`stockBefore + 1`、HTTP 200/409 与守卫原文都来自用例断言与 `ReturnApplyController` 源码；本批没有「实测数字」块。
