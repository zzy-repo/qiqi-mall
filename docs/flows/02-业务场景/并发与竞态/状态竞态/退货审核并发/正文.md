## 退货审核并发（conditional update / affected rows）

退货审核是唯一一条同时动钱和动货的审核：通过 = 记一条退款流水 + 回补库存 + 订单转已退款。它的并发不是「状态显示对不对」，而是真金白银的重复 —— 两个「通过」都生效就是退两次钱、补两次货，而页面上两边都显示「审核完成」，只有对账时才看得出钱多了。

`return_apply` 没有 `version` 列，所以这里不靠版本号，而是把守卫写进 `UPDATE` 的条件：`UPDATE return_apply SET status = ?, status_seq = status_seq + 1 WHERE id = ? AND status = <读到的那个状态>`。这是读-改-写的原子版：InnoDB 把两次写入排成先后，后一个的 `WHERE status = 0` 不再命中 → 影响 0 行 → `requireAffected(...)` → 409、整笔回滚，流水不记、库存不补。这段收敛在 `ReturnStatusService#change`；只有 Java 里那句 `if (status != 0) 拒绝` 挡不住同时点 —— 两个请求都在 `status=0` 时读进来，两个 `if` 都会通过。

预演与执行共用同一套守卫，且守卫排在 `dryRun` 分支之前，预演绝不会说「将通过」而真做时被拒。0 行还有第二种原因：这条申请被并发删了，往不存在的申请上记账同样 fail-closed。审核意见不塞进 `admin_audit_log.reason`（32 宽的原因码列，塞进去会 1406 超长、把整笔审核回滚，这个坑踩过），原文留在 `return_apply.description` 与 `return_status_ledger.reason_detail`（裁 255）。

**验证**　`退货审核并发.spec.js`：1 条用例、34 处断言，两个独立 context。造数全走真实 UI（注册 → 加购 → 支付 → 审核通过 → 下发 → 出库 → 申请退货），申请停在待处理，两个客服会话抢。断言要点：两人打开时申请状态都是「待处理」；甲通过 → 申请「已通过」、订单已退款(6)、退款流水恰好 1 条、金额等于实付、流水号 `MOCKREF…`、库存 `stockBefore + 1`；乙通过 → 结果 `preview-failed`（预演就被拦，没进确认执行）、预演请求 200 + `code=1` + 「该申请已处理，不能重复审核」、表单内显示原文、表单停在原地、所选「通过」仍勾选；三条不变量直查库：退款流水 `type=2` 只有 1 条、支付流水 `type=1` 仍是原那条、库存仍 `stockBefore + 1`、申请没有第二条且状态仍 1、订单仍 6。

**边界**　这张表没有 `version` 列，「版本冲突」这套词不适用：409 来自影响行数 0，不是版本号对不上。主路径是 `code=1`：预演守卫先一步拦下，真 409 只在两次 `UPDATE` 撞进同一毫秒时出现，所以用例不断言 409，写死 409 就是假验收。「0 行即失败」让这套写法天生幂等：重复点几次都不会多记，因为每次都要重新命中 `WHERE status = 0`。库存回补必须与状态迁移同事务：分开写就会出现「申请已通过、库存没补」或「库存补两次、申请还是待处理」；实现顺序是状态写入影响 1 行之后才继续，任何 0 行都整笔回滚。没演到的路径：真 409 那条窄窗口没演；三客服同时审没测；「申请被并发删除」导致的 0 行也没有用例。数字出处：`status` 0/1/6、退款流水 1 条、`stockBefore + 1`、HTTP 200 与守卫原文，全部来自用例断言与 `ReturnApplyController` 源码。
