## 状态与证据对齐（audit trail alignment）

一笔待审核订单跑完一轮审核，只有两条路真的改状态：自动过审把 7 推到 8（台账行 `ref_type=AUDIT_RUN`、`ref_id=run_id`）；人工审核不通过把 7 推到 4（台账一行 + 库存回补，没有 `run_id`）。其余停在 7：`BLOCKED` / `NO_MATCH` 一行台账都不写，`FROZEN` 加冻结标 + 操作审计，库存不足加 `STOCK_SHORT` 标并降级人工，`SKIPPED` 连决策行都不写。所以「这单还在待审核」不是结论。

要看的是时间线，三段查询在服务层合并，不做 `UNION`：决策行（`order_audit_decision`，每单每轮一行、只追加，唯一键 `(order_id, round_no)`）答「怎么判的」，状态台账行答「状态真的变了吗、谁改的」，操作审计行答「谁点了什么」。三张表列语义不同，压成同一形状就分不出哪行属于哪类证据。

对齐分三档：强对齐是决策的 `run_id` 等于台账行 `ref_id` 且 `ref_type=AUDIT_RUN`，同一条因果链；弱对齐是决策行照抄的 `order_status_seq` 等于台账行序号，序号相同但不是本轮推进；都对不上就不配对，页面写「未对齐」，不按时间最接近硬配。序号从键尾取：台账表没有 `status_seq` 列，序号在 `idem_key` 尾段，解析不出给 0，而 0 只对应出生事件，所以最坏是「未对齐」而不是假装对上。

冻结用标表达、不改状态：`active_tag` 是生成列（仅 `active=1` 时非空）挂唯一键，生效冻结由库保证唯一，解冻后再冻结可再插一行。

**效果**　四组只读 SQL（快照 2026-11-14 18:54，`qiqi_mall_test`）：订单 15 第 1 轮决策 `AUTO_PASS` / `run_id=1` / 命中「淘宝-标准单」/ seq 1，对上台账 `15:1` / `AUDIT_AUTO_PASS` / `ref_id=1`，判定强对齐；三分档 强 1 / 弱 0 / 未对齐 49（决策共 50 行，那 49 行是直接落库的种子单，无台账行可配）；订单 1 / 3 / 17 / 20 各 8 轮 `NO_MATCH`、16 八轮 `MANUAL`、18 八轮 `BLOCKED`，皆决策 8 行、台账 0 行；订单 15 推进状态是 1 + 1；19 冻结 1 轮 → 决策 1 行、`status=7`、`FROZEN` 标 1 行、`AUDIT_FREEZE` 审计 1 行、台账 0 行。机制单测可复跑：同一笔冻结单连跑 3 轮，决策行数不增长、每轮 `skipped()==1`、`AUDIT%` 原因的台账行为 0；`NO_MATCH` 那轮仍跑库存预检但只产出证据。另配两条只读体检 SQL（有 `AUTO_PASS` 必有 `AUDIT_RUN` 台账行；`order_status_seq` 必有同序号行走），期望 0 行，非 0 即真断裂。

**边界**　「未对齐」是允许的结论：拿不到强/弱对齐就不配对，配错比配不上更糟 —— 按时间硬配会让那 49 行全部变成假对齐。看到未对齐先查这张单是否被人工改过状态，或中间隔了一轮 `NO_MATCH`。「每单每轮一行」对 `SKIPPED` 不成立：跳过不写决策行，否则冻结久了 `round_no` 一直涨；跳过只在批次 `skipped` 计数上，所以 `total` 与五类之和允许不等。`order_status_seq` 是快照，语义随结局不同，不能当「本轮改了状态」的证据。冻结解冻永远不在状态台账里，要证明「冻过」得查标表与操作审计。数字出处：18:54 那组来自本页 `实测数字.sql`，数字随当次数据变。
