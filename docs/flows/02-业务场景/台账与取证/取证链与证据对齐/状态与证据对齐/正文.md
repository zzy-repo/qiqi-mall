**状态与证据对齐：状态动没动本身就是结论，证据对不上就直说「未对齐」** —— 一笔待审核订单走完一轮有好几种结局，但**只有两条路真的改了状态**（自动过审推到待发货、人工审核不通过推到已关闭），其余全部停在待审核，只在别处留下标或审计。所以"这单还在待审核"从来不是"系统没跑"，得看证据；而证据要跟状态**按因果配对**，对不上就说对不上，绝不按时间最接近硬配一条。

## 场景

运营最常问的一句是「这单怎么还在待审核」。问出这句话时，可能性有四种，四种的处置完全不同：

1. 审核**根本没跑到**它（不在候选范围）；
2. 跑到了，结论就是**不动**（被策略拦、被冻结、没命中任何 AUTO 策略、库存不足降级）；
3. 结论是"应该自动过审"，但**状态没改成功**（这是真缺陷）；
4. 状态改了，**台账没写**（这也是真缺陷）。

只盯 `order.status` 一个字都分不出来。所以这一页要的是**一条时间线**：后台「订单审核」详情的时间线（接口 `GET /admin/order-audit/orders/{id}/trail`，服务 `audit/service/AuditQueryService#trail`，三段查询在 `AuditTrailMapper`），把三类证据按时间拼在一起：

| 证据 | 回答什么 | 来源 |
| --- | --- | --- |
| 决策行 | **怎么判的**：结论、命中策略与版本、条件明细、证据原文 | `order_audit_decision` |
| 状态台账行 | **状态真的变了吗**、谁改的、因为什么 | `order_status_ledger` |
| 操作审计行 | **谁点了什么**（人工冻结/解冻、策略改动） | `admin_audit_log` |

三段是**独立查询、在服务层合并**的，不做 SQL `UNION`：三张表的列语义不同（怎么判 / 怎么变 / 谁点的），`UNION` 会把它们压成同一个形状，前端就再也分不出哪一行属于哪类证据。

## 撑不住的时候

- **只看状态码，把"不动"当成"故障"**。被冻结的单每轮都被跳过，状态一直是 7。运维看状态以为卡住了，于是手工点一次审核通过 —— 而它本来就应该等着。反过来，真的漏判也长成一模一样的样子。**状态是结论，不是原因**，只看结论必然误判。
- **把两条证据当成一条**。决策说 `AUTO_PASS`、状态却还在 7，这中间断了一环（写状态失败/回滚）。如果时间线只显示其中一段，这个断裂就永远看不见 —— 而这正是证据链存在的全部意义：**两段对不上就是缺陷，不是显示问题**。
- **按"时间最接近"配对**。同一张单在一轮里可能同时有决策行、台账行、审计行；跨轮之后就更多。用"时间最接近"去猜哪条台账是这一轮推进的，会配错 —— **配错的对齐比没有对齐更糟**，因为它看起来是对的。
- **想用状态台账证明"冻过"**。冻结/解冻不改 `order.status`（它用标记表达，不动状态），所以状态台账里**永远不会有它们的行**。去那儿找，只会得出"没人冻过"的错误结论。

## 改了什么

**上半：状态这一列，只有两条路真的改了状态**（下表把决策枚举的六个值 + 人工那条路摆在一起）

| 结局 | 状态 | 台账 / 标 / 审计 |
| --- | --- | --- |
| 自动过审 `AUTO_PASS` | 待审核 7 → **待发货 8** | 状态台账一行，`ref_type='AUDIT_RUN'`、`ref_id=run_id`（**唯一由审核批次推进的改状态**） |
| 人工审核不通过 | 待审核 7 → **已关闭 4** | 状态台账一行，同时**库存回补**；**审核批次不参与这一笔**（没有 run_id） |
| 阻止 `BLOCKED` | 仍是 7 | **一行台账都不写** |
| 冻结 `FROZEN` | 仍是 7 | 加一条 `FROZEN` 标 + 一条操作审计 |
| 不命中 `NO_MATCH` | 仍是 7 | **一行台账都不写**（证据只在决策行里） |
| 跳过 `SKIPPED` | 仍是 7 | 这轮没轮到它；**连决策行都不写** |
| 库存不足降级 | 仍是 7（转人工） | 加一条 `STOCK_SHORT` 标 |

**下半：证据这一列，决策行怎么跟台账行对上**

- **决策行是"每单每轮一行、只追加"**：`uk_order_round(order_id, round_no)`、幂等键 `{orderId}:{roundNo}`、`result` 是六值枚举、行上还**照抄了本轮结束时的 `order_status_seq`**。
- **对齐分三档**（`AuditTrailMapper` 类注释 + `AuditQueryService#trail`）：
  1. **强对齐**：决策的 `run_id` 与台账行的 `ref_type='AUDIT_RUN'` + `ref_id=run_id` 相等 —— 这条台账就是那一轮推进出来的，同一条因果链；
  2. **弱对齐**：决策的 `order_status_seq` 等于台账行的序号 —— 序号相同，但**不是本轮推进的**（例：`NO_MATCH` 那轮不推状态，seq 还是旧值）；
  3. **都对不上 → 不加配对**，页面显示「未对齐」。绝不按时间最接近硬配。
- **序号从键尾取，不新增列**：台账表**没有** `status_seq` 列，序号在 `idem_key` 的尾段（`{orderId}:{statusSeq}`，有 shard 前缀也成立），所以是 `SUBSTRING_INDEX(idem_key, ':', -1)` 派生 —— 解析不出数字时给 0 而不是 `NULL`，0 只对应出生事件，所以最多显示"未对齐"，不会假装对上。
- **冻结用标表达**：`order_audit_tag` 上 `active_tag` 是生成列 `{orderId}:{tagCode}`（仅 `active=1` 时非空），挂唯一键 `uk_active`。所以"当前有没有生效的冻结"由库保证唯一，解冻（`active=0`）之后再冻结还能再插一行 —— 冻结历史因此也是只追加的。

## 凭什么证明好了

**① 可复跑的机制单测**（`mvn -B -pl qiqi-mall-server test -Dtest=AuditPendingBehaviorTest,AuditRunIntegrationTest`）

- `skippedDoesNotAppendDecisionRow`：同一笔已冻结单**连跑 3 轮**，决策行数不增长（`SKIPPED` 一行都不写）、每轮 `run.skipped()==1`、单子状态仍 7、标仍生效、**`AUDIT%` 原因的状态台账行数为 0** —— 这条同时钉住了"跳过不写证据"与"冻结不写状态台账"。
- `noMatchStillRunsStockPrecheckForEvidenceOnly`：`NO_MATCH` 那轮**仍然跑库存预检**，但只用来产出证据，不改状态。
- `fiveVerdictBucketsAddUpAndStockShortIsManualDowngrade`：五类计数之和自洽，且库存不足是**降级为人工**而不是"过审后失败"。

**② 真行对照（本页下方「实测数字」四组只读 SQL，快照 2026-11-14 18:54，库 `qiqi_mall_test`）**

| 断言 | 实测 |
| --- | --- |
| 强对齐不是"序号刚好相同"，是同一条因果链 | 订单 15 第 1 轮：决策 `AUTO_PASS` / `run_id=1` / 命中策略「淘宝-标准单」/ `order_status_seq=1` ↔ 台账行 `15:1` / `AUDIT_AUTO_PASS` / `ref_type=AUDIT_RUN` / `ref_id=1` / 操作人 `SYSTEM` |
| 三分档全库计数 | **强对齐 1 行**；**未对齐 49 行**（全是直接落库的种子单，压根没有状态台账行）；**弱对齐 0 行** —— 本批数据里没出现，不是缺档位 |
| 「每单每轮一行」而不是「每单一行」 | 订单 1/3/17/20 各 **8 轮** `NO_MATCH`、16 八轮 `MANUAL`、18 八轮 `BLOCKED` → 都是决策 **8 行** / 状态台账 **0 行**（不推进状态就不写台账）；订单 15 那 1 轮推进了状态 → 1 行决策 + 1 行台账；订单 19 冻结 1 轮 → 1 行决策 + 0 行台账 |
| 冻结只留标与审计 | 订单 19：`status=7`、`status_seq=0`、标 `FROZEN` 生效、`AUDIT_FREEZE` 审计 **1** 行、状态台账 **0** 行 |

注意那 49 行"未对齐"怎么读：它们不是"对齐算法失败"，而是**这 49 轮压根没有状态台账行可以配**（种子直接落库）。正确的结论就是"未对齐"—— 如果按时间最接近硬配一条，这 49 行会全部变成假对齐，那才是真的坏。

**③ 可复跑的对齐体检（只读，两条 SQL，期望都是 0 行；非 0 就是真断裂）**

```sql
-- 强对齐体检：决策说「自动过审」，台账里就必须有那一轮推进出来的行
select d.id, d.order_id, d.run_id, d.round_no
  from order_audit_decision d
 where d.result = 'AUTO_PASS'
   and not exists (select 1 from order_status_ledger l
                    where l.order_id = d.order_id
                      and l.ref_type = 'AUDIT_RUN' and l.ref_id = d.run_id);

-- 序号对齐体检：决策行记的 order_status_seq，台账里应当有同序号的行走
select d.id, d.order_id, d.round_no, d.order_status_seq
  from order_audit_decision d
 where d.order_status_seq is not null
   and not exists (select 1 from order_status_ledger l
                    where l.order_id = d.order_id
                      and cast(substring_index(l.idem_key, ':', -1) as unsigned) = d.order_status_seq);
```

**④ 时间线本身**：打开任意一张经过自动审核的订单的时间线，同屏应能看到「决策行（含命中策略与版本、条件明细、原因原文）+ 对应的状态台账行（`ref_type=AUDIT_RUN`）+ 冻结/解冻时的操作审计行」，且决策行上有明确的 `aligned` 判定（强 / 弱 / 未对齐三值之一）。

## 附：口径与边界

- **「未对齐」是允许的结论，不是错误**。拿不到强/弱对齐就不配对 —— 这比配错好。看到"未对齐"的正确反应是去查这张单是不是被人工改过状态（那条路没有 run_id）或者中间隔了一轮 `NO_MATCH`。
- **「每单每轮一行」对 `SKIPPED` 不成立**：跳过不写决策行（否则冻结久了的单 `round_no` 会一直涨，库里会堆一堆"什么都没发生"的行）。跳过这件事只在 `audit_run` 的 `skipped` 计数上看得到 —— 所以 `total` 与五类计数之和**允许不相等**。
- **`order_status_seq` 是快照，语义随结局不同**：`AUTO_PASS` 那轮记的是**推进之后**的 seq（所以能强对齐）；`NO_MATCH` 那轮记的是当前值（所以只能弱对齐，或者对不上）。别把这一列当"本轮一定改了状态"的证据。
- **冻结/解冻永远不在状态台账里**：状态没变，就没有流转行。想证明"某天冻过"，查两处 —— `order_audit_tag`（打标与解除时间）与 `admin_audit_log`（`AUDIT_FREEZE` / 解冻动作、谁点的）。
- **人工审核不通过没有 run_id**：它由后台按钮直接推进，不走审核批次。所以它的台账行是强对齐不上的 —— 这是设计，不是缺证据（那一行有自己的 `operator`、`reason` 与时间）。
- **本页数字的出处**：本页下方「实测数字」四段只读 SQL（快照 2026-11-14 18:54，库 `qiqi_mall_test`）；其余口径在 `台账七类` 那六页。要注意这批数据里**弱对齐 0 行、未对齐 49 行**是"这批单怎么来的"的函数，不是判定规则的强度 —— 换一批跑过状态服务的单，强对齐会变多、未对齐会变少，而三分档规则不动。
