**与内部系统的边界：平台也是一个仓库** —— 把"平台接入"和"仓库履约"两列逐行摆开，会发现它们在七件事上一一对应（对方身份、我方发什么、对方回什么、结果分几档、第几次尝试、耗时、只追加不改行）。差别只剩三处：**身份从哪来、一次交互记几行、分档与防重**。所以不需要为平台另造一套说法 —— 同一套台账语言管得住它。

## 场景

凡是"我们要主动去喊别人、而这件事在数据库之外有副作用"的边界，都长成同一个形状：

- **平台接入**：从淘宝/抖音店铺拉单（`PULL`），或把运单号回传（`SHIP_PUSH`）。外呼发生在对方系统里，我们只能记录"我们发了什么、对方回了什么"。
- **仓库履约**：把货单下发给 WMS（`REQ`），收仓侧回传（`ACK`）。同样在库外。

这页给的是**判断口径**：新接一个平台、或新增第二家仓时，能不能复用同一套台账、要对齐哪几行、哪里有本质差异。落地的两张表是 `channel_sync_log`（平台侧，`channel/service/ChannelSyncService` 写入）与 `wms_exchange_ledger`（仓库侧，`shared/ledger/WmsExchangeLedgerWriter` 写入）。

七行对照（这是本页上图读法）：

| | 平台接入这边（对外） | 仓库履约这边（对内） |
| --- | --- | --- |
| ① 对方身份 | 平台店铺 + **平台单号（平台给的）** | 仓库编码 + **包裹单号（我们自己生成的）** |
| ② 我方发什么 | 拉单：店铺 + 水位；回传：平台单号、承运商、运单号 | 下发：包裹、明细、要拣哪几件 |
| ③ 对方回什么 | 成批订单报文 / 一句结果码 | 拣货出库结果、运单号、回执报文 |
| ④ 结果分几档 | 成功 `OK` / 失败 `FAIL` / **跳过 `SKIP`** | 成功 `SUCCESS` / 失败 `FAIL` / **超时 `TIMEOUT`** |
| ⑤ 第几次尝试 | `attempt`（回传重试一次就是两行） | `attempt_no`（按方向各自递增） |
| ⑥ 耗时 | `latency_ms`（每次外呼） | `latency_ms`（记在 ACK 行） |
| ⑦ 只追加、不改行 | 是（表上不建外键） | 是（表上不建外键） |

## 撑不住的时候

- **两套语言 = 排查要学两遍**。如果平台侧叫 `result`、仓库侧叫 `status`，平台侧记"第几次调用"、仓库侧记"第几次尝试"，那么"这条链上到底哪一跳断了"这个问题每次都要重新学一遍。图上七行能对齐，就是为了让同一个问题只需要问一次。
- **平台单号不等于内部单号**。平台单号是对方给的，我们自己的 `order` 表里没有这个值。没有映射表，"同一张平台单被拉两次"就会变成**两张内部订单**（两张单、两份库存、两次发货）—— 而重复拉单在平台侧是**常态**（水位回退、超时重取、人工重试）。
- **一次外呼一行 vs 一次交互两行，混着读会读错**。仓库侧是 `REQ` / `ACK` 两行一对；平台侧是一次外呼一行、请求与响应并在同一行。拿仓库侧的口径去读平台日志，会得出"每次都少了回执"的幻觉；反过来拿平台口径读仓库，会把一对读成"一次下发被记了两遍"。
- **拉单流水天生没有唯一键**。它一张表里混了两种行：单据行（回传发货，天然唯一 `{店铺}:SHIP_PUSH:{包裹}:{第几次}`）与汇总行（一次拉单一行"新建 x / 跳过 y / 失败 z"，同一店铺连拉两次是**两件不同的事**，两行都得留）。想给整表加一个唯一键，必然误杀其中一种。

## 改了什么

**① 身份：平台侧靠映射表翻译，仓库侧不用翻译**

`channel_order_map` 上 `uk_map(shop_id, platform_sn)` 是幂等闸门：拉单时**先查闸门**，命中就抛 `DuplicateOrderException`，调用方记一条 `SKIP / IDEMPOTENT`（重复是常态，不是错误）。真正写映射是在建单之后 —— `INSERT ... ON DUPLICATE KEY UPDATE id=id`，影响 0 行说明并发路径已经把这单吃进去了，于是把刚建的订单回滚掉。仓库侧没有这一步：包裹单号本来就是我们自己生成的（`delivery_order.uk_delivery_sn`），不需要翻译。

**② 一次交互记几行：仓库两行一组，平台一行一次**

仓库侧是 write-ahead 两阶段：先写 `REQ`（我要发什么，回执列留空）→ 外呼 → 再追加 `ACK`（结果 + 耗时 + 回执）。平台侧是一次外呼一行，请求与响应同在一行 —— 因为拉单/回传都是"一问一答一次就结束"，没有"发出去之后还要等另一件事"的第二阶段。

**③ 分档：多出来的那一档，各自有各自的理由**

- 平台多一档 **`SKIP`**：重复拉单是常态，幂等命中要能和"失败"分开记（`SKIP / IDEMPOTENT`、`FAIL / SKU_NOT_MATCHED`）。
- 仓库多一档 **`TIMEOUT`**：超时的语义是"报文**可能已经发出去了**，只是没等到回"。归进"失败"就会诱发重试 → 重复发货。所以它单列一档。
- 这两档**不能互相替代**：`SKIP` 是"对方的东西我们已经有了"，`TIMEOUT` 是"我们发的东西对方可能收到了"。同一个人把它们当同义词，重试策略一定写错。

**④ 防重：两边现在都有库上的闸，但闸的粒度不同**

- 仓库侧：`uk_idem`，键 `{包裹ID}:{方向}:{尝试号}`，同一次尝试被重放不会多行。
- 平台侧：原本**只追加、没有任何唯一键**（"重推不重单"只能靠代码自觉，这是叙事上的漏洞）。`V2__channel_sync_idem.sql` 补了一道：生成列 `idem_key = IF(action='SHIP_PUSH', CONCAT(shop_id,':SHIP_PUSH:',ref_id,':',attempt), NULL)` + `UNIQUE uk_sync_idem`。**只有回传发货的单据行非空，拉单汇总行/明细行一律 `NULL`** —— MySQL 唯一索引允许多个 `NULL`，所以它们完全不参与约束，这是有意的。
- 所以平台侧的防重是**两处分工**：拉单的幂等靠 `channel_order_map.uk_map`（按平台单号），回传的幂等靠 `uk_sync_idem`（按店铺 + 包裹 + 尝试）。别把这两处说成一处。
- 写入用 `INSERT ... ON DUPLICATE KEY UPDATE id = id`（不用 `INSERT IGNORE`）：影响 0 行 = 这次尝试已记过账 = 当 `SKIP` 处理，不报错、也不覆盖第一行。

**⑤ 平台侧的另外两条，是为了让"一张单坏了不拖累一批"**

- **按单开事务**（`ChannelOrderImporter` 每张单 `REQUIRES_NEW`）：一张单的 SKU 对不上，不该把同批 20 张单一起回滚 —— 否则"跳过该单"就变成了"跳过整批"。失败各自回滚、各自留一条 `FAIL` 日志。
- **水位只在成功时前进**：`channel_shop.watermark_at` 是上次成功拉单的**开始时刻**，下次 `since` 就传它；拉单失败时水位原地不动，这些单下次还要拉。

**①b 同一件事的列与键级对照（换库也不用改，直接贴给 mysql）**

```sql
-- 列级对照：两本账是不是同一套语言（身份 / 报文 / 分档 / 尝试号 / 耗时）
select table_name, column_name, column_type, is_nullable
  from information_schema.columns
 where table_schema = database() and table_name in ('channel_sync_log','wms_exchange_ledger')
 order by table_name, ordinal_position;

-- 键级对照：谁有幂等闸、闸在哪几列上
select table_name, index_name, non_unique,
       group_concat(column_name order by seq_in_index) as cols
  from information_schema.statistics
 where table_schema = database()
   and table_name in ('channel_sync_log','wms_exchange_ledger','channel_order_map')
 group by table_name, index_name, non_unique
 order by table_name, index_name;
```

判读口径：两表都有 `attempt` 列、都有 `latency_ms`、都有 `result` 枚举、都有 payload、都**没有**指向业务表的外键；差异只在键的粒度上（`wms_exchange_ledger.uk_idem` 对 `channel_sync_log.uk_sync_idem` 生成列，而拉单防重在 `channel_order_map.uk_map`）。

**② `V2__channel_sync_idem.sql` 是可重跑迁移**：加列/加索引前先查 `information_schema`，已存在则空转；删重复时只删"多余的"、保留 `MIN(id)`，重跑为 0 行。它的注释里逐条写了"为什么只闸 `SHIP_PUSH`、为什么不闸 `PULL`"，也就是上面第 ④ 条那段口径的出处。

**③ 代码位置可点**（换谁来读都能顺着找到）：`channel/service/ChannelSyncService`（失败口径 → `OK/FAIL/SKIP` 的映射）、`channel/service/ChannelOrderImporter`（五步落单 + 幂等闸门 + 按单事务）、`shared/ledger/WmsExchangeLedgerWriter`（REQ→外呼→ACK 两阶段）。

## 附：口径与边界

- **"平台也是一个仓库"的判据是五样，不是名字**：外呼、第几次尝试、耗时、结果、失败原因 —— 这五样齐了，它就是同一套台账管得住的对象，不必为它另造说法。少一样（例如没有尝试次数），它就只能记成"流水"，无法回答"发了几次"。
- **`SKIP` 与 `TIMEOUT` 不可互换**，理由见上；`OK/FAIL/SKIP` 与 `SUCCESS/FAIL/TIMEOUT` 是两套枚举，映射时别做"差不多"的合并。
- **平台侧的防重分两处，别合并叙述**：拉单靠 `channel_order_map.uk_map(shop_id, platform_sn)`（**按店铺**，跨店铺同一个 `platform_sn` 是两件事），回传靠 `uk_sync_idem`（按店铺 + 包裹 + 尝试）。拉单汇总行与单张平台单的 `SKIP/FAIL` 明细行 `idem_key` 为 `NULL`，**完全不参与唯一约束** —— 同一张单被平台重推两次，必须能看到两行。
- **唯一"别扭"的地方是买家**：渠道单的买家在平台上，本地没有会员档案，而 `order.member_id` 是 `NOT NULL` + 外键 `fk_order_member`。所以渠道单一律挂在一个公共账号 `channel_platform_buyer`（"平台买家"）上。这是**结构上的必需**（要么建这个账号，要么改 `order` 表允许 `member_id` 为空，后者会动到会员模块的既有约束），代价是"平台买家"这个身份无法区分真实买家 —— 想按会员维度看渠道销售，这条边界绕不过去。
- **表上不建外键是有意的**（"台账 + 外部系统 id"这条铁律）：`channel_sync_log.shop_id`、`channel_order_map.shop_id`、`wms_exchange_ledger.delivery_id` 都没有外键。理由是同一个：**证据不跟着业务级联删除**，外键一挂，删单/删店就会连带删证据或直接删不掉。
- **本页数字的出处**：本页下方「实测数字」五段只读 SQL（快照 2026-11-14 18:53，库 `qiqi_mall_e2e_b`）。行数与具体分布随当次数据变，「两侧都记着身份/发了什么/回了什么/第几次/耗时/结果」「回传单据行才有幂等键」这些结论不变。注意 `result` 是 **ENUM**，`order by result` 按枚举序（`OK → FAIL → SKIP`）而不是字母序，别把分组结果读成字母排序。
