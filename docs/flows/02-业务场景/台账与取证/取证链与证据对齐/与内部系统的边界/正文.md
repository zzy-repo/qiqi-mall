## 与内部系统的边界（channel vs warehouse）

凡是「要主动去喊别人、而这件事在数据库之外有副作用」的边界都长成同一个形状：平台接入从店铺拉单 `PULL`、回传运单号 `SHIP_PUSH`（落 `channel_sync_log`），仓库履约下发 `REQ`、收仓侧回传 `ACK`（落 `wms_exchange_ledger`）。七件事两边一一对应：对端身份、本地发什么、对端回什么、结果分几档、第几次尝试、耗时、只追加不改行。差别只有三处 —— 身份从哪来、一次交互记几行、分档与防重。

身份：平台单号是对方给的，靠 `channel_order_map` 翻成内部订单，`uk_map(shop_id, platform_sn)` 就是幂等键，拉单先查它、命中按 `SKIP / IDEMPOTENT` 记一条（重复是常态，不是错误）；写映射在建单之后，`INSERT ... ON DUPLICATE KEY UPDATE id=id` 影响 0 行说明并发已吃进这单，回滚刚建的订单。仓库侧不用翻译：包裹单号由本地生成。

行数：仓库侧 write-ahead 两行一对（先 `REQ`、回执列留空，拿到回执再追加 `ACK`），平台侧一次外呼一行、请求与响应同在一行 —— 前者外呼之后还要等另一件事，后者一问一答一次结束。

分档与防重：平台多一档 `SKIP`（幂等命中与失败必须分开记），仓库多一档 `TIMEOUT`（报文可能已发出、只是没等到回，归进失败会诱发重试变成重复发货），两档不可互换。键的粒度也不同：仓库 `uk_idem` 键是 `{包裹ID}:{方向}:{尝试号}`；平台回传靠生成列上的 `uk_sync_idem`，只有回传单据行非空，拉单汇总行与明细行一律 `NULL`、不参与约束，拉单幂等另靠 `uk_map`。另两条规矩是「一张单坏了不拖累一批」：按单 `REQUIRES_NEW` 事务；水位 `watermark_at` 只在成功时前进。

**效果**　本页无界面，证据是两侧台账各取真行逐列对照（五组只读 SQL，快照 2026-11-14 18:53，`qiqi_mall_e2e_b`）：4 行映射（店铺 1 → 订单 16、店铺 2 的两单 → 17 / 18、店铺 3 → 19），每张单各有 1 条 `ORDER_CREATE` 出生行；平台侧同一包裹 2 是 `attempt=1 FAIL`（503，3ms）→ `attempt=2 OK`（4ms）；`PULL/OK` 6 行与 `PULL/SKIP` 3 行的 `idem_key` 全空，`SHIP_PUSH` 3 行全有键；仓库侧包裹 1 是 `REQ:1`（结果/耗时/回执全空，报文 73 字）→ `ACK:1 SUCCESS 67ms` → `ACK:2` / `ACK:3`（报文在请求列、`latency` 空）；三把键都在库上（`non_unique` 全 0），三张台账外键数 0。

**边界**　判据是五样：外呼、第几次尝试、耗时、结果、失败原因 —— 齐了才是同一套台账管得住的对象，少一样就只能记成流水，回答不了「发了几次」。平台侧防重分两处：拉单按 `(shop_id, platform_sn)`，回传按店铺 + 包裹 + 尝试。唯一别扭的是买家：渠道单的买家在平台上、本地没有会员档案，而 `order.member_id` 是 `NOT NULL` 加外键，所以渠道单挂在公共账号 `channel_platform_buyer` 上 —— 想按会员维度看渠道销售，这条边界绕不过去。三张台账都不建外键，理由同一个：证据不跟业务级联删除。数字出处：18:53 那组来自本页 `实测数字.sql`，数字随当次数据变。
