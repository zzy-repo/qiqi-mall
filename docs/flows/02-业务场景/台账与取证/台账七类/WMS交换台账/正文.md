## WMS 交换台账（wms_exchange_ledger）

货单要外呼仓库系统，这一步在数据库之外产生副作用：仓库收到就开始拣货，回滚不掉。所以顺序定成 write-ahead —— 外呼之前先写 `REQ` 行（报文快照与第几次尝试，回执列全部留空），拿到回执再追加 `ACK` 行（`result` + `latency_ms` + 回执报文）。先发后记的话，「发出去了但记不上」就是黑洞：仓库认为收到，库里零记录，既查不到也不知道该不该补发。

一次下发最多两行，`REQ` 与 `ACK` 同 `attempt_no` 一对。幂等键是 `{包裹ID}:{方向}:{尝试号}` —— 方向必须进键，否则同一次尝试的 `REQ` 与 `ACK` 在同一张表上会互相撞键；`attemptNo` 按方向各自取，重放同一尝试同一方向撞 `uk_idem` 即静默跳过。超时单独一档（`TIMEOUT`）：报文可能已经发出去、只是没等到回，归进 `FAIL` 会让重试变成重复发货。

两个方向的报文落在不同列：下发回执那行是问与答（`response_payload` 有、`request_payload` 空）；仓库回传那行是对方主动给、没有回（报文落 `request_payload`，另两列空）。两种 `ACK` 不能混在一起算耗时。

一个取舍：两行都在业务事务里，与包裹状态同生共死，外呼抛异常则整笔回滚、`REQ` 行一起消失。它保证的是「接口看到的成败与台账一致」，不是「进程崩溃后仍留痕」—— 后者要独立事务或预写日志，代价是留下「包裹没下发、台账却有 `REQ`」的孤儿行。只追加：重试是新增一组行（尝试号 +1），老的那组一个字都不改。

**效果**　四组只读 SQL（快照 2026-11-14 16:46，`qiqi_mall_e2e_a`）：包裹 1 的记账顺序：`REQ:1`（`result`、`latency`、回执全空，报文有）→ `ACK:1` `SUCCESS` 121ms（回执有、报文空）→ `ACK:2`（回传，报文在 `request_payload`、`latency` 空）；尝试号按方向各自自增：`REQ:1` 14 行、结果全未定论，`ACK:1` 与 `ACK:2` 各 14 行、全 `SUCCESS`，`ACK:3` / `ACK:4` 各 1 行；44 行 = 44 把去重键，键形态合规 44 / 44；结果分布 `SUCCESS` 30 / `FAIL` 0 / `TIMEOUT` 0 / 未定论 14。UI 侧 `WMS交换台账.spec.js`：3 条用例、40 处断言：下发前台账为空，点「下发」后正好 2 行、顺序是 `REQ`、`ACK`；`REQ` 行 `attempt_no=1`、`result` 与 `latency` 与回执都空、报文含 `DL…`；`ACK` 行同一个尝试号、`SUCCESS`、`latency` 非空、回执非空且不复制报文；两把键一把含 `:REQ:`、一把含 `:ACK:`；仓库回传出库再追加一行 `ACK`；同一个回传事件重放两次，台账一行都不多。

**边界**　「这一单发没发」的判据是 `REQ` 行，不是 `ACK` 行：有 `REQ` 没 `ACK` 是发出去没等到回；没有 `REQ` 行意味着它没走过本台账（开关关了或走了别的路径），不是「发送成功」。`FAIL` / `TIMEOUT` 本轮实测 0 行：mock 全成功，且外呼抛异常时整笔回滚连 `REQ` 一起没了 —— 想看真实失败行得先把台账挪进独立事务。去重分两层：`uk_idem` 挡「同一次交换被写两遍」；仓库重投的业务事件在包裹状态那层就被挡住。数字出处：16:46 那组来自本页 `实测数字.sql`，数字随当次数据变。
