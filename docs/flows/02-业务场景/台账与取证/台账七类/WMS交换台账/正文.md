**WMS 交换台账：先记「我要发什么」，再记「对方回了什么」** —— 一次外发最多两行（`REQ` + `ACK`），同一个 `attempt_no` 一对。为什么顺序不能反：货单一旦发出去就**收不回来**，先发后记的话，"发出去了但记不上"就是一个黑洞 —— 仓库认为收到了，我们库里一条记录都没有。

## 场景

平台单进来之后，货要发出去，这一步必须外呼仓库系统（WMS）。它在数据库**之外**产生副作用：仓库收到货单就开始拣货了，这件事回滚不掉。

出问题时问的永远是同一串问题：

- 这一单到底发出去没有？
- 发了几次？（超时重试过吗）
- 每次对方多久回？回的什么？
- 仓库说"我没收到货单"，我们凭什么反驳？

这页就是回答这一串的东西：台账页（`admin-web/src/views/ledger/index.vue`）类型选「WMS 回调」，业务ID 填**包裹 id**，一次下发就是"一问一答"两行。底下那张表是 `wms_exchange_ledger`，接口侧是 `GET /admin/ledgers?type=WMS&bizId=<包裹id>`。

一行 = 一次单向交换：

| 列 | REQ 行（下发） | ACK 行（回执/回传） |
| --- | --- | --- |
| `direction` | `REQ` | `ACK` |
| `attempt_no` | 按 `(包裹, 方向)` 各自从 1 递增 | 同上 |
| `request_payload` | 我要发什么（含包裹单号） | 仓库回传时对方的报文落在这里 |
| `response_payload` | 落库时**必须为空**（还没有回执） | 回执报文 |
| `result` | `NULL`（未定论） | `SUCCESS` / `FAIL` / `TIMEOUT` |
| `latency_ms` | `NULL` | 一次往返的毫秒数 |
| `idem_key` | `{包裹ID}:REQ:{n}` | `{包裹ID}:ACK:{n}` |

## 撑不住的时候

- **先发后记 = 黑洞**。外呼成功的响应还没写库时进程就挂了，或事务回滚了 —— 仓库那边货已经开始拣，我们库里零记录。反过来先记后发，最坏情况是"记了 REQ 但没真正发出去"，那是**可查、可补发、可解释**的；黑洞是既查不到、也不知道该不该补。所以顺序是 `REQ → 外呼 → ACK`。
- **两行挤成一行，精度就没了**。把请求和响应写在同一条记录上（一个 `status` 字段 + 两个 payload 列），就看不出三件事：第几次尝试、每次多久、**超时到底算不算"发出去了"**。超时必须单独一档：超时的语义是"报文可能已经发出去了，只是没等到回" —— 这一档如果被归进"失败"，重试就会变成重复发货。
- **同一尝试被写两次，会多出一对幽灵行**。重试、重放、并发都可能让同一次交换被写两遍。键里不带方向的话，同一次尝试的 `REQ` 与 `ACK` 还会互相撞键 —— 一次外发两行、同表，方向必须进键。
- **仓库回传重复推送**。仓侧重投 `outbound` 是常态。业务侧重投是幂等的（包裹状态不变），但台账如果跟着记，就会出现"回传了三次"的假象。

## 改了什么

① **write-ahead 两阶段，唯一写入口 `shared/ledger/WmsExchangeLedgerWriter`**：

```java
requestSent(...)      // 外呼之前：写 REQ 行（报文快照 + 第几次尝试，回执列留空）
// —— 这里才真的把货单发出去 ——
requestAcked(...)     // 拿到回执：追加 ACK 行（result + latency_ms + 回执报文）
```

`callbackReceived(...)` 处理仓库回传来账（`pick` / `outbound` / `transit` / `signed`），方向仍是 `ACK` —— 这是"仓库给我们的回执"。所以一次下发 + 两次回传，台账里是 `REQ:1 / ACK:1 / ACK:2 / ACK:3` 这样的形状。

② **幂等键 = `{包裹ID}:{方向}:{尝试号}`**：`direction` 必须在键里，否则同一 `attempt` 的 REQ 与 ACK 会撞 `uk_idem`。`attemptNo` 由 `nextAttemptNo(deliveryId, direction)` 按方向各自取，重放同一 attempt 同一方向 → 撞键 → 静默跳过。

③ **超时也记一行失败**，重试再记一组、尝试号 +1，**老的那组一条都不改**（只追加，表上只有 `created_at`）。

④ **一个必须说清的取舍（不是 bug）**：`REQ` / `ACK` 两行都在**业务事务里**，与包裹状态同生共死。外呼抛异常 → 整笔回滚 → `REQ` 行也消失。也就是说它保证的是「接口看到的成功/失败与台账一致」，而**不是**「进程崩溃后仍留痕」—— 后者要 `REQUIRES_NEW` 独立事务或落盘预写日志，代价是会留下"包裹没下发、台账却有 REQ"的孤儿行，那需要另一套对账机制来清。本轮明确选前者。

⑤ **两个方向的报文落在不同列，是刻意的**：下发回执那行是"我们问、对方答"（`response_payload` 有、`request_payload` 空）；仓库回传那行是"对方主动给、我们没回"（报文落 `request_payload`、`response_payload` 空、`latency_ms` 空）。读数据时别把这两种 ACK 混在一起算耗时。

## 附：口径与边界

- **「这一单发没发」的判据是 `REQ` 行，不是 `ACK` 行**。有 `REQ` 没 `ACK` = 发出去了但没等到回执（看 `created_at` 差多少）；有 `REQ` 有 `ACK` 且 `result=SUCCESS` = 确认送达。**一张外发没有 `REQ` 行**意味着它没走过本台账（开关关了，或走了别的路径）—— 不是"发送成功"。
- **`FAIL` / `TIMEOUT` 本轮实测都是 0 行**，不是因为不会失败，而是因为：mock 全成功，且外呼抛异常时**整笔回滚，连 REQ 行一起没了**（见上面第 ④ 条取舍）。所以"失败长什么样"这件事，本页只能给出机制与字段口径，给不出实测行 —— 想看真实失败行，得先把台账挪进独立事务。
- **两道闸的分工**：`uk_idem`（`{包裹}:{方向}:{尝试号}`）挡"同一次交换被写两遍"；重复**业务事件**（仓库重投同一个 `outbound`）在包裹状态那一层就被幂等挡掉了，根本走不到这里 —— 所以台账里不会出现"同一事件两行"。
- **台账只追加**：超时/失败重试是**新增一组行**（尝试号 +1），老的那组一个字都不改。想"改一下上次的结果"这个动作在这张表上不存在。
- **不含业务结果**：台账记的是"我们发了什么、对方回了什么"，不解释"为什么这单不能发"。业务侧的拒发原因在操作审计与包裹状态台账里。
- **本页数字的出处**：本页下方「实测数字」四段只读 SQL（快照 2026-11-14 16:46）。数字随当次数据变，「两行一组 / 键形态 100% 合规 / REQ 行结果为空」这几条结论不变。
