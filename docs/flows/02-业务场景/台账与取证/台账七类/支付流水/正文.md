**支付流水：钱的每一次进出都要能对上订单，也能对上前一笔** —— 付款成功记一条支付流水，退货审核通过记一条退款流水。防重复有**两道闸，管的不是同一件事**：`uk_channel_trade(channel, trade_no)` 挡的是"对方重复通知"，`uk_idem(idem_key)` 挡的是"自己连点和重试"—— 少一道就漏一笔。

## 场景

钱这一侧的对账问题从来不是"有没有记录"，而是"这条记录能不能自证"：

- 买家说"我付了两次" —— 要看渠道流水号是不是同一个；
- 财务说"这笔退款退的是哪一笔钱" —— 要看退款流水有没有指回原支付流水；
- 运营问"这张单退款批了几次" —— 要看退款流水条数与订单实付是否对得上；
- 订单被删了要核账 —— 那张单的流水行已经被清掉，能查的是**台账「审计」那一支里的 `PAYMENT_PURGE` 行**（`orderSn` / 条数 / 金额合计 / 每条 `tradeNo`+`type`+`amount`，按订单 id 反查）；同一方法里那行 `log.warn` 只是伴随的应用日志（这条口径是怎么被发现的，见附里最后几条）。

这页就是这本账：台账页（`admin-web/src/views/ledger/index.vue`）类型选「支付流水」，业务ID 填订单 id，一屏就是这张单的支付 + 退款行；接口是 `GET /admin/ledgers?type=PAYMENT&bizId=<订单id>`（`LedgerSql.PAYMENT_BRANCH`）。行上的四个要素缺一不可：**关联哪张订单、触发它的是哪张单据、操作人是谁、去重键是什么**；退款那条还必须多一个 `origin_flow_id`。

## 撑不住的时候

- **只有一道闸，必然漏一种重复**。业务上"重复"有两种完全不同的来源：渠道把同一笔通知又推了一次（对方的错），和自己重试/连点把同一笔又记了一次（我们的错）。前者带回来的是**同一个** `trade_no`，后者带回来的是一次全新的本地请求 —— 只用一把键去挡，另一种就漏过去了。所以是两道闸，且**语义必须分开**：撞 `uk_channel_trade` = "这笔钱已经记过了，忽略"；撞 `uk_idem` 且 `trade_no` 是新的 = "渠道给这张单发来了第二笔真实扣款"，**必须人工对账，绝不能像重放那样静默吞掉**（那会真丢一笔钱）。
- **"退的是哪一笔钱"说不清**。退款流水如果只记金额和时间，事后只能拿"金额相同 + 时间最接近"去猜 —— 一张单两次部分退款、两次金额一样时，猜不出哪次退的是哪笔。所以退款行必须带 `origin_flow_id` 指回原支付流水。
- **它和订单之间没有外键，两条路都危险**。`payment_record` 按 `order_sn` 字符串关联订单：加 CASCADE 会顺手把对账证据销毁，完全不管又留孤儿行。现行口径是"删单前**显式**清理这张单的流水，且**先写 `admin_audit_log`（`action=PAYMENT_PURGE`，含条数 / 金额合计 / 逐条 `tradeNo`·`type`·`amount`）再删**"（`OrderPurgeService#purgePaymentRecords`：先把那份摘要写进审计表，再按 `order_sn` 删；同事务里那行 `warn` 只是伴随的应用日志）。所以**删单之后查不到那张单的支付流水** —— 能查到的是**台账「审计」那一支**里那条 `PAYMENT_PURGE`（一行 `admin_audit_log`，按订单 id 反查），流水本身已经没了；这就是"删单时证据从流水表挪进审计台账"的实际含义，同一次请求里它紧随订单级那条 `ORDER_DELETE`。另外库里还有历史行 `order_id` 为空（早期没回填这一列，`order_sn` 对应的订单本身还在）—— 这些行能被找出来，**全靠 `order_sn` 快照**。所以"对账键是 `order_sn` 不是 `order_id`"不是偏好，是被数据逼出来的。
- **删单路径不留行：先写一条 `PAYMENT_PURGE` 审计，再按 `order_sn` 删干净**。`payment_record` 上没有外键，但删单路径不会把行留在原地：`OrderController#delete` 先落一条订单级 `ORDER_DELETE` 审计（单号 + 状态快照 + `{deleted:true}`），接着 `purgePaymentRecords` 在**同一事务里、DELETE 之前**往 `admin_audit_log` 写一条 `action=PAYMENT_PURGE`（订单号 / 条数 / 金额合计 / 每条 `tradeNo`·`type`·`amount`，逐条明细另存进 `before_json`），再按 `order_sn` 把这张单的流水删干净，最后才删订单本体（中间任何一步影响行数不符、或审计写失败，都整体回滚）。所以想核"这单删之前收过几次钱"，看的是**台账「审计」那一支里的 `PAYMENT_PURGE` 行**（`GET /admin/ledgers?type=AUDIT&bizId=<订单id>`），不是流水表；同一方法末尾那行 `log.warn` 只是排障时顺眼的伴随日志。流水表上留下的 `order_sn` 快照，服务的是**没被删的单**怎么按单号对账。
- **"重复通知"只能靠沙箱端点演，生产上没有这条路**。本地模拟支付生成的 `trade_no` 是按时间戳编的，永远不会与上一笔相同 —— 所以要让 `uk_channel_trade` 这道闸**被真的撞一次**，只能走 `POST /admin/payments/{id}/replay-channel-callback`（用**原 `trade_no`** 再走一遍渠道回调），而它受 `qiqi.payment.sandbox-endpoints-enabled` 控制、生产默认关。本页此前被标成 `fixme` 是因为连这个端点都没有；现在缺口补上了，但边界要说清：**闸是活的（用例里还直插一条同 `(channel, trade_no)` 的行验证库会拒），可在生产里你无法自己制造一次重复通知**。

## 改了什么

① **两道唯一键，都在库上**：`uk_channel_trade(channel, trade_no)` + `uk_idem(idem_key)`。不是代码里 `select` 一下再决定写不写（那在并发下必然漏），是让数据库拒。实测 `information_schema.statistics` 里这两把键都是 `non_unique=0`。

② **写入分三种结果，不许合并成一个"没写成"**（`PaymentRecordService#recordChannelNotice` 的返回契约）：

| 结果 | 含义 |
| --- | --- |
| `true` | 第一次通知，记账成功（+1 行） |
| `false` | 该 `(channel, trade_no)` 已入过账 = **重复通知，忽略**（不是失败） |
| 抛异常 | 同一个 `idem_key` 已入账，但 `trade_no` 是新的 = 渠道第二笔真实扣款，**必须人工对账** |

③ **记清四个要素 + 溯源**：`order_sn`（对账键，`NOT NULL`）、`order_id`（可空：历史行没回填；删单的流水会被整单清掉，不会靠它悬空留下）、`ref_type` / `ref_id`（触发单据：退款 = `RETURN_APPLY` + 申请 id）、`operator_*`（谁动的）、`origin_flow_id`（退款指向原支付流水）。这些字段**必须由调用方给** —— 只有调用点知道"这笔钱是谁、为什么、因为哪张单据动的"；从 `order_sn` 反推是猜，猜错的台账比没有更坏。

④ **幂等键口径**：支付 `{orderSn}:PAY`，退款 `{orderSn}:REFUND:{退货申请id}` —— 退款键里必须带申请 id：只用 `{orderSn}:REFUND` 会把**第二笔合法退款当成重放吞掉**（那是真丢钱）。

⑤ **撞键之后要能分清"撞的是哪道闸"，而且回查要做两次**（`PaymentRecordServiceImpl#idemKeyAlreadyBooked`）：

- 撞键时先判"这个 `idem_key` 到底已入账没有"。**本事务内**先查一次（看得见自己刚插、还没提交的那行 —— 同一事务里 `record()` 被调两次就是这种）；再在 **`REQUIRES_NEW` 新事务**里查一次（另一条连接 = 新快照，看得见别的写入方刚提交的行）。只做第一道会把"真重放"判成"撞了别键"原样抛出，用户看到失败，而设计承诺的是幂等跳过。
- 两处都没查到 → 撞的必然是另一道闸 `uk_channel_trade`，包成可读的业务异常抛出（原始 `DuplicateKeyException` 挂在 `cause` 上），文案直接点明"疑似同一笔钱重复入账，需人工对账"。
- 为什么不用 `SELECT ... FOR UPDATE` 或改隔离级别：撞键失败的那次 `INSERT` 已经在唯一索引上留了共享锁，同事务再加锁读等于跟自己抢锁；新事务里的普通快照读不加锁、不阻塞，也不用为一次判重改全局隔离级别。
- 回查本身失败（连接池耗尽 / DB 抖动）时，**既不能当"已入账"，也不能把回查的失败当新原因**：原样抛出原始异常，把回查失败 `addSuppressed` 上去，两个事实都留在堆栈里。

⑥ **可重放的渠道回调端点**：`POST /admin/payments/{id}/replay-channel-callback`，用**原 `trade_no`** 再走一遍渠道回调。受 `qiqi.payment.sandbox-endpoints-enabled` 控制（默认 `false`，只有 dev/test/e2e 打开）；写权限 `payment:write` **不可授予**，所以 API Key 一律 403，只有人工 JWT 能调。这是让"重复通知"这个场景能被演出来的前提。

⑦ **流水只追加**：写错了再记一条冲正，不回头改那一条。表上只有 `created_at`。

## 附：口径与边界

- **流水加起来不是余额，三样数也不该强求相等**：`流水条数（27）`、`金额合计`、`订单实付` 谈的是三件事。净额只能按 `Σ(支付) − Σ(退款)` 算，且必须**逐笔**能指回订单与前一笔 —— 拿"条数相等"或"金额相加"当余额校验，结果只有两种：报一堆假错，或者顺手改掉真数据。**行数对平 ≠ 金额对平 ≠ 余额。**
- **两道闸缺一不可，而且不能互相替代**：`uk_channel_trade` 挡对方重复通知，`uk_idem` 挡自己连点/重试。历史有 **14** 行 `idem_key` 为空（新写入必填，历史行为 `NULL`），所以在那个时段，本地去重实际只有渠道流水号一道闸 —— 这是本页最该说清的边界。
- **台账只追加**：写错就再记一条冲正，不 `update`、不改写旧行。所以"改一笔金额"这件事在这张表上不存在，只存在"多一条相反方向的流水"。**唯一的删是删单时的整单清理**（先在 `admin_audit_log` 写一条 `PAYMENT_PURGE`，再按 `order_sn` 删干净）—— 那不是"改账"，是"这单整体退出对账范围"，而"退出"这件事本身留了痕：就是「审计」那一支里那条 `PAYMENT_PURGE`，不是"没痕迹"。
- **`order_id` 会为空，`order_sn` 不会**：`order_id` 是回填来的普通列，历史行没回填时它就是空的（实测 **14** 行，这些行的 `order_sn` 都能在 `order` 里找到对应订单）；`order_sn` 是 `NOT NULL` 的对账键与快照（实测 **27** 行全有）。任何"按订单核账"的实现都必须用 `order_sn`，用 `order_id` 会静默漏掉这 14 行。再强调一遍方向别弄反：**删单会显式删掉该单的流水**（`OrderPurgeService#purgePaymentRecords`），删之前先往 `admin_audit_log` 写一条 `PAYMENT_PURGE` —— 所以删单之后**查不到**那张单的支付流水，但台账里**有一条**"这张单的流水被删了"的行：`PAYMENT_PURGE`，它在同一次请求里**紧随** `ORDER_DELETE`（同一批 `id`、同一个 `request_id`，靠 `request_id:序号` 区分先后），查它用 `type=AUDIT&bizId=<订单id>`。
- **这个缺口已经补上了：清理流水现在先记账、后删除**。原来的状态是"清理流水只留一行应用日志、台账里没有凭证"——`purgePaymentRecords` 的注释与 `log.warn` 文案都写着"已先落审计日志"，但代码里**没有** `AdminAuditWriter` 调用，那一行只进了应用日志（会轮转、会随容器消失、台账页查不到），于是"这张单原本有三条流水、删单时被清掉"这件事事后**查不到台账凭证**。**现在补上的是三件事**：① **先记账后删除** —— `admin_audit_log` 里那行 `PAYMENT_PURGE` 在 DELETE `payment_record` **之前**写入，且与删除**同一个事务**：审计写失败（序列化炸了 / 列超宽）→ 整笔删单回滚、流水一行不动（宁可这次删单失败，也不许台账少一条）；反过来 DELETE 影响行数不符抛异常 → 审计行跟着回滚，于是"有审计行"恰好等价于"这次清理真的提交了"，不会留下"审计说删了 3 条、流水其实还在"的假凭证。② **幂等靠业务前置条件，不靠派生业务键** —— 审计的 `idem_key` 只由 `request_id` 派生（这次落在 `request_id:序号`），**绝不**由 `order_sn` 派生；"重复删单不多写"靠的是流水数为 0 时直接返回（一行不写）、第二次删同一张单在 `OrderController#delete` 的"订单不存在"处就返回、连 `purge` 都进不去 —— 合起来：一次真删 ⇔ 一条 `PAYMENT_PURGE`。③ **只有支付流水这一支补了** —— `stock_ledger` 那一支仍只有 `log.warn`（既定口径，那行 warn 里是回补件数与逐规格净额；见「订单状态台账」那页的对照）。这条缺口的**来历值得记一笔**：它不是被测试逮到的，是**写这页正文时逐句对照代码**才发现的 —— 注释在说"已先落审计日志"，代码里却没有那次写入；所以以后看到"文档/注释说已经有台账行"，就去 `AdminAuditWriter` 的调用点数一遍，别信措辞。
- **重放端点只在沙箱开**：`qiqi.payment.sandbox-endpoints-enabled` 默认 `false`，`payment:write` 不可授予（API Key 403）。这个端点的存在是为了"能演"，不是生产接口 —— 上线时它是关的，所以别在验收里靠它推断生产行为。
- **本页数字的出处**：本页下方「实测数字」四段只读 SQL（快照 2026-11-14 16:46）。数字随当次数据变，「0 重复 / 指得回前一笔 / 单号快照 100%」这几条结论不变。
