**后台操作审计：一次请求一行，连点两次要留两条** —— 改价、改库存、删单、拆单、合并、发货、退货审核，点一次就留一行：动作码、目标、目标单号快照、一句人话摘要、改前改后各一份**只含敏感字段**的快照、以及管理员填的原因。红线只有一条：**去重键只能由请求号派生，绝不能由订单号或包裹号派生**。

## 场景

后台的按钮都带副作用：改一次价影响毛利、改一次库存影响能不能卖、删一张单连包裹和退货申请一起没了。这些动作每天几十上百次，绝大多数没人回头看 —— 直到某天出现「这个价是谁改的」「这单谁删的」「库存怎么少了 3 件」。

这页就是那时候要翻的东西：台账页（`admin-web/src/views/ledger/index.vue`）类型选「审计」，或者直接 `GET /admin/ledgers?type=AUDIT`。它和订单状态台账是**两种完全不同的东西**，别混：

| | 状态台账 | 操作审计 |
| --- | --- | --- |
| 回答的问题 | 这单是怎么走到今天的 | 这个人点了什么 |
| 一行对应 | 一条**流转** | 一次**请求** |
| 去重键来自 | 业务键 + 流转序号 | **请求号**（`X-Request-Id`，没有就现生成 UUID） |
| 连点两次 | 第二次业务失败、台账不会多行 | **必须留两行**（第二次失败本身就是证据） |

## 撑不住的时候

坏环境不是「没有日志」，而是「日志有，但证明不了这件事是谁干的」：

- **按业务键去重，第二次点击会把证据回滚掉**。这是这条红线真正咬人的地方：审计和业务**在同一个事务里**（业务失败就不该留成功的假象，业务成功也不该少一行）。于是 `idem_key` 一旦写成 `ORDER:12:DELETE` 这种形状，同一个人连点两次时，第二次会撞上同一把唯一键 → `INSERT` 失败 → **整个事务回滚** → 用户看到「操作失败」，而库里本该留下的「他确实点了第二次」这条证据一起消失。审计语义直接反转：越想防重，越把重这件事藏起来。
- **整行 dump 的下场是把个人信息复制进只追加表**。`before_json` / `after_json` 如果直接塞整个实体，手机号、收货地址、买家昵称就都进来了。这张表**只追加、永不清理**，复制一份就再也去不掉 —— 为了审一个价格变更，把一批 PII 永久留在了审计表里。
- **「改了但看起来没改」也是一种缺口**。表单整份提交、实际一个字段都没变，如果照样记一行，审计里就会长出一堆「改前=改后」的行，真正有变化的那条被淹掉，读的人还得自己比对。
- **目标被删了，记录跟着没了**。删单审计最有价值的时刻恰恰是订单行已经消失之后 —— 如果那一行只存 `target_id`，那你只知道「有人删了 id=53」，不知道 53 是哪一张单。

## 改了什么

① **唯一写入口 `shared/ledger/AdminAuditWriter#record`**，幂等键 `requestId + ":" + n`，`n` 由同一请求内的 `ThreadLocal<Seq>` 计数（requestId 一变就自动从 1 重新开始）。选 ThreadLocal 而不是 MDC 存计数，是因为审计还要覆盖「不在 HTTP 请求线程里」的情况（定时任务、内部调用）。

② **请求号来源唯一**：`RequestIdFilter`（`@Order(HIGHEST_PRECEDENCE)`）每次请求生成/透传 `X-Request-Id`，写进 MDC、回带响应头。头里的值必须过白名单正则（`^[A-Za-z0-9_.:-]{1,64}$`）：它要落进 `VARCHAR(64)`，超长在 STRICT 模式下是**错误**，会把整个业务事务连同审计一起回滚 —— 不能让一个外部头决定我们记不记审计。

③ **只记敏感字段**：调用方用 `AdminAuditWriter.snapshot("stock", 旧, "stock", 新)` 显式挑字段，不整实体 dump。摘要、目标单号、原因是自由文本，按列宽裁（255 / 64 / 32）；`action` / `target_type` 是代码常量，**绝不裁 —— 超宽直接抛**。

④ **动作码按「哪个字段真的变了」选，不按请求体里有什么**：只改库存就是 `SKU_STOCK_CHANGE`，不是 `SKU_PRICE_CHANGE`。没有任何字段变化 → 一行都不写（整份表单原样提交 = 没有变更 = 不进证据表）。

⑤ **目标单号快照 + 订单 ID 冗余**：`target_sn` 存单号快照（目标被物理删除后仍可读）、`order_id` 冗余一列便于按订单检索这类动作 —— 删单审计正是靠这两列在订单已经不存在之后仍说得清是哪一单。

⑥ **只追加 + CHECK 闭集**：表上只有 `created_at datetime(3)`，没有 `updated_at`；`operator_type` 有 `CHECK (...) in ('ADMIN','MEMBER','APIKEY','SYSTEM')`，非法类型写不进去。

| 断言 | 实测 |
| --- | --- |
| 一次请求一行：行数 = 去重键数 | **83** 行 = **83** 把键；请求号 **79** 个 |
| 去重键只能由请求号派生 | `idem_key` 的前缀正好等于 `request_id` 的：**83 / 83** |
| 连点 = 多行、多个请求号 | 同一规格改库存 **12** 行 / **12** 个请求号（段号全是 `1`）；冻结同一张单 **4** 行 / **4** 个请求号 |

## 附：口径与边界

- **红线只有一句：去重键只从请求号派生**。写成 `ORDER:12:DELETE`、`SKU:1:STOCK` 这类业务键形状，功能测试照样能过（单次点击是成功的），但**连点的第二次会把两条证据一起回滚**。想在代码里防它，看 `AdminAuditWriter` 类注释与 `request_id` 列的 COMMENT —— 那两处写的是同一句话。
- **「一次请求一行」不等于「一行一个动作」**：同一次请求里确实可能写多条审计（例如删单同时冲掉支付流水），这时用 `request_id:1` / `request_id:2` 区分 —— 实测那 4 个双行请求号就是这种形状。
- **台账只追加**：没有 `updated_at`，也没有删除软删列。审计写错了不「修」，只能补一条新事实；`cleanupAuditRows()` 那种清理只存在于测试的 finally 里（清的是本次用例自己造的行），线上没有这个动作。
- **它证明「谁点了什么」，不证明「业务当时对不对」**。审计记的是动作与敏感字段快照，判断对错仍然要靠状态台账 + 业务表 —— 所以两本账并行存在，谁也不替代谁。
- **`request_id` 可空但审计行不许空**：列上留了 `DEFAULT NULL`（历史行、非 HTTP 线程），写入器层是强制的 —— 取不到请求号时生成一次性 id，取到了就用它。反过来，**一个新审计行 `request_id` 为空**说明有人绕过了 `AdminAuditWriter` 直接插表，那是缺陷。
- **本页数字的出处**：全部来自本页下方「实测数字」的五段只读 SQL（快照 2026-11-14 16:46）。具体行数随当次数据变，「行数 = 去重键数 / 键前缀 = 请求号 / 目标删了快照还在」这三条结论不变。
