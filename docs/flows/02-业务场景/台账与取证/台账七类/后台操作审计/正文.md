## 后台操作审计（admin_audit_log）

审计与状态台账回答两个不同的问题：状态台账记「这单走到今天」，审计记「这个人点了什么」。一行对应一次请求，不是一条流转：动作码、`target_type` / `target_id`、`target_sn` 单号快照、`order_id` 冗余列、一句人话摘要、改前改后各一份只含敏感字段的快照、管理员填的原因、操作人与类型、`created_at`。

去重键是 `requestId + ":" + n`，`n` 是同一请求内的段号。写成业务键形状（`ORDER:12:DELETE`、`SKU:1:STOCK`）会把语义反转：审计与业务同事务，第二次连点撞同一把唯一键 → `INSERT` 失败 → 整个事务回滚 → 用户看到「操作失败」，「他确实点了第二次」这条证据一起消失。

请求号只有一个来源：`RequestIdFilter` 生成或透传 `X-Request-Id`，写进 MDC 并回带响应头；值必须过白名单正则 `^[A-Za-z0-9_.:-]{1,64}$` —— 它要落进 `VARCHAR(64)`，超长在严格模式下是错误，会把业务事务连同审计一起回滚。

快照只挑字段，不整实体 dump：`AdminAuditWriter.snapshot(...)` 由调用方显式挑，`before_json` / `after_json` 里只有真正变化的列；表单原样再提交、一个字段都没变，一行都不写。动作码按「哪个字段真的变了」选，只改库存是 `SKU_STOCK_CHANGE`。摘要、单号、原因是自由文本，按列宽裁（255 / 64 / 32）；`action` / `target_type` 是常量，超宽直接抛而不裁。表上只有 `created_at`，没有 `updated_at`。

**效果**　五组只读 SQL（快照 2026-11-14 16:46，`qiqi_mall_e2e_a`）：83 行 = 83 把去重键、79 个请求号；`idem_key` 前缀等于 `request_id` 的 83 / 83；连点不合并 —— 同一规格改库存 12 行 / 12 个请求号、冻结同一张单 4 行 / 4 个请求号；一次请求写两行时靠段号区分，4 个 `request_id` 各 2 行、段号 `1` 与 `2`；删单审计 18 行，`target_sn` 非空 18、对应订单已不存在 18。UI 侧 `后台操作审计.spec.js`：3 条用例、46 处断言：改库存 +7 → 恰好 1 行，摘要逐字为 `修改规格库存：<改前> → <改后>`、两份快照的键只有 `['stock']`；连点两次改成不同值 → 两行、两个请求号，快照首尾相接（`+3` → `+9`），`idem_key` 以 `requestId + ":"` 开头且不夹业务键片段、新增行 `request_id` 无空值；原样再提交 → 一行不新增；真删一张单 → 1 行 `ORDER_DELETE`、`target_sn` 等于原单号、`after_json` 匹配 `{deleted: true}`。

**边界**　红线只有一条：去重键只从请求号派生。一次请求一行不等于一行一个动作 —— 删单同时冲掉支付流水就是同一请求两行。审计只证明「谁在什么时候点了什么、改了哪些字段」，不证明业务当时对不对。`request_id` 列有 `DEFAULT NULL`，写入器层强制生成；新行 `request_id` 为空说明有人绕过 `AdminAuditWriter` 直接插表。整实体 dump 会把手机号、收货地址、买家昵称复制进这张只追加、永不清理的表，所以快照只收敏感字段。数字出处：16:46 那组来自本页 `实测数字.sql`，数字随当次数据变。
