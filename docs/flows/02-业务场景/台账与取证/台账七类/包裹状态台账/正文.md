**包裹状态台账：一条包裹自己的流水，行里带着包裹单号快照** —— 拆单出生、下发、拣货、出库、签收，每走一步留一行。真正的重点是两列"冗余"：`delivery_sn` 快照与 `order_id`。因为订单被删时**包裹行会被真的物理删除**，那座"台账 → 订单"的桥一断，只靠 `delivery_id` 就再也回答不了「这张单发过几个包裹、每个走到哪一步」。

## 场景

一张订单拆成三个包裹，从三个仓出。买家问「我那两个件到哪了」，客服看的是包裹；仓库回传「拣货 / 出库 / 签收」，动的是包裹；出了纠纷要举证「这单到底发出去几件、几点发的」，靠的也是包裹。

这页就是包裹那条线：台账页（`admin-web/src/views/ledger/index.vue`）类型选「包裹状态」，业务ID 填**订单 id**，一屏就是这个订单下所有包裹的每一步。接口侧是 `GET /admin/ledgers?type=DELIVERY_STATUS&bizId=<订单id>`，数据源是 `v_biz_status_timeline` 的 `DELIVERY` 分支，而底下那张表是 `delivery_status_ledger`。

一行 = 一次流转：`前态 → 后态` + 原因码 + 操作人 + 触发单据 + 幂等键 `{包裹ID}:{流转序号}` + 记账时间。原因码序列长这样：

| 步骤 | 前态 → 后态 | 原因码 | 谁触发的 |
| --- | --- | --- | --- |
| 拆单出生 | 空 → 待下发(0) | `DELIVERY_CREATE` | 管理员审核通过 |
| 下发 | 待下发(0) → 已下发(1) | `DELIVERY_DISPATCH` | 管理员点「下发」 |
| 仓库回传拣货 | 已下发(1) → 已拣货(2) | `WMS_PICK` | 仓库回传 |
| 仓库回传出库 | 已拣货(2) → 已出库(3) | `WMS_OUTBOUND` | 仓库回传 |

## 撑不住的时候

包裹这条线的坏环境特别具体：**证据的目标会消失**。

- **订单被物理删除时，包裹行跟着消失**。`OrderPurgeService` 做的是真 `DELETE`，`delivery_order` 里那几行就没了。如果台账只存 `delivery_id`，那么「这张单发过几个包裹、每个走到哪一步」在这张单被删掉的那一刻**永久不可回答** —— 而删单恰恰是最需要事后追溯的动作。
- **桥断得比想象中快**。按订单反查包裹流水，中间必须经过 `delivery_order.order_id`：订单行没了 → 包裹行也没了 → 这座桥两边都空。所以台账上必须**自己**带一份 `order_id`（冗余列），否则「按订单查」这条路在删单后直接断掉。同一类缺口在售后台账上一模一样（`return_apply` 随订单级联删除），两张表必须对称。
- **单号也会一起没**。包裹单号 `DLxxxx` 是仓侧和我们对账时唯一共用的标识。它只长在 `delivery_order` 上，行一删，事后只剩一个孤零零的 `delivery_id` 数字 —— 谁也认不出这是哪个件。
- **重复回传会把一行变成两行**。仓侧重投同一个 `outbound` 事件是常态（超时重试、回调重放）。没有幂等的话，同一件事会被记成两条状态迁移，`status_seq` 被推高，最后「这包裹走了几步」这个数本身就是错的。

## 改了什么

① **两个"已登记冗余列"，缺一个就有一半场景作废**：

- `delivery_sn`（`NOT NULL`）：写入器 `StatusLedgerWriter#requireSn` 对空串**直接抛异常** —— 单号是包裹被物理删除后唯一的追踪线索。
- `order_id`：`#orderIdOf` 优先取实体值，缺了回查一次 `delivery_order.order_id`（`NOT NULL`），回查不到就抛。**拒绝写 `NULL` 蒙过去**，因为这一列存在的全部意义就是删单后仍能按订单反查；写一条 `NULL` 等于把缺口原样保留，还看起来"写成功了"。

② **唯一写入口 + 同一事务**：出生走 `#deliveryBirth`（前态 `NULL`），流转走 `#deliveryChanged`。两者都在 `DeliveryStatusService` 那句 `UPDATE` 成功之后、同一个 `@Transactional` 里 —— 状态与证据同生共死。

③ **幂等键 = `{包裹ID}:{流转序号}`**，序号在同一条 `UPDATE` 里和 `status` 一起自增。所以重投算出同一个键，撞 `uk_idem` 静默跳过。表上还有一道 `uk_event`（外部事件号，允许多 `NULL`）作为第二道闸。

④ **台账上不建外键**：`delivery_id` 只是普通列，注释写的是「业务主键·无外键：证据不随包裹级联删除」。这是有意的 —— 有外键就删不掉、有级联就证据没了，两种都不要。

⑤ **页面口径按「行锚点 + 单号」断言**，不断总行数：包裹分支的 `bizId` 过滤是 `v.biz_id = bizId OR v.order_id = bizId`（**一个输入框两种含义**：既收包裹 id 也收订单 id）。按订单 id 查时，若另有一个"包裹 id 恰好等于这个订单 id"的包裹，它的行也会出现 —— 那是接口设计，不是 bug。所以页面行数一律与**同口径的库查询**对撞。

## 凭什么证明好了

**① 库上的事实（本页下方「实测数字」四组只读 SQL，快照：2026-11-14 16:46）**

| 断言 | 实测 |
| --- | --- |
| 每一步都在台账里，每行都带单号快照 | **48** 行 / **17** 个包裹 / **17** 张订单；带 `delivery_sn` 的 **48** |
| 订单被删后仍读得出是哪一单 | `order_id = 26/30/31` 各 **3** 行，`order_exists=0`、`delivery_exists=0`，单号快照仍在（如 `DL20261114153244525103`） |
| 包裹行本身被物理删除后仍能按订单反查 | **24** 行 / **10** 个包裹 / **10** 张订单，全部靠 `order_id` 反查得到 |
| 重复事件只留一行 | **48** 行 = **48** 把去重键（`event_key` 这一版全空，去重靠 `idem_key`） |

**② 能演的：UI 三条用例（`e2e/tests/scenarios/台账与取证/台账七类/包裹状态台账.spec.js`）**

- **用例一（每一步一行）**：出生后库里**只有 1 行**（前态 `NULL`、后态 `0`、原因 `DELIVERY_CREATE`、`order_id` 指对这个订单、键 `{id}:0`）；点下发 → 2 行；回传拣货 → 3 行；回传出库 → 4 行。原因码序列一字不差是 `DELIVERY_CREATE、DELIVERY_DISPATCH、WMS_PICK、WMS_OUTBOUND`，流转序列 `空→0、0→1、1→2、2→3`，四把键序号是 `0、1、2、3` 且与包裹表的 `status_seq` 一致；四行四份单号快照全都等于同一个 `DL…`。最后回页面：按**订单 id** 查到这四行，业务单号列显示的是单号快照。
- **用例二（重投不多记）**：把同一个 `outbound` 事件从接口**重放两次**（两次都 `code=0`）→ 行数、原因码序列、状态链、`status_seq`、四把键**全都没变**。台账不记「没发生的事」。
- **用例三（删单之后）**：真删这张单 → 包裹行数变 `0`；但台账**一行不少、行 id 也没变**（不是删了又补的新行），每行单号快照仍是 `DL…`，`order_id` 每一行都仍指对这个订单、`order_id is null` 的行是 **0**；页面上按订单 id 仍查得到这四行，业务单号列显示的仍是单号而不是「—」。

## 附：口径与边界

- **「重复推送只留一行」现在靠的是 `idem_key`，不是事件号**。`uk_event` 在表上、允许任意多 `NULL`，但这一版**所有行的 `event_key` 都是空的**（实测 `event_keys=0`）—— 仓侧事件在业务幂等那一层就被挡掉了，根本没走到台账。哪天真把事件号落进来，它才变成第二道闸。所以本页的实测证据是「48 行 = 48 把键」，不要念成「靠事件号去重」。
- **`delivery_sn` 与 `order_id` 是"已登记冗余列"**，不是临时补丁：它们是"删单后仍可查"这句话的全部物理依据。任何一条写入路径把其中一列写成 `NULL` 或空串，这句话立刻作废 —— 所以写入器是**抛异常**而不是"尽力而为"。
- **`行数 = status_seq + 1` 只在开关打开、且每次流转必写一行的前提下成立**（`qiqi.ledger.enabled=false` 时一行不写，等式不成立）。它是判读口径，不是数据库约束。
- **包裹台账只追加，不改行**：写错了补一条新事实，不 `update` 历史。表上没有 `updated_at`，物理上也没有"改过"的位置。
- **`bizId` 一个输入框两种含义**：包裹分支同时匹配 `v.biz_id`（包裹 id）与 `v.order_id`（订单 id）。规范用法是**订单 id**（用户视角就是"看这张单的几个件"），包裹 id 是兼容口径。两种都要能用，所以两种都在用例里钉过。
- **本页数字的出处**：本页下方「实测数字」四段只读 SQL（快照 2026-11-14 16:46）。数字随当次数据变，「对平 / 0 重复 / 0 例外」这几条结论不变。
