## 包裹状态台账（delivery_status_ledger）

一条包裹自己的流水：拆单出生、下发、拣货、出库、签收，每走一步留一行 —— 前态与后态、原因码（`DELIVERY_CREATE` / `DELIVERY_DISPATCH` / `WMS_PICK` / `WMS_OUTBOUND`）、操作人、触发单据、幂等键 `{包裹ID}:{流转序号}`、`created_at`。序号在同一条 `UPDATE` 里与 `status` 一起自增，仓侧重投算出同一个键，撞 `uk_idem` 静默跳过，`status_seq` 不会被推高。

两列冗余是这张表的全部要点，因为订单被物理删除时包裹行会跟着真删（`OrderPurgeService` 是真 `DELETE`）：`delivery_sn` 单号快照（`NOT NULL`，写入器对空串直接抛）与 `order_id` 冗余列（缺了就回查 `delivery_order.order_id`，回查不到也抛）。只存 `delivery_id` 的话，「这张单发过几个包裹、每个走到哪一步」在删单那一刻永久不可回答；单号只长在 `delivery_order` 上，行一删就只剩一个没人认得的数字。所以这两列是「删单后仍可查」的物理依据，写 `NULL` 蒙过去等于把缺口原样保留。

台账上不建外键：有外键删不掉、有级联证据没了，`delivery_id` 只是普通列。读侧走只读视图 `v_biz_status_timeline` 的 `DELIVERY` 分支，页面一个输入框两种含义（`biz_id = ? OR order_id = ?`），既收包裹 id 也收订单 id。

**效果**　四组只读 SQL（快照 2026-11-14 16:46，`qiqi_mall_e2e_a`）：48 行 / 17 个包裹 / 17 张订单，带 `delivery_sn` 的 48 行；订单 26 / 30 / 31 各 3 行，而订单行与包裹行都已不存在，单号快照仍在；包裹本身被物理删除后仍能按 `order_id` 反查出来的 24 行 / 10 个包裹 / 10 张订单；48 行 = 48 把去重键（`event_key` 这一版全空）。UI 侧 `包裹状态台账.spec.js`：3 条用例、56 处断言：出生只有 1 行（前态 `NULL`、后态 0、原因 `DELIVERY_CREATE`），下发 / 拣货 / 出库各多 1 行，原因码序列与流转序列逐字对上，四把键序号 `0、1、2、3` 与包裹表 `status_seq` 一致，四行四份单号快照等于同一个 `DL…`；把同一个出库事件从接口重放两次（两次都 `code=0`）→ 行数、原因码、状态链、序号、四把键全不变；真删这张单 → 包裹行数变 0，台账一行不少、行 id 不变、`order_id` 无一行为 `NULL`，页面按订单 id 仍查得到四行且业务单号列仍显示单号。

**边界**　「重复推送只留一行」现在靠的是 `idem_key`，不是事件号：`uk_event` 在表上、允许任意多 `NULL`，这一版所有行的 `event_key` 都为空，仓侧事件在业务幂等那层就被挡掉了；哪天真把事件号落进来，它才是第二道。`行数 = status_seq + 1` 只在台账开关打开、且每次流转必写一行的前提下成立，`qiqi.ledger.enabled=false` 时一行不写、一句 SQL 都不发。台账只追加，写错补一条新事实。`bizId` 的两种含义是接口设计：按订单 id 查时，若另有一个包裹 id 恰好等于这个订单 id，它的行也会出现，所以页面行数一律与同口径的库查询对撞，不断总行数。数字出处：16:46 那组来自本页 `实测数字.sql`，数字随当次数据变，口径不变。
