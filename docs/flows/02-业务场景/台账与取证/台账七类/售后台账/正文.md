## 售后台账（return_status_ledger）

一张退货申请自己的流水：买家提交留出生行（`NULL` → 0，`RETURN_CREATE`），审核通过留 `0 → 1`（`RETURN_APPROVE`），审核拒绝留 `0 → 2`（`RETURN_REJECT`，理由进 `reason_detail`）。幂等键 `{申请ID}:{流转序号}`，序号在同一条 `UPDATE` 里与 `status` 一起自增：两个人同时点「通过」只有一个把 `0 → 1` 改成功，另一个影响 0 行、不进台账，所以「通过」的行数天然等于申请数。

每行都带 `order_id` 冗余列。`return_apply.order_id` 上挂着 `ON DELETE CASCADE`，订单被物理删除时申请行必然消失；台账只存 `return_apply_id` 的话，「这张单退过几次、谁审的」在删单那一刻永久不可回答，而这正是退款纠纷与财务对账最先要回答的问题。写入器对 `return_apply_id` 与 `order_id` 都是每行必填，这两列是删单后按订单反查的唯一通道。

订单侧的状态变更另记一本账，且落点不是常量：审核拒绝后订单从退款中回到由未取消包裹聚合推导出的值（全出库 → 已发货，全签收 → 已完成），记在订单状态台账里的原因码是 `DELIVERY_AGGREGATE`，不是售后台账的 `RETURN_REJECT`。自由文本按列宽裁：`reason_detail` 是 `VARCHAR(255)` 而申请说明允许 500，写入器裁到 255，不裁就是审核接口 500。

**效果**　四组只读 SQL（快照 2026-11-14 16:46，`qiqi_mall_e2e_a`）：16 行 / 9 张申请 / 9 张订单，`order_id` 非空 16 行；拒绝三例：申请 3 / 6 / 8 → 订单 32 / 38 / 40，申请侧 `RETURN_REJECT → 2`、同一单上订单侧 `DELIVERY_AGGREGATE` 是 `8 → 2`；通过 4 行 / 4 张申请、重复通过 0；申请与订单都已物理删除后仍读得出的 8 行（`apply_exists` 与 `order_exists` 都 0）。UI 侧 `售后台账.spec.js`：3 条用例、87 处断言：买家提交 → 只多 1 行（`RETURN_CREATE`、`reason_detail` 为「买家自助申请」、`ref_type` 与 `event_key` 为空），同时钉住另一侧：订单台账另有一行 `2 → 5` / `RETURN_APPLY` / `ref_id` 指这张申请，且售后台账里不许出现 `RETURN_APPLY`；审核通过 → 再留 1 行 `0 → 1`，同一时刻支付流水出现一条退款行；拒绝 → 理由进 `reason_detail`，订单状态等于包裹聚合推导值，断言它不是 `已付款(1)` 也不是 `退款中(5)`，订单台账最后一条 `DELIVERY_AGGREGATE` 是 `5 → 2`；真删这张单 → 申请行没了，售后台账按订单 id 仍查得到那两行。

**边界**　三个数谈的不是同一件事：申请数 9、台账行数 16、通过 4 笔 —— 一张申请正常产生 1~2 行。行数不等于余额，也不等于「退了几笔钱」，退钱只去 `payment_record` 的退款流水里数。台账只追加，写错补一条新事实。`RETURN_CREATE` 与 `RETURN_APPLY` 是两张账的原因码，不能互相替代。`bizId` 两种含义（申请 id 与订单 id），按订单 id 查时若另有申请的 id 恰好等于该订单 id 也会被命中，所以页面行数一律与同口径的库查询对撞。数字出处：16:46 那组来自本页 `实测数字.sql`，数字随当次数据变。
