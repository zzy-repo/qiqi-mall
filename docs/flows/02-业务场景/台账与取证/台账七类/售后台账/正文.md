**售后台账：一张退货申请自己的流水，每行都额外记着订单号** —— 买家提交留出生行（空 → 待处理），管理员通过留一行到已通过，拒绝留一行到已拒绝。关键只在那个**冗余的订单号**：`return_apply` 的 `order_id` 上是 `ON DELETE CASCADE`，订单一删，申请行跟着没了 —— 没有这一列，"这张单退过几次、谁审的"就彻底断链。

## 场景

退货是钱往回走的那一段，也是最容易吵起来的一段：买家说申请提交了没人处理，客服说审核通过了但没收到钱，财务想知道这张单到底退了几笔、是谁批的。

这页就是售后那条线：台账页（`admin-web/src/views/ledger/index.vue`）类型选「售后状态」，业务ID 填**订单 id**（规范口径），一屏就是这张单下所有退货申请的每一步。接口是 `GET /admin/ledgers?type=RETURN_STATUS&bizId=<订单id>`，数据源是 `v_biz_status_timeline` 的 `RETURN` 分支，底下是 `return_status_ledger`。

一张申请走完全程也就几行，原因码只有三个：

| 事件 | 前态 → 后态 | 原因码 | 操作人 |
| --- | --- | --- | --- |
| 买家提交申请 | 空 → 待处理(0) | `RETURN_CREATE` | `MEMBER`（买家登录名） |
| 管理员审核通过 | 待处理(0) → 已通过(1) | `RETURN_APPROVE` | `ADMIN` |
| 管理员审核拒绝 | 待处理(0) → 已拒绝(2) | `RETURN_REJECT` | `ADMIN`（拒绝理由进 `reason_detail`） |

## 撑不住的时候

售后这条线的坏环境是**"证据跟着业务一起被删"**，而且比包裹那边更隐蔽：

- **级联删除就在建表语句里**。`return_apply` 的 `CONSTRAINT fk_return_order ... ON DELETE CASCADE` 是明写的：订单被物理删除时，退货申请行必然消失。如果售后台账只存 `return_apply_id`，那么删单那一刻，"这张单有过一次退货申请、被谁拒了"就永久不可回答 —— 而这恰恰是删单之后最需要回答的问题（退款纠纷、财务对账都从这儿起）。
- **两张账会被人当成一张看，于是都写歪**。"买家提交退货"这件事在两张台账里各留一行，但**原因码不同**：售后台账是 `RETURN_CREATE`（空 → 待处理），订单台账是 `RETURN_APPLY`（已发货 2 → 退款中 5，`ref_type=RETURN_APPLY`、`ref_id` 是这张申请）。想省事只记一处，另一处就永远缺一段；想把两处合并，就分不清"申请的状态"和"订单的状态"。
- **两个人同时点「通过」**。审核页是列表 + 弹窗，两个运营看到的是同一行待处理。没有状态迁移的原子性，就会出现两条"通过"、甚至两次退款。
- **审核拒绝之后订单该回到哪**。不是常量。有未取消包裹时，订单状态要由包裹聚合推出来（全部 ≥ 已出库 → 已发货 2；全部 ≥ 已签收 → 已完成 3），这条推导如果被手写成一个固定值，拒绝之后订单就会停在错的格子里。

## 改了什么

① **两列冗余 + 一个拒写规则**：`return_status_ledger.return_apply_id` 是普通列（无外键，注释写的是「业务主键·无外键：证据不随申请级联删除」）；另加 `order_id` 冗余列，写入器 `StatusLedgerWriter#returnBirth` / `#returnChanged` **每行都填**。没有"能填就填"的余地 —— 这一列存在就是为了删单后按订单反查。

② **唯一写入口 + 同一事务**：出生与流转都走 `StatusLedgerWriter`，调用点在 `ReturnStatusService` 那句 `UPDATE`（`status = ?, status_seq = status_seq + 1`）成功之后，同一个 `@Transactional`：要么状态和证据都落，要么都不落。

③ **幂等键 = `{申请ID}:{流转序号}`**：序号在同一条 `UPDATE` 里和 `status` 一起自增。所以两个人同时点「通过」，只有一个能把 `0 → 1` 改成功，另一个影响 0 行、不进台账 —— 台账里就只有一行"通过"。

④ **订单侧改状态交给聚合，不写死**：审核拒绝后订单从"退款中(5)"回到由包裹聚合推导出的值，订单台账那一行的原因码是 `DELIVERY_AGGREGATE`（申请侧是 `RETURN_REJECT`）。两个原因码各归各账，谁也不冒充谁。

⑤ **自由文本按列宽裁**：拒绝理由走 `reason_detail`（`VARCHAR(255)`），而 `return_apply.description` 允许 `VARCHAR(500)` —— `LedgerText.clip` 在写入器里裁到 255，不裁就是"用户写 300 字退货说明 → 审核接口 500"。原因码一律不裁，超宽直接抛。

⑥ **页面口径双入参**：售后分支的 `bizId` 同时匹配 `v.biz_id`（申请 id）与 `v.order_id`（订单 id）。规范用法是**订单 id**，申请 id 作为兼容口径保留 —— 两种都在用例里各查一次，任一条退化立刻红。

## 附：口径与边界

- **三个数谈的不是同一件事，别互相对平**：`申请数（9）`、`台账行数（16）`、`通过笔数（4）` —— 一张申请正常会产生 1~2 行，通过只占其中一部分。**行数相等不等于余额，也不等于"通过了几笔钱"**；"退了几笔钱"只去 `payment_record` 的退款流水里数（那是另一本账，见 `支付流水`）。把这三者拿去互相校验，只会报一堆假错，或者顺手改掉真数据。
- **台账只追加**：写错补一条新事实，不 `update` 历史行。表上只有 `created_at`，没有 `updated_at`。
- **`order_id` 冗余列是硬要求，不是优化**：`return_apply.order_id` 上是 `ON DELETE CASCADE`，订单一删申请就没了。这一列写空或写错，删单后按订单反查这条路直接断 —— 所以写入器不允许它缺。
- **`RETURN_CREATE` 与 `RETURN_APPLY` 是两张账的原因码，不要互相替代**：前者记在 `return_status_ledger`（申请出生），后者记在 `order_status_ledger`（订单进退款中）。实测里两条都在、且都指得动对方，这是本页最容易讲错的一点。
- **审核拒绝之后订单落到哪，不是常量**：由未取消包裹的聚合状态决定（全部 ≥ 已出库 → 已发货；全部 ≥ 已签收 → 已完成；都没出库 → 待发货）。所以"拒绝后订单回到已付款"这种断言在这套口径下永远是错的。
- **`bizId` 一个输入框两种含义**：按订单 id 查时，若**另有**一张申请的 `return_apply_id` 恰好等于这个订单 id，它的行也会被命中 —— 这是接口设计（一个输入框同时收订单 id 与售后 id）。所以页面行数断言一律与同口径的库查询对撞，不写死一个数。
- **本页数字的出处**：本页下方「实测数字」四段只读 SQL（快照 2026-11-14 16:46）。数字随当次数据变，「对平 / 0 重复 / 0 例外」这几条结论不变。
