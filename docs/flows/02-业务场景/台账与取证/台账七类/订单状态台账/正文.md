## 订单状态台账（order_status_ledger）

订单状态每变一次留一行只追加的事实，一行只回答四件事：从哪来、到哪去、为什么、谁干的。列是逐字契约：前态与后态、`reason` 原因码（必填）、`operator_type`（`ADMIN` / `MEMBER` / `APIKEY` / `SYSTEM`，`CHECK` 闭集）与 `operator_name` 名字快照、`ref_type` / `ref_id` 触发单据、`idem_key`、`created_at`。表上没有 `updated_at`，也就没有「改一行」这个动作。

去重键是 `{订单ID}:{流转序号}`，序号在同一条 `UPDATE` 里自增：「更新成功」与「seq 变成 N」是同一件事，没有中间态，重放算出的键必然相同，撞 `uk_idem` 即静默跳过，不多记一行。键里不用「业务ID + 前态 + 后态」三列：状态可以合法回到同一个值（7→8 审核通过、包裹全取消退回 7、再审核 8），三列键会把第二次合法流转当重复丢掉。

写入口只有 `StatusLedgerWriter`，调用点落在三个状态服务那句 `UPDATE` 成功后（影响行数 > 0），同一 `@Transactional` 包住：要么两者一起落，要么一起不落。拿不到可信序号就抛 `IllegalStateException`：宁可失败，也不写一条可能撞键被静默跳过的台账。

`order_id` 没有外键：订单会被物理删除，证据不跟业务行走，删单后仍能按订单号反查。三张状态台账列结构一致，只读视图 `v_biz_status_timeline` 用 `UNION ALL`（不去重）拼起来并翻成中文。

**效果**　六组只读 SQL（快照 2026-11-14 16:46，`qiqi_mall_e2e_a`，全量套件刚跑完）：订单 37 / 38 / 39 都是 `status_seq=5`、台账各 6 行、键 `37:0 … 37:5` 全覆盖；有台账的 11 张单里例外 0 张；全表 103 行 = 103 把去重键；`ADMIN` 53 行 / 1 人、`MEMBER` 50 行 / 20 人；删单后仍读得出 56 行。今晚复跑同一组查询，结论一致（例外 0、行数 = 去重键数）。`订单状态台账.spec.js`：3 条用例、47 处断言：建单 → 审核通过 → 下发回传出库恰好 3 行，原因码 `ORDER_CREATE` / `AUDIT_PASS` / `DELIVERY_AGGREGATE`，流转 `空→7` / `7→8` / `8→2`，三把键互不相同、序号严格递增；审核不通过只多 1 行（`7→4`、`AUDIT_REJECT`，页面读到「已关闭」）；视图 ORDER 分支行数逐行等于台账，包裹分支 `order_id` 无空行。

**边界**　`行数 = status_seq + 1` 只在一组前提下成立：出生行占 seq 0、之后每次流转 seq 严格 +1 且必写一行、台账开关开着（`qiqi.ledger.enabled`）。开关一关，写入器全部方法直接 `return`，一行不写、一句 SQL 都不发 —— 它是口径，不是物理约束。`event_key` 这版全空，去重只有 `idem_key`；`uk_event` 留给外部事件号。写错的处理是补一条冲正事实，不是 `update` 历史行。三张状态台账不参与删单清理（`OrderPurgeService` 里引用 0 处）；`stock_ledger` 与 `payment_record` 是显式清理的，留痕也不同：支付写 `PAYMENT_PURGE` 审计行，库存只落应用日志。数字出处：16:46 那组来自本页 `实测数字.sql`，数字随当次数据变，口径不变。
