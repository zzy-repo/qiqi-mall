**订单状态台账：状态不是被改出来的数字，而是一串只追加的事实** —— 每变一次状态留一行，一行只回答四件事：从哪来、到哪去、为什么、谁干的。幂等键 `{订单ID}:{流转序号}` 里的序号，是在改状态那条 `UPDATE` 里**一起自增**的，所以同一瞬的重复推送（重试 / 重放 / 并发）只会撞同一把唯一键，后到的被静默跳过 —— 不会多记一行。

## 场景

一张订单出问题的时候，第一个问题永远是「这单怎么变成现在这样的」。问的人可能是客服（买家说没收到货，系统里却是已发货）、可能是运营（这单为什么被关掉了）、也可能是财务（这笔退款的单子当初是自动过审还是人审的）。

这页就是回答它的地方：后台「台账查询」页（`admin-web/src/views/ledger/index.vue`），类型选「订单状态」、业务ID 填订单 id，一屏就是这张单的完整流转史。同一份数据有两个入口 —— 页面背后的 `GET /admin/ledgers?type=ORDER_STATUS&bizId=<订单id>`，和给「不写三段 SQL 也能拼出全链路」准备的只读视图 `v_biz_status_timeline` 的 `ORDER` 分支。

一行长这样（字段是逐字契约，前端直接吃）：

| 列 | 含义 | 例 |
| --- | --- | --- |
| 前态 → 后态 | 状态码，页面上翻成中文 | 待发货(8) → 已发货(2) |
| reason | 原因码（必填，不许空） | `AUDIT_PASS` / `DELIVERY_AGGREGATE` |
| operator_type / name | 谁干的 + 名字快照 | `ADMIN` / `admin` |
| ref_type / ref_id | 触发单据（包裹、售后申请、审核批次） | `DELIVERY` #37 |
| idem_key | 去重键 `{订单ID}:{流转序号}` | `37:2` |
| created_at | 记账时间（毫秒精度） | — |

## 撑不住的时候

没有这张表时，坏环境有三种常见形状，每一种都不是「慢一点」，而是**事后无法回答**：

- **「状态就是一个数字」**。`order.status` 只有当前值，被每个调用点随手 `update` 覆盖。要回答「谁把它从待发货推成已发货的」，只能去翻应用日志 —— 而日志会被轮转、会被清理、容器一重建就没了。更糟的是并发：两个请求各自读到旧值、各自写新值，最后一个赢，中间的流转**从来没有存在过**。
- **「台账和状态分两个事务」**。这会出现两种都不能接受的结果：状态改了、台账没写（中间崩溃/回滚）→ 证据缺失；台账写了、状态没改 → **台账在说谎，比没有台账更坏**。所以 `StatusLedgerWriter` 的调用点全部落在 `OrderStatusService` / `DeliveryStatusService` / `ReturnStatusService` 那句 `UPDATE` 成功之后（`rows > 0`），由同一个 `@Transactional` 包住：要么两个都落，要么两个都不落。
- **「去重键用 (业务ID, 前态, 后态)」**。看起来很自然，其实会**误杀合法流转**：状态可以合法地回到同一个值（7→8 审核通过 → 包裹全取消退回 7 → 再审核 8）。用三列当唯一键，第二次合法的 7→8 会被当成重复直接丢掉。所以键里用的是**单调递增的流转序号**，它永远不会误杀。

还有一条容易被忽略的：订单**会被物理删除**（`OrderPurgeService`）。删单之后，业务表里什么都没了 —— 如果证据跟业务表做外键级联，它会跟着一起消失。本页这张表上**一个外键都没有**，`order_id` 只是一个普通列。

## 改了什么

① **唯一写入口 + 与业务同事务**。所有订单状态流转只经过 `shared/ledger/StatusLedgerWriter#orderBirth` / `#orderChanged`，没有第二个写点。台账行的 `reason` 必填（没有原因的台账回答不了「为什么」）、`operator_type` 有 `CHECK` 闭集（`ADMIN/MEMBER/APIKEY/SYSTEM`）、操作人名字是快照而不是回头去 join 管理员表。

② **序号在同一条 UPDATE 里自增**。三个状态服务那句 `update ... set status = ?, status_seq = status_seq + 1` 是原子的：**「更新成功」与「seq 变成 N」是同一件事**，不存在中间态。于是重放（同一笔业务被提交两次）算出同一个 seq → 同一个键 → 撞 `uk_idem` → 静默跳过。实体上的 `statusSeq` 是只读字段（`insertStrategy=NEVER, updateStrategy=NEVER`），写者只有那条 UPDATE。

③ **拿不到可信序号就抛异常，而不是写一条不可信的台账**。`nextSeq()` 在实体缺值时回查一次，回查也没有就 `IllegalStateException`：没有可信 seq 就没有可信去重键，宁可直接让业务失败 —— 也不写一条「可能撞键被静默跳过」的台账。

④ **只追加，没有 `updated_at`**。表上只有 `created_at datetime(3)`。这不是漏列：没有 `updated_at` 就没有「改一行」这个动作的可能；写错的处理方式是再记一行，而不是回头改历史。

⑤ **三张台账同构 + 一张只读视图**。订单 / 包裹 / 售后三张状态台账列结构一致，`v_biz_status_timeline` 用 `UNION ALL`（**不去重**）把三支拼起来，并把状态码翻成中文。所以「这张单 + 它的包裹 + 它的售后」用一次查询就能按时间排开，不用三段 SQL、也不会因为 `DISTINCT` 偷偷少行。

⑥ **页面如实显示，不做推断**。状态码翻中文（`待发货` / `已发货`），操作人列渲染「名字快照 + 类型文案」（`admin` + 管理员）—— 两样都看得见，而不是把机器码直接甩给人。

## 附：口径与边界

- **`行数 = status_seq + 1` 只在一组前提下成立**：出生行占 seq 0、之后每次流转 seq 严格 +1 且必写一行、且 `qiqi.ledger.enabled`（或 `status-enabled`）是开着的。开关一关，`StatusLedgerWriter` 全部方法直接 `return` —— 一行不写、一句 SQL 都不发，这条等式立刻不成立。它是「口径」不是「物理约束」，别拿它当唯一索引。
- **`event_key` 这一版全空**，所以现在的去重**只有 `idem_key` 一道闸**。`uk_event` 唯一索引在表上、允许任意多 `NULL`，它的位置是留给「外部事件号」的：真有仓侧/渠道事件号落进来的那天，它就变成第二道闸（包裹台账那边就是靠事件号挡重投的）。在那之前，说「重复推送不会多记」的证据是 103 行 = 103 键，不是 `uk_event`。
- **台账只追加，没有「修」这个动作**。`reason` 写错了、`operator` 记错了，正路是补一条冲正事实，不是 `update` 历史行 —— 表上没有 `updated_at`，物理上也没有地方存「这一行被改过」。
- **删单不删这三张状态台账**：`OrderPurgeService` 里对 `order_status_ledger` / `delivery_status_ledger` / `return_status_ledger` 的引用是 **0 处** —— 它删的是业务行（物流、退货申请、发货单明细、订单明细、订单本体）。别和另外两张表混起来：`stock_ledger` 与 `payment_record` 是**显式**清理的（各有独立清账路径：库存台账要先按净额回补再删、支付流水按 `order_sn` 删），因为它们分别有"扣了不还货""钱的事说不清"的额外风险 —— 但这两处删行时**只写应用日志（`log.warn`），不写台账行**；删单那一刻留在台账里的，只有订单级那条 `ORDER_DELETE` 审计。
- **它不回答「为什么没变」**。状态没动的那一轮（不命中、被拦、跳过）在**订单状态台账里没有行** —— 那是审核决策表的活。两本账分工见 `状态与证据对齐` 那一页。
- **删单之后按订单反查**：订单分支靠 `order_id` 列（普通列，无外键）；包裹/售后分支靠它们各自的 `order_id` 冗余列。这三列任意一列写成 `NULL`，「删单后仍可查」这句话就作废 —— 所以写入器对包裹那条冗余列是**拒绝写 NULL**（回查不到直接抛），不是「能写就写」。
- **`id` 只在同一张台账内唯一**：七类合并成一个列表后 id 会撞（订单台账第 12 行和包裹台账第 12 行是两条完全不同的记录），页面只把它当行 key，别当全局主键用。
- **本页数字的出处**：全部来自本页下方「实测数字」的六段只读 SQL，快照时点是 2026-11-14 16:46（e2e 全量套件跑完 `qiqi_mall_e2e_a` 那一刻）。具体数字随当次数据变，**「行数 = seq+1 / 0 重复 / 0 例外」这三条结论不变**。
