# 面试准备（逐步积累）

> 用途：面试口头表达素材。每个方向一段口语化文本，方便背诵。面试官问"介绍一下你的项目/架构"时按此作答。

## 方向一：项目演进叙事（约 1 分钟）

我的项目不是一个一次成型的商城，是一步步演进出来的，我觉得这个演进过程比项目本身更能说明问题。

一开始它就是一个最基础的单体商城，有商品、订单、退货这些基本模块，前后端分离，一个后端一个管理后台。

然后我做了第一层拆分，就是 C 端和 B 端的分离。买家商城和管理后台拆成两个独立的前端应用，后端虽然还是一个工程，但接口按 portal 和 admin 两条路径分流，各自有独立的过滤器链，买家和管理员是两套完全隔离的账号体系，不共用登录框、不共用 token。

第二层是多实例。我做了压测之后发现，内存里存的东西，像验证码、幂等令牌，一旦起第二个实例就全失效了，因为它们是进程私有的。所以我把这些短命数据抽成了一个 KvStore 接口，内存实现和 Redis 实现各一套，用配置开关切换。接口不变，只换实现，这个抽象是提前埋好的。然后用 nginx 做了 upstream 负载均衡，双实例部署，还做了滚动发布的验证，停掉一个实例另一个能独立撑住，服务不中断。

第三层是订单中台，也就是 OMS。我把代码按边界拆成了 portal、oms、catalog、member 这几个包，商城只负责产生交易意图，审核、拆单、下发仓库这些履约的事归 OMS 管，两边只通过一个入口交互。然后在此基础上实现了拆单和发货单：订单审核通过后按分仓库存自动拆成多个发货单，每个发货单有自己独立的状态机，仓库回传出库之后，父订单的状态是所有子单聚合出来的。

所以整个演进路径就是：单体商城，到 C 端 B 端分离，到多实例加 Redis，到订单中台。每一步都是因为遇到了真实问题才做的，不是为了用技术而用技术。

背诵记忆点：四个节点——单体 → 端分离 → 多实例 → 订单中台。每个节点一句话：分离是为了隔离买家和管理员；多实例是因为内存态会失效；中台是为了商城和履约解耦。
