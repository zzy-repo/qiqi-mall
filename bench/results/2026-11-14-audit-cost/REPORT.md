# 审计写入成本测量（Redis Stream 异步化 · 第一步）

> 时间：2026-11-14 07:48–08:31（机时全部独占，`bench-lock.sh` 持有 → 已释放）
> 对象：后台操作审计 `admin_audit_log`（唯一写入口 `shared/ledger/AdminAuditWriter`）
> 判据（**跑之前就写死**，见 §1）
> 一句话结论：**不做**。审计在 450 rps 的下单路径上 **0 条/单、0 ms/单**（它根本不在这条路上）；
> 即使在后台动作路径上它是 1 条/操作、服务器端 0.225 ms，折成事务占比 3.6%，
> 而这条路径是"人点按钮"的速率 —— MQ 在这里能省的时间上限就是"1 条 INSERT"，代价却是在同事务里多写一条 outbox。

---

## 1. 判据（先写下来的那个，不事后改）

| 若审计写入占每单事务时长 | 判定 |
| --- | --- |
| **< 2%**（吞吐收益必然落在 ±2.8% 噪声带内） | **不做**。该做的不是 MQ，是减少事务数 / 削锁等待 |
| **≥ 5%** | 值得做，进入第二步（outbox + Stream） |

实测结果两边都落在"不做"：下单路径 **0%**（结构上不在路径上），后台路径 **3.56%**（在 2%~5% 的夹缝里，
且那是个"人点按钮"的速率，没有吞吐可拿）。

---

## 2. 方法：这是个**干净**的开关对照（不是"没法单独关审计"）

任务书里担心"没有开关"，实测**有，而且是分项开关**：

```
qiqi.ledger.audit-enabled  →  AdminAuditWriter.record() 第一行 if (!props.auditOn()) return;
```

所以两臂只差一个环境变量，**业务代码一行没动**：

```
bench/ledger-audit.override.yml   # QIQI_LEDGER_AUDIT_ENABLED=true|false（compose override，只透传一个环境变量）
bench/tools/auditcost.sh          # deploy on|off / run / ship / restore
bench/tools/auditcost.py          # 从 P_S DIGEST + 事务聚合 + 样本 里算「条/单」「耗时占比」「延迟分位」
```

不重建镜像、不切镜像：`qiqi-mall-server:test` 的 **image digest 全程未变**
（`sha256:935feb00…39d9`），jar 用 `bench/jar-mount.override.yml` 只读挂载（HEAD 打的那份，
`md5=2fce23c8a4b08991ead5ab99df134e28`，两臂**同一份 jar、同一 md5**）。

**生效证据只看启动日志那一行**（打的是生效值，已经与总闸与过），不看配置文件：

```
audit=on   → [ledger] 台账写入已启用：ledger.enabled=true status=true audit=true  wms=true payment-trace=true
audit=off  → [ledger] 台账写入已启用：ledger.enabled=true status=true audit=false wms=true payment-trace=true
```

`status / wms / payment-trace` 三项在两臂里**始终是 true** —— 三张状态台账、
`wms_exchange_ledger`、`payment_record` 的行为两臂完全一致，唯一变量就是 admin 审计。

## 3. ① 审计写入到底在哪些路径上？（这决定了"能省多少"）

代码事实（`grep auditWriter.record` 的 24 个调用点）——**下单路径（`POST /portal/orders`）一个都没有**：

| 路径 | 是否写审计 | 条/次 |
| --- | --- | --- |
| **买家下单** `POST /portal/orders`（= 450 rps 压测打的那条） | **不写** | **0** |
| 后台建单 `POST /admin/orders` | 不写 | 0 |
| 发货 `POST /admin/orders/{id}/ship` | 写（`ORDER_SHIP`） | 1 |
| 审核通过 `audit-pass` → 拆单 `ORDER_SPLIT` | 写 | 1 |
| 删单 `ORDER_DELETE`、退货审核、发货单编辑、仓库、SKU 删除、API Key、审核策略/标签 | 写 | 1 |
| 定时审核调度（每 30 分钟一轮） | 写（`AUDIT_RUN` 等） | 每轮 1 条 |

**实测两条独立证据，都指向"下单 0 条"：**

1. **表行数前后差**：每轮 27k 单跑完，`admin_audit_log` 行数 `delta = 0`（12 轮全部为 0，见 `runs.csv` 的
   `audit_rows_delta` 列）。整段实验期间唯一新增的审计行是 08:12:22 定时调度写的那 **1 条** `AUDIT_RUN`。
2. **performance_schema 按 DIGEST 统计**：窗口内 `INSERT INTO admin_audit_log` 的 `COUNT_STAR` 增量 = **0**。
   同一窗口的业务语句是 **12.0–12.3 条/单**（`sql_per_order` 列），一条都没少。

→ **π 口径回答"每单 1 条还是每个敏感动作 1 条"**：审计是**"每个敏感动作 1 条"**（且一次请求可写多条，
`idem_key = requestId:序号`）。下单不是敏感动作，所以它 0 条。

### 4.1 结论 1：两臂之间**没有任何可归因于审计的差异**（因为路径上没有审计）

`SQL/单` 两臂完全重叠（11.24–12.27，方差来自窗口边缘），`审计语句 = 0`、`审计行 = 0`，两臂都是。
**"审计写入占每单事务时长 = 0 / 17.6 ms = 0.0%"**（300 rps 稳态：SQL 服务时间 6.49 ms/单、
事务墙钟 17.62 ms/单、2.73 个事务事件/单）。

### 4.2 结论 2：**这台机器给不出干净的 450 档对照臂** —— 噪声带远大于任何可能的审计效应

450 档上 p50 在 **87 ms ↔ 6.7 s** 之间乱跳，**同一臂内**跳动就有 60 倍，且方向与开关**无关**
（off 臂既有 311 ok/s 也有 449.9 ok/s；on 臂也有 449.8 和 381.8）。原因查清了，不是被测物：

1. **这台是 4 核共享机，压测期间宿主 CPU 一直打满**：`env.csv` 里 `us+sy ≈ 99%`、`id ≈ 0`，
   `loadavg` 峰值 30（压测前基线 2.8）。
2. **450 档就压在这台机器的膝点上**（300 档 12 ms，450 档 0.09–6.7 s —— 队列放大），
   任何扰动都被放大成秒级。
3. **"部署后首跑" 系统性偏慢**：同一臂、同一开关，`deploy → 首跑` 永远慢（p50 2.4–6.7 s），
   `同容器第二跑` 永远快（p50 12–14 ms）。冷 JVM 的 JIT 编译线程在已饱和的 4 核上抢不到 CPU，
   请求线程被饿死 —— 这是**实验装置的偏差，不是审计的代价**（两臂对称地中招）。
   → 300 档上"首跑 vs 次跑"在**两臂里都成立**：on 臂 5194→13.9 ms，off 臂 3133→12.0 ms。

**所以对 450 档的正式表述是：开关是干净的（启动日志可验），但机器没有安静窗，450 档的两臂差异
（±45%，方向还互相打脸）全部落在环境噪声里，不能作为"审计影响吞吐"的证据 —— 也不需要它来当证据，
因为结构性证据（0 条/单）已经把效应钉死在上界 = 0。**

## 5. ③ 审计真正在的路径：后台发货（1 条/操作，占 3.6%）

用真实 HTTP 把"后台发货"这一条**带审计**的链路量了 300 次（串行、同一份 jar、两臂只差开关）：

| 指标 | audit=on | audit=off |
| --- | --- | --- |
| 审计表新增行 | **300**（1.0 行/操作） | **0** |
| SQL 语句/操作（P_S DIGEST 前后差） | **7.01** | **6.01** |
| 其中审计 INSERT 次数 | **300**（1.0 次/操作） | 0 |
| 审计 INSERT 服务器端耗时 | **0.225 ms/次** | — |
| 窗口内审计占全部 SQL 时间 | **10.2%** | — |
| 单次发货墙钟（p50 / 平均） | 5.91 / 6.32 ms | 6.76 / 7.42 ms |
| **审计占单次操作墙钟** | **3.56%** | — |

两条**与漂移无关**的硬证据：`7.01 − 6.01 = 1.00 条语句/操作`（正好是那条 INSERT），
以及审计行数 300 vs 0。
墙钟差（on 5.91 vs off 6.76 ms）**方向是反的** —— 又是环境漂移，再次说明这台机器上
差异 < 1 ms 的延迟对照没有判别力（这也正是"3.56% 落进噪声带"的实证）。

## 6. 判定：**不做**（理由三条，互相独立）

1. **下单路径上审计写入 = 0**（0 条/单、0 ms/单，12 轮实测 + DIGEST + 代码调用点三重证据）。
   在没有审计的路径上异步化审计，吞吐收益**恒等于 0**。
2. **即使假设**把"1 条审计/单"硬塞进下单事务：0.225 ms / 17.62 ms = **1.28%**（对 SQL 时间 3.5%），
   **仍 < 2% 判据** → 收益依然在 ±2.8% 噪声带内。
3. **后台路径上（真写审计的地方）1 条/操作、3.56%**，而那是人在点按钮的速率
   （实测最高也就 300 次/分钟量级，且一条审计 0.225 ms）——**没有吞吐可拿**。
   更关键：教科书做法（outbox）要在**同一个业务事务里多写一条 INSERT**（outbox 行），
   省下的是"1 条 INSERT 写进审计表"，付出的又是"1 条 INSERT 写进 outbox 表" ——
   **事务内的写次数没减，Redis 的活还得 relay/consumer 再干一遍**。净收益 ≤ 0，
   代价是多一套 relay + consumer + DLQ + 幂等 reintroduce 的故障面。

> 一句话：**该做的不是 MQ，是减少事务数 / 削锁等待**（接上一轮结论）。

---

## 7. 那该做什么（把"不做"变成"做什么"）

同一批数据里能直接读出下一个杠杆：

| 观察 | 数字（300 rps 稳态，单实例两副本） | 含义 |
| --- | --- | --- |
| SQL 服务时间/单 | **6.49 ms** | 服务器在 SQL 上花的时间 |
| 事务墙钟/单 | **17.62 ms** | 端到端每单占用的时间 |
| → SQL 之外的等待 | **11.1 ms（63%）** | 锁等待 / 连接往返 / 应用侧 |
| P_S 事务事件/单 | **2.73** | 一单被拆成 2.73 个事务事件（含自动提交语句） |
| SQL 条数/单 | **12.0–12.3** | 已经是上轮 `useLocalSessionState` 压过一轮后的值 |

→ 下一个该做的是：**把 2.73 个事务/单往下压（多语句合并成一个事务边界）、把 63% 的
非 SQL 等待拆开看（行锁/桶锁 vs 网络往返）**。审计、统计、通知这三类"派生写"在这个结论下
都不该进 MQ：它们要么不在写路径上（审计 0 条/单），要么是低频写（调度 1 条/30min），
要么本来就该走"同事务 outbox 之外的读侧聚合"（统计/指标）。

## 8. 复现 & 现场

```bash
/root/.qiqi-standing/bench-lock.sh acquire audit-cost-step1     # 必须，令牌池是硬资源
MEMBER_PASS=… bench/tools/auditcost.sh deploy on                # 同一镜像 + 只读 jar 挂载 + audit=true
MEMBER_PASS=… STEPS_OVERRIDE=300,300 STEP_INDEX=1 \
              bench/tools/auditcost.sh run on-300-w 300 60 30 300   # 预热档 60s + 测量档 60s
MEMBER_PASS=… bench/tools/auditcost.sh ship ship-on 300         # 后台发货路径（带审计）微基准
MEMBER_PASS=… bench/tools/auditcost.sh deploy off               # 只切 audit-enabled=false
MEMBER_PASS=… bench/tools/auditcost.sh restore                  # 拆挂载 + 去掉环境变量覆盖
/root/.qiqi-standing/bench-lock.sh release
```

现场口径（都已还原，见 §9）：

* 镜像 `sha256:935feb00…39d9` **未重建**；两臂容器内 `/app/app.jar` md5 全程 `2fce23c8…4e28`；
  restore 后回到镜像自带 jar（`md5=e8b9cc01…8b1d`，与我进场时一致）。
* 每轮 reset + 桶重置 + 令牌切片；`purge` 消化门禁（`trx_rseg_history_len`）已加进 `auditcost.sh`：
  reset 会一次删掉上一轮几万单，purge 没消化完就开跑会把 p50 抬到秒级。
* 幂等令牌**每轮换切片**（`/tmp/loadgen/.token_offset` 滚动）：`gen.mjs` 的 tokenIdx 每轮从 0 开始，
  而令牌是 GETDEL 一次性消费 —— 复用同一批会成片报"请勿重复提交订单"（本轮实测 12000/12000 全失败）。
