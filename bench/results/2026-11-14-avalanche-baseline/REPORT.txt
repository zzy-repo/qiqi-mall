       memory.current / memory.peak / memory.events(high,max,oom_kill) / cpu.stat / *.pressure
     200ms 一次，零 docker exec（起进程本身会成为干扰），**只读、不改容器配置**。

     jcmd 路线走不通 → 改走 JAVA_OPTS 注入 -Xlog:gc*，**重启容器但不重建镜像**：
       -XX:MaxRAMPercentage=75                       ← 原值原样保留
       -Xlog:gc*:file=/tmp/gc.log:time,uptimemillis,level,tags:filecount=0   ← 只加观测
     落地方式：bench/jvm-gc.override.yml（临时 -f 叠加，**不改仓库里的 docker-compose.yml**）
       docker compose -f docker-compose.yml -f bench/jvm-gc.override.yml up -d --no-deps server-1 server-2

【3】雪崩点在第几档、哪个判据先触发
  判据（事前写定）：① p99 相对上一档翻倍 ② 错误率 >1% ③ GC 时间占比 >20%
  → 判据 ② 与 ③ **全程一次都没触发**（错误率峰 0.03%、GC 峰 1.2%）。
  → 判据 ① 机械扫描第一次命中 = 第 2 档（150 rps，27.8→62.5ms，×2.25）。
  → **但 150 档是伪触发**：绝对量健康（p99 62.5ms、0 错、0 丢），下一档没继续恶化（200 档 62.6ms 持平），
     且当时无任何资源被压（堆 50MB / 线程 23 / CPU 0.36 核）。
  ★ 真正的雪崩点 = **400 rps 档**（拐点在 350→400 之间），触发判据仍是 **① p99 翻倍**，
    但这次是 ×13.9 且**不再恢复**：p99 322.6→4477.1ms（第二轮 283.2→3130.3，×11.1，复现），
    p50 67ms→1697ms；再往上（450/500 档）开始丢请求 3292/6796，**吞吐天花板 ≈405–415 ok/s**。
  ★ 当时状态：after-GC 堆 86MB（上限 11.5GB 的 0.75%）/ GC 占比 1.2% / GC 67 次 **0 次 Full GC** /
    容器 memory.current 峰 754MB / memory.events(high,max,oom_kill) 全 0 / CPU 0.72 核 / **Tomcat 线程 202（=200 满）**

【4】雪崩时的现象
  · 响应时间形态：p50 也从 67ms 跳到 1697ms —— 不是「少数慢请求」，是**整条分布一起塌**（典型排队饱和）；
    p99 4.5s、max 6.9s；到 450/500 档 p50 已达 5s 量级，p99 7-10s。
  · 错误类型：**没有 5xx、没有超时、没有限流**。全轮仅 26 条业务拒绝（code=1 唯一键碰撞），
    错误率 0.03% —— 也就是说「雪崩」表现为**延迟塌陷**，而不是报错。
  · 无 OOM：memory.events 的 oom_kill=/max=/high= 全 0；0 次 Full GC；GC 占比 ≤1.2%。
  · 有丢弃：450 档 3292、500 档 6796（开环生成器调度落后 >3s 的请求被丢弃并标 saturated），
    450/500 档 saturated 秒数分别 49/74（各 75s）—— 即**供不上货**，不是服务器拒绝。

【6】「雪崩其实不是内存」——是，如实说
  不是内存，也不是 CPU，也不是 MySQL 被打爆。证据链（全部可复核）：
  · 内存：after-GC 堆 86–89MB / 上限 11.5GB；堆容量只长到 600MB（G1 根本没扩）；0 次 Full GC；
    PSI memory some avg10 = 0.00（内存侧零 stall）。
  · CPU：服务器只用了 0.7 核/容器（4 核机器），客户端 node 17–22%。CPU 不是约束。
  · MySQL：同时段 Threads_running 10–14、无死锁、行锁等待 ~180/s（中等），DB 没有被压爆。
  · 线程栈（400 rps 档 SIGQUIT 实证）：server-1 **190/202**、server-2 **186/202** 个 http-nio 线程
    全部停在 com.zaxxer.hikari.pool.HikariPool.getConnection（SynchronousQueue.poll 等连接），
    只有 8 个线程真的在跑 SQL（socketRead 等回包）。
  ⇒ 根因是**应用侧排队：200 个 Tomcat 工作线程抢 10 个 HikariCP 连接**（默认 maximumPoolSize=10，
    每单约 11 条 SQL）。按 A 型口径这仍属「线程池打满」，但**闸门在数据库连接池，不在堆**。
  ⇒ 直接可用的推论（未在本轮验证，别当结论）：把连接池 10→30 或把每单 SQL 数压下来，
    拐点应显著右移；而调大 -Xmx / 换 GC **不会**改善这个拐点。

【7】本轮暴露的口径缺陷（下一轮要改，但本轮没改口径）
  1. 判据①「p99 翻倍」在低基线上必然误报（150 档 ×2.25=62ms 被判雪崩）。建议改成
     「×2 且 p99>200ms 且下一档不回落」。
  2. 档内状态累积：第 k 档面对前 k−1 档留下的数据（400 档时 order 表 20 万行）；300 档 p99 两轮差 8 倍
     就是累积/瞬态的表现。要把 350~400 精确定位到 ±25 rps，需每档独立 reset + 各自预热。
  3. 容器**没有内存上限** ⇒ memcg 的 max/high 事件物理上不可能触发，这一列只能证明「没 OOM」，
     不能证明「没内存压力」；「不是内存」的判断建立在堆 89MB vs 11.5GB 这个量级差上。
  4. -Xlog:gc* 本身有 <0.1%/事件的观测开销，本轮绝对延迟含它。
