# 每单 2.18 个事务 / 63% 时间不在 SQL 上 —— 拆开量、合并一处、再量

> 时间：2026-11-14 08:30–09:55（`bench-lock.sh` 全程独占 → 已释放）
> 对象：`POST /portal/orders` 下单主路径（300 / 350 rps，两档都**避开膝点**）
> 判据：**跑之前就写死**（§1），事后一个字没改
> 一句话：**2.18 个事务里只有 1 个（写事务）有正确性理由**；另外 1 个（提交后回读明细）没有，已合并掉
> （2.19 → 1.19，−46%）。但「每个事务的固定开销 ≥3ms」这条判据**不命中**（实测被删掉的那个事务的固定开销
> 只有 0.2–0.4 ms）→ **压事务数换不到 20% 吞吐**（实测 ok/s 不动、p50 持平、p99 略好）。
> 真正值钱的三个杠杆是：**写事务的提交落盘 1.33 ms/单**、**行锁等待 0.67（300 档）→1.47 ms（350 档）/单**、
> 以及**事务之外那 5 ms**（Tomcat/Spring/JSON/nginx/Redis，跟 MySQL 无关）。

## 1. 判据（先写下来，不事后改）

| 若 | 判定 |

| 每个事务的固定开销（提交 fsync + 借还连接 + 往返）**≥ 3 ms** | 把 2.7 压到 1~1.5 应带来 **≥20% 吞吐**，值得做 |

## 2. ① 每单这几个事务分别是哪来的（`performance_schema` 事务↔语句逐条配对）

### 2.1 装置：先把环形缓冲清空，再逐事务配对

```
performance_schema.events_transactions_history_long  ─┐
performance_schema.events_statements_history_long     ─┴→ 按 (THREAD_ID, NESTING_EVENT_ID) 配对
```

两条教训（都踩过，写进 `bench/tools/txncost.sh` 里了）：

1. **不能拿 digest CSV 的「首行 vs 末行」做差**：`events_statements_summary_by_digest` 会被回收/清空
   （上一轮的 CSV 里 `COMMIT` 的 `COUNT_STAR` 从 531 万掉到 1265），做差会算出「2800 万条语句」这种鬼数字。
   本轮**只用窗口紧邻的前后两次快照**做差。
2. **跑之前必须 `truncate` 两张 history_long**：不清空时它保留前几轮的几千条语句，配对会缺行
   （实测主事务只配到 8/10 条，拆出来的"间隙"全是假的）。

### 2.2 逐事务结果（同一连接、连续三单，节选单连接时间线）

```
STMT  SET autocommit=0                                        0.086 ms   ← 不在任何事务事件里
STMT  SELECT ... FROM sku WHERE id=?                          0.157 ms   ← 事务的第一条读
TXN#1 ██████████████████████████████████████████ 4.206 ms
  STMT SELECT ... FROM product WHERE id=?                     0.124
  STMT INSERT INTO `order` ...                                0.191
  STMT INSERT INTO order_status_ledger ...                    0.173
  STMT INSERT IGNORE INTO stock_ledger ...                    0.140
  STMT UPDATE sku_bucket SET stock=stock-1 WHERE ...          0.200   ← 热点行锁
  STMT UPDATE stock_ledger SET bucket_no=...                  0.162   ← 同一条台账的第二次写
  STMT INSERT INTO order_item ...                             0.167
  STMT commit                                                 1.032   ← **提交 = 1.03 ms（fsync）**
STMT  SET autocommit=1                                        0.053 ms
STMT  SELECT ... FROM order_item WHERE order_id=?             0.187 ms
TXN#2 █ 0.073 ms                                                        ← **只读事务：唯一理由"没有"**
```

### 2.3 结论表：来源 + 每个"为什么要独立"

| # | 事务 | 条/单（300 rps） | 墙钟 | 有正确性理由吗 |
| --- | --- | --- | --- | --- |
| 1 | **写事务** `OrderTransactionalCreator#create`（`REQUIRES_NEW`） | 1.000（`Com_commit/单 = 1.001`） | 10.4 ms | **有**：整单要么全成要么全不成（订单+出生台账+库存台账+桶扣减+明细），且 `REQUIRES_NEW` 是**死锁重试**的前提（外层 `OrderCreateService` 重试时必须拿到"上一轮什么都没留"的干净状态） |
| 2 | **提交后回读明细**（controller 的 `detailBody` → `SELECT ... FROM order_item`，自动提交） | 1.000 | 0.07 ms | **没有**。它读的就是本事务刚写进去的行，既不跨请求、也不需要看见别人后来的提交 —— 纯多余事务。**本轮合并掉的就是这一处** |
| 3 | **后台 `StockCacheRefresher`**（`UPDATE sku s JOIN (SELECT SUM(stock) FROM sku_bucket ...)`，自动提交） | 0.18 | — | 不在下单路径上（`sku.stock` 是展示缓存的周期回写）。它按固定节奏跑（300 档约 54 次/s），P_S 把每一次都记成一个事务，所以按订单数摊出来是 0.18 条/单 |
| | **合计** | **2.187** | | 只有 #1 是必须的 |

> 上一轮报的 **2.73** 与这里的 **2.18** 不矛盾：同一套结构，差别只在**窗口组成**——那一轮的窗口里
> 后台事务/其它写入占比更高（#3 这类按秒计数的东西，摊到订单上完全取决于窗口里跑了几单）。
> 本轮 12 轮窗口的 `事务/单` 极差只有 0.3%（2.174–2.189），这个数是稳的。

## 3. ② 11 ms 等待的三项拆分（+ 往返实测）

### 3.1 先对账：上一轮那个 17.62 ms 是从哪来的

| | 上一轮（审计那轮的旁证） | 本轮实测（300 rps，12 轮中位） |
| --- | --- | --- |
| SQL 服务时间/单 | 6.49 ms | **6.98 ms**（同一量级，差在窗口） |
| 事务墙钟/单 | 17.62 ms | **10.43 ms** |
| 差 | 11.1 ms | **3.51 ms** |

17.62 ms 那一份把**同一个窗口里所有事务**（含后台刷新、以及 purge 消化期的慢事务）都摊到了订单上；
本轮按"窗口紧邻快照 + 窗口内成功订单数"重算，事务墙钟/单 = 10.4 ms，**比 p50（15.6 ms）还小**——
这是对的：一单的事务都在一单的请求里，事务之和 ≤ 请求墙钟。

### 3.2 11 ms 到底在哪（300 rps 中位，单位 ms/单）

| 项 | 值 | 占事务墙钟 | 怎么量的 |
| --- | --- | --- | --- |
| **SQL 服务时间** | **6.98** | 67% | `events_statements_summary_by_digest.SUM_TIMER_WAIT` 前后差 |
| ├ 其中**行锁等待** | 0.67（350 档 1.47） | 6–11% | `Innodb_row_lock_time` 前后差；与 digest 的 `SUM_LOCK_TIME` 对得上（0.745 vs 0.729） |
| └ 其余服务端执行 | 6.31 | 60% | 上面两项之差（`UPDATE sku_bucket` 2.2 ms、`COMMIT` 2.0 ms、4 条 INSERT 共 0.9 ms…） |
| **提交落盘（日志 I/O）** | **1.33** | 13% | `wait/io/file/innodb/innodb_log_file` 的 `SUM_TIMER_WAIT` 前后差（9.3 次/单，共 1.35 ms）。`innodb_flush_log_at_trx_commit=1` + `sync_binlog=1`：实测 **3.37 次 fsync/单 ≈ 1.7 次/写事务** |
| **语句间隙（往返 + 应用侧）** | **2.18** | 21% | 事务墙钟 − 语句时间（11.2 个间隙 → 0.195 ms/间隙） |
| ├ 往返（RTT） | ≈ 0.9–1.0 | 9% | **实测**：同一主机上 1000 次 `SELECT 1` 往返 86.4 ms（0.0864 ms/次），服务端执行 0.0122 ms/次 → RTT ≈ 0.07 ms；按 12 条语句 ≈ 0.9 ms |
| └ 应用侧（MyBatis 映射/参数绑定/调度） | ≈ 1.2 | 12% | 间隙 − 往返（0.195 − 0.09 ≈ 0.10 ms/条） |
| **连接借还** | ≈ 0 | — | Hikari 借还是池内操作；MySQL 侧 `Threads_created/单 = 0.0000`（没有新建连接），`Com_begin = 0`（事务由 `SET autocommit=0` 隐式开启，没有额外往返） |

**事务之外还有 5.2 ms**（p50 15.6 − 事务墙钟 10.4）：Redis 幂等令牌 `GETDEL`、Spring/Tomcat、
JSON 序列化、nginx、压测客户端自己。**这一段是最大的一块，但跟 MySQL 一点关系都没有**。

| 判据 | 实测 | 命中？ |
| --- | --- | --- |
| 每事务固定开销 ≥ 3 ms | **写事务**：提交 1.03–2.66 ms（含 fsync 1.33）+ 2 次 `SET autocommit` 往返 ≈ **1.5–2.9 ms**；**被删掉的只读事务**：0.07 ms 事务 + 1 次往返 ≈ **0.2–0.4 ms** | **不命中**。贵的那个（写事务）每单只有 1 个、删不掉；能删的那个便宜得要命 |

## 4. ③ 合并了哪一处 + 为什么安全

**一句话**：把 controller 在**建单事务提交之后**才发的 `SELECT ... FROM order_item WHERE order_id=?`
（一个自动提交只读事务）挪进建单事务里，事务数 **2 → 1**。

改动只落在"明细从哪来"这一条链上（3 个文件，39 增 11 删）：

| 文件 | 改了什么 |
| --- | --- |
| `oms/service/OrderTransactionalCreator.java` | 新增 `record CreatedOrder(Order order, List<OrderItem> items)`；`create()` 返回它，并在 `saveBatch` 之后**在本事务内**回读明细 |
| `oms/service/OrderCreateService.java` | `createWithRetry` 返回 `CreatedOrder`（重试逻辑一行没动） |
| `portal/controller/PortalOrderController.java` | `create()` 用 `created.order()/created.items()` 拼响应；新增 `detailBody(Order, List<OrderItem>)` 重载（`GET /{id}` 那条路径仍然自己查） |

**正确性论证（四条，逐条对齐原来的行为）**

1. **读的是同一批行**：这条 SELECT 读的是本事务 `saveBatch` 刚插进去的行，同事务内天然可见
   （`REPEATABLE READ` 下自己的写自己看得见）。SELECT 文本、`orderByAsc(id)` 排序一个字没改。
2. **没有任何"必须看见别人提交"的需求**：它是"写完之后回显刚写的东西"，不是跨请求读、不是对账读。
   对照 `PaymentRecordServiceImpl` 那种"撞幂等键后回查"才是真的需要 `REQUIRES_NEW`（另一条连接 = 新快照）
   —— 这里正好相反。
3. **失败语义不变**：这条 SELECT 原来在事务之外，抛异常就是 500 但订单已提交；现在它在事务内，
   抛异常 = 整单回滚。这是个**语义变化**，必须说清：一条按主键/索引回读刚写入行的 SELECT 抛异常，
   只可能是连接断了/SQL 服务挂了 —— 那种情况下"订单已落库但用户看到 500"本来就是更坏的结果
   （用户重试 → 幂等令牌已消费 → 报"请勿重复提交"）。所以新语义（整单回滚）反而更自洽。
   **代价**：`REQUIRES_NEW` 事务的时长 +0.3~1.2 ms（明细读 + 一次往返），持锁时间同比变长
   —— 实测行锁等待 0.67→0.73 ms（300 档）、1.09→1.47 ms（350 档），见 §5，这是这次合并**唯一**的副作用。
4. **原有的独立理由都不受影响**：写事务仍然 `REQUIRES_NEW`（死锁重试要干净状态）；台账/库存台账/桶扣减
   本来就在同一个事务里，**没有被合进来也没有被拆出去**；渠道落单的 `ChannelOrderImporter.REQUIRES_NEW`
   （"一单失败不拖累同批"）不在下单路径上，一行没碰。

`mvn -o test`：**246 通过 / 0 失败 / 0 错误 / 0 跳过**（35 份 surefire 报告）。

## 6. ⑤ 结论：该不该合并 / 下一个该动什么

### 6.1 合并这一处：**该合，但别指望吞吐**

* **该合**，因为它把"一单两个事务"变成"一单一个事务"，而且删掉的那个事务**没有任何正确性理由** ——
  留着它只是历史遗留（明细回显写在 controller 里，而事务在 service 里）。
  `事务/单 −46%`、`语句往返 −1 次`、p99 略好、语义更自洽（§4.3）。
* **不该指望吞吐**：判据「每事务固定开销 ≥3 ms」不命中（被删的那个只有 0.2–0.4 ms），
  实测 ok/s 一动不动、p50 持平 —— **压事务数在 300/350 档拿不到任何吞吐**。
* **代价要记住**：持锁时间 +0.3~1.2 ms，350 档行锁等待 +35%。热桶竞争一加剧，这点代价会先反噬。

### 6.2 下一个该动的（按"每单能省多少"排序，全部有本轮的实测账）

| 优先级 | 杠杆 | 每单可省的账 | 怎么动 |
| --- | --- | --- | --- |
| **1** | **行锁等待**（`sku_bucket`） | 0.67 ms（300 档）→ **1.47 ms（350 档）**，随 rps 线性涨；`UPDATE sku_bucket` 单条 2.2 ms 里绝大部分是等锁 | ①**把持锁时间压到最短**：这条明细回读就不该在事务里 —— 明细实体本来就在内存里（`saveBatch` 后自增 id 已回填），**直接返回内存里的 `items`，连那条 SELECT 都省掉**（再省 1 次往返 + ~0.3 ms 持锁）；②桶数 8 → 16/32（`qiqi.stock.bucket-count` 可配，但**要同步重分桶**，属于迁移级动作，另开一轮） |
| **2** | **提交落盘 1.33 ms/单**（9.3 次日志 I/O、3.37 次 fsync/单） | 1.33 ms（13%） | 每单只有 1 个写事务，`group commit` 已经在起作用（1.7 次 fsync/写事务）。真要动只能动 durability（`innodb_flush_log_at_trx_commit` / `sync_binlog`）—— **那是拿持久性换吞吐，不允许**。所以这一项只适合"接受现状" |
| **3** | **SQL 外那 2.18 ms 间隙** | 往返 ~0.9 + 应用侧 ~1.2 | 往返部分靠**合并语句**（上一轮已做过一轮：总额一次写对）；应用侧是 MyBatis 映射/参数绑定，能动的只有"减少语句条数"，不是"减少事务数" |
| **4** | **事务之外那 5.2 ms**（p50 15.6 − 事务 10.4） | 5.2 ms —— **最大的一块** | Redis 幂等令牌 `GETDEL` + Spring/Tomcat/JSON + nginx。本轮没量细分，是**下一个该做的第一件事**（它比任何 MySQL 侧改动都大） |

> 一句话给下一轮：**"每单 2.18 个事务"这个杠杆已经用完了（−46% 事务换 0% 吞吐）；
> 剩下的大头在事务之外的 5.2 ms 和热点桶的行锁上——一个跟 MySQL 无关，一个跟事务数无关。**

## 7. 复现

```bash
/root/.qiqi-standing/bench-lock.sh acquire txn-count

# 基准臂（HEAD）
cd qiqi-mall-server && mvn -o -DskipTests package        # md5 2fce23c8…（= 上一轮量过的那份，逐字节相同）
cd .. && bench/tools/txncost.sh deploy qiqi-mall-server/target/qiqi-mall-server-0.0.1-SNAPSHOT.jar head

# ① 归因探针（会 truncate 两张 history_long，跑完自动关 consumer）
bench/tools/txncost.sh probe probe-e 20 5

# ③ 吞吐/成本对照（每档 75s + 预热 90s@100rps，窗口=测量档中段前后紧邻快照）
bench/tools/txncost.sh run base-300-r1 300 75 90 100
bench/tools/txncost.sh run base-350-r1 350 75 90 100     # … ×3 轮

# 合并后再跑一遍
cd qiqi-mall-server && mvn -o test && mvn -o -DskipTests package   # 246 绿；md5 c140afa3…
cd .. && bench/tools/txncost.sh deploy …/qiqi-mall-server-0.0.1-SNAPSHOT.jar merge1
bench/tools/txncost.sh run after-300-r1 300 75 90 100    # … ×3 轮 × 两档

python3 bench/tools/txncost_agg.py bench/results/2026-11-14-txn-count base- after-   # 中位 + Δ%
bench/tools/txncost.sh restore                            # 拆挂载，容器回镜像自带 jar
/root/.qiqi-standing/bench-lock.sh release
```

现场口径：
* 镜像 `sha256:935feb00…39d9` **全程未变**；两臂容器内 `/app/app.jar` md5 分别为 `2fce23c8…` / `c140afa3…`；
  `restore` 后回到镜像自带 jar（`e8b9cc01…`，与进场时一致）。
* `events_statements_history_long` 在吞吐轮前是**硬门禁**（开着的状态下 MySQL 会被拖垮）：本轮探针结束后已关闭，
  每轮 `run` 都会先检查再开跑。
* 每轮 reset + 桶重置 + purge 消化门禁（`trx_rseg_history_len < 400`）+ **全新的令牌切片**（1.4M 池，每轮只切 1.2×需求）。
