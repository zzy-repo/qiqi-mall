# 优化项3：滚动发布下的内存态失效 —— Redis 引入的需求复现

> 方法论：模拟靶子=滚动更新（服务迭代的真实可用性诉求，非凭空多实例）
> 预期：一次实验暴露全部"进程内存态"在多实例下的失效模式
> 状态：**已实验闭环**（2026-11-10，基线/修复两组数据见文末「五、实验结果」）

## 一、实验设计

### 环境搭建
```
实例1: qiqi-server 8081 (现有dev实例)
实例2: qiqi-server 8082 (同库同配置新起,模拟"新版本实例")
分发层: nginx/简单轮询脚本,将请求轮流打到两个实例
```

### 实验步骤与预期翻车点

| 步骤 | 操作 | 预期失效 |
|---|---|---|
| ① 验证码 | 实例1生成验证码 → 登录请求打到实例2 | ⛔ 校验失败(令牌在实例1内存) |
| ② 幂等令牌 | 结算页令牌由实例1发放 → 提交打到实例2 | ⛔ 令牌查无 → 正常下单被拒 |
| ③ 幂等防线 | 同一tokenId两次请求分别路由到两实例 | ⛔ 双del各自成功 → 重复订单(防线失效) |
| ④ 部分无碍 | 下单扣库存(数据库行锁) | ✅ 原子扣减天然跨实例(SQL层共享) |
| ⑤ 发布窗口 | 实例2滚动替代实例1期间持续下单 | 观察失败率曲线 |

## 二、量化预期(实验前预注册,防事后编数据)

- ③ 重复订单率: 轮询下理论上 100% 的重复提交都会成功两次
- ① 验证码失败率: 50%请求(打到未生成实例的)必失败
- ④ 库存一致性: 始终正确(对照组:证明只有"进程内存态"坏了)

## 三、修复方案(实验确认后实施)

1. compose 加 redis 容器
2. TokenStore/CaptchaStore 抽接口 → Redis 实现(内存实现保留作单实例档)
3. 迁移后同实验复跑: ①~③ 全部修复,④ 不变
4. (联动)Redis SETNX 分布式锁 → 自动关单任务(待 order.create_time)

## 四、价值定位

发布不断服(可用性)是滚动更新的硬诉求 → 多实例是它的必然形态 →
内存态失效是多实例的必然结果 → Redis 是这个链条的终点。
整个链每一环都有业务动机,无一处硬凑。

## 五、实验结果（2026-11-10，脚本 `run.sh`）

环境：`docker compose` 双实例（`qiqi-server-1:8082` / `qiqi-server-2:8083`）+ `qiqi-gateway`（nginx upstream 轮询，宿主机 18080）+ `qiqi-redis`；两前端容器均经网关转发。

执行：`bash benchmark/3-滚动发布实验/run.sh memory` 与 `... redis`

### 5.1 修复前：KV_STORE=memory（进程内存态）

| 指标 | 观测值 | 结论 |
|---|---|---|
| ① 5 次失败登录后 `captcha-required` | **false** | 失败计数被轮询摊到两个实例（各 2~3 次），谁都到不了阈值 5 → 验证码机制实际失效 |
| ② 验证码跨实例使用 | 不可用 | 明文只存在于签发实例内存，另一实例验不过 |
| ③a 令牌由实例1发放、提交经网关（6 次） | **误拒 3/6（50%）** | 打到实例2的合法下单被判「请勿重复提交」——用户侧直接失败 |
| ③b 同一令牌连续提交 4 次 | 成功 1 次 | 令牌只存在于一个实例，另一实例查无此 token；**未出现双成功，但出现了误拒** |
| ④ 停掉 server-1 后 10 次请求 | 10/10 成功 | 数据库层原子扣减不受影响，nginx 也会摘除不健康实例 |
| ⑤ 库存一致性 | 正确 | 对照组：只有「进程内存态」坏了 |

> 与预注册预期（②"重复订单率 100%"）的偏差：**token 是唯一 id，只会存在于签发它的那一个实例**，两个实例同时认可同一 token 的前提不成立；因此内存档的真实失效表现是「**合法下单被误拒**」而非「双成功」。实验以实测为准，记录在此。

### 5.2 修复后：KV_STORE=redis（共享 KV）

| 指标 | 观测值 | 结论 |
|---|---|---|
| ① `captcha-required` | **true** | 计数在 Redis 共享，跨实例累计 |
| ② 验证码跨实例使用 | **code=0 通过** | 实例A 生成 → 从 Redis 取明文 → 经网关提交成功 |
| ③a 跨实例误拒（6 次） | **0/6** | 令牌在 Redis 中全局可见 |
| ③b 同一令牌提交 4 次 | **成功 1 次** | 幂等防线跨实例有效 |
| ④ 停掉 server-1 后 10 次请求 | 10/10 成功 | 滚动发布窗口无失败 |
| E2E（portal-web/admin-web 均经 nginx） | **5/5 全绿** | 场景1~4 覆盖浏览/下单/履约/售后 |

### 5.3 对比小结

| 维度 | memory（单实例档） | redis（多实例档） |
|---|---|---|
| 验证码跨实例 | ❌ 失效 | ✅ 生效 |
| 幂等令牌跨实例 | ❌ 合法下单误拒 50% | ✅ 0 误拒、重复提交被拒 |
| 发布窗口可用性 | ✅ 10/10（数据库层兜底） | ✅ 10/10 |
| 依赖 | 无 | Redis（单机） |

结论：JWT 无状态 + MySQL 共享这两点决定了「多实例只差进程内存态外移」，实测印证——
外移后除依赖新增一个 Redis 外，业务代码零改动（两个 Store 内部委托 KvStore，调用方未动一行）。

### 5.4 复现命令

```bash
docker compose up -d --build            # 起双实例 + 网关 + redis
bash benchmark/3-滚动发布实验/run.sh memory   # 基线（会临时把两实例切到 memory 档）
bash benchmark/3-滚动发布实验/run.sh redis    # 修复后
```
