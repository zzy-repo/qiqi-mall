# 优化项3：滚动发布下的内存态失效 —— Redis 引入的需求复现

> 方法论：模拟靶子=滚动更新（服务迭代的真实可用性诉求，非凭空多实例）
> 预期：一次实验暴露全部"进程内存态"在多实例下的失效模式
> 状态：方案设计，未执行

## 一、实验设计

### 环境搭建
```
实例1: qiqi-server 8081 (现有dev实例)
实例2: qiqi-server 8082 (同库同配置新起,模拟"新版本实例")
分发层: nginx/简单轮询脚本,将请求轮流打到两个实例
```

### 实验步骤与预期翻车点

| 步骤 | 操作 | 预期失效 |
|---|---|---|
| ① 验证码 | 实例1生成验证码 → 登录请求打到实例2 | ⛔ 校验失败(令牌在实例1内存) |
| ② 幂等令牌 | 结算页令牌由实例1发放 → 提交打到实例2 | ⛔ 令牌查无 → 正常下单被拒 |
| ③ 幂等防线 | 同一tokenId两次请求分别路由到两实例 | ⛔ 双del各自成功 → 重复订单(防线失效) |
| ④ 部分无碍 | 下单扣库存(数据库行锁) | ✅ 原子扣减天然跨实例(SQL层共享) |
| ⑤ 发布窗口 | 实例2滚动替代实例1期间持续下单 | 观察失败率曲线 |

## 二、量化预期(实验前预注册,防事后编数据)

- ③ 重复订单率: 轮询下理论上 100% 的重复提交都会成功两次
- ① 验证码失败率: 50%请求(打到未生成实例的)必失败
- ④ 库存一致性: 始终正确(对照组:证明只有"进程内存态"坏了)

## 三、修复方案(实验确认后实施)

1. compose 加 redis 容器
2. TokenStore/CaptchaStore 抽接口 → Redis 实现(内存实现保留作单实例档)
3. 迁移后同实验复跑: ①~③ 全部修复,④ 不变
4. (联动)Redis SETNX 分布式锁 → 自动关单任务(待 order.create_time)

## 四、价值定位

发布不断服(可用性)是滚动更新的硬诉求 → 多实例是它的必然形态 →
内存态失效是多实例的必然结果 → Redis 是这个链条的终点。
整个链每一环都有业务动机,无一处硬凑。
